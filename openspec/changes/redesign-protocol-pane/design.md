## Goals / Non-Goals

**Goals**
- Панель Protocol как в макете 18/18a, без бизнес-логики в виджетах.
- Кадры ACP из одной точки клиентского ядра, замаскированные до хранения, ограниченные по памяти, с поколением соединения.
- Release-сборка не хранит полные кадры нигде: ни в буфере кадров, ни во встроенном журнале (OBS-005).
- Закрыть утечку секрета в паре `name`/`value`.

**Non-Goals**
- Новые методы, поля или semantics ACP.
- Трасса в CLI (`--include-acp`, `--trace-file`).
- Изменение `structured_log_fluent` и полноэкранного просмотра.
- Сохранение фильтров и вида панели между запусками.

## Decisions

### D1. Вид панели: переключатель Frames/Log, действия в шапке дока, стек «таблица — разделитель — выбранное»

Панель — один организм кита `CodeLabProtocolPane` (D12) с двумя видами. Переключатель `Frames <N>` / `Log <N>` — `CodeLabSelectorBar` со счётчиками кадров и записей в области панели — сессия в фокусе и элементы соединения (D6), без учёта поиска и переключателей. Справа от него — подсказка сочетаний активного вида.

Действия `Pause`, `Clear`, `Export…` стоят в строке вкладок дока, справа, только пока активна вкладка Protocol. Для этого `CodeLabDockTab` получает необязательное поле `actions` (D12). Действия относятся к активному виду (D10).

Тело вида — колонка: панель фильтров, таблица, горизонтальный `CodeLabResizeHandle`, панель выбранного элемента, подвал. Доля таблицы по умолчанию — 52 % в Frames и 56 % в Log, как в макете; перетаскивание ограничено минимумом 96 px у каждой части. Положение разделителя — своё у каждого вида — живёт в `ProtocolPaneState` (D7): переживает закрытие и повторное открытие вкладки (spec «Панель Protocol: виды Frames и Log»), но не сохраняется между запусками (вне scope: «Не входит»). Организм получает долю параметром и сообщает о перетаскивании колбэком (D12). Без выбранного элемента нижняя часть показывает подсказку `Select a frame to see its details.` / `Select a record to see its fields.`.

Подвал — подпись `Panes follow the focused session · <сочетание>`; вторая часть подписи макета убрана (D6, D13); сочетание — `CodeLabShortcut.toggleProtocol.compactFor(platform)` (⇧⌘I на macOS, `Ctrl+Shift+I` на остальных).

Альтернативы:
- оставить два раздела одной колонкой (как сейчас) и добавить переключатель внутрь каждого — отклонено: макет показывает один вид за раз, а таблице и деталям нужна высота;
- две панели дока (Frames и Log отдельными вкладками) — отклонено: макет и §12.3 (экран 18) — одна панель «Protocol: кадры ACP и лог», `ToolPane` уже один;
- действия в строке переключателя видов, а не в шапке дока — отклонено: расходится с макетом, а поле `actions` нужно и будущим панелям (Terminal, Diff).

### D2. Источник кадров — точка трассировки в `AcpClientApplication`

`ProtocolFrame` строится там же, где сейчас `_traceProtocolMessage`: `_sendTracedMessage` для исходящих и обработчик `_transport.inbound` после проверки поколения для входящих. Это единственная точка, через которую проходят все сообщения в обе стороны, и там уже есть поколение соединения.

Состав `ProtocolFrame` (freezed, `codelab_client_acp`, `application/`). Поля с типом без `?` — `required` в конструкторе; nullable-поля необязательны, по умолчанию `null`:

| Поле | Тип | Значение |
|---|---|---|
| `seq` | `int` | номер кадра в пределах экземпляра `AcpClientApplication`, растёт через поколения; ключ выбора и связи Log → Frames |
| `time` | `DateTime` | время записи по часам ядра (параметр конструктора `clock`, ниже) |
| `direction` | `ProtocolFrameDirection` | `outbound` (клиент → агент) или `inbound` |
| `connectionGeneration` | `int` | `_generation` на момент записи |
| `kind` | `ProtocolFrameKind` | `request`, `notification`, `result`, `error` |
| `method` | `String?` | метод запроса или уведомления; у ответа — метод запроса с тем же id из противоположного направления, иначе `null` |
| `id` | `JsonRpcId?` | id сообщения; у уведомления `null` |
| `sessionId` | `String?` | строка с провода: `params.sessionId`; у ответа — `sessionId` запроса, у результата `session/new` — `result.sessionId`. Не `SessionId`: кадр — проекция провода для показа, сравнение с фокусом — по `SessionId.value` |
| `detail` | `String?` | у `session/update` — `params.update.sessionUpdate`; у результата `session/request_permission` — `result.outcome.optionId` или `cancelled`; у ошибки — текст по D3 |
| `errorCode` | `int?` | `error.code` у вида `error`, иначе `null` |
| `size` | `int` | длина UTF-8 `jsonEncode(message.toJson())` до маскирования |
| `payload` | `Map<String, Object?>?` | замаскированный JSON-объект сообщения (результат `SecretRedactor.redact` над `message.toJson()`) или `null` (D3) |
| `payloadOmitted` | `ProtocolPayloadOmitted?` | `null` (payload есть), `policy` (действующая политика `metadataOnly`) или `tooLarge` |

Публичный API ядра для кадров (экспорт из бареля `codelab_client_acp`):
- перечисления `ProtocolFrameDirection { outbound, inbound }`, `ProtocolFrameKind { request, notification, result, error }`, `ProtocolPayloadPolicy { full, metadataOnly }`, `ProtocolPayloadOmitted { policy, tooLarge }`;
- параметры конструктора `AcpClientApplication`: `ProtocolPayloadPolicy protocolPayloads = ProtocolPayloadPolicy.metadataOnly` (D3) и `DateTime Function()? clock` (по умолчанию `DateTime.now`; имя — как у `ClientWorkspace`);
- `Stream<ProtocolFrame> get protocolFrames` — закрывается в `dispose`;
- `bool get traceAvailable` — `true`, если базовая политика `metadataOnly`; через него `AcpClientBackend` отвечает порту kit (D5);
- `void setFrameTrace(bool enabled)` — режим Trace (D17), правила вызова — там же;
- `extension ProtocolFrameRedaction on ProtocolFrame { ProtocolFrame withoutPayload(); }` — единое правило снятия payload (D17), им пользуются kit и app.

Стандартное имя кода ошибки (`standardErrorName`) — внутренний помощник пакета: его используют `withoutPayload` и `ProtocolFrameRecorder`, вне пакета он нужен только тестам. Если исполнитель оставит его в бареле — это поправка этого абзаца, не новое решение.

Геттера действующей политики и признака «Trace включён» у ядра нет: состояние Trace для хоста держит буфер kit (`ProtocolFrameLog.traceEnabled`, D5), второму источнику истины не из чего возникнуть (`AGENTS.md` §13).

Сопоставление ответа с запросом держит внутренний `ProtocolFrameRecorder`: карта `(направление запроса, id) → (method, sessionId)` текущего поколения. Ключ — `JsonRpcId` с учётом типа: числовой `1` и строковый `"1"` — разные запросы (JSON-RPC 2.0). Строковые `method` и `detail` кадра обрезаются до 120 символов без разрыва суррогатной пары: кадр не хранит произвольно длинные строки агента.

**Все исходящие сообщения — через точку кадров.** Ни одно сообщение не уходит транспорту в обход `_sendTracedMessage`, в том числе автоматический ответ `cancelled` на `session/request_permission`, который ядро шлёт само — когда хода нет или он отменяется (`05-Prompt Turn.md#cancellation`), и при снятии ожидающих одобрений. Такой ответ даёт исходящий кадр `result` с методом `session/request_permission` и подробностью `cancelled` (ревью безопасности change: иначе в панели не видно, что клиент ответил агенту). Ответ снимает запись. Смена поколения очищает карту. Размер карты ограничен 1024 записями: запрос, на который не ответили, не держит память вечно, вытесняется самый старый.

Все поля, кроме `payload`, читаются только из полей схемы ACP (`17-Schema.md`: `sessionId` в параметрах сессионных методов, `SessionNotification.update.sessionUpdate`, `RequestPermissionOutcome`, `Error.code`/`message`). Незнакомый метод или незнакомая форма дают кадр без `detail`, а не ошибку (forward compatibility, `acp-boundary.md` §18, §19, §22). Recorder не бросает исключений наружу: сбой построения кадра логируется (debug `protocol_frame.build_failed {method, error_class}`), кадр не публикуется, а отправка и обработка сообщения идут как без кадра. Запись `protocol_message` того же сообщения пишется без `size` и `payload`, но с `direction`, `kind`, `method` и `request_id`: размер считается один раз для кадра и трассы, и его сбой не должен ронять трассу. Учёт запросов при этом всё равно получает запрос, поэтому исходящий ответ клиента на него (`Method not found`) получает метод запроса. Сообщение, декодированное с провода, всегда кодируется обратно в JSON, поэтому сбой — защитная ветка; тест воспроизводит её входящим запросом незнакомого метода, в `params` которого значение, не кодируемое в JSON (`{'bad': Object()}`, через `FakeAcpTransport.emitInbound`), и ждёт `build_failed` и ответ агенту `Method not found`.

**Поздние сообщения старого поколения.** `_replaceTransport` увеличивает поколение и синхронно, до первого `await`, отменяет подписки на старый транспорт, затем привязывает новый. Отменённая подписка событий не доставляет, поэтому сообщение старого транспорта после замены до обработчика не доходит вовсе, и кадра нет. Проверка `boundGeneration != _generation` в `_bindTransport` с записью `event_ignored {reason: stale_generation}` остаётся защитной веткой; через транспорт она недостижима и наблюдаемым требованием к кадрам не является (spec acp-protocol-client, сценарий «Поздний кадр старого соединения» — только «кадра нет»).

Поток — `AcpClientApplication.protocolFrames`, broadcast, `sync: false`: подписчик не может синхронно войти обратно в `AcpClientApplication` из обработчика транспорта, порядок доставки сохраняется. Исходящий кадр записывается до передачи транспорту, как и трасса сейчас; если `send` сорвался, кадр остаётся, а сбой виден в Log (`_recordDiagnostic`). Это осознанно: кадр — «что клиент отдал транспорту».

Альтернативы:
- **декоратор транспорта в `codelab_acp_transports`** — отклонено: у транспорта нет поколения и пар «запрос — ответ», а маскирование и политика — ответственность клиентского ядра (`observability.md` §3);
- **разбор записей `protocol_message` из `LogBuffer` в app** — отклонено: app разбирал бы ACP (`acp-boundary.md` §10), панель зависела бы от уровня и маршрутизации журнала, а в release payload в журнале не будет (D3);
- **`InspectorProjection`** — отклонено: это снимок сессии, а не кадры, без исходящих сообщений и без порядка провода.

### D3. Политика payload и маскирование до хранения

`enum ProtocolPayloadPolicy { full, metadataOnly }` — **базовая политика** хоста, параметр конструктора `AcpClientApplication(protocolPayloads: …)`, по умолчанию `metadataOnly`. Она одна на весь процесс и задаёт и кадры, и запись `protocol_message`. Поверх неё для кадров действует runtime-режим Trace (D17): действующая политика кадров — `full`, если базовая `full` **или** Trace включён. Пакет чистый Dart и не знает режима сборки, поэтому решение принимает composition root (как `configureCodeLabLogging`, `observability.md` §48):
- desktop: `kDebugMode ? full : metadataOnly` (`lib/app/app_scope.dart`);
- CLI: `verbose ? full : metadataOnly` (`apps/codelab_cli/lib/src/composition_root.dart`): без `--verbose` логгер CLI молчит, с ним вывод остаётся прежним.

При `full` payload кадра — `SecretRedactor().redact(message.toJson())` с правилом D4. Порог 256 KiB проверяется в два шага: если исходный `size` больше 256 KiB, кадр сразу получает `payload = null`, `payloadOmitted = tooLarge` — без маскирования (маскировать мегабайт ради того, чтобы выбросить, незачем); иначе payload маскируется и проверяется размер **замаскированного** JSON в UTF-8 (маскирование может удлинить текст: `<redacted>` длиннее короткого значения). Повторный `jsonEncode` замаскированного payload пропускается, если `size * 4 ≤ 256 KiB`: маскирование не удлиняет текст больше чем вчетверо (оценка с запасом), поэтому такой payload заведомо проходит порог. Так большой `fs/read_text_file` не съедает буфер (`observability.md` §29).

При `metadataOnly` payload не строится вовсе. `detail` ошибки при `metadataOnly` — только стандартное имя кода, известное `codelab_acp_protocol` (`Parse error`, `Invalid Request`, `Method not found`, `Invalid params`, `Internal error`, `Resource not found`); незнакомый код — без `detail`; текст `error.message` агента не хранится — он может содержать пути и фрагменты данных. При `full` `detail` — `redactText(error.message)`, обрезанный до 120 символов.

К записи `protocol_message` применяется только **базовая** политика, Trace её не меняет (D17): при `metadataOnly` запись несёт `direction`, `kind`, `method`, `request_id`, `size` и корреляцию `session_id`, `connection_generation`, но не `payload`. Типы полей записи: `direction` и `kind` — имя значения перечисления (`'outbound'`, `'request'`), `method` — строка или отсутствует, `request_id` — строка `id.toJsonValue().toString()` (как в `event_ignored`; числовой id `5` даёт `'5'`), `size` — `int`; при `full` `payload` — замаскированный `Map`. Поля без значения не пишутся (`dropNullValues`). Это закрывает дефект «полный payload в release» (proposal, п. 1) для встроенного журнала и `protocol.log` одним правилом. Sink `debug-panel` по-прежнему принимает категорию `protocol` (решение 5 `replace-debug-log-panel-with-fluent` не меняется): видимость — фильтр категории, содержимое — политика payload.


**Сырые данные в ветках ошибок** (решение пользователя 2026-11-23, ревью безопасности п. 6). Базовая политика действует не только на `protocol_message`, но и на диагностику ядра, которая раньше клала в контекст сырые данные сообщения: `_recordDiagnostic` при сбое декодирования или обработки ответа и запроса (`result`, `params`) и `_skipUnsupportedSessionUpdate` (`payload`). При `metadataOnly` такие записи несут только метаданные — `method`, `requestId`, `session_id`, `sessionUpdate` (если он прочитан), `size`, класс ошибки, — но не `params`, `result` и `payload`. `size` здесь — длина UTF-8 `jsonEncode` сырого значения (`params`, `result` или уведомления); если значение не кодируется в JSON, поле `size` не пишется. При `full` — замаскированные данные, как прежде. Иначе release-сборка хранила бы промпты и содержимое файлов в журнале через ветку ошибки, в обход правила выше. Это касается и причины сбоя: текст исключения декодирования (`cause.toString()`) цитирует фрагменты сообщения, поэтому при `metadataOnly` диагностика этих веток пишет только класс ошибки (`error_class`), без текста причины; при `full` — замаскированный текст, как прежде.

Альтернативы:
- политика по умолчанию `full` — отклонено: забытый параметр в новом хосте открыл бы полный payload в release (безопасность — приоритет 1);
- обязательный параметр без значения по умолчанию — отклонено: правка десятков тестов ядра без пользы для безопасности; значение по умолчанию и так безопасное;
- хранить payload и прятать его в UI release-сборки — отклонено: макет требует «Release builds keep metadata only», данные в памяти попадали бы в Copy и Export.

### D4. Секрет в паре `name`/`value` — правило того же `SecretRedactor`

`SecretRedactor.redact` для `Map`: если у объекта есть строковое `name`, которое подпадает под правило секретных имён (`_sensitiveKeyPattern`, с прежним исключением для счётчиков токенов), и есть ключ `value`, значение `value` заменяется на `<redacted>`. Остальные поля объекта обрабатываются как раньше. Так `HttpHeader` и `EnvVariable` (`17-Schema.md`) с `Authorization`, `X-Api-Key`, `GITHUB_TOKEN`, `OPENAI_API_KEY` маскируются в кадрах, записях журнала и диагностике — везде, где уже работает `SecretRedactor`.

Исключение для счётчиков токенов действует в паре так же, как для ключа: только для **числового** `value`. Строковое `value` под `name` вида `tokens_in` скрывается — строка под именем со словом `token` может быть учётными данными.

**Линейное время маскирования текста** (часть этого change). Кадры с payload до 256 KiB проходят `redactText`, а шаблон `_assignmentSecretPattern` с ведущим `[A-Za-z0-9_.-]*` в группе 1 давал квадратичное время на строке без разделителей: 20 000 символов — около 23 с. Префикс убран из группы: совпадение начинается с самого секретного слова, префикс остаётся в строке нетронутым, поэтому результат замены прежний (`my_api_key=x` → `my_api_key=<redacted>`). Остальные источники сверхлинейного времени закрыты так же:
- хвост имени после секретного слова (`api_key_prod_eu` до `:`/`=`) ограничен `{0,64}` символами: без предела строка из повторов секретных слов (`token` × 50 000) давала квадратичный перебор — каждое вхождение заново сканировало остаток строки;
- `_privateKeyPattern` (ленивое `[\s\S]*?` между `BEGIN … PRIVATE KEY` и `END …`) заменён линейным поиском: найти `BEGIN`, затем ближайший `END` после него; блок без `END` не маскируется, как и раньше.

Регрессионные тесты (`secret_redaction_test.dart`): строка 250 000 символов без разделителей, повторы секретных слов (`token`, `secret`, `password`, `api_key` × 50 000) и повторы `BEGIN … PRIVATE KEY` без `END` маскируются не дольше 5 с каждая (бюджет с запасом под нагруженный CI: линейный шаблон укладывается в десятки миллисекунд, квадратичный превысил бы его на порядки).

**Цена предела 64.** У идентификатора, где между **последним** секретным словом и `:`/`=` больше 64 символов (`token_used_by_the_nightly_reporting_job_of_the_eu_west_cluster_primary=…`), значение больше не маскируется шаблоном присваивания; раньше маскировалось. Оценка — приемлемо:
- имена переменных и ключей конфигурации длиннее 64 символов после секретного слова редки; у переменных окружения, ключей YAML и заголовков HTTP типичная длина — до 40 символов;
- для структурированных данных — а payload кадров и контекст журнала структурированы — действуют правило по ключу JSON и правило пары `name`/`value`, у которых предела нет: `{"token_…_primary": "…"}` и `{"name": "TOKEN_…_PRIMARY", "value": "…"}` маскируются при любой длине имени. Предел касается только секрета в свободном тексте вида `имя=значение` (строка лога, вывод команды);
- больший предел (256) удлиняет худший случай квадратичного перебора вчетверо и не закрывает класс целиком. Меньший (32) задевает реальные имена.
Цена закреплена тестом границы (`secret_redaction_test.dart`): хвост ровно в 64 символа между секретным словом и `=` — значение маскируется, 65 символов — нет. Если такие имена встретятся на практике — расширять правило отдельным change вместе с частыми именами секретов (proposal, «Не входит»).

Правило — расширение существующего, отдельного набора правил нет (approval-safety «Редактирование секретов»; structured-logging «Маскирование секретов в structured-выводе»). Ключи `name`/`value` выбраны по схеме ACP; другие пары (`key`/`val`) не трогаются — их в ACP нет.

Альтернатива — маскировать каждое `value` любого объекта с `name` — отклонено: скрыло бы безвредные данные (`{"name": "PATH", "value": …}`, имена файлов в `ResourceLink`) и сделало бы кадры бесполезными для отладки.

### D5. Буфер кадров — `ProtocolFrameLog` в `codelab_client_core`, владелец — `ClientWorkspace`

Буфер — клиентское состояние, а владелец клиентского состояния — kit (`codelab_client_core/AGENTS.md` §1). Kit видит ядро только через порт `AgentBackend`, поэтому порт получает `Stream<ProtocolFrame> get protocolFrames`, `AcpClientBackend` отдаёт поток `AcpClientApplication`.

`ProtocolFrameLog` (`lib/src/protocol/protocol_frame_log.dart`):
- `List<ProtocolFrame> get frames` — неизменяемый снимок, старые сначала;
- `Stream<void> get changes` — сигнал «буфер изменился», без копии списка на каждый кадр;
- `int get revision` — растёт при каждом изменении; по нему хост понимает, что снимок устарел;
- `void clear()`;
- привязка запроса `session/new` к сессии: при записи результата `session/new` с `sessionId` кадр запроса с тем же id и поколением из противоположного направления заменяется копией с этим `sessionId` (D6);
- лимиты: 2000 кадров и 8 MiB суммарного размера `payload` в UTF-8; при превышении любого вытесняются самые старые кадры; лимиты одинаковы при базовой политике `full` и в режиме Trace. Объём payload буфер считает сам — `utf8` длиной `jsonEncode(payload)` при записи кадра: `size` кадра — длина всего сообщения **до** маскирования и для учёта 8 MiB не годится (маскирование меняет длину, а у кадра без payload `size` ненулевой). Повторный `jsonEncode` оставлен ради точности учёта: около 1 µs на малый кадр и только для кадров с payload — в debug-сборке или в режиме Trace;
- `bool get traceAvailable` (базовая политика `metadataOnly`), `bool get traceEnabled`, `void setTrace(bool enabled)` — режим Trace (D17): включает действующую политику `full` кадров через порт бэкенда; выключение возвращает `metadataOnly` и **снимает payload** со всех кадров буфера (копии с `payload = null`, `payloadOmitted = policy`; счётчик объёма payload — 0; ревизия растёт). Пока Trace выключен при базовой `metadataOnly`, буфер снимает payload и с входящих кадров: кадр, построенный до выключения, но доставленный после (поток `sync: false`, D2), не принесёт payload обратно.

Владелец — `ClientWorkspace`: создаёт буфер в конструкторе, подписывается на `backend.protocolFrames`, отписывается и закрывает `changes` в `dispose` (`AGENTS.md` §9: у долгой подписки явный владелец). В `WorkspaceState` кадры не входят: частота кадров при стриминге сотни в секунду, а `WorkspaceState` перестраивает рабочее место.

Переподключение буфер не очищает (решение пользователя 2026-11-22, Q6): кадры несут поколение, и для разбора гонки reconnect нужны кадры до и после. Поздние кадры старого поколения в буфер не попадают — их отбрасывает `AcpClientApplication` до записи (D2), kit опирается на это, как и для остальных потоков (`codelab_client_core/AGENTS.md` §3).

Альтернативы:
- буфер в Cubit app — отклонено: политика «что хранить и сколько» — клиентское состояние, а не отображение (`AGENTS.md` §5, описание `codelab_client_core`); к тому же Cubit живёт по правилам UI-scope;
- буфер внутри `AcpClientApplication` — отклонено: ядро протокола не держит истории для UI, поток — его единственный контракт;
- `WorkspaceState.frames` — отклонено по частоте обновлений.

### D6. Область — сессия в фокусе и элементы соединения; панель следует за фокусом

Решение пользователя 2026-11-22 (Q1): панель Protocol показывает только сессию в фокусе, как остальные панели дока («Panes follow the focused session»). Сессия в фокусе — `WorkspaceState.activeSessionId` kit, единственный источник фокуса рабочего места; `ProtocolPaneCubit` подписан на него (D7).

**Что входит в область.** Кадр или запись журнала входит в область, если:
- его сессия — сессия в фокусе (`ProtocolFrame.sessionId`, поле `session_id` записи), или
- у него нет сессии — это **элемент соединения**: `initialize`, `authenticate`, `session/list` и ответы на них, уведомления и ответы без `sessionId`, ошибки на такие запросы; в журнале — события подключения, переподключения, транспорта и app без `session_id`.

Элементы соединения показываются в области любой сессии: без них не видно рукопожатия, переподключения и ошибок, общих для всех сессий. В таблице они помечены тегом `connection` в колонке `Method` (Frames) и `Event` (Log). Отдельного переключателя для них нет: их мало по сравнению с кадрами сессии.

Кадры и записи **других** сессий в области нет.

**Запрос `session/new`.** Запрос ещё не знает id сессии: он появится только в результате. Чтобы запрос не выглядел элементом соединения и не показывался во всех сессиях, буфер kit при записи результата `session/new` с `sessionId` подставляет этот id в кадр запроса с тем же id и поколением из противоположного направления (копия кадра, ревизия растёт; D5). До ответа запрос — элемент соединения; ответ-ошибка на `session/new` оставляет запрос и ошибку элементами соединения. Это правило — в kit, а не в app: app не сопоставляет запросы и ответы (`acp-boundary.md` §10).

**Выбора сессии нет.** ComboBox `All sessions` убран из обоих видов: область задаёт фокус, а второй способ выбрать сессию противоречил бы «панели следуют за фокусом». Колонка `Session` убрана из обеих таблиц: в области у строки либо сессия в фокусе, либо её нет (тег `connection`). `session_id` остаётся в панели выбранного кадра и в полях записи.

**Смена фокуса.** Таблицы обоих видов сразу показывают область новой сессии; поиск и переключатели сохраняются; выбор снимается, если выбранный элемент не входит в новую область (выбранный элемент соединения остаётся); таблица прокручивается к последнему элементу; пауза вида сохраняется и применяется к снимку с новой областью.

**Фокуса нет** (проект не выбран, сессий нет, сессия ещё создаётся): область — только элементы соединения. Над таблицей — строка `No session in focus. Showing connection frames only.` (в Log — `… connection records only.`). Если и их нет — `No frames yet.` / `No records yet.`.

**Буфер не меняется: один на соединение** (D5), фильтрация по области — в application app. Причины: при смене фокуса история новой сессии видна сразу, без повторного захвата; элементы соединения не дублируются по сессиям; Clear, Export и лимиты остаются одним правилом. Цена: шумная фоновая сессия вытесняет кадры сессии в фокусе из общего лимита 2000 кадров (Risks).

Альтернативы:
- все сессии соединения с фильтром (прежний вариант по умолчанию, как макет) — отклонено решением пользователя;
- фокус по умолчанию и `All sessions` по выбору — отклонено: два источника выбора сессии и снова «Protocol shows every session»;
- скрывать элементы соединения в области сессии — отклонено: рукопожатие и ошибки переподключения пропали бы из панели целиком;
- буфер на сессию в kit — отклонено по причинам выше.

### D7. Application app: feature `protocol`, `ProtocolPaneCubit` в root scope

Новая feature `apps/codelab_desktop/lib/features/protocol/`. Вход фокуса — `ClientWorkspace` (`activeSessionId` из потока `WorkspaceState`, без повторов): Cubit пересчитывает область при его смене (D6).

- `application/protocol_pane_cubit.dart` — `ProtocolPaneCubit` и неизменяемый `ProtocolPaneState` (`protocol_pane_state.dart`): активный вид, сессия в фокусе, фильтры Frames (`query`, `showRequests`, `showNotifications`, `errorsOnly`), фильтры Log (`query`, `category`, `minLevel`), пауза каждого вида со снимком, выбранный кадр и запись (копия объекта, а не индекс: вытесненный из буфера выбранный кадр остаётся в деталях), доля разделителя каждого вида (`framesSplit`, `logSplit`; `null` — доля по умолчанию организма), состояние экспорта и заметка сбоя;
- `application/protocol_frame_filter.dart`, `log_record_filter.dart` — чистые функции области (D6) и фильтров;
- `application/protocol_pane_view.dart` — маппер состояния в данные кита: строки таблиц (подписи, тон), заголовок и теги выбранного, сегменты JSON с признаком «замаскировано» (D12);
- `application/protocol_export.dart` — сборка JSON Lines (D10);
- `application/log_record_source.dart` — порт `LogRecordSource { List<Map<String, Object?>> get records; Stream<void> get changes; void clear(); }`. Реализация `LogBufferRecordSource` над `LogBuffer` — в `lib/app/` (composition root): `LogBuffer` — тип `structured_log_flutter`, application его не видит.

Cubit создаётся в root scope (как `TerminalTabsCubit`), поэтому кадры, пришедшие до первого открытия панели, видны, а фильтры переживают закрытие вкладки. Подписки — на `workspace.protocolFrames.changes`, `logRecordSource.changes` и фокус рабочего места; все отменяются в `close()`.

Частота: Cubit публикует состояние не чаще раза в 100 мс (`streaming.md` §15, `concurrency.md` §36). Таймер склейки отменяется в `close()`; публикация после `close()` невозможна. Пока вид на паузе, его список — снимок на момент паузы; захват продолжается, `Resume` показывает накопленное (кроме вытесненного). Счётчики переключателя на паузе продолжают расти: они считают область в буфере, а не замороженный список.

Фасад `CodeLabShellState` панель не проксирует: данные панели нужны только виджету панели и шапке дока, а фасад и так перестраивается часто. Виджет читает Cubit через `BlocBuilder`, как панель Terminal.

**Реализация состояния (принятые отступления).**
- `ProtocolPaneState` — обычный неизменяемый класс с ручным `copyWith`, `==` и `hashCode`, а не freezed: в `dependencies` app нет `freezed_annotation`, и остальные состояния app (`OnboardingState`, `ProjectTreeState`) написаны так же (`AGENTS.md` §14). Списки `visibleFrames` и `visibleRecords` и выбранная запись сравниваются по ссылке: Cubit строит новый список при каждой публикации, а поэлементное сравнение 2000 кадров на каждом `emit` дороже самой публикации.
- **Ленивое состояние.** Cubit живёт в root scope и получает изменения буфера, даже когда панель закрыта. Поэтому таймер склейки существует, только пока на `stream` есть подписчик:
  - изменение буфера помечает снимок устаревшим; геттер `state` пересчитывает его при чтении;
  - при подписчике первое изменение публикуется сразу, дальнейшие склеиваются таймером `publishInterval`;
  - действия пользователя и смена фокуса публикуются сразу при любом числе подписчиков;
  - когда уходит последний подписчик, таймер отменяется, и отложенная публикация не выполняется; снимок остаётся помеченным, поэтому следующий читатель `state` или следующее изменение дают свежие данные;
  - `close()` отменяет таймер и подписки на буфер кадров, источник записей и фокус, затем закрывает поток.
  Инварианты, которые обязан сохранить код: (1) `state` никогда не старше буфера на момент чтения; (2) потоку не нужно доставлять каждое промежуточное состояние, но после серии изменений при подписчике последняя публикация отражает последнее изменение — не позже чем через `publishInterval`; (3) после `close()` публикаций и таймеров нет. Цена: `state` может быть новее последнего значения в `stream` (снимок пересчитан при чтении, но ещё не опубликован). `BlocBuilder` строит первый кадр из `state` и дальше получает публикации, поэтому расхождение безвредно; код, которому нужна каждая промежуточная публикация, на этот Cubit не опирается. Причина — таймер без зрителя «висел» в тестах app, где Cubit создаётся в root scope (`AGENTS.md` §12: у долгой операции понятный жизненный цикл).

**Уточнения по тестам 4.1–4.7.**
- Время в тестах Cubit — поддельные часы `testWidgets` (`tester.pump(Duration)`): таймер склейки — обычный `Timer`, и эти часы его двигают. `fake_async` в `dev_dependencies` app не добавляется: он не нужен, а новая тестовая зависимость без нужды противоречит `AGENTS.md` §4 и §19.
- Конструктор: `ProtocolPaneCubit({required workspace, required logRecords, required exportSaver, required basePolicy, logger, publishInterval = 100 ms, required appVersion, required platform, clock})`. `basePolicy` (`ProtocolPayloadPolicy`) — базовая политика хоста, её же получает `AcpClientApplication`; по ней выбирается вариант InfoBar и подпись `build` в заголовке экспорта. `appVersion` — `codelabDesktopVersion` (`lib/app/build_version.dart`), `platform` — `BuildInfo.label` (`lib/core/platform/build_info.dart`, вида `macOS arm64`); оба передаёт `lib/app/app_scope.dart`.
- **Id строк.** Кадр — строка `seq` (устойчив при вытеснении и `Clear`). У записи журнала id нет, поэтому id строки Log — индекс в **опубликованном** списке видимых записей; он служит только адресом строки для `onRowSelected` и разрешается против того же опубликованного состояния. Выбор хранится не индексом, а копией объекта (`selectedFrame`, `selectedRecord`), признак `selected` строки — сравнение с ним. Поэтому выбор переживает вытеснение, `Clear` другого вида и закрытие вкладки, а сдвиг индексов при вытеснении выбор не переносит на чужую запись.
- **Пустой вид и Export.** Если в активном виде нет видимых элементов, кнопка `Export…` недоступна (`onPressed == null`), а `exportActive` ничего не делает и событий не пишет.

Альтернатива — состояние фильтров в `State` виджета (как сейчас у `WorkbenchDebugLogPane`) — отклонено: действия в шапке дока и тело панели — разные поддеревья, а Pause/Clear/Export и переход Log → Frames меняют общее состояние.

### D8. Вид Log — своя таблица над тем же `LogBuffer`; полноэкранный просмотр остаётся `FluentLogViewerPage`

Переиспользуется: `LogBuffer` (захват, ёмкость, тот же экземпляр, что у полноэкранного просмотра), процессор маскирования, `DebugLogViewerDialog`/`FluentLogViewerPage` без изменений. Таблица, область сессии и панель записи — свои.

Почему не встраивать `FluentLogViewer` как есть (`AGENTS.md` §4, §14):
1. у `LogViewerController` нет фильтра по сессии, а D6 требует области сессии в фокусе с записями соединения;
2. список-плитки и детали сбоку по порогу ширины против таблицы с колонками и деталей снизу под разделителем;
3. собственные Pause/Clear пакета дублировали бы действия шапки дока;
4. в деталях нет места для действия «Show frame in Frames».

Фильтры Log повторяют смысл `LogViewerController`: подстрока без учёта регистра по всем полям, кроме уровня и времени; минимальный уровень; точная категория. Повтор — около 30 строк чистой функции с тестами на совпадение с пакетом по тем же примерам. Риск расхождения записан в Risks.

`Clear` вида Log вызывает `LogRecordSource.clear()` → `LogBuffer.clear()`: как и сейчас `Clear` в `FluentLogViewer`, это очищает и полноэкранный просмотр (буфер общий).

`Expand` — кнопка-иконка в строке фильтров вида Log; открывает `DebugLogViewerDialog.show` с тем же буфером. `/logs` открывает панель Protocol и делает активным вид Log; полноэкранный просмотр открывается только `Expand` (как и сейчас в коде; спецификация «Полноэкранный log viewer» приводится к этому).

Ячейки таблицы кита — строки (D12), поэтому `component` в колонке `Event` не показывается: колонка — только текст события (отступление — D13); `component` виден в полях записи. Время в таблице Log — локальное `HH:mm:ss.SSS`, в таблице Frames — `HH:mm:ss`. Поле `time` в панели выбранного — и записи, и кадра — и в тексте `Copy` — локальное `yyyy-MM-dd HH:mm:ss.SSS`, как в макете; в экспорте — UTC ISO 8601 (D10). Поле `payload` записи журнала (`protocol_message` при `full`) показывается JSON-текстом (`jsonEncode`; если значение не кодируется — `toString()`), а не `toString()` словаря Dart.

Фильтры Log — `ComboBox` категории и уровня. Значение «все» показывает подпись `All categories` и `All levels` (каталог app), а не пустое поле. В панелях кадра и записи поля без значения (`null`) не показываются.

Подписи Log: колонка Event — текст события; для `protocol_message` текст строится из полей: `→ session/prompt · id 2`. Уровень — тег: TRACE и DEBUG нейтральные, INFO акцентный, WARNING предупреждающий, ERROR и CRITICAL опасные. Фильтр уровня по умолчанию — все уровни: в макете стоит «Debug and above», но в той же таблице видна запись TRACE; trace нужна, чтобы видеть `protocol_message` (D13).

Панель записи: заголовок — текст события; теги — уровень и категория; `Copy` копирует запись JSON-ом; поля — все поля записи, кроме уровня и времени, ключ — значение, в порядке записи, первым `time`. У `request_id` — ссылка `Show frame in Frames`: ищется кадр с тем же `id` (сравнение строковой формы) и тем же `connection_generation`, если он есть в записи, иначе — последний такой кадр; кадр ищется только в области (D6), а запись из области ссылается на кадр той же сессии или соединения; найденный кадр выбирается, вид переключается на Frames, фильтры Frames сбрасываются к умолчанию, если скрывали кадр. Кадра в буфере нет — ссылка недоступна, подсказка `The frame is no longer in the buffer.`. InfoBar: `Same buffer as /logs and Expand.` + `Secrets are masked before a record is stored; protocol_message records carry the full frame only in debug builds.`

Альтернативы:
- встроить `FluentLogViewer` как есть — отклонено, см. пункты 1–4;
- доработать `structured_log_fluent` (фильтр-предикат, построитель строки, слот действий деталей) — отклонено в этом change решением пользователя 2026-11-22 (Q3): пакет внешний, его выпуск — отдельный цикл; переход вида Log на пакет возможен отдельным change.

### D9. Карточки Inspector уходят из app

Карточки показывали одобрения, вызовы (с `rawInput`/`rawOutput`), обновления и ход последнего хода. После `redesign-transcript-rows` и `lighten-approval-block` почти всё это есть в строке вызова ленты: риск, статус, исход одобрения, сырые аргументы одобрения за раскрытием («Approval panel offers a collapsed raw input view»). Обновления и ход — теперь кадры с точным порядком. Держать третий вид тех же данных — дублирование.

Что теряется без Trace: сырые `rawInput`/`rawOutput` вызова **без** одобрения. Строка вызова их не показывает намеренно (acp-client-kit «Строка инструмента без сырого JSON»). В debug-сборке они видны в кадрах `session/update · tool_call` / `tool_call_update`; в release-сборке — только в режиме Trace (D17), в кадрах, записанных, пока он включён; без Trace — нигде в UI (раньше — в карточке, замаскированными). Решение пользователя 2026-11-22 (Q8, уточнение «при trace показывать все данные»): без Trace потеря принята, с Trace данные доступны через кадры.

Удаляются: `widgets/inspector_pane.dart`, `widgets/debug_log_pane.dart`, `ActiveSessionState.inspectorEntries` и `_emptyInspectorEntry`, `CodeLabShellState.inspectorEntries`, typedef `CodeLabInspector*` в `ui_mappers.dart`, ARB `workbenchInspector*` и `workbenchDebugLog*`, которые больше не используются.

`InspectorProjection` в `codelab_client_core` остаётся: это публичный API kit, кандидат для CLI `/inspect` (`Coverage.dc.html`, R-23). Решение пользователя 2026-11-22 (Q4): остаётся.

Спецификации: сценарий «Переключение сессий показывает только состояние этой сессии» и «Тесты Flutter UI» больше не упоминают записи инспектора; требование «Debug log — отдельная докнутая панель…» удаляется и заменяется требованиями панели Protocol. Его область — «записи текущей сессии» — сохраняется по смыслу (D6: сессия в фокусе плюс элементы соединения) и распространяется на вид Log; удаляется требование из-за структуры (два раздела одной колонки, карточки Inspector, имя, ссылающееся на Inspector), а не из-за области.

### D10. Pause, Clear, Export

Действия шапки относятся к **активному виду** (решение пользователя 2026-11-22, Q2):
- `Pause` / `Resume` — замораживает список вида (D7); подпись меняется на `Resume`;
- `Clear` — Frames: `ProtocolFrameLog.clear()`, сброс паузы и выбора; Log: `LogRecordSource.clear()`. Буфер общий на соединение (D6), поэтому `Clear` удаляет элементы всех сессий, а не только видимые в области: частичной очистки буфер не умеет, и она была бы неожиданной для полноэкранного просмотра журнала;
- `Export…` — сохраняет то, что видно в активном виде: область сессии в фокусе с текущими фильтрами (как `Export CSV` панели Usage); пустой вид — кнопка недоступна.

Формат — JSON Lines, UTF-8 без BOM, LF. Первая строка — заголовок:

```json
{"type":"codelab.protocol_export","format":1,"view":"frames","build":"debug","app_version":"…","platform":"macOS arm64","exported_at":"2026-11-22T14:02:41.000Z","session_id":"s_7f3a","count":412}
```

Далее по строке на кадр: `{"type":"frame","seq","time","direction","connection_generation","kind","method","id","session_id","error_code","detail","size","payload","payload_omitted"}`; поля `null` опускаются. Ключи — snake_case, значения перечислений — имена значений Dart как есть (`"outbound"`, `"request"`, `"policy"`, `"tooLarge"`), как в `protocol_message` и `protocol_frames.policy` (D3, D17). `time` — UTC ISO 8601 с миллисекундами (`2026-11-22T12:00:03.000Z`). `app_version` — `codelabDesktopVersion`, `platform` — `BuildInfo.label`, `build` — `debug` при базовой политике `full`, иначе `release`. В виде Log — строки `{"type":"record", …поля записи как в буфере}`. `session_id` заголовка — сессия в фокусе или `null` без фокуса. JSON Lines выбран по образцу `--trace-file` CLI (`CliTrace.dc.html`): построчный разбор `jq` и `grep`, одна запись — одна строка.

Маскирование: в файл идут уже замаскированные данные буфера; повторное маскирование не нужно и не делается. В release payload в буфере нет, поэтому нет и в файле. `observability.md` §50: версия app (`app/build_version.dart`), платформа (`BuildInfo`), корреляция (поколение, id) — в каждой строке; объём ограничен буфером.

Предупреждение (§50): если в экспортируемом наборе Frames есть хоть один кадр с payload (debug-сборка или Trace в release), перед диалогом сохранения — `ContentDialog` `Export full payloads?` с текстом `The file will contain prompts, file contents and tool output from these frames. Secrets are masked.` и кнопками `Export` / `Cancel`. Без кадров с payload и для вида Log подтверждения нет (решение пользователя 2026-11-22, Q5). Текст файла строится в момент подтверждения: выключение Trace во время диалога сохранения уже подтверждённый набор не меняет.

Запись — новый порт `ProtocolExportSaver` в `lib/core/platform/protocol_export_saver.dart` по образцу `UsageCsvSaver`: `save({suggestedName, text})` → sealed `ProtocolExportSaveResult` (`Saved | Cancelled | Failed(errorClass)`), `FileSelectorProtocolExportSaver` на `getSaveLocation` и общей `writeFileAtomically`. Имя файла — `codelab-protocol-<frames|log>-<yyyyMMdd-HHmmss>.jsonl`, его строит Cubit. Отказ в диалоге — без заметки; сбой — заметка `Couldn't save the file.` в панели, сбрасывается следующим действием.

Альтернативы:
- обобщить `UsageCsvSaver` в общий `TextFileSaver` — отклонено в этом change: переименование чужого порта и его тестов (`AGENTS.md` §19); общий `writeFileAtomically` уже переиспользуется;
- один JSON-массив — отклонено: тяжелее для потоковой обработки и для больших экспортов;
- экспорт всего буфера без фильтров — отклонено: как в Usage, экспортируется видимое; «всё» — это сброс фильтров.

### D11. Клавиатура

Новые записи каталога `CodeLabShortcut` (`codelab_ui`, `atomics/codelab_shortcuts.dart`), группа `navigation`:

| id | Действие | macOS | Windows, Linux | Где |
|---|---|---|---|---|
| `toggle-protocol` | Show or hide the Protocol pane | ⇧ ⌘ I | Ctrl Shift I | Workbench |
| `protocol-frame-move` | Previous or next frame | ⌥ ← / ⌥ → | Alt ← / Alt → | Protocol pane, Frames view |
| `protocol-record-move` | Previous or next log record | ⌥ ↑ / ⌥ ↓ | Alt ↑ / Alt ↓ | Protocol pane, Log view |

`toggle-protocol` действует как `toggle-files`: привязку держит `CodeLabWorkbenchShortcuts` кита, новый необязательный параметр `onToggleProtocol` (`VoidCallback?`, без колбэка сочетание не привязано — как `onToggleFiles`); app передаёт `() => LayoutCubit.togglePane(ToolPane.protocol)`. В стороже кита `codelab_shortcut_bindings_test.dart` запись проверяется через `CodeLabWorkbenchShortcuts` (`_InKit`). Это сочетание из §12.3, шаг 3. Alt+←/→ — та самая зарезервированная за навигацией инспектора пара (DSK-18), Alt+↑/↓ — её пара для записей; существующие сочетания не переназначаются.

`protocol-frame-move` и `protocol-record-move` привязывает виджет панели Protocol в app (`lib/features/protocol/presentation/protocol_pane.dart`, задача 5.4), а не кит: условие «фокус в панели и не в текстовом поле» и выбор следующего элемента — состояние Cubit. В стороже кита они помечены `_InApp`, нажатия проверяет `keyboard_bindings_test.dart` app (задача 5.3). У организма `CodeLabProtocolPane` колбэков навигации нет: выбор приходит готовым (`CodeLabProtocolTableRow.selected`), прокрутка к выбранной строке — забота организма при смене выбранной строки.

Порядок альтернатив в каталоге и на странице «Keyboard» — порядок слов в подписи действия: «Previous or next frame» — `⌥ ←` / `⌥ →`, «Previous or next log record» — `⌥ ↑` / `⌥ ↓`. Существующий `file-tree-fold` («Expand or collapse a folder» — `→` / `←`) следует тому же правилу и не меняется; `file-tree-move` («Move through files», `↑` / `↓`) — тоже. Единое правило — «первая альтернатива соответствует первому действию подписи».

**Фокус для навигации.** Таблица — фокусируемая область (`Focus` вокруг организма в виджете app, в обходе Tab). Фокус она получает щелчком по любому месту таблицы, в том числе по пустому месту или строке (щелчок по строке ещё и выбирает её), и клавишей Tab. Обработчик Alt-стрелок висит на уровне панели и возвращает `KeyEventResult.ignored`, если первичный фокус — в `EditableText` (поле поиска): так поле получает Alt+←/→ как обычно. Без выбранной строки работает правило «первый / последний видимый» ниже.

Навигация действует, когда фокус внутри панели Protocol и **не** в текстовом поле: в поле поиска Alt+←/→ на macOS двигают курсор по словам, это поведение не перехватывается. Без выбора Alt+→ / Alt+↓ выбирают первый видимый элемент, Alt+← / Alt+↑ — последний; на краю списка выбор не меняется. Выбранная строка прокручивается в видимую область.

По правилу `apps/codelab_desktop/AGENTS.md` («Страница «Keyboard»») в том же change: записи каталога, ARB `settingsKeyboardAction…`/`settingsKeyboardWhere…`, сценарии нажатия в сторожах `keyboard_bindings_test.dart` и `codelab_shortcut_bindings_test.dart`, строки страницы «Keyboard» (MODIFIED app-settings).

- Организм `CodeLabProtocolPane` (`organisms/codelab_protocol_pane.dart`): переключатель видов, слоты фильтров, таблица, разделитель, панель выбранного, подвал. Кит не знает ACP, кадров и записей журнала; подписи, тоны и сегменты строит маппер app (`codelab_ui/AGENTS.md` §2). API (зафиксирован тестом 3.3):
  - `enum CodeLabProtocolView { frames, log }`;
  - `CodeLabProtocolPane({required view, required onViewChanged, required framesCount, required logCount, viewHint, filters, required columns, toneColumn = 1, tagColumn = 1, required rows, required onRowSelected, emptyRowsText, notices = const [], detail, splitFraction, onSplitChanged, followTail = true, tailScope, required footer})`: `onViewChanged` — `ValueChanged<CodeLabProtocolView>`; `filters` — `Widget?`-слот строки фильтров (поиск, переключатели, `Expand` строит app); `columns` — `List<String>` заголовков; `toneColumn` и `tagColumn` — индексы колонок, к которым относятся тон и тег строки (Frames — 1 и 1, колонка `Method`; Log — 1 и 3: тон красит `Level` по D8, тег `connection` стоит у `Event`); `onRowSelected` — `ValueChanged<String>` с `id` строки; `emptyRowsText` — текст вместо строк при пустом `rows`; `notices` — `List<CodeLabProtocolInfo>`, строки над таблицей: `No session in focus. Showing connection frames only.` (тон `neutral`) и заметка сбоя `Couldn't save the file.` (тон `danger`); `detail` — `CodeLabProtocolDetail?`, `null` — подсказка пустого выбора;

  - `CodeLabProtocolTag({required label, tone})`; `CodeLabProtocolInfo({required title, required message, tone})` — InfoBar: `warning` → `InfoBarSeverity.warning`, `danger` → `error`, иначе `info`. Так один класс покрывает все варианты D13 и D17: debug (`warning`), release (`neutral`), `Trace on: full payloads.` (`warning`), InfoBar вида Log (`neutral`);
  - `CodeLabProtocolField({required label, required value, linkLabel, onLink, linkUnavailableHint})`: ссылка есть при `linkLabel`; при `onLink == null` и `linkUnavailableHint` — недоступна, с `Tooltip` подсказки;
  - `CodeLabMaskedSegment(String text, {required bool masked})`.
- **Хвост таблицы** (spec «Таблица кадров»: «Пока пользователь не прокрутил таблицу вверх и вид не на паузе, новые кадры SHALL прокручивать таблицу к последнему»; сценарий «Хвост не отнимает прокрутку»). Знание делится так: пауза — у app (Cubit), отрыв пользователя от низа — только у организма (контроллер прокрутки приватный). Поэтому:
  - `followTail` (`bool`, по умолчанию `true`) — app передаёт «вид не на паузе». `tailScope` (`Object?`) — ключ области: app передаёт id сессии в фокусе (`null` без фокуса).
  - Организм держит признак **отрыва** от низа. «У низа» — `pixels >= maxScrollExtent - rowExtent / 2`. Признак пересчитывается по положению после любой прокрутки, кроме собственного прыжка к хвосту: колесо, перетаскивание, полоса прокрутки, клавиши и прокрутка к выбранной строке. Пользователь, вернувший таблицу к низу, снова следует за хвостом.
  - После обновления строк (после кадра, по `itemExtent`): если `followTail` и нет отрыва — прыжок к последней строке. При `followTail == false` позиция не меняется; при возврате `followTail` в `true` (Resume) без отрыва — прыжок к хвосту.
  - Смена `view` или `tailScope` снимает отрыв и прыгает к последней строке (spec «Панель Protocol: виды Frames и Log»: при смене фокуса «таблица прокручивается к последнему элементу»). Пауза при этом не нарушается: на паузе прыжок идёт к последней строке замороженного снимка.
  - **Выбор и хвост.** Прокрутка к хвосту выбор не меняет: выбор — состояние app, а панель выбранного продолжает показывать выбранный элемент, даже если его строка ушла за экран. В обновлении, где сменилась выбранная строка, приоритет у прокрутки к выбранной (минимальная, как сейчас); прыжка к хвосту в этом обновлении нет. После неё отрыв пересчитывается по положению: если выбранная строка у низа, таблица продолжает следовать за хвостом; если прокрутка подняла таблицу (выбор Alt+← строки за верхним краем) — это отрыв, и поток больше не уводит выбранную строку. Выбор видимой строки щелчком таблицу не двигает и отрыва не создаёт: при следовании за хвостом выбранная строка уйдёт вверх с новыми кадрами — кто хочет её удержать, прокручивает вверх или ставит паузу.
  - **Первая раскладка** (организм создан, в том числе при повторном открытии вкладки): приоритет у выбранной строки, как при смене выбора, — минимальная прокрутка к ней и пересчёт отрыва по положению; без выбранной строки — прыжок к последней строке, если `followTail == true`, иначе таблица остаётся вверху.
  - Правила одинаковы в `Frames` и `Log`: таблица одна, у каждого вида своя область и своя пауза.
  - Альтернатива — `ScrollController` или колбэк «пользователь у низа» наружу, решение о прыжке в Cubit — отклонено: позиция прокрутки — состояние отрисовки, а не приложения; Cubit публикует не чаще раза в 100 мс и не знает высоты области.
- Ключи для тестов хоста: `ValueKey('protocol-table')` — таблица, `ValueKey('protocol-detail')` — панель выбранного, `ValueKey('protocol-row-<id>')` — строка.
- Владение текстами. Каталог кита (`codeLabStringsOf`, `codelab_ui_*.arb`): подписи переключателя `Frames` и `Log` (счётчик — число от хоста), подсказки пустого выбора `Select a frame to see its details.` и `Select a record to see its fields.` (по `view`), кнопка `Copy`, подпись `••••••• (masked)`. От маппера app (ARB app): заголовки колонок, `viewHint`, `emptyRowsText`, тексты `notices`, заголовок, теги, InfoBar, поля, `note`, подпись ссылки и её подсказка, подвал. Действия шапки — `Trace`, `Pause`/`Resume`, `Clear`, `Export…` — **не** часть организма: app строит их виджетами и передаёт в `CodeLabDockTab.actions` вкладки Protocol.
- Доля разделителя — доля высоты таблицы в сумме «таблица + панель выбранного». Организм контролируемый с запасным состоянием: при `splitFraction == null` берёт долю по умолчанию вида (0.52 Frames, 0.56 Log) и держит перетаскивание в своём `State`; при заданном `splitFraction` рисует её и сообщает новую долю через `onSplitChanged` (`ValueChanged<double>?`). При раскладке доля ограничивается так, чтобы обе части были не меньше 96 px. App передаёт долю из `ProtocolPaneState` (D7), поэтому она переживает закрытие вкладки; тест 3.3 проверяет неконтролируемый режим.
- `columnWidths` (`List<double?>?`) — ширины колонок таблицы: число — фиксированная ширина, `null` — гибкая. Без параметра: колонка тега (`tagColumn`) гибкая, колонка стрелки направления (пустой заголовок) — 28, остальные — 72. App передаёт ширины, измеренные по заголовку колонки и образцу содержимого (`00:00:00` — время Frames, `00:00:00.000` — время Log, `CRITICAL` — уровень) шрифтом темы с учётом масштаба текста: фиксированные 72 px обрезали русские заголовки и время при крупном шрифте. Если гибкой колонке остаётся меньше 88 px, кит пропорционально ужимает фиксированные. Текст гибкой колонки сжимается с многоточием; тег в ячейке — не шире 60 % ячейки, тоже с многоточием, чтобы текст метода или события оставался виден. Теги заголовка панели выбранного переносятся на следующую строку (`Wrap`), а не обрезаются.
- Размеры (высота строки таблицы, отступы, шрифт JSON и полей, толщина линии разделителя) берутся из макета (`Inspector.dc.html`, `InspectorLog.dc.html`: `.ptbl`, `.lkv`, `.pjson`, `.hsplit`) через токены кита и тестами не проверяются. Исключения, которые проверяются: минимум 96 px, доли по умолчанию, фиксированная высота строки (`itemExtent`), при которой строятся только видимые строки.
- Подсветка маскирования: маппер делит отформатированный JSON на сегменты по маркеру `<redacted>` **без кавычек** — так находятся и значения, замаскированные целиком (`"<redacted>"`), и маркеры внутри строки, оставленные маскированием текста (`"1| API_TOKEN=<redacted>"`). Кит рисует замаскированный сегмент как `••••••• (masked)` тоном предупреждения; кавычки и остальной текст строки — обычным текстом. Строка, которую агент сам прислал с `<redacted>`, тоже подсветится — безвредно.

Таблицы — `ListView.builder` с фиксированной высотой строки: буфер до 2000 строк, строятся только видимые.

### D17. Режим Trace: полные payload кадров в release по явному включению

Решение пользователя 2026-11-22 к Q7 и Q8: «при trace показывать все данные». Толкование: панель Protocol в release показывается; по умолчанию кадры — только метаданные; явное включение Trace хранит и показывает полные payload кадров.

**Что такое Trace.** Отдельный runtime-переключатель **политики кадров** в ядре клиента: `AcpClientApplication.setFrameTrace(bool)`, через `AgentBackend` и `ProtocolFrameLog.setTrace` (D5). Действующая политика кадров — `full`, если базовая `full` или Trace включён.

**Правила вызова.**
- Порт `AgentBackend` получает три члена: `Stream<ProtocolFrame> get protocolFrames`, `bool get traceAvailable`, `void setFrameTrace(bool enabled)`; `AcpClientBackend` передаёт их ядру.
- `setFrameTrace` идемпотентен: повторный вызов с тем же значением ничего не меняет и не пишет событий.
- Событие info `protocol_frames.policy {policy, reason}` пишется только при смене **действующей** политики кадров; `policy` — имя значения `ProtocolPayloadPolicy` (`'full'`, `'metadataOnly'`), `reason` — `trace_on` или `trace_off`.
- При базовой `full` (`traceAvailable == false`) `setFrameTrace` — no-op без события и без исключения: действующая политика и так `full`, вызов ничего не раскрывает. Исключение отклонено: хост, который не спрятал переключатель, ронял бы панель ради ошибки без последствий для безопасности; переключателя в debug-сборке нет и так (ниже).
- `ProtocolFrameLog.setTrace` при `traceAvailable == false` тоже no-op: бэкенд не вызывается, `traceEnabled` остаётся `false`, ревизия не растёт. Повторный вызов с тем же значением — no-op; payload снимается только при переходе «включён → выключен».

Рассмотрены и отклонены:
- **существующий `setProtocolTracingEnabled`** (`structured_log_logger.dart`) — это переключатель *файла* `protocol.log`: включив его, release писал бы промпты и содержимое файлов на диск с ротацией до 60 MB (10 MB × 6 файлов), и данные переживали бы процесс. Trace держит данные только в памяти, в буфере, который он сам и чистит. Файловый sink, его выключенность по умолчанию и отсутствие UI-переключателя не меняются;
- **минимальный уровень журнала `trace`** — это фильтр показа, а не решение о сборе: уровень меняют для чтения, и он не годится как явное согласие хранить чувствительные данные (`observability.md` §49);
- **Trace, меняющий и запись `protocol_message`** — отклонено: `LogBuffer` пакета не умеет снять поле с уже записанных записей, поэтому после выключения Trace payload оставались бы в журнале до вытеснения. Журнал остаётся на базовой политике; InfoBar вида Log «protocol_message records carry the full frame only in debug builds» остаётся верным.

**Где включается.**
- Desktop: переключатель `Trace` в строке вкладок дока перед `Pause` / `Clear` / `Export…`, оба вида. Есть только в release-сборке (`traceAvailable`); в debug-сборке payload и так полные, переключателя нет. Сочетания и пункта палитры нет: включение — осознанное действие в самой панели. Переключатель — `ToggleButton` с видимым нажатым состоянием (родной стиль: акцентный фон) и semantics `toggled`, чтобы включённый Trace было видно и экранному диктору.
- CLI: отдельного переключателя нет. Явное согласие CLI — `--verbose` (базовая `full`), кадров CLI не показывает.

**Не сохраняется между запусками.** При каждом старте Trace выключен. Почему: согласие хранить промпты и содержимое файлов должно даваться в том запуске, где данные собираются (`AGENTS.md` §2, приоритет 1; `observability.md` §27 — release без developer-диагностики по умолчанию, §49 — только явное действие, никогда автоматически). Переподключение и смена профиля Trace не выключают: это тот же процесс и то же согласие.

**Маскирование действует всегда.** Payload кадра в Trace строится тем же `SecretRedactor` с правилом D4; секреты не хранятся и не показываются ни при какой политике.

**Индикация.** Пока Trace включён: переключатель нажат; InfoBar панели выбранного кадра — предупреждение `Trace on: full payloads.` с текстом `Prompts, file contents and tool output are kept in memory until Trace is turned off. Secrets are masked.` вместо release-варианта. Кадр, записанный до включения Trace, показывает поля кадра и строку `Recorded before Trace was turned on: metadata only.`.

**Единое правило снятия payload.** `codelab_client_acp` экспортирует `extension ProtocolFrameRedaction on ProtocolFrame { ProtocolFrame withoutPayload(); }` (D2): копия кадра с `payload = null`, `payloadOmitted = policy` (уже стоящая пометка `tooLarge` сохраняется) и у **любого** кадра-ошибки `detail` = стандартное имя кода (`Parse error`, `Invalid Request`, `Method not found`, `Invalid params`, `Internal error`, `Resource not found`; у незнакомого кода — `null`; внутренний помощник `standardErrorName`). Замена `detail` касается и кадров-ошибок с `payloadOmitted == tooLarge`: payload у них нет, но `detail` при `full` несёт замаскированный текст агента, и выключение Trace снимает его так же. Тем же правилом пользуются ядро при `metadataOnly` (D3), буфер kit при выключении Trace и для кадра в пути (D5) и app — для выбранного кадра и снимка паузы. Второй реализации снятия нет: расхождение правил дало бы текст агента в одном из мест.

**Выключение.** Ядро сразу возвращается к `metadataOnly`; буфер снимает payload со всех кадров (D5), Cubit — с выбранного кадра и снимка паузы. У кадра-ошибки вместе с payload заменяется и `detail`: замаскированный текст `error.message` агента уступает стандартному имени кода (или `null` для незнакомого кода), как у кадра, построенного при `metadataOnly` (D3). Замена действует везде, где кадр живёт: в буфере, у кадра в пути (построен до выключения, доставлен после), у выбранного кадра и в снимке паузы. В памяти app полных payload после выключения не остаётся; файл, уже сохранённый экспортом, — ответственность пользователя (подтверждение Q5 предупредило). Лимиты 256 KiB на payload и 8 MiB на буфер те же.

**Экспорт.** Подтверждение Q5 действует, если в наборе есть кадр с payload, — значит, и в release в режиме Trace (D10).

Противоречий со спецификациями безопасности нет: structured-logging требует включать полный payload только явным действием и не автоматически — Trace таков; approval-safety «Открыт debug-лог» разрешает показ промптов при явной настройке — это она; секреты скрыты всегда.

## Risks / Trade-offs

- **Стоимость `jsonEncode` на каждый кадр** (размер, D2) и `redact` в debug. Стриминг — сотни мелких кадров в секунду; большие кадры — редкие `fs/*`. → Тест производительности ядра: 10 000 кадров `agent_message_chunk` записываются без заметной задержки обработки (порог в задаче 1.x); Замер задачи 1.7: при политике `full` обработка потока стоит 1,36–1,40× от базы при пороге 1,5× (база — без подписчиков кадров, но с построением записи кадра); построение кадра — около 2,8 µs на кадр, около 7 % стоимости обработки чанка. Оптимизация, вошедшая в change: повторный `jsonEncode` замаскированного payload пропускается при `size * 4 ≤ 256 KiB` (D3). Запасной вариант `size = null` в release не понадобился; `size` остаётся `int`.
- **Общий лимит буфера при области одной сессии** (D6). Шумная фоновая сессия вытесняет кадры сессии в фокусе: 2000 кадров — это несколько минут стриминга одной сессии. → Лимит общий осознанно (решение пользователя Q1 при буфере на соединение); если окажется мал на практике — отдельным change поднять лимит или ввести долю на сессию; счётчик и `Clear` описаны честно в спецификации.
- **Расхождение фильтров Log с `LogViewerController`** (D8). → Тесты фильтра на примерах пакета; при обновлении `structured_log_flutter` тест сравнения фиксирует расхождение.
- **Политика payload по умолчанию `metadataOnly`** меняет содержимое `protocol_message` у хостов, которые её не передают (тесты ядра, проверяющие `payload` в трассе). → Такие тесты явно передают `full`; поведение desktop debug и CLI `--verbose` прежнее.
- **Правило пары `name`/`value`** может скрыть безвредное значение у имени со словом `token`/`auth` (`{"name": "AUTHOR", "value": …}` — `auth` совпадает). → Это уже свойство общего правила имён (`author` в ключе скрывается и сейчас); отдельных исключений не вводим.
- **Удаление карточек Inspector** — в release-сборке сырые аргументы и результат вызова без одобрения больше не видны (D9). → Принято решением пользователя 2026-11-22 (Q8); руководство app обновляется в этом change; в debug-сборке они есть в кадре `session/update · tool_call_update`.
- **Утечка через `Copy`** в буфер обмена ОС. → Копируется только замаскированное; в release без Trace — только метаданные.
- **Trace оставлен включённым надолго** — промпты и файлы копятся в памяти (до 8 MiB). → Видимая индикация, сброс при перезапуске, выключение снимает payload (D17).

## Migration Plan

Данных для переноса нет: кадры и журнал живут в памяти. Ключи `codelab.dock.*` прежние, вкладка `protocol` остаётся. После обновления release-сборка перестаёт хранить payload в журнале — это намеренно.

## Решения пользователя

Ответы на вопросы Q1–Q8 — 2026-11-22:
- **Q1.** Панель Protocol показывает только сессию в фокусе, а не все сессии соединения (D6; отступление от макета — D13).
- **Q2.** `Pause` / `Clear` / `Export…` действуют на активный вид (D10).
- **Q3.** Вид Log — своя таблица над `LogBuffer` в этом change; доработка `structured_log_fluent` — не здесь (D8).
- **Q4.** `InspectorProjection` в `codelab_client_core` остаётся (кандидат для CLI `/inspect`); доказательства R-23 дополняются, а не заменяются (D9).
- **Q5.** Перед экспортом полных payload в debug-сборке — подтверждение (D10).
- **Q6.** Переподключение не очищает буфер кадров; поколение видно в деталях кадра (D5).
- **Q7.** Панель Protocol есть в release-сборке, по умолчанию только с метаданными; уточнение «при trace показывать все данные» — режим Trace с полными payload кадров по явному включению, без сохранения между запусками (D3, D17). Решение фиксируется в `observability.md` §27, §49.
- **Q8.** Без Trace потеря сырых `rawInput`/`rawOutput` вызова без одобрения в release принимается; в режиме Trace они доступны в payload кадров (D9, D17). Показ в строке вызова — отдельный вопрос.
