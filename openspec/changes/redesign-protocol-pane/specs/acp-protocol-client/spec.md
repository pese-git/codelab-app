## ADDED Requirements

### Requirement: Кадры ACP клиента
Ядро клиента ACP SHALL публиковать поток кадров — по одному на каждое сообщение JSON-RPC, которое клиент передаёт транспорту, и на каждое входящее сообщение текущего поколения соединения, декодированное в `JsonRpcMessage` (design.md change `redesign-protocol-pane`, D2). Кадр SHALL строиться в той же точке, что и протокольная трасса, и SHALL содержать: порядковый номер в пределах экземпляра ядра, время, направление, поколение соединения, вид (`request`, `notification`, `result`, `error`), метод, id, id сессии, код ошибки (у вида `error`), подробность и размер сообщения в байтах UTF-8 до маскирования.

Метод ответа SHALL быть методом запроса с тем же id из противоположного направления в том же поколении; без такого запроса — отсутствовать. Id сессии SHALL браться из `params.sessionId`, у ответа — из его запроса, у результата `session/new` — из `result.sessionId`. Подробность SHALL браться только из полей схемы ACP (`docs/protocols/acp/protocol/17-Schema.md`): `update.sessionUpdate` у `session/update`; `outcome.optionId` или `cancelled` у результата `session/request_permission`; у ошибки — текст по политике ниже. Незнакомый метод или форма SHALL давать кадр без подробности, а не ошибку; сбой построения кадра SHALL NOT мешать отправке и обработке сообщения. Учёт запросов без ответа SHALL быть ограничен (не больше 1024 записей) и SHALL очищаться при смене поколения; id сопоставляется с учётом типа (`1` и `"1"` — разные запросы). Строковые метод и подробность кадра SHALL быть не длиннее 120 символов. Каждое исходящее сообщение, включая ответ `cancelled` на `session/request_permission`, который ядро отправляет само, SHALL давать кадр.

Базовую политику payload SHALL задавать хост при создании ядра: `full` или `metadataOnly`, по умолчанию `metadataOnly`. Поверх неё ядро SHALL давать runtime-режим Trace для кадров: пока Trace включён, действующая политика кадров — `full`; при выключенном Trace — базовая. Trace SHALL быть выключен при создании ядра и SHALL включаться только явным вызовом хоста, никогда автоматически (design.md change `redesign-protocol-pane`, D17). При базовой `full` вызов включения или выключения Trace SHALL ничего не менять и SHALL NOT давать ошибку. Ядро SHALL записывать в журнал смену действующей политики кадров с новой политикой и причиной (`trace_on`, `trace_off`); повторный вызов с тем же значением смены не даёт. Политика сравнивается в момент построения кадра. При действующей `full` кадр SHALL нести payload — JSON сообщения после маскирования секретов (approval-safety «Редактирование секретов», «Секрет в паре name/value»); payload больше 256 KiB SHALL NOT храниться, кадр помечается `tooLarge`: сообщение, исходный размер которого больше 256 KiB, SHALL помечаться `tooLarge` без маскирования, а у остальных SHALL проверяться размер замаскированного payload. При `metadataOnly` payload SHALL NOT строиться, а текст ошибки агента SHALL NOT попадать в кадр: подробность ошибки — стандартное имя кода, известное пакету протокола, а у незнакомого кода её нет. При `full` подробность ошибки — `error.message` после маскирования, не длиннее 120 символов. Только базовая политика (не Trace) SHALL определять, несёт ли запись трассы `protocol_message` поле `payload` (structured-logging «Protocol tracing выключен по умолчанию в release»).

Входящее сообщение прежнего поколения SHALL NOT давать кадр: при замене транспорта ядро перестаёт слушать прежний транспорт до привязки нового, а сообщение, всё же дошедшее до обработчика, отбрасывается проверкой поколения до трассы, как и сейчас.

Если кадр построить не удалось, ядро SHALL записать в журнал `protocol_frame.build_failed` с методом и классом ошибки, SHALL NOT публиковать этот кадр и SHALL обработать сообщение так же, как без кадра.

#### Scenario: Ответ получает метод и сессию запроса
- **WHEN** клиент отправляет `session/prompt` с id 2 и `sessionId` `s_7f3a`, и агент отвечает результатом с id 2
- **THEN** кадр ответа — вид `result`, метод `session/prompt`, id 2, сессия `s_7f3a`, направление `inbound`

#### Scenario: Ответ клиента на запрос разрешения
- **WHEN** агент присылает `session/request_permission` с id `a9`, и клиент отвечает исходом `selected` с `optionId` `allow_once`
- **THEN** исходящий кадр — вид `result`, метод `session/request_permission`, id `a9`, подробность `allow_once`

#### Scenario: Поздний запрос одобрения при отмене
- **WHEN** ход сессии отменяется, и агент присылает `session/request_permission` с id `p4`, на который ядро само отвечает исходом `cancelled`
- **THEN** публикуется входящий кадр запроса и исходящий кадр — вид `result`, метод `session/request_permission`, id `p4`, подробность `cancelled`

#### Scenario: Id разного типа не сопоставляются
- **WHEN** клиент отправил запрос с числовым id `1`, и агент отвечает результатом со строковым id `"1"`
- **THEN** кадр ответа — без метода запроса

#### Scenario: Release-политика не хранит payload и текст ошибки
- **WHEN** ядро создано с политикой по умолчанию, и агент отвечает ошибкой `{"code": -32603, "message": "failed at /Users/dev/secret-project"}`
- **THEN** кадр не несёт payload, код ошибки `-32603`, подробность — `Internal error`, пути в кадре нет; запись `protocol_message` этого сообщения не несёт `payload`

#### Scenario: Debug-политика маскирует до хранения
- **WHEN** ядро создано с политикой `full`, и клиент отправляет `session/new` с MCP-сервером, у которого заголовок `{"name": "Authorization", "value": "ghp_abc"}`
- **THEN** payload кадра содержит `<redacted>` вместо `ghp_abc`, а `size` — длина исходного сообщения

#### Scenario: Большой payload не хранится
- **WHEN** ядро создано с политикой `full`, и клиент отвечает на `fs/read_text_file` содержимым 1 MiB
- **THEN** кадр ответа без payload с пометкой `tooLarge`, остальные поля заполнены

#### Scenario: Незнакомый метод
- **WHEN** агент присылает уведомление `_vendor/custom` с произвольными параметрами
- **THEN** кадр с методом `_vendor/custom`, видом `notification` и без подробности публикуется, обработка уведомления идёт как раньше

#### Scenario: Поздний кадр старого соединения
- **WHEN** после переподключения прежний транспорт выдаёт входящее сообщение
- **THEN** кадр с этим сообщением не публикуется, а кадры нового поколения публикуются как обычно

#### Scenario: Сбой построения кадра
- **WHEN** агент присылает запрос незнакомого метода, и построить его кадр не удаётся
- **THEN** кадр не публикуется, журнал содержит `protocol_frame.build_failed` с методом и классом ошибки, запись `protocol_message` этого сообщения несёт направление, вид, метод и id, но не размер и payload, а агент получает ответ `Method not found`, как без кадра

#### Scenario: Смена поколения очищает учёт запросов
- **WHEN** клиент отправил `session/prompt` с id 3, соединение заменено, и в новом поколении приходит ответ с id 3
- **THEN** кадр ответа — без метода `session/prompt`: запрос старого поколения не сопоставляется

#### Scenario: Trace в release-политике
- **WHEN** ядро создано с политикой по умолчанию, хост включает Trace, и клиент отправляет `session/prompt`
- **THEN** кадр несёт замаскированный payload, а запись `protocol_message` — нет; после выключения Trace следующий кадр снова без payload

#### Scenario: Trace выключен при создании
- **WHEN** ядро создано, и хост не вызывал включение Trace
- **THEN** кадры строятся по базовой политике; сбой или ошибка протокола Trace не включают
