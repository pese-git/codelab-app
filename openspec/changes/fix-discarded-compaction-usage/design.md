## Context

Задача пользователя (2026-11-17): закрыть риск R11 change `add-usage-ledger`. Компактор отбрасывает проход без выигрыша, и оплаченный вызов суммаризатора пропадает из учёта usage.

### Как устроено сейчас

Код сверен с `develop` после слияния PR #346 (`1c033fd4`, задача 0.2а). В `develop` уже влиты `fix-compaction-estimate-and-no-gain`, `anchor-context-estimate-after-compaction` (CMP-11, якорь оценки на последнее сжатие; D9 «порог по `max(after, H(после))`» снят) и `fix-config-change-during-background-compaction` (SES-16, CMP-12, `appendWith`, исход `stale`). Все три не архивированы.

**Компактор** (`codelab_agent_core/lib/src/compaction/compactor.dart`, `compact`). Один проход:
1. регион и точка среза; без среза — `compaction.skipped` с `reason: "no cut point"`, суммаризатор не вызывается;
2. `summarize(...)` → `SummaryResult` (`text`, `usage`, `model`). Если проход делает несколько запросов (разрезанный ход), `usage` — их сумма (D4 change `add-usage-ledger`);
3. `cancel.throwIfCancelled()`;
4. выбор навыков и согласованная оценка `after`;
5. если `after >= before` (порог и выигрыш — по согласованному `after`) — лог `compaction.skipped` (`reason: "no reduction"`, `tokens_before`, `tokens_after`) и `return done ?? const NothingToCompact('no reduction')`. Это проверка до очереди писателя, по снимку начала прохода. На этой ветке `result.usage` и `result.model` теряются;
6. иначе запись `compaction` с `details.summaryModel` и `details.usage` через `writer.appendWith` (CMP-12). В построителе, уже в очереди писателя:
   - отменённый токен → `null`, затем `cancel.throwIfCancelled()` → `CancelledException`;
   - между листом начала прохода и текущим листом есть запись не из списка состояния (`model_change`, `mode_change`, `config_change`, `session_info`) или лист начала прохода не на пути → `null`, лог `compaction.skipped` уровня `warning` с `reason: "stale"` и `blocking_type`, `return done ?? const NothingToCompact('stale')`. По D3 того change исход в текущем ядре недостижим, это защита на будущее;
   - иначе запись ложится на текущий лист;
7. после записи — `onCompacted` (якорь CMP-11), `ContextCompacted(usage, model)`, лог `compaction.done`.

Где суммаризатор уже оплачен, а записи `compaction` нет: `no reduction` (шаг 5), `stale` (шаг 6), отмена в очереди (шаг 6), а также отмена сразу после ответа (шаг 3). Сбой суммаризатора (`CompactionFailed`) usage не возвращает. Без среза (`no cut point`) суммаризатор не вызывается.

Все четыре триггера — `manual` (`/compact`), `afterTurn` (фон после хода), `preflight` и `overflow` (аварийный путь цикла) — идут через один `compact` (`AgentSession._compact`). Различается только реакция на исход: `/compact` отвечает `Nothing to compact.`, `_emergency` возвращает `null` («сжатие не помогло», CMP-8), `afterTurn` молча завершается. Если отбросить проход внутри `compact`, этого достаточно для всех путей.

**Учёт суммаризатора** (change `add-usage-ledger`):
- живая сумма. `SessionBridge` на `ContextCompacted(usage, model)` вызывает `UsageAccounting.summarizerEnded(usage, priced: …)` и шлёт снимок `trigger: "compaction"` (D4);
- журнал usage. `buildUsageLedger` по всем записям файла берёт `CompactionRecord` с `details.usage` и строит `summaries` (`count`, `usage`, `models`) и `summaryCalls` для правила цены (D1 п. 6, D2);
- засев на `session/load`: `UsageAccounting.seed` по свёртке. Инвариант «сразу после засева `session` равен `total` ответа журнала» держится по построению (D8, D15 п. 6).

Все три пути завязаны на запись `compaction`. У отброшенного прохода её нет.

**Журнал сессии** (`agent-core/08-sessions.md`):
- §8.2.4 — `custom` (`customType`, `data`) — «данные хоста; неизвестный `customType` сохраняется и игнорируется», в контекст модели не входит;
- §8.6, шаг 4b — неизвестный `type` читается как `CustomRecord("unknown:<type>")` и тоже сохраняется.

Ядро уже пишет `custom` само: `customType: "codelab.cwd_changed"` на `session/load` с другим `cwd` (`agent_runtime.dart`; `agent-runtime` «loadSession», §13.5 шаг 2). `buildLlmContext` (§8.7, шаг 6) кладёт `custom` в «прочее → ничего». `healInterruptedTurn` (§8.8) смотрит только на ответы модели и результаты.

## Goals / Non-Goals

**Goals:**
- Каждый оплаченный вызов суммаризатора, после которого компактор вернул исход без отмены и без сбоя, попадает в живую сумму сессии, в журнал usage (`/usage`, `usage.json`, ответ `_codelab/session/usage/ledger`) и в засев после `session/load`.
- Причины неполноты (`noUsage`, `noPrice`) у такого вызова считаются по тем же правилам, что у вызова из записи `compaction`.
- Инвариант «засев = `total`» (D8 change `add-usage-ledger`) сохраняется.
- Проекция контекста, транскрипт, исход `compact` и ответ `/compact` не меняются (CMP-10 в силе).

**Non-Goals:** R3 (сбой суммаризатора, отмена после ответа), ограничение повторных отброшенных проходов, usage детей, разбор `discarded` на клиенте (proposal, «Не входит»).

## Decisions

Решения, отмеченные «решение пользователя Qn», приняты 2026-11-17 (раздел «Решения пользователя 2026-11-17»). Остальное — технические решения в рамках этих ответов.

### D1. Служебная запись учёта отброшенного прохода (решение пользователя Q1 (а))

Отбросив проход по CMP-10 (шаг 5 выше), компактор дописывает в журнал одну запись `custom`:

```json
{"type":"custom","id":"r7k2m9p1","parentId":"q1w2e3r4","timestamp":"2026-11-17T10:00:05.000Z",
 "customType":"codelab.compaction_discarded",
 "data":{"reason":"no reduction","trigger":"manual","pass":1,"tokensBefore":3043,"tokensAfter":3567,
         "summaryModel":"openai/gpt-4o-mini",
         "usage":{"input":764,"output":171,"cacheRead":0,"cacheWrite":0,"cost":{"input":0.0001146,"output":0.0001026,"cacheRead":0,"cacheWrite":0}}}}
```

Правила:
- **Когда.** На ветке «нет выигрыша» (шаг 5) и при исходе `stale` (шаг 6; решение пользователя Q6 (а)). Для `stale` запись идёт отдельным `append` после того, как `appendWith` вернул `null` и отмена проверена; `data.reason: "stale"`, родитель — текущий лист. Общие условия: после ответа суммаризатора, после проверки отмены и после выбора навыков. Без среза (`no cut point`) суммаризатор не вызывался, и записи нет. Сбой суммаризатора (`CompactionFailed`), отмена сразу после ответа и отмена в очереди писателя (CMP-12) записи не дают (R3, Q5). В цепочке проходов (CMP-5) отброшенным может быть только последний проход вызова `compact`: после него `compact` возвращает исход. Поэтому записей учёта на один вызов не больше одной. Записанные раньше проходы, как и прежде, дают свои записи `compaction`.
- **Поля `data`.**
  - `usage` и `summaryModel` — те же имена и та же форма, что у `compaction.details` (форма `usage` — §8.2.3). Свёртка читает обе записи одним правилом (D3). `usage` — сумма всех запросов прохода (D4 change `add-usage-ledger`). `summaryModel` пишется всегда: `SummaryResult.model` в ядре — непустая `String` (D11).
  - `reason` — `"no reduction"`. Поле задел под R3: другие значения сможет ввести отдельный change, свёртка учитывает запись при любом `reason`.
  - `trigger`, `pass`, `tokensBefore`, `tokensAfter` — для диагностики. Ядро на них не опирается.
  - Текста резюме нет: он не нужен ни учёту, ни диагностике, а в журнале был бы второй копией пересказа пользовательских данных.
- **Место в дереве** — по общему правилу §8.4: `parentId` — текущий лист, лист после записи — её `id`. Проекция контекста от этого не меняется: `buildLlmContext` пропускает `custom` (§8.7, шаг 6), якорь оценки ищется только среди ответов модели (§9.3), `healInterruptedTurn` записи не видит (§8.8). Следующее сжатие может получить эту запись в регион. Суммаризатор берёт из региона только `message`, а точка среза ставится по границам сообщений — так же уже лежат в регионах `model_change` и `custom` `codelab.cwd_changed`. Это проверяет тест (задача 1.1).
- **Запись** — `SessionWriter.append` без `durable`, а не `appendWith`.
  - Родитель, id и время вычисляются в очереди писателя по листу после предыдущих записей (SES-16). Смена конфигурации, пришедшая во время резюме, остаётся на активной ветке перед записью учёта.
  - Проверка CMP-12 записи учёта не нужна: запись не даёт сообщений контексту и не уводит другие записи с активной ветки.
  - Запись учёта — последнее, что пишет вызов `compact`. Поэтому она не может оказаться между листом начала прохода и записью `compaction` того же вызова и не даёт `stale`. Следующий вызов берёт лист начала прохода заново.
  - Без `durable`, потому что запись производная от уже потраченных денег, а не точка восстановления. По политике `checkpoints` (§8.5) она сбросится на ближайшем `TurnEnded`. При отключении питания до сброса теряется только учёт.
- **Сбой записи** обрабатывается как сбой записи `compaction` на соседней ветке: исключение уходит из `compact` (SES-8). `/compact` завершается ошибкой хода. `afterTurn` пишет `compaction.failed`. Аварийный путь завершает ход `failed`. Особого «тихого» пути нет: продолжать сессию с неработающим журналом нельзя (SES-8).
- **Инвариант CMP-13** (`09-compaction.md` §9.9, задача 0.3): каждый оплаченный вызов суммаризатора, после которого сжатие не записано (`no reduction`, `stale`), оставляет ровно одну запись учёта и одно `CompactionDiscarded`; проекция, транскрипт и якорь от неё не меняются.
- **Совместимость чтения.** Старое ядро (`develop` до change и код `add-usage-ledger`) читает `custom` с незнакомым `customType` и игнорирует его (§8.2.4). Сессия открывается, контекст тот же, учёт прежний (без вызова). Разбор журнала и `SessionRecord` не меняются.

*Альтернативы* (вопрос Q1):
- **(б) новый `type` записи** (например, `compaction_discarded` или `summary_call`) с полями верхнего уровня. Это новая ветка `SessionRecord`, `fromJson`/`toJson`, строка таблицы §8.2.4. Старый код прочтёт запись как `unknown:<type>` — тоже безопасно. Плюс — типизированные поля. Минус — постоянный элемент формата ради узкого факта учёта. Эту роль уже покрывает `custom` (прецедент `codelab.cwd_changed`).
- **(в) поле в существующей записи.**
  - Следующая запись `compaction` может не появиться вовсе. До неё usage пришлось бы держать в памяти, и он терялся бы при перезапуске; в цепочке «проход 1 записан, проход 2 отброшен» запись прохода 1 уже на диске, а журнал только дописывается (SES-1).
  - Записи хода у `/compact` и `afterTurn` нет: встроенная команда в журнал не пишется (ACP-12), `afterTurn` идёт вне хода.
  - Ответ модели шага `overflow` есть только у одного триггера из четырёх, и usage суммаризатора смешался бы с usage шага, хотя в ход он не входит (D4 change `add-usage-ledger`).
- **(г) только событие ядра, без записи.** Живая сумма вызов учтёт, а свёртка, `usage.json`, ответ журнала и засев — нет. Внутри одной сессии сервера ответ журнала разошёлся бы с живой суммой. После `session/load` сумма сессии стала бы меньше, чем до перезагрузки. Инвариант «засев = `total`» формально держится, но потеря тогда переезжает из живой суммы в «после загрузки», а не устраняется. Отклонено.
- **(д) оставить R11 принятым риском.** Отклонено задачей пользователя.

### D2. Событие `CompactionDiscarded`

Новая ветка sealed-иерархии `AgentEvent` — это точка расширения ядра (`codelab_agent_core/AGENTS.md` §3 (г)):

```dart
final class CompactionDiscarded extends AgentEvent {
  final int tokensBefore, tokensAfter; // согласованная оценка прохода (D1 change fix-compaction-…)
  final Usage usage;                   // сумма запросов прохода
  final String model;                  // `<provider>/<id>` из `SummaryResult.model` (non-null, D11)
}
```

- Эмитится тем же `emit`, что `ContextCompacted`, сразу после успешной записи D1. Событие означает «вызов суммаризатора оплачен, сжатие не записано».
- `ContextCompacted` не расширяется полем «applied»: по спецификации `agent-loop` и у потребителей оно значит «сжатие записано». Это снимок `compaction` с `used = tokensAfter` и итог `/compact`. Флаг заставил бы ветвиться всех потребителей.
- `TurnEnded.usage` вызов не включает, в том числе на аварийном пути. Правило D4 change `add-usage-ledger` для суммаризатора не меняется.
- `AgentLoop` не меняется: `_emergency` по-прежнему возвращает `null`.
- Реплей (`session/projections.dart`) события не даёт. Отброшенный проход ничего не показывает пользователю, а сумму после загрузки даёт засев (D5). Если бы реплей эмитил событие, мосту пришлось бы отличать его от живого, чтобы не учесть вызов дважды.
- Исчерпывающие `switch` по `AgentEvent` получают ветку. В `codelab_agent_acp/event_projection.dart` это `const []`: кадров ACP нет. `SessionWriter.handle` событие пропускает: запись пишет компактор.

### D3. Свёртка журнала usage (решения пользователя Q2 (а), Q3 (а))

`buildUsageLedger` (D1 п. 6 change `add-usage-ledger`) при обходе всех записей файла считает вызовом суммаризатора, кроме `CompactionRecord` с `details.usage`, ещё `CustomRecord` с `customType == "codelab.compaction_discarded"`, у которого `data` — объект и `data.usage` — объект.
- Вызов попадает в `summaryCalls` (`usage`, `model` из `data.summaryModel`), в `summaries.count`, `summaries.usage`, `summaries.models` и в итог. Правила цены и `noUsage` — те же, что у вызова из записи `compaction` (D2, D4 того change). Отдельного правила нет.
- `UsageLedgerGroup` суммаризатора получает `discarded` — число таких вызовов (по умолчанию 0). Вызов остаётся вне ходов, как и сейчас.
- Запись с `data` или `data.usage` неверной формы пропускается без причины неполноты, как неразбираемая строка (D1 п. 9 того change). Ремонтом журнала она не считается.
- `usage.json` остаётся версии 1 (Q3 (а)). В блок `summaries` добавляется ключ `discarded`, сразу после `count`, только при ненулевом значении. Порядок ключей и детерминизм (OBS-10) сохраняются. Версия не повышается, потому что содержимое файла не читает ни отчёт, ни засев: отчёт строится из снимка журнала, файл проверяется только на свежесть по `source` (сверка с кодом итерации 1 change `add-usage-ledger`, D2). Читатели формата v1 незнакомый ключ пропускают.

### D4. `/usage`

Строка суммаризатора — `Summaries: <count> (<n> discarded), <usage>`. Часть `(<n> discarded)` выводится только при ненулевом `discarded`. Без неё строка прежняя. Правило `<cost>` и `~` не меняется: части строки — все вызовы, в том числе отброшенные. Остальной текст §12.6.1 в редакции change `add-usage-ledger` не меняется. Пример после `/compact` без выигрыша — `Summaries: 1 (1 discarded), input 764, output 171, cache read 0, cache write 0, cost $0.0002`.

### D5. Адаптер ACP (решения пользователя Q2 (а), Q4 (а))

- **Живая сумма.** `SessionBridge` на `CompactionDiscarded(usage, model, tokensBefore)` вызывает `UsageAccounting.summarizerEnded(usage, priced: …)` по тому же правилу цены, что для `ContextCompacted`: модель есть в каталоге сессии с ценами. Вызов входит в сумму сессии и не входит в ход.
- **Снимок** `_codelab/session/usage` с `trigger: "compactionDiscarded"` — соединениям, объявившим `usage`. Отправляется всегда, когда пришло событие, в том числе при нулевом usage: тогда `noUsage`, как у записанного сжатия.
  - Полей `turnId`, `step` и `turn` нет, как у `compaction`.
  - `session` — сумма с вызовом.
  - `context.used` — `tokensBefore` прохода. Это согласованная оценка текущего заполнения. На первом проходе она равна якорной оценке перед сжатием, на следующем — `tokensAfter` записанного прохода, который уже ушёл снимком `compaction`. Заполнение не меняется, и индикатор не прыгает.
  - `size` и `compactAt` — последнего `StepEnded`, как у снимка `compaction`. Если заполнение мосту неизвестно, поля `context` нет.
  - `seq` растёт по общему правилу. Отправка пишет debug `acp.usage.sent` с этим поводом.
  
  Клиент v1 незнакомый повод принимает как снимок без шага (D2 change `add-usage-extension`): обновляет `session` и `context`. Правка клиента не нужна, это проверяет тест (задача 3.1).
- **Ответ журнала** `_codelab/session/usage/ledger`: у объекта `summaries` появляется необязательное `discarded` — целое, только при ненулевом значении. По правилу совместимости D6 change `add-usage-ledger` новое необязательное поле добавляется без смены `usageLedger.version`. Декодер клиента незнакомое поле пропускает.
- **Засев на `session/load`** берёт `summaries` из свёртки (D3), в том числе отброшенные вызовы. Инвариант «засев = `total`» держится по построению, правки засева нет.
- **Поздние события** (`AGENTS.md` §9). Событие идёт тем же потоком сессии, что `ContextCompacted`. После закрытия моста оно отсекается тем же владельцем подписки. Фоновое `afterTurn` отменяется при закрытии сессии до проверки выигрыша (`CancelledException` на шаге 3), и тогда ни записи, ни события нет. Гонка «ответ журнала включает вызов, снимок которого ещё в пути» — та же, что R8 change `add-usage-ledger`, и решается тем же `seq`.

*Альтернативы* (вопрос Q4):
- (б) повод `compaction`. Он означает «сжатие записано, `used` уменьшился» (фикстура `acp/compact-usage-context` проверяет `used` меньше последнего снимка хода), а здесь сжатия нет.
- (в) без снимка. Сумма придёт в следующем снимке `step`/`turn`/`load`. Ход `/compact` без шагов снимка `turn` не даёт, поэтому строка статуса до следующего шага модели показывает сумму без только что оплаченного вызова. Протокол не меняется, но состояние у клиента отстаёт.

### D6. Наблюдаемость

- `compaction.skipped` с `reason: "no reduction"` или `"stale"` (каталог §12.3; changes `fix-compaction-estimate-and-no-gain`, D3, и `fix-config-change-during-background-compaction`) получает поля:
  - `summary_model` — всегда (`SummaryResult.model` non-null, D11);
  - `usage_record_id` — id записи D1 для связи лога с журналом (§16, correlation id).
  
  Лог пишется после успешной записи. Токенов и денег в логе нет, как в `compaction.done`. Текста резюме нет, как и раньше.
- Адаптер: `acp.usage.sent {session_id, seq, trigger: "compactionDiscarded"}` — прежняя запись. Новых логов нет.

`acp/compact-no-gain-usage`, роль `agent`: только `conformance:agent`, как `acp/compact-usage-summary`. Метки `usage` и `usageLedger`, ссылка `spec` на `15-Extensibility.md`.

2. Ход с одним шагом на модели с ценами.

### D8. Дельты спецификаций и порядок архивации

Требования, которые этот change уточняет, вводят ещё не архивированные changes:
- `agent-compaction` «Сжатие без выигрыша не применяется» — `fix-compaction-estimate-and-no-gain`;
- «Usage суммаризатора», `agent-sessions` «Журнал usage сессии», «Файл usage.json и порт UsageLedgerStore», `agent-slash-commands` «Команда /usage», `agent-acp-server` «Уведомление `_codelab/session/usage`» и «Запрос `_codelab/session/usage/ledger`» — `add-usage-ledger`.

Все они — в активных, ещё не архивированных changes, и в `openspec/specs/` их нет. Поэтому все дельты — **ADDED**-требования в тех же capability. Каждое называет требование, которое уточняет, и говорит, что меняется. Так `openspec validate fix-discarded-compaction-usage --strict` проходит независимо от порядка архивации, и текст чужого change не пересобирается заранее: R1 change `add-usage-ledger` показал, как дорого держать пересобранные копии в синхроне.

Цена решения — противоречие при архивации. «Сжатие без выигрыша не применяется» говорит «журнал и транскрипт не меняются» и в сценарии «журнал побайтово не изменился», а ADDED-требование этого change дописывает запись учёта. Поэтому архивация идёт в порядке `fix-compaction-estimate-and-no-gain` → `anchor-context-estimate-after-compaction` и `fix-config-change-during-background-compaction` → `add-usage-ledger` → этот change. Перед архивацией этого change задача 5.2 переводит уточняющие ADDED-требования в MODIFIED поверх уже архивированного текста, если основная спецификация иначе останется противоречивой.

## Risks / Trade-offs

- **R1. Зависимость от неархивированных changes.** PR #346 влит, ветка обновлена merge-коммитом `08ffb64a` от `develop`. Код опирается на `SummaryResult`, `ContextCompacted.usage`, `buildUsageLedger`, `UsageAccounting.summarizerEnded`, `UsageLedgerGroup` и `SessionWriter.append` (SES-16). Сверка — D11 (задача 0.2а выполнена). Если до реализации эти changes снова поменяют компактор или свёртку, сверку нужно повторить.
- **R2. Меняется наблюдаемое правило CMP-10 «журнал побайтово не изменился».** Тесты change `fix-compaction-estimate-and-no-gain` (`compactor_test.dart` «Резюме длиннее региона», «Второй проход без выигрыша», `builtin_slash_commands_test.dart` «/compact без выигрыша», `overflow_then_compact_test.dart` «Аварийное сжатие без выигрыша») проверяют пустой `store.appended` или отсутствие новых записей. Они переписываются намеренно: теперь там ровно одна запись `custom` учёта, а проекция, транскрипт и записи `compaction` не меняются. Это характеризационная правка (исключение (а) TDD ядра), каждая — со ссылкой на D1.
- **R3. Смешанные версии.** Журнал с записью учёта, открытый старым кодом: вызов не учитывается, как до change. Ошибки нет. Если старый код при этом запишет `usage.json` без `discarded`, новый код покажет верные числа: отчёт строится из журнала, а файл обновится при следующем дописывании журнала. До этого файл на диске занижен — это касается только внешних читателей файла.
- **R4. Повторные отброшенные проходы `afterTurn`.** Если после хода оценка снова выше порога, а резюме опять не даёт выигрыша, каждый ход платит за вызов суммаризатора. Change это не исправляет, но делает видимым: `Summaries: n (k discarded)`. Ограничение — отдельная задача компактора, например не повторять проход, пока регион не вырос.
- **R5. Рост журнала.** Одна строка около 400 байт на отброшенный проход. По R4 это не больше одной строки на ход.
- **R6. Неучтённые вызовы остаются.** R3 change `add-usage-ledger` (сбой, отмена после ответа) и суммаризаторы субагентов. Сумма может быть занижена без «~», как раньше.
- **R7. Новый повод в протоколе расширения.** Сторонний клиент, который знает только `step`/`turn`/`compaction`, должен по D2 change `add-usage-extension` принимать незнакомый повод. Если он этого не делает, он нарушает версию 1 расширения, а не ACP. Стандартные типы ACP не меняются.

## Migration Plan

Миграции данных нет. Старые журналы записей учёта не содержат, и их свёртка не меняется. `usage.json` версии 1 пересчитывается по прежним правилам свежести. Откат кода безопасен (R3). Вызовы, отброшенные до этого change, в журнале не записаны и не восстанавливаются.
