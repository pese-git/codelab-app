## Context

CodeLab сегодня не читает файловую систему напрямую нигде: единственная точка соприкосновения с диском — `WorkingDirectoryProvider.currentPath` (`Directory.current.path`), просто строка, без listing или чтения содержимого (`apps/codelab_app/lib/core/platform/working_directory_provider.dart`). Всё остальное содержимое файлов, которое видит пользователь, приходит от агента через `ContentBlock` (`packages/dart/acp_protocol/lib/src/acp/prompt.dart:100-140`) или через `rawInput`/`rawOutput` tool call в инспекторе — обрезанные до нескольких строк (`inspector_pane.dart:224`).

Протокольный слой уже готов к отображению богатого контента: `ContentBlock` поддерживает `text`/`image`/`audio`/`resourceLink`/`resource`, и `ToolCallLocation` (`packages/dart/acp_protocol/lib/src/acp/tool_call.dart:114-121`) уже несёт `path` для локации, к которой agent обращался.

## Goals / Non-Goals

**Goals:**
- Read-only просмотр файла с номерами строк и подсветкой диапазона из `ToolCallLocation`, когда источник — tool call.
- Read-only просмотр файла, когда источник — клик в дереве каталогов (прямое чтение диска).
- Ленивое дерево каталогов рабочей директории (раскрытие по требованию, не eager recursive listing всего дерева).
- Явная, видимая пользователю разница источника контента ("from agent's tool call" vs "read directly from disk") — не смешивать провенанс.

**Non-Goals:**
- Редактирование файлов внутри CodeLab — панель строго read-only, никакого текстового ввода/сохранения.
- Полнотекстовый поиск по дереву/файлам — не в этом MVP-объёме.
- Git-статусы в дереве (изменённые/новые файлы) — можно добавить позже, не блокирует текущий change.
- Синхронизация "Following" с открытым редактором стороннего IDE — Following относится только к внутреннему состоянию CodeLab (последняя `ToolCallLocation` активной сессии).

## Decisions

- **Один UI-компонент на оба источника.** `AcpFilePreviewPanel` (новый organism в `acp_ui`) принимает `content`, `path`, необязательный `highlightRange`, и `provenance: {toolCall, disk}` — рендерит одинаково, меняется только подпись источника внизу панели. Не создаём два разных виджета: контент и разметка идентичны, отличие — только откуда взяты данные и что написано в футере.
- **Directory listing и file read — новый reader в `core/platform`**, а не в `acp_transports` (тот пакет — исключительно про ACP wire transport, смешивать с общим fs-доступом нарушило бы его границу). Новый класс `WorkspaceFileReader` (интерфейс + `dart:io`-реализация, как `WorkingDirectoryProvider`), с двумя методами: `listDirectory(path)` (один уровень, не рекурсивно — дерево дозапрашивает при раскрытии узла) и `readFile(path)` (с ограничением размера — см. Risks).
- **Игнор-лист, не полноценный `.gitignore`-парсер, для MVP.** Захардкоженный список директорий (`.git`, `.dart_tool`, `build`, `.venv`, `node_modules`, `.pub-cache`) в `WorkspaceFileReader`. Полноценный `.gitignore`-парсинг — отдельная, более тяжёлая задача (нужна библиотека или самописный парсер gitignore-синтаксиса с негациями/wildcards) — не обязательна для того, чтобы дерево было пригодно для использования; выносится в Open Questions.
- **"Sessions"/"Files" — переключение контента существующего слота**, не новый слот в `AcpWorkbenchLayout`. Состояние активной вкладки — presentation-level ephemeral UI state (`docs/architecture/state-management.md` §13, аналогично решению для command palette/dialog), не требует нового поля в `CodeLabShellState`, если не должно переживать пересоздание виджета — если требуется сохранять выбор вкладки между пересборками (вероятно да, для UX-целостности), хранится в `CodeLabShellState` как простой enum `activeSidebarTab {sessions, files}` — не boolean-флаг, чтобы не плодить несовместимые состояния.
- **File Preview — overlay, не route и не постоянный слот layout**, по уже принятому паттерну `EditProfileDialog`/`CommandPalette` (в приложении нет роутинга).
- **"Following" не завязан на новую подписку/поток** — переиспользует уже существующий механизм обновления `CodeLabInspectorEntry`/`ToolCallLocation` из session updates; при открытой панели и активном Following просто перечитывает последнюю известную локацию при каждом обновлении инспектора, не заводит отдельный stream.

## Risks / Trade-offs

- [Прямое чтение диска — новый инвариант, отличается от принципа File Preview "показываем только то, что вернул агент"] → явно различать источник в UI (уже заложено в Goals), не маскировать под единый "agent-provided" контент.
- [Секреты в файлах при просмотре с диска (`.env`, credential-файлы) — `SecretRedactor` на это не рассчитан, он работает со структурированными логами/диагностикой, не с произвольным содержимым файла] → для MVP не решается здесь; фиксируется как known follow-up, не блокирует этот change, но должно быть явно сказано пользователю (например, в футере панели или в самом дереве для файлов вида `.env*`) в последующей итерации.
- [Чтение очень больших файлов (бинарники, сгенерированные файлы) может забить UI/память] → `WorkspaceFileReader.readFile` вводит верхний лимит размера (например, несколько сотен КБ) и по превышению показывает сообщение "file too large to preview" вместо контента.
- [Ленивое дерево на очень больших монорепах всё равно может быть медленным при раскрытии директорий с тысячами файлов] → не решается в этом MVP; можно добавить пагинацию/виртуализацию списка позже, если станет проблемой на практике.

## Open Questions

- Нужен ли полноценный `.gitignore`-aware фильтр вместо захардкоженного игнор-листа — решить после первой обратной связи от использования MVP-версии.
- Нужно ли явно помечать потенциально чувствительные файлы (`.env`, `*.pem`, `id_rsa` и т.п.) в дереве/превью — вынесено как known follow-up, не блокирует MVP.
