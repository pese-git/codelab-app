## Context

`packages/dart/acp_protocol/lib/src/acp/acp_validation.dart` предоставляет `requireAcpObject(value, {path, allowedKeys})`, который сначала проверяет, что значение — JSON-объект (`requireJsonObject`), затем зовёт `requireOnlyRootKeys`, выбрасывающий `JsonRpcProtocolException.invalidShape` на любом ключе верхнего уровня, которого нет в `allowedKeys`. Это единственный decode-helper для ACP-объектов и используется одинаково строго во всех `.dart`-файлах пакета: `initialize.dart`, `session_update.dart`, `prompt.dart`, `tool_call.dart`, `permission.dart`, `fs.dart`, `terminal.dart`, `session.dart`.

В `initialize.dart` этим же helper'ом decode'ятся вложенные capability-объекты `initialize`-handshake: `AgentCapabilities`, `McpCapabilities`, `PromptCapabilities`, `SessionCapabilities`, `SessionListCapabilities`, а также `ClientCapabilities`/`FileSystemCapabilities` (эти два — по конструкции исходящие, но модель симметрично умеет и decode их).

Ручная проверка против реального агента (`@zed-industries/claude-code-acp`, обёртка над Claude Code) показала: его `initialize`-ответ содержит `agentCapabilities.sessionCapabilities: {"fork": {}, "list": {}, "resume": {}}`. `SessionCapabilities.fromJson` знает только про `list`/`_meta` — `fork`/`resume` не входят в `allowedKeys`, `requireOnlyRootKeys` бросает исключение, `initialize` целиком падает, соединение уходит в `Failed`. Агент — не баг-репорт: `fork`/`resume` — реальные capability-флаги апстрим ACP-спеки, которых просто нет в текущем вендоренном снапшоте `docs/acp/protocol/` (см. proposal.md, Why).

## Goals / Non-Goals

**Goals:**
- Незнакомое поле верхнего уровня внутри capability-объектов `initialize` (`agentCapabilities` и всё, что под ним) — decode'ится успешно, поле молча игнорируется; CodeLab не пытается его использовать (не читает значение, ничего не сохраняет) — просто не считает его существование протокольной ошибкой.
- Область изменения — только `initialize.dart`'s capability-модели. Вся остальная ACP-валидация (`session_update.dart`, `prompt.dart`, `tool_call.dart`, `permission.dart`, `fs.dart`, `terminal.dart`, `session.dart`, а также сам верхний уровень `InitializeRequest`/`InitializeResponse` и `Implementation`/`AuthMethod` в `initialize.dart`) остаётся строгой, как раньше — эти формы предсказуемы и версионируются вместе с `protocolVersion`, а не растут независимо, как набор capability-флагов.

**Non-Goals:**
- Не разбираем/не поддерживаем сами `fork`/`resume` как capabilities — это отдельная, самостоятельная работа (свой OpenSpec change, если/когда понадобится), не входящая в этот фикс. Здесь только "не падать", а не "уметь использовать".
- Не меняем `requireOnlyRootKeys`/`requireAcpObject` глобально и не ослабляем строгую валидацию где-либо ещё в пакете.
- Не трогаем `docs/acp/protocol/` (вендоренный снапшот спеки) — источник истины ACP не редактируется этим change (AGENTS.md §3.4).

## Decisions

- **Новый decode-helper `requireAcpCapabilityObject(value, {required path})` рядом с `requireAcpObject` в `acp_validation.dart`.** Делает только то же, что и `requireJsonObject` — проверяет, что значение вообще является JSON-объектом, — но не зовёт `requireOnlyRootKeys`: сама реализация конкретной capability-модели уже читает только известные ей поля (`source['list']`, `source['loadSession']` и т.д.), поэтому незнакомые поля и так не используются — единственное, что менялось, — это то, что их присутствие раньше **дополнительно** явно проверялось и запрещалось. Альтернатива — добавить `allowedKeys`-параметр вида `Set<String>? allowedKeys` в существующий `requireAcpObject` (null = не проверять) — отклонена: сигнатура с опциональным null, меняющим семантику метода, менее явно читается на call site, чем отдельная именованная функция, прямо говорящая "это capability-объект, к нему другие правила".
- **Область применения — только `initialize.dart`'s: `AgentCapabilities`, `McpCapabilities`, `PromptCapabilities`, `SessionCapabilities`, `SessionListCapabilities`, `ClientCapabilities`, `FileSystemCapabilities`.** Их `.fromJson` переключаются с `requireAcpObject(..., allowedKeys: {...})` на `requireAcpCapabilityObject(..., path: ...)` — параметр `allowedKeys` для них становится не нужен и убирается из call site (сравнение с допустимыми ключами всё равно никогда не выполнялось бы). `Implementation`, `AuthMethod`, `InitializeRequest`, `InitializeResponse` — остаются на `requireAcpObject` со строгим `allowedKeys`, как и весь остальной пакет.
- **Это не "придумывание ACP-семантики" (AGENTS.md §3.4/§7).** CodeLab не интерпретирует и не хранит значение незнакомого поля — оно просто перестаёт быть фатальным для остальной, понятной части ответа. Расширяемость capability-объектов — часть самой ACP-модели capability negotiation (клиент и агент независимо растут набором флагов, каждая сторона использует только то подмножество, которое понимает); строгий reject неизвестного флага — не защита протокола, а причина полного разрыва совместимости с любым чуть более новым агентом.

## Risks / Trade-offs

- [Более лояльный decode может замаскировать настоящий баг агента — например, действительно сломанный/усечённый JSON внутри `sessionCapabilities`] → `requireAcpCapabilityObject` всё ещё требует, чтобы значение было валидным JSON-объектом (`requireJsonObject`); маскируется только "лишнее поле верхнего уровня", а не структурная невалидность. Отдельные вложенные поля (`sessionCapabilities.list`), которые CodeLab действительно понимает, по-прежнему decode'ятся и валидируются как раньше через `SessionListCapabilities.fromJson`.
- [Область "только initialize.dart" может показаться непоследовательной по сравнению с остальным пакетом] → это осознанное, узкое решение: остальные ACP-сообщения (session/update, tool_call, permission, fs/*, terminal/*) — не capability negotiation, а runtime-протокол с версионированной, некапабилити-зависимой формой; смешивать два разных класса объектов под одно правило было бы более рискованно, чем оставить их раздельными.
