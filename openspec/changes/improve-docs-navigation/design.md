## Context

Сайт собирает документацию из репозитория по allowlist (`site/src/lib/publish.ts`, D3 `add-astro-site`) и выводит адрес страницы из пути файла (D4). Навигация — чистая функция `buildNav` в `site/src/lib/nav.ts` (D9): шесть групп по префиксу пути, внутри группы `README.md` первым, остальные по заголовку (`Intl.Collator('ru')`). Её используют две страницы:
- `src/pages/docs/index.astro` — оглавление `/docs/`: все группы карточками, каждая — плоский список;
- `src/pages/docs/[...path].astro` — страница документа: слева вся группа (`nav.doc-nav`), справа оглавление по `##` (`nav.doc-toc`, видно от 1200 px).

Документация живёт по схеме `.claude/skills/codelab-docs/SKILL.md` §3: `apps/<app>/doc/user/NN-<тема>.md` — главы руководства пользователя, `doc/user-guide.md` — их оглавление, `doc/NN-<тема>.md` — главы разработчика с оглавлением `doc/README.md` и входом `doc/development.md`, `doc/operations.md` — DevOps; у пакетов — `README.md`, `doc/README.md`, `doc/NN-<тема>.md`, вложенные каталоги (`codelab_agent_core/doc/algorithms/` с `README.md`). Номер главы уже есть в имени файла, а у вложенного каталога — `README.md` с заголовком. Значит, порядок и подгруппы можно вывести из путей, не трогая документы.

Состояние на 2026-11-26 и запрос пользователя — в `proposal.md`. Клиентские скрипты сайта подчиняются правилу D2 `redesign-site-showcase`: модули Astro, собранные Vite в `/_astro/*.js`; встроенный скрипт один — тема; логика — чистые модули в `src/lib/` с vitest; DOM-слой в `src/scripts/` только связывает логику с разметкой; прогрессивное улучшение; бюджет 12 КБ gzip, который считает `scripts/check-links.mjs` по манифесту чанков (`src/plugins/build-chunks.ts`).

## Goals / Non-Goals

**Goals:**
- порядок глав из имени файла и подгруппы по аудитории — без frontmatter и ручных списков, новый документ появляется без правки сайта (сценарий «Новый документ появляется без правки сайта»);
- навигация на странице: меню секции, мобильное меню без JavaScript, крошки, «Назад / Далее»;
- оглавление `/docs/` по ролям читателя; пакеты — по слоям ADR-0002;
- копирование кода, подсветка текущего раздела, поиск — по правилу скриптов D2 `redesign-site-showcase`;
- адреса документов не меняются.

**Non-Goals:**
- правка документов под сайт, переименование файлов;
- новые источники публикации;
- хостинг и CSP-заголовки (H1–H3 `add-astro-site`);
- фильтры поиска, поиск вне документации, подсветка совпадений на целевой странице;
- браузерные e2e (D14 `add-astro-site` остаётся в силе).

## Decisions

### D1. Порядок внутри списка: вход → номер → заголовок → путь

Каждый документ получает ключ сортировки из пути:
1. **ранг входа**: `README.md` каталога списка — 0, `doc/README.md` приложения и пакета — 1, `doc/user-guide.md` в «Руководстве» и `doc/development.md` в «Для разработчика» — 0; прочие — нет ранга;
2. **номер главы** — префикс имени файла по шаблону `^(\d+)-`, сравнивается как число (`10` после `9`);
3. **заголовок** — `Intl.Collator('ru')`, как сейчас;
4. **путь** — последний ключ, чтобы порядок был полным и стабильным между сборками.

Документ без номера идёт после глав с номером, по заголовку. Одинаковый номер у двух файлов — порядок по заголовку. Ни один из этих случаев не ломает сборку: правило D9 «новый документ не ломает сайт» сохраняется, а ошибку в нумерации видит автор в меню.

**Номер в навигации.** Подпись пункта — «`03` · Полноэкранный режим»: число как в имени файла, разделитель `·` (U+00B7) с пробелами. Номер — отдельный элемент разметки, чтобы стиль задавал ширину колонки номеров. Заголовок страницы (`<h1>`, `<title>`, описание) номера не получает: документ на GitHub и на сайте называется одинаково. Номер показывают меню секции, оглавление `/docs/`, «Назад / Далее».

**Подпись входа «Обзор».** Если заголовок документа совпадает без учёта регистра и крайних пробелов с названием, под которым стоит его список, — с названием секции (меню пакета: секция `codelab_setup`, README `# codelab_setup`) или с заголовком вложенной подгруппы (`codelab_agent_core/doc/algorithms/`: подгруппа и её README — «Алгоритмы ядра агента»), — пункт подписывается «Обзор». Подмена не делается, если в том же списке уже есть другой документ с заголовком «Обзор»: два одинаковых пункта хуже повтора. Правило — чистая функция `entryLabel(entry, list, section)` в `site/src/lib/nav.ts`; её вызывают меню секции (`DocMenu.astro`, обе копии D4) и вложенные подгруппы оглавления `/docs/` (D6). Меняется только подпись пункта: `<h1>`, `<title>`, описание, порядок D1, адрес, крошки и «Назад / Далее» остаются с заголовком документа.

Почему: заголовок секции или `<summary>` подгруппы и первый пункт под ним показывали одно и то же название подряд, и читатель не видел, что первый пункт — вводный документ.

Альтернативы подписи входа:
- **Скрыть вход из списка** и сделать ссылкой заголовок секции. Меню теряет единообразие «каждый документ — пункт», а `aria-current="page"` у README оказывается на заголовке.
- **Всегда «Обзор» для `README.md`.** Ломает осмысленные заголовки входов (`docs/user/README.md`, «`codelab`: руководство пользователя»), которые с названием секции не совпадают.

Альтернативы:
- **Номер в заголовке документа** («# 03. Полноэкранный режим»). Правка ~180 документов ради сайта и дублирование номера, который уже есть в имени файла; нарушает «документы не правятся под сайт».
- **Порядок из оглавлений (`user-guide.md`, `doc/README.md`)** — разобрать ссылки оглавления и упорядочить по ним. Точнее отражает замысел автора, но связывает навигацию с разметкой текста: переписанное оглавление молча меняет меню, а документ вне оглавления теряет место. Номер в имени файла — уже принятое соглашение `codelab-docs` §3.
- **Сортировка строк путей** (`03-tui` < `10-…` лексикографически). Ломается на `100-` и не даёт «вход первым».

### D2. Подгруппы по пути файла

Навигация строится из **секций** (что показывает меню одной страницы) и **списков** внутри секции:

| Путь | Секция | Список |
|---|---|---|
| `docs/user/*.md` | «Пользователю» | основной, без заголовка |
| `docs/ops/*.md` | «Эксплуатация» | основной |
| `apps/<app>/README.md`, `apps/<app>/doc/README.md` | группа приложения (таблица D9) | вход, без заголовка |
| `apps/<app>/doc/user-guide.md`, `apps/<app>/doc/user/**` | группа приложения | «Руководство» |
| `apps/<app>/doc/operations.md` | группа приложения | «Эксплуатация» |
| `apps/<app>/doc/*.md` (остальные) | группа приложения | «Для разработчика» |
| `packages/<каталог>/<пакет>/README.md`, `…/doc/*.md` | пакет (внутри группы «Пакеты») | основной |
| `<корень секции>/<каталог>/**` (кроме `apps/<app>/doc/user/`) | та же секция | подгруппа с заголовком `# ` из `<каталог>/README.md`, без него — имя каталога |

Корень секции для вложенных каталогов: `docs/user/`, `docs/ops/`, `apps/<app>/doc/`, `packages/<каталог>/<пакет>/doc/`. Глубже первого уровня вложенности новых подгрупп нет: файлы идут в подгруппу каталога первого уровня, порядок — по D1 с путём как последним ключом.

- **Почему три подгруппы приложения, а не две.** Пользователь просил «Руководство» и «Для разработчика». `doc/operations.md` — документ для DevOps, третьей аудитории `codelab-docs` §1; в «Для разработчика» он оказался бы рядом с главами о composition root. Подгруппа из одного документа дешевле, чем неверная аудитория. Решение пользователя — D13, Q2.
- **Пакет — своя секция.** В меню страницы пакета — только его документы (у `codelab_agent_core` их 31, у всех пакетов вместе — 147). Группа «Пакеты» остаётся уровнем крошек и блоком оглавления `/docs/` (D6).
- **Заголовок вложенной подгруппы из `README.md`.** Имя каталога (`algorithms`) — английское слово из пути; заголовок `README.md` («Алгоритмы ядра агента») уже написан для читателя. Без `README.md` — имя каталога, а не ошибка.
- **Неизвестный файл** (например, `apps/<app>/doc/notes.md` или новый каталог) попадает в «Для разработчика» или во вложенную подгруппу по таблице, без ошибки.
- Группы верхнего уровня и их порядок — таблица D9 `add-astro-site` без изменений, включая группу с именем каталога для неизвестного приложения.

Альтернативы:
- **Две подгруппы, `operations.md` во входе приложения.** Короче, но вход — это «что это и куда идти», а не руководство DevOps; на `/docs/` (D6) эксплуатация приложения тогда не попадает в блок «Развернуть и разрабатывать».
- **Метка аудитории во frontmatter.** Противоречит D3 `add-astro-site`.
- **Список пакетов вручную по слоям.** Второй источник правды рядом с именами пакетов; см. D3.

### D3. Слой пакета — по префиксу имени (ADR-0002), без списка

Имена пакетов закреплены ADR-0002 и проверяются сторожем (`package_naming_test.dart`): `codelab_<сторона>_<слой>` для сторон `acp`, `client`, `agent`; пакеты без стороны — `codelab_<назначение>`, мосты не получают префикс `codelab_agent_`. Поэтому слой выводится из пути без ручного списка:

| Путь | Слой |
|---|---|
| `packages/*/codelab_*_tests` | «Проверки» — сейчас `codelab_architecture_tests`; правило проверяется первым, раньше префиксов сторон |
| `packages/dart/codelab_acp_*` | «Протокол ACP» |
| `packages/dart/codelab_client_*` | «Клиент» |
| `packages/dart/codelab_agent_*` | «Агент» |
| `packages/dart/*` (остальные) | «Мосты и служебные пакеты» — сейчас `codelab_embedded`, `codelab_setup` |
| `packages/flutter/*` | «Интерфейс Flutter» — `codelab_ui` |
| любое другое расположение | «Другие пакеты» |

Порядок показа слоёв: «Протокол ACP», «Клиент», «Агент», «Мосты и служебные пакеты», «Интерфейс Flutter», «Проверки», «Другие пакеты»; внутри слоя — по имени каталога. Пакет с новым префиксом стороны или новый каталог `packages/<x>/` не ломает сборку и попадает в «Мосты и служебные пакеты» или «Другие пакеты». Название пакета на сайте — имя каталога (оно равно имени пакета, это проверяет сторож), а не заголовок README: так список одинаков у пакета без README.

Альтернативы:
- **Явная таблица «пакет → слой».** Точнее подписывает `codelab_architecture_tests` (он не мост), но каждый новый пакет требует правки сайта — против сценария «Новый документ появляется без правки сайта».
- **Слой из `AGENTS.md` или README пакета.** Разбор текста ради классификации; хрупко и неочевидно автору.
- **`codelab_architecture_tests` в «Мостах и служебных пакетах».** Без отдельной строки, но сторож — не мост, и подпись слоя вводила бы читателя в заблуждение. Пользователь выбрал отдельный слой «Проверки» (D13, Q4).
- **Слой «Проверки» по точному имени `codelab_architecture_tests`.** Это ручной список из одного пункта; суффикс `_tests` — правило по имени, которое подхватит следующий пакет только с тестами без правки сайта.

### D4. Меню секции и мобильное меню

**Широкий экран (от 900 px).** Колонка `nav.doc-nav` слева, как сейчас, но с секцией вместо всей группы:
- документы списка входа и основного списка — ссылками без заголовка;
- каждая подгруппа — `<details>`, `<summary>` — «Руководство (14)» у `codelab` (вход и 13 глав); подгруппа текущего документа — `<details open>`, остальные свёрнуты. Это держит меню `codelab` (31 документ) коротким и работает без JavaScript: `<details>` — нативный элемент с клавиатурой (Enter, пробел) и озвучиванием состояния;
- у пакета над списком — ссылка «Все пакеты» на блок пакетов `/docs/` (`#packages`).

**Узкий экран (до 900 px).** Перед статьёй — `<details class="doc-nav-compact">` с `<summary>` «Документы раздела (N)», внутри — то же меню. Колонка `nav.doc-nav` на узком экране скрыта `display: none`, компактное меню на широком — тоже. Разметка меню выводится дважды одним компонентом (`DocSectionNav.astro`); в каждый момент видна и доступна вспомогательным технологиям одна копия (`display: none` убирает её из дерева доступности).

Альтернативы:
- **Один `<details>`, раскрытый на широком экране скриптом.** Без JavaScript на широком экране меню было бы свёрнуто — нарушает прогрессивное улучшение (D2 п. 5 `redesign-site-showcase`).
- **`<details>` с раскрытием через CSS (`::details-content`).** Поддержка в Safari неполная; нельзя опираться на поведение, которое ломает меню в одном из двух браузеров приёмки.
- **Перенос меню под статью CSS-свойством `order`.** Без дублирования, но меню оказывается после всего текста, и с первого экрана к нему нет пути.
- **«Гамбургер» с чекбоксом.** Ненативная семантика, нужен ARIA вручную; `<details>` даёт то же без кода.

Цена — дублирование разметки меню (у самой большой секции — 31 ссылка, около 3 КБ HTML без сжатия). Это меньше, чем скрипт.

### D5. Крошки и «Назад / Далее»

**Крошки** — компонент `DocBreadcrumbs.astro` над `<article>`: `nav aria-label="Путь"`, внутри `ol`, разделитель `›` — псевдоэлементом CSS, чтобы его не читал экранный диктор. Уровни и цели ссылок:

| Уровень | Цель |
|---|---|
| «Документация» | `<base>docs/` |
| группа | `README.md` корня группы (`docs/user/`, `docs/ops/`, `apps/<app>/`); для «Пакеты» — `<base>docs/#packages` |
| пакет (только пакеты) | `README.md` пакета |
| подгруппа | вход подгруппы (`user-guide.md`, `development.md`, `<каталог>/README.md`) |

Уровень без своего документа ведёт на первый документ уровня по D1. Уровень, который ведёт на текущую страницу, не показывается: ссылка на себя не помогает, а текущую страницу называет заголовок сразу под крошками. Основной список и список входа уровня в крошках не дают: у них нет названия.

**«Назад / Далее»** — компонент `DocPager.astro` после текста статьи, перед ссылкой на исходный файл: `nav aria-label="Соседние документы"`, ссылки с `rel="prev"` и `rel="next"`, подпись — «Назад» / «Далее» и номер с заголовком. Соседи берутся из того же списка (вход, основной список, подгруппа): переход из руководства пользователя в главы разработчика был бы сменой аудитории без предупреждения.

Обе функции — чистые, в `nav.ts`: `breadcrumbs(nav, repoPath)` и `neighbours(nav, repoPath)`; адреса — через `pageUrl` и `withBase`. Ссылки проходят `check-links`, в том числе якорь `#packages` на `/docs/`.

Альтернативы:
- **Крошки по сегментам адреса** (`docs › apps › codelab_cli › doc › user`). Механично, но сегменты — имена каталогов, а не названия для читателя, и половина уровней не имеет страниц.
- **«Назад / Далее» через всю группу.** Длинная цепочка из руководства в «Для разработчика»; см. выше.

### D6. Оглавление `/docs/` по ролям

Новый модуль `src/lib/docs-index.ts` строит модель оглавления из результата `buildNav` (без своих правил группировки):

1. **«Начать работу»** (`id="start"`): «Установка и быстрый старт» (`docs/user/run-from-source.md`), `docs/user/README.md`, карточки приложений — `README.md` с описанием и ссылка «Все документы» на `doc/README.md`, если он есть.
2. **«Пользоваться»** (`id="use"`): остальные `docs/user/`; по приложению — подгруппа «Руководство»: вход (`user-guide.md`) — видимой ссылкой вне `<details>`, затем `<details>` «Главы (N)», где N и содержимое — только главы по D1, без входа. Так же «Для разработчика» в блоке 3: `development.md` — видимой ссылкой, главы — в `<details>`.
3. **«Развернуть и разрабатывать»** (`id="build"`): `docs/ops/`; по приложению — «Эксплуатация» и «Для разработчика» (главы — в `<details>`), вложенные подгруппы приложения; блок «Пакеты» (`id="packages"`) с подблоками по слоям D3 (`id="packages-acp"`, `…-client`, `…-agent`, `…-shared`, `…-flutter`, `…-checks`, `…-other`) и карточкой пакета по правилу «Руководство пакета в карточке» ниже.

**Руководство пакета в карточке.** Карточка пакета строится из его секции `buildNav` (D2), без своих правил:
- ссылка на `README.md` пакета с описанием (первый абзац, `docMeta`), подпись — имя каталога пакета (D3), как раньше;
- если у пакета есть документы `doc/`, — видимая ссылка на вход руководства. Вход берётся только из основного списка `doc/` (документы верхнего уровня, без вложенных подгрупп): `doc/README.md`, подпись — его заголовок («Руководство по ядру агента»); без `doc/README.md` вход — первая глава верхнего уровня по D1, подпись — номер и заголовок, как в меню («00 · Альфа»). Если основной список пуст (все документы `doc/` — во вложенных подгруппах), видимой ссылки на вход нет: подгруппы показываются в «Главах (N)» целыми, каждая со своим входом («Обзор» по `entryLabel`), и M считается с ним. Подпись — заголовок документа, а не «Руководство разработчика» или «Все документы»: заголовки `doc/README.md` у всех 14 пакетов уже называют руководство («Руководство по клиентскому слою»), и одинаковая подпись у 14 карточек подряд была бы неразличима. Правило «Обзор» (D1) к этой ссылке не применяется: над ней не список, а карточка, и подпись «Обзор» рядом со ссылкой на README пакета не объясняла бы, что это руководство;
- `<details class="toc-chapters">` «Главы (N)», свёрнутый: документы `doc/`, кроме входа руководства, в порядке D1 — сначала основной список пакета, затем вложенные подгруппы (`doc/algorithms/`) — каждая вложенным `<details>` с `<summary>` «<название подгруппы> (M)», как в меню секции D4; подпись входа подгруппы — по `entryLabel` (D1), у `algorithms/README.md` — «Обзор». N — число документов `doc/` без входа руководства, включая документы вложенных подгрупп; M — число документов подгруппы с её входом. Без JavaScript `<details>` работают так же, как у глав приложений;
- пакет без документов `doc/` — одна ссылка на README, как раньше; пакет без `README.md` — ссылка карточки ведёт на вход руководства, и отдельной ссылки на него нет (документ один раз); если у такого пакета ещё и основной список `doc/` пуст, ссылка карточки ведёт на первый пункт первой подгруппы по D1, и этот пункт исключается из подгруппы — каждый документ показывается один раз, M подгруппы считается без него;
- отдельное «число документов пакета» больше не выводится: его заменяет «Главы (N)», у пакета без `doc/` документ один.

Почему: пользователь нашёл в браузере, что руководство разработчика ядра агента (`packages/dart/codelab_agent_core/doc/`: вход, главы `00`–`13`, туториал, подгруппа `algorithms/` из 14 документов) почти недоступно из `/docs/`: у пакета в блоке «Пакеты» была одна ссылка на README, а карточка приложения `codelab-agent` показывает только 4 главы приложения. До этого change главы пакетов стояли в общем списке группы «Пакеты»; первая редакция D6 убрала их из оглавления, и путь к руководству пакета шёл только через README пакета и меню его страницы. То же у остальных пакетов с `doc/` — сейчас это все 14 пакетов. Свёрнутые главы возвращают их на `/docs/`, не возвращая стену ссылок.

Альтернативы:
- **Ссылка из карточки приложения `codelab-agent` на руководство ядра.** Решает только один пакет и вводит ручную связь «приложение → пакет», которая устаревает молча (против сценария «Новый документ появляется без правки сайта»); остальные 13 пакетов остаются без глав. Отвергнуто.
- **Оставить как есть** — руководство в двух переходах через README пакета. Отвергнуто: это и есть найденная проблема; README пакета описывает пакет, а не ведёт в руководство, и читатель `/docs/` не узнаёт, что у пакета есть 30 документов.
- **Главы пакетов открытым списком, как до change.** Возвращает стену из ~150 ссылок, которую D6 убирал.
- **Вход руководства из первой подгруппы, если основной список пуст** (её вход — видимой ссылкой, M подгруппы — без него). Даёт видимую ссылку у каждого пакета с `doc/`, но подгруппа в оглавлении выглядела бы иначе, чем в меню секции (D4): без входа и с другим M. Отвергнуто; вход из подгруппы берётся только для ссылки карточки пакета без `README.md`, где иначе у карточки не было бы ссылки вовсе.

Правила:
- документ показывается в оглавлении один раз: `run-from-source.md` и `docs/user/README.md` — только в «Начать работу»; вход руководства пакета — только видимой ссылкой, не в «Главах (N)»;
- пустые блоки и карточки не выводятся; неизвестное приложение — карточки с именем каталога;
- `id` выводятся из путей и слоёв (латиница), а не из русских заголовков: крошки (D5) и внешние ссылки на блоки не ломаются от переименования блока;
- путь документа установки — одна константа (`installDocPath`), которую сейчас строкой повторяют `Header.astro` и `[...path].astro`; оглавление использует её же.

Альтернативы:
- **Оглавление по группам (как сейчас) с `<details>` у каждой группы.** Убирает стену, но порядок «по продуктам» не отвечает на вопрос читателя «что мне делать»; пользователь выбрал роли.
- **Ручной список «Начать работу»** (курированная подборка). Точнее, но устаревает молча; правило из путей обновляется само.

### D7. Скрипты страниц документации: копирование и подсветка оглавления

Правило D2 `redesign-site-showcase` распространяется на документацию без исключений:
- компоненты `src/components/docs/CopyCode.astro`, `TocSpy.astro` (и `DocSearch.astro`, D8) с `<script>`; Vite собирает их в `/_astro/*.js`; страницы, где компонента нет, кода не получают. Витрина (`src/components/showcase/`) и документация общих модулей, кроме планировщика, не имеют;
- логика — чистые модули `src/lib/doc-page/*.ts` без `document`, таймеры через `Scheduler` из `src/lib/showcase/scheduler.ts` (переиспользуется, а не копируется; перенос файла — вне задачи); DOM-слой — `src/scripts/doc-page/*.ts`;
- без новых зависимостей, без `innerHTML`; кнопки создаются скриптом (`createElement`, `textContent`): без JavaScript их нет, а не «мёртвые» кнопки в разметке.

**Копирование кода.** Скрипт находит `.prose pre.astro-code` (Shiki), пропускает `pre[data-mermaid]`, оборачивает блок и добавляет кнопку `type="button"` с текстом «Копировать» и `aria-label="Копировать код"`. Текст — `textContent` элемента `code` без изменений. Запись — `navigator.clipboard.writeText`. Итог — в одной общей области `aria-live="polite"` страницы: «Код скопирован» или «Не удалось скопировать» (нет API, небезопасный контекст, отказ браузера). Обходной путь через устаревший `document.execCommand('copy')` не делается: он требует выделения текста и меняет фокус. Надпись кнопки «Скопировано» держится 2 секунды. Автомат `copy-state.ts`: `idle → copied | failed → idle`, каждый переход несёт номер нажатия, и таймер старого нажатия не сбрасывает состояние нового (поздний таймер, `AGENTS.md` §12). Фокус остаётся на кнопке.

**Подсветка оглавления.** Модуль `toc-spy.ts` — чистая функция `activeHeading(tops, offset, atBottom)`: индекс последнего заголовка `##`, верх которого выше линии чтения; в конце страницы — последний; до первого — нет активного. DOM-слой пересчитывает её по `scroll` с `requestAnimationFrame` (один пересчёт на кадр) и при `hashchange`, ставит `aria-current="location"` ровно одной ссылке `nav.doc-toc`. Работает, только пока оглавление видно (`matchMedia('(min-width: 1200px)')` и его `change`). Фокус не переносится, прокрутки и анимаций нет — при `prefers-reduced-motion` вести себя иначе не нужно.

**Бюджет.** `check-links` уже считает все модули `type="module"` на каждой странице, кроме темы и mermaid (D12 `redesign-site-showcase`). Скрипты документации входят в ту же сумму 12 КБ gzip; ожидаемый размер всех трёх — несколько килобайт. Сообщение проверки переименовывается с «showcase JavaScript budget» на «page JavaScript budget». Рантайм поиска (D8) в сумму не входит: он не подключается из HTML и не проходит через Vite.

Альтернативы:
- **Кнопка копирования в разметке при сборке (rehype-плагин).** Без JavaScript кнопка ничего не делает — запрещено D2 п. 5.
- **Подсветка через `IntersectionObserver`.** Даёт события пересечения, а не «последний заголовок выше линии»: короткие разделы между двумя событиями теряются. Пересчёт по кадру проще проверить чистой функцией.

### D8. Поиск — Pagefind: решение о зависимости

Поиск без сервера и без чужих хостов требует индекса, построенного при сборке. Выбран **Pagefind** (`pagefind`, MIT; на 2026-11-26 — 1.6.0):
- индексирует готовый `dist/` после `astro build`, поэтому видит ровно то, что опубликовано, включая перевод ссылок и защиту D11 `add-astro-site`;
- индекс разбит на фрагменты: браузер скачивает только нужные части, а не весь текст документации;
- поддерживает русский язык со стеммингом: язык берётся из `<html lang="ru">`;
- весь рантайм — файлы в `dist/pagefind/`, запросов к чужим хостам нет.

**Конфликт со skill `codelab-site` и решение по каждому пункту:**

| Правило | Решение |
|---|---|
| §8 «Новая зависимость — только по задаче `tasks.md`» | задача 6.1; `pagefind` — `devDependency` с точной версией: в `dist/` попадает не пакет, а сгенерированный им рантайм |
| §8 лицензии | `pagefind` — MIT; платформенные пакеты `@pagefind/<платформа>` (бинарь индексатора) проверяются в задаче 6.1; в `dist/` попадают только файлы рантайма Pagefind (MIT) |
| §8 `npm ci --ignore-scripts` | бинарь приходит платформенным пакетом через `optionalDependencies`, install-скриптов у `pagefind` нет — исключение в skill не нужно; `package-lock.json` содержит записи всех платформ, в том числе `linux-x64` для CI и `darwin-arm64` для локальной сборки |
| §6 бюджет 12 КБ | рантайм (JS, WebAssembly, фрагменты индекса) грузится только по действию и в бюджет страницы не входит; в бюджет входит только модуль `DocSearch` (поле, отрисовка результатов). `check-links` запрещает статические ссылки HTML на `pagefind/` (`<script src>`, `modulepreload`, `preload`), чтобы рантайм не стал «бесплатно» обязательным |
| §6 скрипты D2: без `innerHTML` | свой интерфейс на API `pagefind.js`, а не готовый Pagefind UI; фрагмент результата разбирается чистой функцией `excerptParts` (`src/lib/doc-page/search.ts`): распознаются только `<mark>` и `</mark>`, декодируются только `&lt;` и `&gt;` — так Pagefind 1.6.0 экранирует текст фрагмента; любые другие теги и сущности (`&amp;`, `&quot;` …) остаются текстом как есть: `&` индексатор не экранирует, поэтому `&amp;` во фрагменте — буквальный текст документа (например, глава об экранировании HTML), и его декодирование исказило бы цитату; узлы — `createElement`/`textContent` |
| §6 «нет запросов к чужим хостам» | рантайм и индекс — из `<base>pagefind/`; адрес строится `withBase` и передаётся `pagefind.options({ baseUrl })`, чтобы ссылки результатов учитывали `SITE_BASE` |
| §7 работа без JavaScript | `<form role="search">` с `hidden` в разметке, скрипт его показывает; без JavaScript поля нет, ссылка «Документация» (крошки, шапка) ведёт на оглавление по ролям |
| D2 п. 6 движение | анимаций нет; результаты меняются только по вводу |
| CSP (H3 `add-astro-site`) | Pagefind компилирует WebAssembly в веб-воркере `pagefind-worker.js`: хостингу нужны `script-src 'self' 'sha256-<тема>' 'wasm-unsafe-eval'` и `worker-src 'self'` (R1). `'wasm-unsafe-eval'` разрешает только компиляцию WebAssembly, а не `eval` JavaScript. Пользователь принял это (D13, Q1); требование записывается в skill §6 и передаётся change хостинга как входное условие CSP (R1) |

**Индексация.** `"build": "astro build && pagefind --site dist && node scripts/prune-pagefind.mjs"` (у `astro build` — ещё `ASTRO_TELEMETRY_DISABLED=1`); `verify` уже запускает `build` до `check:links`, поэтому джоб `site` проверяет индекс без правки CI. Индексируется только `<article data-pagefind-body>` страниц документов: главная, возможности, новости и `/docs/` не попадают (если хотя бы одна страница размечена `data-pagefind-body`, Pagefind пропускает неразмеченные). Блоки кода индексируются: по командам ищут.

Подпись группы результата — `data-pagefind-meta="group:<название>"` на `<article>`: у документа пакета — имя пакета (название его секции, как уровень пакета в крошках D5), у остальных — название группы верхнего уровня («Пользователю», «`codelab`» …). Имя пакета, а не «Пакеты»: в результатах поиска 147 документов пакетов с подписью «Пакеты» неразличимы. Значение выводится на странице документа из того же `buildNav`, что меню и крошки, — второго правила группировки нет.

**Удаление неиспользуемого UI Pagefind** (`prune-pagefind`). CLI Pagefind 1.6 всегда кладёт в `dist/pagefind/` и готовые интерфейсы, которые сайт не грузит (свой интерфейс — см. таблицу выше). Шаг сборки `node scripts/prune-pagefind.mjs` после `pagefind --site dist` удаляет их: логика — чистая функция `prunePagefind(dir)` в `site/src/lib/prune-pagefind.ts` с тестом `site/test/prune-pagefind.test.ts`, скрипт `site/scripts/prune-pagefind.mjs` только вызывает её для `dist/pagefind` (или каталога из аргумента). Удаляются только файлы с закреплёнными именами прямо в этом каталоге, без рекурсии: `pagefind-ui.*`, `pagefind-modular-ui.*`, `pagefind-component-ui.*`, `pagefind-highlight.js`. Рантайм (`pagefind.js`), воркер (`pagefind-worker.js`), WebAssembly, фрагменты, индексы и `pagefind-entry.json` не трогаются; отсутствующий каталог — не ошибка (пустой результат), чтобы шаг не маскировал отсутствие индекса: его ловит проверка D10 п. 3.

Альтернативы:
- **Флаг CLI, отключающий запись UI.** В Pagefind 1.6.0 такого флага нет.
- **Оставить файлы.** Десятки килобайт мёртвого кода в публикации, который никто не загружает и не проверяет.
- **Удаление по шаблону `pagefind-*`.** Задело бы `pagefind-worker.js` и `pagefind-entry.json`; закреплённый список имён не трогает рантайм при обновлении Pagefind, а новый файл UI в следующей версии просто останется.

**Поведение поля.** Поле — на `/docs/` над блоками и на странице документа в начале `.doc-main`, над крошками, а не в меню секции: меню выводится в двух копиях (D4), и форма внутри него дублировала бы `id` поля, области `aria-live` и списка результатов и давала бы два поля поиска на странице. Компонент `DocSearch` выводится ровно один раз на страницу. Загрузка рантайма — по первому `focus` или `input` в поле: `import(/* @vite-ignore */ withBase('pagefind/pagefind.js', base))`, затем `options` и `init`. Запросы — с задержкой 200 мс через `Scheduler`; у каждого запроса номер, отрисовывается только ответ последнего (защита от устаревшего результата, `AGENTS.md` §9, §12). Итог — `aria-live="polite"`: «Найдено: N», «Ничего не найдено», «Поиск недоступен» (ошибка загрузки или инициализации; поле остаётся, страница работает). Результаты — `ol` ссылок; клавиша Esc очищает поле и результаты; фокус скриптом не переносится.

Альтернативы:
- **Свой индекс заголовков и разделов (JSON при сборке) без зависимости и WebAssembly.** Нет конфликта с CSP и §8, но ищет только по названиям, без словоформ; для русского текста «разрешение» не найдёт «разрешения». Не выбран: пользователь принял `'wasm-unsafe-eval'` (D13, Q1); остаётся запасным, если хостинг не сможет выставить эту директиву.
- **MiniSearch или Lunr с `lunr-languages`.** Зависимость и стемминг отдельным пакетом; индекс скачивается целиком (весь текст ~200 документов), что больше бюджета на порядки.
- **Готовый Pagefind UI.** Больше по размеру, свои стили вне токенов, разметка результатов строится вне нашего контроля доступности.
- **Внешний поиск (Algolia DocSearch и подобные).** Запросы к чужим хостам — запрещено спецификацией «Оформление и темы».

**Почему в этом change, а не отдельно.** Поиск отвечает на ту же проблему — читатель не находит главу. Но он независим от D1–D7: задачи группы 6 идут последними и не нужны остальным. Пользователь оставил поиск в этом change (D13, Q1); отделимость группы 6 сохраняется только как порядок работ.

## Risks / Trade-offs

- **R1. CSP с `'wasm-unsafe-eval'` — принятый риск** (пользователь, 2026-11-26; D13, Q1). Будущая политика хостинга: `script-src 'self' 'sha256-<тема>' 'wasm-unsafe-eval'`. Директива разрешает компиляцию WebAssembly, но не `eval` JavaScript; `'unsafe-inline'` и `'unsafe-eval'` по-прежнему не нужны. **Вход для change хостинга** (H3 `add-astro-site`): CSP-заголовок обязан содержать `'wasm-unsafe-eval'`, иначе поиск покажет «Поиск недоступен», а остальная навигация не пострадает. Требование записывается в skill `codelab-site` §6 (задача 7.4). Запасной вариант — индекс заголовков (D8).
  **Воркер.** Pagefind 1.6 загружает поиск в веб-воркере: `pagefind.js` создаёт `new Worker('<base>pagefind/pagefind-worker.js')`, и WebAssembly компилируется в нём. Поэтому входное условие change хостинга полнее: CSP разрешает воркеры с хоста сайта — `worker-src 'self'` (без `worker-src` браузер берёт `child-src`, затем `script-src`, поэтому `script-src 'self'` — запасной вариант), и политика с `'wasm-unsafe-eval'` действует и для документа воркера. Воркер, загруженный по сетевому адресу, политику страницы не наследует: его CSP задаётся только заголовками ответа на `pagefind-worker.js`. Если хостинг ставит CSP на все файлы, эта политика обязана содержать `'wasm-unsafe-eval'`; если CSP стоит только на HTML, у воркера политики нет и WebAssembly компилируется. Иначе поиск уходит в «Поиск недоступен», остальная страница работает. Проверено на собранном `dist/pagefind/*.js` Pagefind 1.6.0: нет `eval(`, `new Function`, `URL.createObjectURL` (воркер не создаётся из `blob:`) и `importScripts(` — значит, `'unsafe-eval'`, `blob:` в `worker-src` и дополнительные источники скриптов не нужны. При обновлении Pagefind проверка повторяется (задача обновления зависимости).
- **R2. Бинарь индексатора из npm.** `pagefind` запускает платформенный исполняемый файл при сборке. Смягчение: точная версия, lock, `npm ci --ignore-scripts`, джоб `site` без секретов и без публикации (D13 `add-astro-site`), проверка лицензий в задаче 6.1. На платформе без пакета `@pagefind/<платформа>` сборка падает — это локальная проблема разработчика, CI на `linux-x64`.
- **R3. Время и размер сборки.** Индексация ~200 страниц — секунды; `dist/` растёт на индекс (порядка мегабайта фрагментов). Задача 6.4 записывает фактические числа в PR.
- **R4. Ошибки нумерации видны только в меню.** Пропущенный или повторённый номер не ломает сборку (D1). Смягчение: правило в `codelab-docs` §3; автор видит порядок на сайте.
- **R5. Порядок поменялся для привыкших читателей.** Адреса прежние; меняется только порядок пунктов меню.
- **R6. Двойная разметка меню** (D4). Около 3 КБ HTML на самой большой секции; одна копия всегда скрыта `display: none`. Тест компонента не нужен: оба места рендерит один компонент.
- **R7. Устаревший ответ поиска или таймер копирования.** Закрыто номером запроса и номером нажатия в чистых автоматах (D7, D8) с тестами.
- **R8. Буфер обмена в небезопасном контексте.** `astro preview` по `http://localhost` — безопасный контекст; на `http://` хостинге копирование даст «Не удалось скопировать», а не ошибку страницы.
- **R9. Шум в результатах поиска от блоков кода.** Осознанно: команды и ключи ищут. Если шум помешает — `data-pagefind-weight` у заголовков, отдельной задачей.
