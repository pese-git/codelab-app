## Decisions

### D1. Порт: отдельный `SkillFilesSource`, реализация в `ProjectFilesLoader`

Ядро объявляет порт `SkillFilesSource.loadSkills(SkillFilesQuery)` и необязательное поле `AgentCoreServices.skillFiles`. Запрос: канонический `cwd`, `projectTrusted` (fail-closed, тот же расчёт, что у файлов проекта), элементы `skills.extra_roots`, токен отмены. Результат `SkillFiles {skills: List<SkillFile>, diagnostics}`; `SkillFile` — разобранный хостом frontmatter (или ошибки разбора) и тело `SKILL.md`, канонический каталог, область, номер корня в порядке приоритета, относительные пути сопутствующих файлов.

Реализует порт тот же класс `ProjectFilesLoader`: общие граница, лимиты, чтение UTF-8. Хост кладёт один объект в оба поля; `serve --ws` — ни в одно (D3). Рантайм запускает две фазы открытия сессии **параллельно**, каждую со своим таймаутом 5 с и общей отменой: медленный корень навыков не отнимает у сессии `AGENTS.md`. Таймаут фазы навыков — сессия без навыков, диагностика `timeout`; поздний результат выбрасывается. Порт не вызывается при выключенной capability `skills`.

*Альтернативы:* (а) поле `SessionSpec`, как в прежнем §17.2.1, — у `loadSession` нет спецификации, а ACP-адаптер не имеет `dart:io` (D1 change `add-agent-project-files`); (б) поле `ProjectFiles.skills` — общий таймаут и полное перечитывание файлов проекта ради отпечатка E-19; (в) отдельный класс — дублирование границы.

### D2. Разделение хост / ядро

Хост читает: перечисляет корни и подкаталоги, читает `SKILL.md` через `BoundedEnv` каталога навыка, отделяет frontmatter, перечисляет сопутствующие файлы. Разбор frontmatter для навыков — мягкий (D4): хост отдаёт результат разбора с позициями (`ConfigTree`) или ошибки разбора с позициями файла, а одна попытка починки выполняется в хосте (YAML — не дело ядра, CFG-5); сырой текст frontmatter ядру не передаётся — ядро YAML не разбирает, а лишнее поле с текстом файла только повышает риск попадания фрагментов в логи. Ядро проверяет поля, применяет `skills.disabled`, `max_skills`, приоритет и строит неизменяемый снимок `SkillCatalog {skills, modelVisible, diagnostics}` чистой функцией `parseSkills(files, settings, rules: …)`: правила разрешений конфигурации (`PolicyRules`) нужны для `modelVisible` (D7, agent-skills «Каталог навыков сессии»). `SkillCatalog` содержит только навыки: шаблоны в коде живут отдельно (`List<CommandTemplate>`), сведение их в один тип — переписывание рабочего кода (`AGENTS.md` §19). Точные типы и сигнатуры — D16.

### D3. Корни, приоритет, доверие и хосты (решения Q13, Q21, Q22)

Корни по уровням, от высшего приоритета:

| # | Корень | Уровень | Когда читается |
|---|---|---|---|
| 1…2k | на каждом уровне каталогов от `cwd` вверх до корня git-репозитория (без репозитория — только `cwd`), ближний первым: `<уровень>/.codelab/skills`, затем `<уровень>/.agents/skills` | `project` | только доверенный проект |
| далее | `$CODELAB_HOME/skills`, затем `~/.agents/skills` (домашний каталог процесса, а не `$CODELAB_HOME`) | `user` | всегда, кроме `--llm-script` |
| далее | элементы `skills.extra_roots` по порядку | `extra` | согласие пользователя; `~` и `~/…` — от домашнего каталога процесса, как абсолютный (Q41); относительный путь — от `cwd` и только для доверенного проекта |

Источники: руководство (§«Where to scan») советует сканировать собственный каталог клиента и общий `.agents/skills` в проекте и у пользователя, допускает подъём к корню git для монорепозиториев и предлагает пускать проектные навыки только для доверенной папки (§«Trust considerations»); CC и OC читают свои и общие каталоги без отдельного вопроса (Q13). Подъём до корня git и «ближний перекрывает дальний» — как у `AGENTS.md` (Q22; поиск корня — общий с `agent-project-context` «Поиск инструкций проекта», не больше 64 уровней). Доверие — по правилу файлов проекта: признак `projectTrusted` канонического `cwd` (fail-closed) открывает или закрывает весь уровень `project`. `.claude/skills`, `~/.codex/skills` и прочие каталоги конкретных агентов — только через `skills.extra_roots` (строка E-06 матрицы уточнена).

Конфликт имён решает ядро (`parseSkills`) по имени навыка (`name`, без него — имя каталога) после мягкой проверки; навык, пропущенный с `error`, ничего не перекрывает (решение Q39): побеждает корень с меньшим номером в таблице, внутри корня — первый каталог в байтовом порядке. Проигравший — **`warning` `shadowed`** с обоими путями и между уровнями, и внутри уровня (Q21: перекрытие должно быть видно в `config check`; руководство §«Handling name collisions» — предупреждать при коллизии).

**Приоритет `skills.extra_roots`** (решение Q31): и абсолютные, и относительные (`.claude/skills`) элементы стоят ниже своих корней — проекта, затем пользователя. `extra_roots` в первую очередь подключают каталоги других агентов, и свой каталог должен быть выше чужого. Сравнение (пересказ первоисточников пользователя): OpenCode тоже ставит каталоги совместимости (`.claude`, `.agents`) ниже своих (`packages/core/src/skill.ts`, `plugin/internal.ts`, `config/plugin/compatibility.ts`); Codex победителя не выбирает и оставляет обе копии (`codex-rs/ext/skills/src/loader/host_merge.rs`, `skills/src/selection.rs`); у Claude Code порядок «enterprise > personal > project» — пользователь выше проекта (документация skills, «Resolve skills that share a name»). CodeLab следует руководству agentskills.io и OpenCode: проект выше пользователя, ближний уровень выше дальнего, свой каталог выше чужого — и, в отличие от всех трёх, предупреждает о перекрытии (Q21).

Согласие на корень `extra` дают слои, которые пишет пользователь: глобальный конфиг, хранилище приложения, `--config`/`CODELAB_CONFIG` и `config.local.yaml` доверенного проекта; проектный `config.yaml` — никогда (SKL-2).

Внутри корня навык — подкаталог **первого уровня** с файлом `SKILL.md`; каталоги на `.` и записи-не-каталоги пропускаются молча (место для указателей E-18). Рекурсивный поиск не делается сознательно: результат детерминирован и не зависит от глубины дерева, открытие сессии не обходит большие каталоги, раскладка совпадает с Claude Code. Вложенная раскладка по группам (`skills/<группа>/<навык>/SKILL.md`) не поддерживается: такой навык не найдётся, нужен отдельный корень в `extra_roots`. Каталог корня раскрывается `realpath`: корень проекта должен остаться внутри своего уровня, `$CODELAB_HOME/skills` — внутри `$CODELAB_HOME` (как каталоги шаблонов пользователя), иначе корень целиком пропускается с `warning` `outside_root` (решение Q42); `~/.agents/skills` и элементы `extra_roots` — каталоги, названные явно, их `realpath` не ограничивается; общие навыки из другой папки подключаются только через `extra_roots`. Каталог навыка, чей `realpath` вне реального пути корня, пропускается с `outside_root`; каталог навыка, чей `realpath` уже найден через другой корень или другую запись (одна папка, видимая по двум путям), пропускается молча, без `shadowed`: это один и тот же навык, а не коллизия (D16); файлы читаются через `BoundedEnv` с корнем в реальном пути каталога навыка. Предел — 1000 подкаталогов на корень (`warning` `limit_exceeded`).

Хосты (как файлы проекта, agent-binary «Файлы проекта в бинаре»): `serve --stdio`, встроенный агент app и CLI — порт есть; `serve --ws` — порта нет (D16 change `add-agent-project-files`); `--llm-script` — уровень `user` не читается, проект недоверенный, абсолютные `extra_roots` из `--config` читаются.

### D4. Формат `SKILL.md` и мягкая проверка (решения Q11, Q14, Q19, Q20)

Источник: руководство §«Lenient validation» — предупреждать, но загружать, когда возможно; пропускать только без описания и при совсем нечитаемом YAML; §«Handling malformed YAML» — одна попытка починки значений с двоеточием без кавычек. Прежнее правило «строго в своих корнях» отменено (Q11).

Правила одинаковы во всех корнях:
- **YAML.** Строгий профиль CFG-21. Если разбор не удался, хост один раз переписывает строки верхнего уровня `ключ: значение`, у которых значение без кавычек и содержит `: `, в строку **в одинарных кавычках** с удвоением `'` внутри (в YAML такая строка не обрабатывает `\`, поэтому `C:\temp` и `"` остаются как есть) и разбирает снова; удалось — `warning` `yaml_repaired`; нет — `error`, навык пропущен.
- **`name`.** Спецификация Agent Skills требует 1–64 символа из строчных буквенно-цифровых символов Unicode и дефиса, без дефиса в начале и в конце и без двух дефисов подряд, и совпадения с именем каталога. CodeLab сознательно сужает «рекомендованное» правило до ASCII — `^[a-z0-9]+(-[a-z0-9]+)*$`, не длиннее 64, — потому что имя становится словом команды, а разбор команды ASCII (`parseCommandLine`). Нарушение этого правила и несовпадение с именем каталога — `warning` (`invalid_name`, `name_mismatch`), навык загружается под именем из `name`. Нет `name` — `warning` `missing_name`, имя — имя каталога. Пропуск — только если имя нельзя сделать командой и значением `enum`: не соответствует `^[A-Za-z0-9][A-Za-z0-9_-]*$` (разбор команды ASCII, `parseCommandLine`) или длиннее 128 символов; диагностика `error` `invalid_name` называет допустимые символы. Нелатинское имя поэтому всегда пропускается с понятной диагностикой (техническое решение по «мелочам»).
- **`description`.** Нет или пусто после схлопывания пробелов — `error` `missing_description`, пропуск. Длиннее 1024 символов — `warning`, навык загружается, а в каталог (D6) описание идёт обрезанным до 1024 символов с `…`; в блок навыка описание не входит.
- **`argument-hint`** (1–80), **`user-invocable`**, **`disable-model-invocation`** — неверный тип или длина: `warning`, поле по умолчанию.
- **`compatibility`** (Q19) — передаётся модели атрибутом блока навыка (D7); длиннее 500 — `warning`, обрезается до 500; пустое — `warning`, поле считается отсутствующим, атрибута нет.
- **`metadata.codelab-operative`** (K-06; решение Q32) — закреплённые строки навыка хранятся в `metadata`, а не полем верхнего уровня: спецификация (`specification.md`, поле `metadata`) отводит `metadata` под собственные свойства клиента и задаёт значения строками, поэтому строгие валидаторы (skills-ref) такой навык не бракуют. Ключ `codelab-operative`: префикс имени клиента исключает совпадение с ключами других агентов (`author`, `version`), дефис — как в именах полей спецификации. Кодирование: одна строка (обычно блок `|`), каждая непустая строка после обрезки пробелов — одно правило; не больше 16 правил по 1–512 символов. Нарушение или нестроковое значение — `warning`, правил нет; непустой список — `info` `not_applied` (до K-06). Поле верхнего уровня `operative` — обычный неизвестный ключ (`warning` `unknown_key`). `argument-hint`, `user-invocable`, `disable-model-invocation` остаются на верхнем уровне, как у Claude Code.
- **`license`, `metadata`, `allowed-tools`** — известные поля без диагностики и без применения (из `metadata` читается только ключ `codelab-operative`; остальные ключи — без диагностики) (Q14: спецификация называет `allowed-tools` экспериментальным, поддержка зависит от агента; применение позже — неломающее изменение отдельным change). `allowed-tools` прав не расширяет.
- **Неизвестный ключ** — `warning` `unknown_key`, навык загружается.
- Шаблоны и определения агентов сохраняют свои пределы (тело 32 КиБ, файл 64 КиБ): у них свой формат.
- **Тело.** Пустое — `warning` `empty_body`, навык загружается (Q20). Больше 64 КиБ — `error` `too_large`, пропуск (навык из ~500 строк, как советует руководство для авторов, помещается); файл `SKILL.md` больше 128 КиБ не читается; не UTF-8 — `not_utf8`. Это пределы ресурсов, а не косметика. **Обрезка тела:** тело — текст после закрывающей строки `---` с удалёнными пробельными символами в начале и в конце (руководство: «всё после закрывающего `---`, без краевых пробелов»); от этой обрезанной формы считаются `empty_body`, размер 64 КиБ, отпечаток SHA-256 (D15) и сравнение при повторе (D8); перевод строк `\r\n` внутри тела нормализуется в `\n`.

Диагностики идут в `config check` и в лог `project_files.diagnostic` (D13). Сообщения — фиксированные тексты кодов, без фрагментов файла.

### D5. Сопутствующие файлы, скрипты и граница только для чтения (решения Q4, Q17, Q23, Q24, Q25, Q26)

Источник: руководство §«Listing bundled resources» (перечислять, не читать заранее, ограничивать список) и §«Permission allowlisting» (каталоги навыков читаются без лишних вопросов); так же OC. Для скриптов — `skill-creation/05-using-scripts.md`: пути в навыке относительны его каталога, и агент выполняет команды навыка из него (Q17).

- Загрузчик перечисляет обычные файлы каталога навыка на глубине до 3, не больше 50 путей в байтовом порядке, без каталогов на `.`, без каталога `evals/` (техническое решение: по `skill-creation/04-evaluating-skills.md` там лежат тестовые запросы и ожидаемые ответы для автора навыка, а не инструкции; в список они не входят, и при `read` доверие Q30 на `evals/` не распространяется), без `SKILL.md`, без ссылок, чей `realpath` вне каталога навыка; содержимое не читается. Больше 50 — признак неполного списка, блок кончается строкой `[more files not listed]`. **Предел обхода — 5000 записей** (файлы и каталоги вместе) на каталог навыка: предел 50 ограничивает список, но не работу, а каталог навыка с `node_modules` или выгруженными данными заставил бы открытие сессии обходить десятки тысяч записей при таймауте фазы 5 с (техническое решение). Детерминизм: каталоги читаются в глубину, записи каждого каталога — в байтовом порядке имён, счётчик растёт на каждую просмотренную запись; на 5000-й обход прекращается и список помечается неполным (`companionsTruncated`), а 50 путей берутся в байтовом порядке из найденного. Одинаковое дерево даёт одинаковый список.
- `BoundedEnv` получает `readOnlyRoots` — канонические каталоги загруженных навыков **вне** рабочей папки — и `readOnlyFs` — файловую систему процесса агента (`AgentCoreServices.hostFiles`). Чтение (`read`, `ls`) из них идёт в `readOnlyFs` с обычной политикой уровня `read`. Каталог навыка внутри рабочей папки (`.codelab/skills`, `.agents/skills` у `cwd`) — обычная часть корня сессии, его правку решает PERM-11 (D9).
- Запись, правка и удаление в `readOnlyRoots` — `outsideWorkspace` до обращения к env (ENV-3).
- **`exec` с `cwd` в каталоге навыка** (Q17) разрешён, если env сессии исполняет команды на машине агента (`execInReadOnlyRoots`: встроенный агент app и CLI, `AcpServerConfig.localEnv`), но **не советуется** (Q26): блок навыка просит запускать скрипты по абсолютному пути с рабочей папкой проекта, потому что команды навыка обычно относятся к проекту (`git log`, `eslint .`, `CHANGELOG.md`), а относительные файлы данных при `cwd` в каталоге навыка разрешались бы не туда. Команда идёт по обычной политике уровня `exec`; критичность PERM-11 снимают только узкие исключения E1–E3 (скрипт под `<dir>/scripts/`, рабочий каталог навыка — лишь для такого скрипта или команды белого списка чтения, ресурс под `<dir>/assets/` без `.md`; D9, решения Q24, Q25, Q29, Q33–Q38).
- **Через клиента ACP** (`AcpClientExecutionEnv`, `serve --stdio` без `localEnv`) команды запускает клиент (`terminal/create`), а клиент CodeLab по `AGENTS.md` §10 и `acp-terminal-client` отклоняет `cwd` вне рабочей папки сессии как ошибку безопасности. Каталог пользовательского навыка (`$CODELAB_HOME/skills`, `~/.agents/skills`, `extra_roots`, уровни выше `cwd`) лежит вне неё, поэтому такой `exec` агент отклоняет сам, до запроса клиенту, ошибкой инструмента с подсказкой: запустить скрипт по абсолютному пути из блока навыка с `cwd` рабочей папки (решение Q23 (а)). Блок навыка говорит то же заранее одной строкой для обоих режимов (Q26, D7). Отличить этот отказ от прочих `outsideWorkspace` env не обязан: проверку с подсказкой делает инструмент `exec` до вызова env — `cwd` лежит в `readOnlyRoots` сессии, а env не исполняет там команды (`execInReadOnlyRoots == false`); `BoundedEnv` остаётся последним рубежом с обычным `outsideWorkspace`. Каталог навыка проекта у `cwd` внутри рабочей папки — `terminal/create` уходит как обычно. Containment клиента не меняется. Источник: CC даёт навыку переменную `${CLAUDE_SKILL_DIR}` с абсолютным путём каталога, а `cwd` после выхода командой `cd` наружу возвращает в проект — то есть скрипты навыка запускаются по абсолютному пути из проекта. Для справки: ни claude-code-acp, ни codex-acp, ни `opencode acp` не используют `terminal/create` — команды исполняет сам агент, поэтому у них этой проблемы нет; у CodeLab с клиентом по stdio она есть, потому что команды идут в терминал клиента.
- Тот же параметр `readOnlyRoots` нужен T-28 (каталог выноса, §17.4.4, 1.0).

### D6. Каталог в системном промпте (решение Q18)

Шаг 9a `composeSystemPrompt`: секция `skills/catalog` после `mcp` и до `project_context`, если capability включена и есть навыки `modelVisible`. Строки `- <name>: <description>` по имени, описание **целиком** (до 1024 символов, более длинное обрезается до 1024 с `…`, D4; Q18 — модель выбирает навык только по описанию). Бюджет `skills.catalog_max_chars` (8000): если сумма длин больше, описания режутся **поровну** — короткие остаются целыми, остаток бюджета делится одинаковыми долями между длинными, каждое режется по границе символа с `…`; если не помещаются и имена без описаний — с конца удаляются строки, последняя строка `[<N> more skills not listed]`; лог `skills.catalog.truncated` (warning). Без путей, дат и счётчиков — побайтово одинаково для одного снимка (SKL-4). Текст — английский, написан для CodeLab: когда звать `skill`, что пути внутри навыка относительны его каталога, что инструкции навыка не отменяют правил безопасности и решений пользователя. Источник: руководство §«Building the skill catalog», §«Behavioral instructions».

### D7. Инструмент `skill` и блок навыка (решения Q4, Q5, Q10, Q12, Q19, Q26)

- **Схема.** `{"name": {"type": "string", "enum": [<имена modelVisible по порядку>]}}`, обязательное, без лишних полей (Q12; руководство §«Model-driven activation» советует ограничить имя перечислением, чтобы модель не выдумывала навыки). Нет навыков `modelVisible` — инструмент не регистрируется. Навык, которому политика запрещает `skill` с этим именем (`permissions.tools.skill: deny` или `permissions.deny` `skill:<name>`), в `enum` и в секцию каталога не входит (техническое решение: модель не должна видеть недоступное), но остаётся командой пользователя `skill:<name>`: правило `permissions.deny` ограничивает инструмент модели, а явный вызов человеком — его решение. Цена для E-19 — в D10.
- **Свойства.** Уровень `read`, вид `read`, исполнение `parallel`, `permissionPattern` — имя, `present` — `Load skill <name>`, `locations: [<dir>/SKILL.md]`.
- **Блок навыка** (Q4, Q5, Q19, Q26) — общий для результата `skill`, сообщения `/skill:` и приложения после сжатия: `<skill name="…" dir="…"[ compatibility="…"]>`, тело без frontmatter (руководство §«What the model receives»: большинство реализаций с отдельным инструментом снимают frontmatter), `</skill>`, затем **всегда** строка о путях — одна для обоих режимов исполнения: `This skill's own files (scripts, references, assets and files named in its instructions) are relative to its directory; task data is relative to the project. In tool calls, refer to the skill's files by absolute path, and run its scripts with the project as the working directory.` (аналог `${CLAUDE_SKILL_DIR}` в CC); совет об абсолютных путях распространён на все вызовы инструментов, а не только на запуск скриптов, — руководство советует абсолютные пути для файлов навыка в любых вызовах; строка не ссылается на список «ниже», поэтому верна и без сопутствующих файлов — и, если есть, список сопутствующих файлов абсолютными путями, при неполном списке — `[more files not listed]`. Экранирование: в теле любой открывающий или закрывающий тег `skill` (без учёта регистра, с пробелами) получает `\` после `<`; в атрибутах `"`, `<`, `>`, `\r`, `\n` → `_`. `outputTrust: trusted` (D9).
- **Повторная активация** (Q10; руководство §«Deduplicate activations», так же CC). Если навык активен (D15), результат — одна строка `Skill "<name>" is already loaded in this conversation; follow the instructions above.`, `isError: false`, лог `skill.activated {via: tool, repeated: true}`. Чтение `SKILL.md` инструментом `read` активацией **не считается** (осознанное решение): сырой файл с frontmatter — данные, модель получает тело навыка через `skill`; учёт `read` потребовал бы разбора путей вывода и сделал бы `activeSkills` зависимой от файловой системы.
- **Ошибка** (`isError: true`). Имя вне `enum` отклоняет проверка аргументов исполнителя до `execute` (§6.3.2): `Invalid arguments for tool "skill"` с перечнем допустимых имён, без тела. Сам инструмент на имя вне `modelVisible` отвечает `Unknown skill: <name>. Available skills: <a>, <b>.` — защита в глубину для прямого вызова (D17).

### D8. Команды `/skill:<name>` (решения Q5, Q7, Q10)

- **Список.** `AgentSession.commands`: встроенные, шаблоны по имени, затем `skill:<name>` навыков с `userInvocable` по имени. `inputHint` — `argument-hint`, иначе `"arguments"`. `SlashCommandSource.skill`.
- **Разбор.** Встроенная → шаблон → `skill:` при включённой capability → неизвестная. Нет навыка или `userInvocable == false` — `Unknown skill: <name>. Run /help to list commands.` без модели; при выключенной capability — обычная «Unknown command».
- **Подстановка** (Q7). Одна функция `substituteArguments` с шаблонами промптов: `$ARGUMENTS`, `$1`…`$9` (нумерация шаблонов, с единицы), один проход; без плейсхолдеров при непустом вводе — хвост `\n\nARGUMENTS: <ввод>` (так делает и CC). Буквальный `$` пишется как `\$` или `$$` — и в шаблонах, и в навыках (решение Q15 (а)). Отсутствующий позиционный аргумент даёт пустую строку — текущее поведение шаблонов (E-07, D8 change `add-agent-project-files`) сохраняется для обоих видов; CC в этом случае оставляет плейсхолдер текстом; отличие сознательное (решение Q28). **Решение дорого менять потом:** оно задаёт смысл текста уже написанных навыков, и любая смена правил подстановки молча изменит, что получит модель. Защиты блоков кода (`$1` в примере кода тоже подставляется) нет ни у CC, ни у других агентов; риск принят пользователем.
- **Сообщение** (Q5). Тело после подстановки, без frontmatter, оборачивается `prompts/skills/invoked.md` (`vars: [name, block]`, где `block` — блок навыка D7 с `dir`, телом, строкой о путях и списком файлов; экранирование D7) и заменяет первый текстовый блок промпта — уходит сообщением пользователя.
- **Повторный вызов активного навыка** (Q10). Содержимое активации — тело после подстановки без хвоста `ARGUMENTS:`. Если навык активен (D15) и его содержимое совпадает с активным, тело не вставляется: сообщение — строка `The user invoked the skill "<name>" again; its instructions are already loaded above.` и, при непустом вводе, `ARGUMENTS: <ввод>`. Если содержимое другое (плейсхолдеры с новыми аргументами) — полная обёртка: это новый текст, а не повтор.
- **Журнал.** `command: {"source": "skill", "name": <имя>, "args": <raw>}`; реплей и заголовок — `/skill:<name>[ <args>]`.
- **`/help`** — суффикс ` (skill)`.

Клиенты кода не получают; метка источника в палитре app по префиксу имени не вводится — ACP не передаёт источник команды.

### D9. Доверие к телу и безопасность (решения Q5, Q9, Q16, Q24, Q25, Q27)

Тело — недоверенный по происхождению текст, допущенный гейтами (SKL-1, SKL-2, D3). Оно идёт инструкцией (без ограды: огороженная инструкция инертна, §17.2.11), но:
- прав не даёт: каждое действие проходит политику §7, `allowed-tools` не применяется (Q14); текст каталога и обёрток говорит, что навык не отменяет правил безопасности и решений пользователя;
- экранирование тегов не даёт телу выйти из своего блока;
- тело, описание, аргументы и сопутствующие файлы не пишутся в логи;
- **файлы каталога загруженного навыка** (`references/*.md`, `assets/…`) при чтении `read` — того же доверия, что тело `SKILL.md` (решение Q30; `specification.md`, «Progressive disclosure»: `references/` — третий уровень раскрытия инструкций): вывод не огораживается, даже если путь содержит сегменты `node_modules`, `.dart_tool`, `vendor`, и в нём экранируются теги `skill`, как в теле. Правило «не отменяет безопасность и не даёт прав» действует. Остальные файлы и вывод `exec` — по прежней политике доверия вывода. Сверка с кодом: в CodeLab `read` огораживает только пути под `node_modules`, `.dart_tool`, `vendor`, а вывод `exec` — только у сетевых команд (`agent-tools` «Ограда недоверенного вывода»); обычные файлы проекта уже не огораживаются, поэтому Q30 для обычных путей поведение не меняет, а закрепляет его для каталогов навыков.

**PERM-11** (Q9 (б), Q16). Сверка с кодом показала, что `$CODELAB_HOME/agents` и `$CODELAB_HOME/prompts` (и `state/`) уже входят в пути конфигурации от хоста (`agentConfigPathsFor`, спецификация `agent-permissions`); часть Q9 про `prompts`/`agents` выполнена до этого change. Добавляются:
- в проектный список §7.6.1 — `.agents/skills/**` (`write`/`edit` — критические, `exec` с записью — критический шаблон; Q16);
- в защищаемые пути — **все корни навыков** с поддеревом, существующие или ещё нет, независимо от доверия проекту (Q27): `$CODELAB_HOME/skills`, `~/.agents/skills`, абсолютные элементы `skills.extra_roots` — путями от хоста (`AgentCoreServices.agentConfigPaths`, общие для процесса); корни, зависящие от `cwd` сессии, — уровни проекта выше `cwd` (`<уровень>/.codelab/skills`, `<уровень>/.agents/skills`, Q22) и относительные элементы `skills.extra_roots`, разрешённые от `cwd` (`.claude/skills` проекта), — **путями сессии**: рантайм при открытии сессии добавляет их к защищаемым путям политики этой сессии (`ConfigCheck` и так создаётся на сессию с её корнем), вычисляя их той же функцией списка корней, что даёт их загрузчику. Поле хоста не меняется: оно действует на весь процесс, а эти корни — только на сессию с этим `cwd`.

**Запуск скрипта навыка** (Q17; решения Q24, Q25, Q29, уточнённые Q33–Q38). По действующему правилу белого списка чтения команда не из списка с аргументом внутри защищаемого каталога — критическая: и `scripts/x.py` при `cwd` в каталоге навыка, и `python3 <dir>/scripts/x.py` из рабочей папки (рекомендованный путь Q23 и Q26) были бы критическими — вопрос даже в `bypass`, отказ в `autopilot`. Поэтому вводятся три узких исключения для одной простой команды, с проверкой по каноническому пути и сравнением имени `SKILL.md` без учёта регистра (точный SHALL-текст — `agent-permissions`, «Критические пути правок конфигурации агента»): **E1** (Q25, Q34, Q36, Q37) — исполняемый файл — обычный файл под `<dir>/scripts/` (без сегментов на `.`, `node_modules`, `site-packages`, `vendor`; не `SKILL.md`), первым словом с `/` или первым позиционным аргументом интерпретатора, узнанного по голому имени в `PATH`; перед скриптом **нет ни одной опции интерпретатора**, кроме `pwsh -File`/`-f` (allowlist безопасных опций не заводится, поэтому «неизвестная опция» тоже отключает E1); нет префиксных присваиваний, `env NAME=…`, `env -S/-i/-u` и предшествующих `export`/`declare`/`typeset`/`readonly`/`local NAME=…` (fail closed); **E2** (Q24, сужено Q33) — рабочий каталог в каталоге навыка (`cd`, `pushd`, `ExecOptions.cwd`) не делает команду критической, только если её исполняемый файл — скрипт по E1 или команда из белого списка чтения; `env -C` и `-C DIR` под E2 сознательно не подпадают; **E3** (Q29, Q35, Q38) — существующий обычный файл под `<dir>/assets/` **того же** навыка, не `.md`, аргументом его скрипта по E1; `references/`, `scripts/`, `SKILL.md`, файлы другого навыка, слова с маской или фигурными скобками и значения опций вывода (`-o`, `-o<path>`, `-O`, `--output`, `--output=…`, `--out`, `--out=…`, `--outfile`, `--output-file`, `--out-file`, `--outdir`, `--dest`, `--target`, `--write`, `-w`, `of=…`) исключения не получают; жёсткие ссылки E3 не различает — `FileStat` не отдаёт `nlink` (известный предел). Пишущие команды перечня PERM-11 и перенаправления в каталог навыка критичны всегда. Источники: `specification.md` (каталоги `scripts/`, `references/`, `assets/`), `skill-creation/02-best-practies.md` и `05-using-scripts.md`. Найденные обходы, которые закрыли уточнения: `cd <dir> && tar -xf …`, `git pull`, `npm install` (Q33); `perl -pi -e`, `python3 -c`, `node -e`, `bash -c` (Q34); `--output <dir>/SKILL.md` (Q35); `<dir>/node_modules/.bin/shx cp …`, `prettier --write`, `.venv/bin/pip`, вложенный `tsx -e` (Q36); `NODE_OPTIONS=…`, `BASH_ENV`, `PERL5OPT`, `export …;` (Q37); скрипт, правящий `references/*.md` на месте (Q38).

### D11. Конфигурация

Ключи раздела `skills` с потребителем: `enabled` (`true`), `extra_roots` (`[]`; схема `<scheme>://` — проблема `value`), `disabled` (`[]`), `max_skills` (200, 1–1000), `catalog_max_chars` (8000, 1000–64000), `reattach.per_skill_tokens` (5000, 0–16384; `0` — без повторного приложения), `reattach.total_tokens` (25000, 0–200000; `0` — без повторного приложения). Значения по умолчанию повторного приложения — как у CC (Q6). `skills.operative.*` — без потребителя (`config.key.not_applied`); capability `skills` в `profile.<name>` — известная.

Доверие проектным слоям: `enabled: false`, `disabled`, уменьшение числовых ключей — из любого слоя; недоверенный проект не снимает запреты пользователя (решение Q43, CFG-3): `enabled: true` поверх `false` нижних слоёв — `config.project.untrusted_key`, `disabled` объединяется с нижними слоями; увеличение из проектного слоя недоверенного проекта — `config.project.untrusted_key` по ключу, сравнение — с итогом нижних слоёв, а не с умолчанием; доверенный проект увеличивать может (решение Q40; как `budget.*` и `tools.project_context.max_bytes`, `trust.dart`); элемент `extra_roots` на `~user` — проблема `value` (решение Q41); `extra_roots` в `config.yaml` проекта — всегда отброшен, в `config.local.yaml` — только для недоверенного проекта. Реестр настроек: все ключи `skills.*` — `fileOnly`. Новые значения действуют на сессии, открытые после перезагрузки.

Область действия (решение Q44): `skills.*` — ключи сессии, как `permissions.*` (agent-runtime «Конфигурация сессии вне корня запуска»). Сессия другой папки берёт их из `CoreConfig` своей папки, корни навыков проекта и `projectTrusted` — по её каноническому `cwd`; `skills.*` из слоёв папки не попадают в `config.session.process_keys_ignored`. Capability `skills` — на процесс, её сужает только `profile.<name>.skills: off` (решение Q45). `skills.enabled` capability не сужает ни в `buildAgentCore`, ни у сессии: `false` в `CoreConfig` сессии — корня запуска или другой папки — выключает навыки только сессий этой папки (пустой снимок, порт не вызывается). Так `skills.enabled` симметричен для всех папок, а перезагрузка корня меняет его для новых сессий корня в обе стороны без перезапуска.

### D15. Активные навыки и повторное приложение после сжатия (решения Q6, Q10)

Источник: руководство §«Protect skill content from context compaction» (содержимое навыков не должно пропадать при сжатии) и §«Deduplicate activations»; лимиты и порядок выпадения — как у CC (решение пользователя).

**Активация** — сообщение пользователя с `command.source == "skill"` или успешный результат `skill` с телом (не пометка повтора) на активной ветке.

**Функция `activeSkills(SessionSnapshot snapshot, SkillCatalog catalog, SkillsConfig settings) → List<ActiveSkill>`** — одна для повтора, приложения после сжатия и K-06; та же сигнатура во всех документах. Она возвращает упорядоченный (от новой активации к старой) список `ActiveSkill {name, full, content}`, где `content` — SHA-256 содержимого активации: для активации инструментом `skill` и для приложения после сжатия — обрезанного тела навыка, для команды `/skill:` — тела после подстановки её аргументов (из `command.args` записи) без хвоста `ARGUMENTS:` навыков, чьё тело сейчас есть в контексте модели:
1. `last` — последняя запись `compaction` на пути к листу (или нет);
2. `carried` — результат приложения `last` (ниже, «Приложение»): записи `last.skills`, которые приложены целиком (`full: true`) или усечёнными (`full: false`); выпавшие по общему бюджету и отсутствующие в каталоге в `carried` не входят;
3. активации в хвосте после `last.firstKeptId` (или на всём пути, если сжатий не было) дают `full: true` и поднимают навык в начало списка;
4. повторов нет: более новая запись о навыке заменяет более старую.

Определение не замкнутое: шаг 2 зависит только от `last`, каталога и бюджетов, а не от самой `activeSkills`.

**Активный навык** (для повтора, D7, D8) — элемент с `full: true`. Повтор `/skill:<name> <args>` — если навык активен и SHA-256 тела после подстановки этих аргументов (без хвоста `ARGUMENTS:`) равен `content`. Случаи: навык загружен моделью, затем `/skill:<name>` — если в теле нет плейсхолдеров, подстановка тела не меняет, `content` совпадает — короткая строка повтора (и `ARGUMENTS:` при непустом вводе); если плейсхолдеры есть, подстановка меняет текст — полный блок. Приложенный после сжатия целиком — так же, как активация инструментом. Приложенный усечённым — не активен: повторная активация вставляет тело полностью.

**Запись сжатия.** Запись `compaction` получает необязательное поле `skills: [{name, fingerprint}]` — элементы `activeSkills` до нового сжатия (с `full: true` и `false`), кроме навыков, чья последняя активация остаётся в хвосте после нового `firstKeptId` (их тело и так в контексте), в том же порядке. Так навык, приложенный прошлым сжатием (целиком или усечённым), переносится в новый список; выпавший по общему бюджету прошлого приложения не переносится и больше не возвращается до новой активации. `fingerprint` — SHA-256 обрезанного тела (D4) из снимка. Ни тела, ни аргументов в записи нет (CMP-2 не нарушается: старые записи не меняются).

**Приложение.** `buildLlmContext` после сообщения-резюме добавляет одно сообщение пользователя (в журнал не пишется — производное, как резюме) по `prompts/skills/reattached.md`: по блоку `<skill name dir>` на навык в порядке записи. Тело берётся из снимка каталога сессии по имени, в форме результата `skill` (без подстановки аргументов: аргументы относились к запросу, который ушёл в резюме). Бюджеты (оценка §9.3): тело длиннее `per_skill_tokens` усекается по границе строки с пометкой; навыки сверх `total_tokens` выпадают, начиная с давней активации. Нет навыка в снимке — выпадает, лог; отпечаток не совпал (сессия загружена после правки файла) — прикладывается текущее тело, лог `skills.reattach.changed`. `tokensAfter` и CMP-5 учитывают приложенное сообщение. Одинаковые входы дают одинаковое сообщение — кэш после сжатия стабилен.

**Общий механизм с K-06.** K-06 берёт правила `metadata.codelab-operative` всех элементов `activeSkills` (и `full: true`, и `false`) — той же функцией; закреплённые строки K-06 живут в **последней секции системного промпта** (§17.2.7, SKL-10), а не в сообщении после резюме: общей у K-06 и приложения навыков остаётся только функция `activeSkills`, место у них разное. Новых записей журнала не нужно.

*Альтернативы:* (а) не защищать (прежняя рекомендация Q6) — модель молча теряет инструкции; (б) исключить сообщения навыков из сжатия — хвост раздувается и ломает CMP-5; (в) писать тела в запись сжатия — дублирование в журнале и устаревание при правке файла.

  const SkillFilesQuery({required this.cwd, required this.projectTrusted,
      this.extraRoots = const [], required this.cancel});
  final String cwd;                 // канонический корень сессии

final class SkillFile {
  const SkillFile({required this.dir, required this.scope, required this.rootIndex,
      this.frontmatter, this.parseErrors = const [], this.repaired = false,
      required this.body, required this.bodyLine,
      this.companions = const [], this.companionsTruncated = false});
  final String dir;                 // realpath каталога навыка; «имя каталога» — его последний сегмент
  String get path => '$dir/SKILL.md';
  final ExtensionScope scope;
  final int rootIndex;              // номер корня, см. ниже; ядро сравнивает только порядок

  final List<ExtensionDiagnostic> parseErrors;   // error syntax/profile с позициями файла; непуст ⇒ frontmatter == null

  final String body; final int bodyLine;          // тело как в файле (LF), обрезку делает ядро
  final List<String> companions;    // пути от dir через '/', байтовый порядок, ≤ 50
  final bool companionsTruncated;
}
final class SkillFiles {

  final List<ExtensionDiagnostic> diagnostics;   // диагностики корней и файлов, не ставших SkillFile

abstract interface class SkillFilesSource { Future<SkillFiles> loadSkills(SkillFilesQuery query); }
// AgentCoreServices.skillFiles: SkillFilesSource? (null — навыков нет)

- **`rootIndex`** — позиция корня (с нуля) в списке, который строит шаг 1 алгоритма §17.2.4: уровни проекта (только для доверенного проекта), `$CODELAB_HOME/skills`, `~/.agents/skills`, затем элементы `extra_roots`. Номер получает каждый корень списка, существует ли каталог или нет: так номер одного корня не зависит от того, есть ли соседние, а та же функция списка корней даёт и защищаемые пути PERM-11 (D9). Корень, пропущенный по доверию (относительный `extra_roots` недоверенного проекта, уровни проекта без доверия), номера не получает. Ядро использует номер только для порядка (стабильная сортировка по `rootIndex`, внутри — порядок списка); значения в журнал и логи не пишутся (D10: место для корня `builtin` в конце).
- **Что в `parseErrors`, а что в `diagnostics`.** Ошибка разбора frontmatter — в `SkillFile.parseErrors`: ядро переносит её в диагностики каталога и пропускает навык, зная, какой навык не загрузился. Файл, который не стал `SkillFile` (`too_large` > 128 КиБ, `not_utf8`, `outside_root`), и диагностики корней (`untrusted_project`, `limit_exceeded`) — в `SkillFiles.diagnostics`.
- **Перекрытие имён** — в ядре по имени навыка (поле `name`, без него — имя каталога) после мягкой проверки, как в §17.2.4 и в `parseCommandTemplates`: загрузчик отдаёт все найденные навыки и `shadowed` не выдаёт. Решение Q39 (а). Повтор одного канонического каталога (`dir`) через другой корень или другую запись загрузчик пропускает молча, до ядра он не доходит: это одна папка, а не два навыка (Q42).

Алгоритм (D6, решение Q18; детерминированный, SKL-4):
1. Навыки сортируются по `name` (байтово). Описание длиннее 1024 рун — первые 1024 и `…` (не считается укорочением: предупреждение уже выдано при загрузке, D4).
2. Стоимость строки — её длина плюс 1 (перевод строки); бюджет — `maxChars`, в него входит и строка `[<N> more skills not listed]` с её переводом (вопрос A3 исполнителя: да, входит). Если сумма стоимостей не больше бюджета — строки `- <name>: <description>`, `shortened = omitted = 0`.
3. Иначе ищется наибольшая общая доля `s ≥ 0` (целое число рун), при которой сумма стоимостей не больше бюджета: описание длиной `≤ s` остаётся целым; длиннее — первые `s − 1` рун и `…`; при `s = 0` строка — `- <name>` без двоеточия. `shortened` — число описаний, укороченных этим шагом (в том числе до нуля).
4. Если даже при `s = 0` строки не помещаются, строки удаляются с конца: берётся наибольшее `k`, при котором `k` строк вида `- <name>` и строка `[<n − k> more skills not listed]` помещаются в бюджет, затем для этих `k` строк заново считается доля шага 3 с бюджетом за вычетом строки об опущенных. `omitted = n − k`.
5. `entries` — строки через `\n`, без завершающего перевода.

Такой путь — `ContentTrust.trusted` при любых сегментах (`vendor`, `node_modules`, `.dart_tool`), а текст файла проходит `escapeSkillTags` до нумерации строк. Остальные пути — прежняя политика `isUntrustedPath`, без экранирования. Сравнение лексическое: путь через другую форму корня (`/var` и `/private/var`) получает прежнюю политику (безопасная сторона: огораживание по сегментам остаётся).

**`ExecTool`** (`tools/builtin/exec.dart`; задача 2.9):

```dart
ExecTool({List<String> readOnlyRoots = const [], bool execInReadOnlyRoots = false});
```

В `execute` до вызова env: если `execInReadOnlyRoots == false`, `abs = normalizePath(ctx.env.cwd, cwd)` и `abs` лежит в одном из `readOnlyRoots` по правилу сегментов — `isError: true` с текстом `The working directory <cwd> is outside the client workspace; run the skill script by its absolute path from the skill block, with the workspace as the working directory.`, где `<cwd>` — значение аргумента как передано моделью; env вызова не получает. Иначе — прежний путь (`BoundedEnv` — последний рубеж, `Path is outside the workspace: <cwd>`). *Альтернатива* — проверка в `preflight` до политики разрешений (без лишнего вопроса пользователю перед заведомой ошибкой); отклонена: `preflight` не видит корня сессии, относительный `cwd` потребовал бы корень в конструкторе, а случай редкий — блок навыка заранее советует абсолютный путь (Q26).

**Граница только для чтения** (`env/bounded_env.dart`; agent-execution-env «Корни только для чтения»):

```dart
static Future<ExecutionEnv> wrap(ExecutionEnv inner, String root, {
    List<String> readOnlyRoots = const [], ExecutionEnv? readOnlyFs, bool execInReadOnlyRoots = false});
// SkillCatalog: List<String> readOnlyRoots(String sessionRoot)
// AgentCoreServices: final ExecutionEnv? hostFiles;   // файловая система процесса агента; null — корней нет
// SessionHostPorts: final bool execOnHost;           // env сессии исполняет команды на машине агента; по умолчанию false
```

- `SkillCatalog.readOnlyRoots(sessionRoot)` — `dir` навыков `skills` (в их порядке), которые не лежат в `sessionRoot` и **не содержат** его по правилу сегментов: каталог навыка, внутри которого открыта сессия (правка своего навыка), — часть рабочей папки, а не корень только для чтения, иначе запись в рабочей папке стала бы `outsideWorkspace`.
- `readOnlyFs == null` или `readOnlyRoots` пуст — поведение и набор опциональных возможностей прежние, проверки только по `root`.
- Каждый корень нормализуется; если `readOnlyFs` — `PathResolver`, раскрывается `realpath` **один раз** при создании (ошибка — остаётся нормализованная форма, как у `root`).
- Классификация пути `abs = normalizePath(root, path)`: (1) лексически в `root` или в его реальной форме — прежняя проверка рабочей папки; (2) иначе лексически в корне только для чтения (нормализованной или реальной форме) — ветка корня; (3) иначе — прежняя проверка (ссылка извне в рабочую папку принимается, всё остальное — `outsideWorkspace`). Внутренний env пути ветки (2) не видит — ни `stat`, ни `realpath`.
- Ветка корня, чтение (`readText`, `readBytes`, `stat`, `listDir`, `realpath`): раскрытие ссылок — через `readOnlyFs` тем же алгоритмом «глубочайший существующий предок», что у `_Guard`; реальный путь должен остаться в **том же** корне, иначе `outsideWorkspace`; вызов идёт в `readOnlyFs` с `abs`. Возможности нет у `readOnlyFs` (ENV-4) — `Err(FileError(unsupported, path))` без вызова env; сама обёртка реализует возможность, только если её реализует `inner` (матрица классов не меняется).
- Ветка корня, запись (`writeText` и будущие правка и удаление): `outsideWorkspace` сразу, без обращения к любому env (ENV-3).
- `exec` с `ExecOptions.cwd` в ветке корня: при `execInReadOnlyRoots == false` — `ExecError(outsideWorkspace)` с прежним текстом без вызова env; при `true` — раскрытие через `readOnlyFs` и проверка «в том же корне», затем `inner.exec(command, options.copyWith(cwd: abs))`.
- Рантайм: `env = BoundedEnv.wrap(ports.env ?? services.baseEnv, cwd, readOnlyRoots: hostFiles == null ? const [] : catalog.readOnlyRoots(canonicalCwd), readOnlyFs: services.hostFiles, execInReadOnlyRoots: services.hostFiles != null && (ports.env == null || ports.execOnHost))`. Обёртка создаётся **после** фаз загрузки (сейчас — до них; фазы env сессии не используют). `ports.env == null` — сессия исполняет на `baseEnv` хоста, это машина агента. `AcpAgentServer` ставит `execOnHost: true` только в ветке `localEnv` (встроенный агент); у `AcpClientExecutionEnv` и `ListingOverlayEnv` — `false` (вопрос A7 исполнителя: признак явный, по виду env, а не по типу объекта — обёртки env скрыли бы тип).

- Исключения E1–E3 — одна функция проверки простой команды в `permissions/agent_config_rules.dart`, встроенная в двухфазную проверку `findCritical`: первый проход собирает кандидатов (исполняемый файл, аргументы, рабочий каталог), `AgentConfigScope.canonicalizeSeen` раскрывает их `realpath` и, если резолвер политики — `FileSystem`, кэширует признак «обычный файл» (`stat` → `FileType.file`); второй проход решает по кэшу. Резолвер не `FileSystem` или `stat` неудачен — исключение не действует (fail closed; вопрос B2 исполнителя: новый порт не вводится — в рантайме резолвер всегда `ExecutionEnv` сессии или хоста, проверка `is` — образец опциональных возможностей ENV-4). Каталоги навыка — `skillDirs` по каноническому пути с учётом `caseInsensitive`; имя `SKILL.md` — по базовому имени без учёта регистра всегда.
- Тексты не меняются: `write`/`edit` — вопрос с `reason: 'agent configuration: <path>'`, в `autopilot` и без gate — `Editing agent configuration requires a human: <path>`; `exec` — `reason: 'critical command: write to agent configuration'`, в `autopilot` — `critical command blocked in autopilot: write to agent configuration` (PERM-9 основной спецификации `agent-permissions`). Сценарий «Навыки в autopilot» дельты называл для `exec` текст `write`/`edit` — исправлен (вопрос B1 исполнителя).

## Risks / Trade-offs

- **Новый канал инструкций** (приоритет 1): вредный навык в доверенном проекте, в `~/.agents/skills` или в разрешённом `extra_roots` управляет моделью в пределах её прав. *Смягчение:* гейты, политика §7, экранирование, PERM-11 на корнях (Q9, Q16), тело не в логах. `~/.agents/skills` читается без отдельного согласия (Q13): туда может положить навык другой агент пользователя — принято как соглашение формата.
- **Мягкая проверка** (Q11): опечатка в своём навыке не ломает загрузку, но видна только в `config check` и логе.
- **Починка YAML** (Q11) может прочитать значение не так, как задумал автор. *Смягчение:* одна попытка, только для двоеточия в значении без кавычек, предупреждение `yaml_repaired`.
- **Граница только для чтения** — новый путь в `BoundedEnv`. *Смягчение:* только каталоги загруженных навыков вне рабочей папки, правило сегментов, запись отклоняется до env; `cwd` команды — только при локальном исполнении (Q17, Q23); тесты SKL-9.
- **Модель угрозы исключений** (оговорка ревьюера безопасности): известный предел «скрипт из файла» (§7.6.1) и так обходит PERM-11 в `bypass` — модель может записать программу в рабочую папку и запустить её. Исключения E1–E3 не обязаны закрывать этот класс; их требование — не убирать срабатывание там, где путь записи в корень навыков явно виден в команде.
- **Скрипт навыка пишет в свой каталог или исполняет переданный код** (остаточный риск E1–E3): скрипт под `<dir>/scripts/` может сам изменить файлы навыка, а `<dir>/scripts/run.sh "rm …"` исполнит переданную строку; политика содержимое программ не разбирает — тот же класс, что «скрипт из файла». Рабочий каталог навыка снимает критичность только у скрипта по E1 и у команд белого списка чтения (Q33), не у любой команды. *Смягчение:* запуск по обычной политике `exec` (вопрос в `standard`); явная запись командой и перенаправление остаются критическими.
- **TOCTOU** (остаточный риск): проверка исключений идёт в `beforeToolCall`, а процесс запускается позже — файл или ссылка в каталоге навыка могут смениться между ними. *Смягчение:* каталог навыка защищён PERM-11 от записи командами, которые видны политике.
- **Абсолютные пути из `$CODELAB_HOME` через клиента ACP** (допущение): команда `python3 <home>/.codelab/skills/x/scripts/a.py`, отправленная клиенту `terminal/create`, работает, только если клиент запущен на той же машине, что агент (`serve --stdio` — дочерний процесс клиента). Для `serve --ws` навыки не читаются вовсе (D3), так что удалённого клиента это не касается; клиент stdio на другой машине (через ssh-туннель) получит ошибку запуска — это видимый отказ, а не обход границы.
- **Скрипт перезаписывает свой ресурс** (остаточный риск Q29, как у Q25): существующий файл под `<dir>/assets/` без `.md` (Q38), переданный аргументом *скрипту этого же навыка*, скрипт может изменить сам — политика не знает, читает он его или пишет; без Q35 любой скрипт с параметром `--output` превращался бы в запись `SKILL.md`.
- **Обходы через неявную запись и код в интерпретаторе** (закрыты Q33, Q34): `cd <dir> && tar -xf …`, `unzip -o`, `7z x`, `cpio -i`, `jar x`, `git pull`, `git merge`, `npm install`, `find -delete` без пути, а также `perl -pi -e … <dir>/SKILL.md`, `python3 -c …`, `node -e`, `bash -c …`, `python3 - <<EOF`, `python3 -m zipfile` получили бы исключения E1/E2 — теперь критичны. Остаются известные пределы разбора `exec` (§7.6.1): команда в shell через stdin (`echo … | sh`), запись из `sed -n 'w …'` и `awk '{print > …}'`, `pwsh -Command`, `fish -c`, `${HOME:-x}`, переменные (`F=…; rm $F`), подмена программы в каталоге из `PATH`. Любая другая программа с таким аргументом остаётся под PERM-11: в первой формулировке Q29 исключение распространялось на любую команду, и `sed -i`, `cp`, `rm`, `curl -o` на существующий `SKILL.md`, а с Q24 и `cd <dir> && rm SKILL.md` проходили бы в `bypass` без вопроса — вопреки Q9, Q16, Q27 и SKL-9; формулировка сужена решением пользователя.
- **Файл, записанный скриптом навыка, становится доверенным** (остаточный риск Q30 вместе с Q25 и Q29): то, что скрипт навыка записал в свой каталог, `read` потом отдаёт как доверенный текст навыка. *Смягчение:* запуск скрипта — по политике `exec` (в `standard` — с вопросом); тело `SKILL.md` перечитывается только в новой сессии (снимок каталога); в `bypass` риск принимает пользователь.
- **Скрипты, открывающие свои файлы относительно `cwd`** (Q26): если модель следует совету запускать скрипт с рабочей папкой проекта, такой скрипт ломается и при локальном исполнении, а не только через клиента ACP. *Смягчение:* строка о путях различает собственные файлы навыка (от его каталога) и данные задачи (от проекта); руководство для авторов советует скриптам находить свои файлы от собственного пути; `cwd` в каталоге навыка локально по-прежнему разрешён (Q17).
- **Один текст — разный результат по способу активации** (Q15): `$$` и `\$` в примерах кода тела при `/skill:` превращаются в `$`, а в результате инструмента `skill` и в приложении после сжатия остаются как есть. *Смягчение:* правило задокументировано (D8); подстановка затрагивает только путь команды.
- **Скрипты пользовательских навыков через клиента ACP** (Q23 (а)): с внешним клиентом по stdio скрипт, рассчитанный на запуск из каталога навыка, модель должна запускать по абсолютному пути из рабочей папки; часть навыков с относительными путями внутри скрипта может не сработать. Во встроенном агенте app и CLI ограничения нет.
- **Подъём к корню git** (Q22): навык из родительского каталога монорепозитория действует во всех подпроектах доверенного проекта; перекрытие ближним видно как `shadowed`.
- **Пути сессии PERM-11 без фазы навыков** (известный предел, решение Q46 (а)): корни навыков, зависящие от `cwd` (уровни выше `cwd` до корня git, относительные и собственные абсолютные `extra_roots` папки), защищены только в сессиях, где фаза навыков завершилась результатом. Не защищены: при `skills.enabled: false` в конфигурации папки, у хоста без порта (`serve --ws`, web), при таймауте, исключении или отмене фазы. Пример: в сессии `/repo/apps/demo` с выключенными навыками запись `../../.agents/skills/x/SKILL.md` не критична, а навык загрузит сессия `/repo`, если там навыки включены и проект доверенный. Корни хоста и проектное правило у `cwd` защищены всегда (D17).
- **Гонки** (§9, §12): две фазы открытия, общая отмена, поздние результаты выбрасываются; каталог неизменен до закрытия; приложение после сжатия — чистая проекция.
- **Подстановка `$1`** в чужих навыках (Q7): примеры кода с `$1` при `/skill:` превратятся в аргумент; модельный путь тело не меняет; `\$` даёт литерал. Решение дорого менять потом (D8).
- **Окно после сжатия** (Q6): до 25 000 токенов приложенных навыков уменьшают выигрыш сжатия; на малом окне приложение может не дать опуститься ниже порога. *Смягчение:* ключи `reattach.*`, `0` выключает; CMP-5 — не больше трёх проходов.
- **Кэш промпта и `enum`** (Q12) — принятая цена для E-19 (D10).
- **Forward compatibility.** ACP не меняется. Журнал: старое ядро читает `source: "skill"` как неизвестный источник, а поле `compaction.skills` — как неизвестное поле записи без потери (§8.2.2).
