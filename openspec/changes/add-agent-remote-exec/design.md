## Context

Где исполняются инструменты, решает то, что хост положил в `AcpServerConfig` (`packages/dart/codelab_agent_acp/lib/src/agent_server.dart`, `_Connection._wire`; сквозное описание — `packages/dart/codelab_agent_core/doc/algorithms/execution-sides.md`):

| Ветка | Кто задаёт | env сессии | `fs/*`, `terminal/*` клиенту | `ls`, `search` |
|---|---|---|---|---|
| 1. `localEnv` | встроенный агент (`codelab_embedded/lib/src/assemble.dart`) | `localEnv(cwd)` = `LocalExecutionEnv`, `execOnHost: true` | нет | да, из `localEnv` |
| 2. `localListing` | `serve --stdio` | `ListingOverlayEnv(AcpClientExecutionEnv, LocalExecutionEnv)` | да | да, локально |
| 3. ничего | `serve --ws` | `AcpClientExecutionEnv` | да | нет (`fileListing` off) |

Gate во всех ветках — `AcpPermissionGate` (`session/request_permission`), containment — `BoundedEnv` ядра по `cwd` (ENV-2), решение «спрашивать ли» — `PermissionPolicy` ядра (PERM-1).

`AgentHost.build` (`apps/codelab_agent/lib/src/host/agent_host.dart`) по `--ws` дополнительно:
- выключает `fileListing` и `mcp` (серверы клиента и конфигурации пропускаются `mcp.server.skipped`);
- не передаёт `ProjectFilesLoader`, `hostFiles` и `projectConfig` (`project_files.skipped`);
- собирает ядро с `configCommand: false`.

Причина везде одна: `cwd` приходит из сети, и клиент может быть на другой машине.

`serve --ws` (`serve/serve_ws.dart`) требует Bearer-токен при upgrade (`401`/`426`, сравнение за постоянное время), TLS не обслуживает. Не-loopback `--host` даёт только предупреждение `serve.ws.non_loopback`. `detachGrace` бинаря — ноль для обоих транспортов (change `cancel-turn-on-ws-disconnect`, D1). На этом построен клиент: он помечает прерванный ход после `session/load` (там же, D2).

Документ ядра уже предусматривает режим. В §10.4 у `shellExec` профиля `agent-serve` транспорт `local` по флагу `--local-exec`. В `HostProfile.of('agent-serve')` в коде то же: `{'acp-terminal', 'local'}`. В §15.6 флаг сопоставлен ключу `exec.local_fallback` со смыслом «локально, если клиент не объявил `terminal`», ключ в схеме с `applied: false`. Флага в парсере `serve` нет.

Сессии сервера лежат в общей таблице `_sessions` по id. `_bridge(id)` владельца не сверяет (REV-35, issue #514): любое соединение того же процесса может прислать `session/prompt` в чужую сессию, а вопросы о разрешении уйдут владельцу.

## Goals / Non-Goals

**Goals:**
- `codelab-agent serve --ws` (и `--stdio`) на машине агента сам исполняет `read`, `write`, `edit`, `exec`, `ls`, `search` и MCP; клиент только показывает поток и отвечает на вопросы о разрешении.
- Граница безопасности не слабее встроенного агента: та же политика, тот же gate, тот же `BoundedEnv`, окружение команд по allowlist ENV-6, плюс явные корни рабочих папок, которые задаёт оператор машины агента.
- Нулевые изменения ACP и клиентов.

**Non-Goals:**
- Удалённая папка в клиентах (Q2), TLS в бинаре (Q1), возобновление хода после разрыва, ключи `exec.*` (D8), аренда журнала (REV-36).
- Песочница для команд: `exec` ограничен только своим `cwd` (`execution-sides.md`, «Чего не гарантирует»). Режим даёт держателю токена оболочку от имени пользователя процесса агента, и это сказано в документах.

## Decisions

### D1. Включение: флаг `--local-exec` для обоих транспортов, без ключа конфигурации

`codelab-agent serve (--stdio | --ws) --local-exec --workspace-root <dir> [--workspace-root <dir> …]`. Умолчание прежнее: без флага файлы и команды идут через клиента.

- **Оба транспорта.** По stdio режим даёт самую безопасную удалённую схему: клиентский профиль `stdio:ssh devbox codelab-agent serve --stdio --local-exec --workspace-root ~/proj`. Аутентификацию и шифрование даёт SSH, токена и открытого порта нет. То же работает с `docker exec -i <контейнер> codelab-agent serve --stdio --local-exec …`. Без флага по такому профилю агент сейчас читает листинг на своей машине, а файлы через клиента, то есть на другой машине. Флаг это расхождение снимает.
- **Только флаг.** Режим меняет, на какой машине исполняется всё, что делает модель. Это решение оператора о конкретном запуске, и в командной строке (`ps`, unit-файл службы) его видно сразу. Ключ конфигурации включал бы режим незаметно для всех запусков пользователя.
- **`exec.local_fallback` не реализуется.** Смысл ключа по §15.6 — «команды локально, если клиент не объявил `terminal`». Это смешанный режим: файлы через клиента, команды у агента, причём выбирает его неявно объявление клиента. Две машины в одной сессии ломают модель «один `cwd` — одна ФС». Ключ остаётся в схеме с `applied: false`, строки §15.6 и §17.9.2 исправляются (Q4).
- **Профиль хоста не нужен.** `agent-serve` уже допускает `shellExec: local`. Отдельный профиль `agent-serve-local` дал бы второе имя для сужений `profile.<name>.*` без новых возможностей.

Отвергнуто: ключ `serve.local_exec` в конфиге (незаметное включение); флаг только для `--ws` (теряется схема SSH + stdio); переименовать `exec.local_fallback` в `exec.local` (то же, что ключ конфига).

### D2. Рабочая папка: `cwd` как есть, обязательные корни, без сопоставления путей

ACP требует, чтобы `cwd` из `session/new` был рабочей папкой сессии «regardless of where the Agent subprocess was spawned» (`03-Session Setup.md`, «Working Directory»: MUST, SHOULD — граница операций с ФС). Поэтому агент использует `cwd` как есть, на своей ФС.

- **`--workspace-root <dir>` обязателен при `--local-exec` и повторяем.** Корень задаёт оператор машины агента. Относительный путь берётся от текущего каталога процесса, как `--config`. При старте хост строит для каждого корня пару `WorkspaceRoot {path, resolved}`: `path` — заданный путь, нормализованный и приведённый к виду ядра (`toCorePath`), `resolved` — он же после `resolveSymbolicLinks`. Обе формы нужны. На macOS корень `/tmp/w` раскрывается в `/private/tmp/w`, а клиент присылает `cwd` в той форме, которую видит сам. С одной раскрытой формой лексическая проверка отклонила бы законный `/tmp/w/proj`. Несуществующий корень или не каталог — код `64`. `--workspace-root` без `--local-exec` и `--local-exec` без корня — тоже `64`.
- **Проверка в `session/new` и `session/load`** (`_checkCwd`, до создания сессии и до `reattach`):
  1. `cwd` не абсолютный → `-32602` (как сейчас);
  2. **лексическая** проверка: нормализованный `cwd` (`normalizePath`) должен лежать внутри корня (`isInside`) в заданной или в раскрытой форме. Иначе `-32602` `cwd is outside the workspace roots of the agent`, `data.codelab.reason: "cwdOutsideWorkspaceRoots"`. ФС при этом не трогается: ответ не выдаёт, существует ли каталог вне корней;
  3. `realpath` через `PathResolver` окружения `localEnv(cwd)`. Ошибка `realpath` при заданных корнях — отказ `-32602` `cwd does not exist: <cwd>`. Сейчас `_checkCwd` в этом случае молча берёт нераскрытый путь (`agent_server.dart`, `_checkCwd`). При корнях так нельзя: непроверенный путь прошёл бы мимо шага 5 (fail closed);
  4. раскрытый путь не каталог → `-32602` `cwd does not exist: <cwd>`;
  5. раскрытый путь проверяется по формам `resolved`: символическая ссылка внутри корня, ведущая наружу, даёт тот же `cwdOutsideWorkspaceRoots`.
- **Журнал загружаемой сессии.** `AgentRuntime.loadSession` берёт `cwd` из запроса, а не из заголовка журнала (`agent_runtime.dart`, `loadSession`). Без дополнительной проверки клиент загрузил бы сессию папки `/old` вне корней, прислав `cwd` внутри корня, и получил бы реплей чужого транскрипта. Поэтому `session/load` сессии, которой нет в памяти, передаёт ядру `admitJournalCwd` (agent-runtime «Допуск папки журнала при загрузке»). Рантайм зовёт её с `cwd` заголовка сразу после открытия журнала, до конфигурации, модели и MCP. Сервер проверяет заголовок шагами 2 и 5; шаг 5 — только если каталог ещё существует. Отказ — тот же `cwdOutsideWorkspaceRoots`. Ядро о корнях не знает: оно получает только функцию допуска. Открытый в памяти мост (`reattach`) повторной проверки заголовка не требует: его создали `session/new` или `session/load` этого же процесса с теми же корнями.
- **`session/list` при корнях** отбрасывает сессии, чей `cwd` лексически вне корней. Иначе удалённый клиент видел бы пути и заголовки всех сессий машины агента. `nextCursor` остаётся курсором хранилища, поэтому страница может оказаться короче или пустой. ACP это допускает: курсор непрозрачен, а наличие `nextCursor` значит «есть ещё» (`04-Session List.md`).
  
  Корни в ответе не перечисляются: удалённому клиенту не нужны пути машины агента. В лог они попадают при старте (D10).
- **Где проверка.** В `codelab_agent_acp`: новое поле `AcpServerConfig.workspaceRoots` (`List<WorkspaceRoot>?`, `null` — без проверки). Это продолжение `_checkCwd` (change `add-dart-agent-acp-server`, D5). `HostWiringException` при создании сервера даёт любое из трёх условий: корни без `localEnv`; `localEnv('/')` не `PathResolver` (по образцу проверки `DirectoryListing`); пустой список корней. `dart:io` в пакет не попадает (PKG-3). `normalizePath` и `isInside` экспортируются из бареля ядра, а не пишутся второй раз (§14). Встроенный агент поле не задаёт: у него `cwd` выбирает сам пользователь в своём процессе.

Отвергнуто:
- **Сопоставление путей** (`/Users/a/proj` клиента → `/home/a/proj` агента). Нарушает MUST `03-Session Setup.md`, ломает `locations` и `diff` карточек и путь в `session/list`.
- **Один корень вместо `cwd`.** Агент подменяет `cwd` клиента — то же нарушение.
- **Корень по умолчанию = каталог запуска.** Запуск из `$HOME` открыл бы весь домашний каталог. Явный флаг дешевле ошибки.

Следствие для клиентов. CLI проверяет `-C` на своей машине (`_sessionFolder`), desktop показывает локальное дерево. Значит, в первой версии абсолютный путь должен существовать на обеих машинах: общий путь, контейнер с `-v $PWD:$PWD`, смонтированная ФС. Снять это ограничение может только клиентский change (Q2).

### D3. Доступ по сети: под `--local-exec` WebSocket слушает только loopback

С `--local-exec` токен WebSocket даёт оболочку на машине агента. По `ws://` без TLS он идёт по сети открытым текстом (REV-31, вторая часть — на стороне клиента). Поэтому:

- `--local-exec --ws` с `--host` не на loopback — ошибка использования, код `64`: `--local-exec over --ws listens only on a loopback address; reach it through an SSH tunnel or a TLS reverse proxy`. Проверок две:
  - **до привязки**, в `serve_args.dart` вместе с остальными кодами `64`: `--host` — `localhost` или литерал IP с `InternetAddress.isLoopback`. `::ffff:127.0.0.1` в Dart не loopback (IPv6 с ненулевыми байтами) и отклоняется — fail closed;
  - **после привязки**, в `serve_ws.dart`: `HttpServer.address.isLoopback`. Это защита от `localhost`, который `HttpServer.bind(String)` разрешает через `hosts` и может получить не-loopback адрес. Тогда сокет закрывается до приёма подключений;
- **длина токена.** Loopback не значит «один пользователь»: до сокета доберутся другие локальные пользователи общей машины и любой, кто подключится к порту `ssh -L`. Токен остаётся единственным барьером, а попытки после `401` не ограничиваются. Поэтому под `--local-exec --ws` токен короче 32 байт (UTF-8) — код `64` до привязки, в тексте только имя переменной. Ограничение частоты попыток в этот change не входит (D11);
- аутентификация в остальном прежняя: Bearer при upgrade, `401`/`426`, постоянное время, токен не в логе (agent-binary «Аутентификация WebSocket»). Проверка `Origin` не добавляется: браузер не может поставить заголовок `Authorization` в рукопожатие WebSocket, так что страница без токена получает `401` и так;
- рекомендованные схемы (в `operations.md`): SSH + `--stdio` (D1); `ssh -L 8765:127.0.0.1:8765 devbox` и `ws://127.0.0.1:8765` у клиента; обратный прокси с TLS на машине агента к loopback (так `wss://` уже описан в `02-connect-clients.md`);
- без `--local-exec` поведение прежнее: не-loopback даёт только предупреждение.

Отвергнуто в этом change (Q1): `--allow-remote` без TLS (токен оболочки открытым текстом) и встроенный TLS `--tls-cert`/`--tls-key` (как у A2A, §17.15.4). Последнее — нормальный следующий шаг, но не обязательный для цели. Обратный прокси и SSH его закрывают.

Контейнер, где сервер обязан слушать `0.0.0.0` ради проброса порта, этим запрещён. Для него — `docker exec -i … --stdio --local-exec` (D1).

Телефон и планшет (`docs/architecture/proposals/dart-agent-and-clients/12-8-phone-and-tablet.md`, §12.8.2) подключаются к агенту с `--local-exec` по сети. При ответе (а) на Q1 им доступен только `wss://` через TLS-прокси на машине агента. Задача 0.1 правит этот документ.

### D4. Владелец сессии (REV-35) входит в change как предусловие

Мост сессии хранит `owner` (соединение, которое создало сессию или последним загрузило её `session/load`; `reattach` уже меняет его). Обработчики, которые ищут сессию через `_bridge(id)`, сверяют владельца:

| Вход | Чужая сессия |
|---|---|
| `session/prompt`, `session/set_mode`, `session/set_config_option`, `_codelab/session/usage/ledger` | `-32002` `Session not found: <id>`, `data.codelab.reason: "sessionNotOwned"`; лог `acp.session.not_owned {session_id, method}` (warning) |
| уведомление `session/cancel` (и терпимый запрос `session/cancel`) | ход не отменяется; лог `acp.session.not_owned`; на запрос — прежний ответ `null` |
| `session/load` | не меняется: загрузка и есть смена владельца; занятая чужим ходом сессия — `sessionBusy`, как сейчас. Если сессию забирают у другого соединения — warning `acp.session.owner_changed {session_id}` |
| `session/list` | правилом владельца не ограничивается (фильтр по корням — D2) |

**Момент проверки.** Владелец проверяется синхронно при приёме запроса, до первого `await`. Например, `_setMode` и `_setConfigOption` ждут `bridge.setMode`, и за это время `session/load` другого соединения может забрать сессию. Решение: запрос, принятый от владельца, доводится до конца. Ответ уходит приславшему, а эхо `current_mode_update` — текущему владельцу (мост уже переключил `sink`). Перепроверка после `await` отменила бы смену, которая уже записана в журнал: состояние разошлось бы с ответом. Сценарий «Загрузка во время смены режима» закрепляет это поведение.

Требования, которые правило сужает («session/prompt, проекция и итог хода», «session/cancel», «Режимы и опции сессии», «Запрос `_codelab/session/usage/ledger`»), переписаны в дельте как MODIFIED со ссылкой на новое требование.

Почему это блокер режима. Все соединения одного процесса предъявляют один токен, так что второе соединение и сейчас может перехватить простаивающую сессию через `session/load`. Опасно другое: подмешать `session/prompt` в сессию, за которой следит человек. Вопрос о разрешении уйдёт этому человеку, и он одобрит команду как свою. С `--local-exec` это команда на машине агента. Без режима — тоже команда, но на машине клиента. Поэтому правило действует для любого сервера и транспорта, а не только под флагом.

Почему `-32002`, а не `-32602`. Для этого соединения сессии нет: оно её не создавало и не загружало. Путь восстановления тот же, что при неизвестном id, — `session/load`. Причина `sessionNotOwned` нужна для диагностики. Коды ACP берутся только из `ErrorCode` схемы (`17-Schema.md`). Новые значения `reason` — часть расширения `data.codelab.reason` (change `add-dart-agent-acp-server`), как ранее `sessionBusy`, `turnActive`, `projectConfigInvalid`.

Влияние на существующих клиентов. Встроенный агент и `--stdio` работают в одном соединении, для них ничего не меняется. Клиент CodeLab после переподключения по WebSocket сначала делает `session/load` (change `cancel-turn-on-ws-disconnect`, D2). Клиент, который после переподключения шлёт `session/prompt` без `session/load`, получит `-32002`. По `03-Session Setup.md` сессия устанавливается в соединении через `session/new` или `session/load`, и после этого клиент шлёт `session/prompt`. Работу с сессией, которую соединение не устанавливало, ACP не описывает. Ответ «не найдена в этом соединении» не вводит новой семантики.

### D5. Сборка хоста под `--local-exec`

`AgentHost.build` вводит признак `localExec` и строит из него одно правило «сторона агента»: `agentSide = stdio || localExec`. Все сужения, которые сейчас зависят от `stdio` по причине «клиент может быть на другой машине», переходят на `agentSide`:

| Что | `--stdio` | `--ws` | `--ws --local-exec` | `--stdio --local-exec` |
|---|---|---|---|---|
| `AcpServerConfig.localEnv` | — | — | `(cwd) => LocalExecutionEnv(cwd: cwd)` | то же |
| `AcpServerConfig.localListing` | `LocalExecutionEnv` | — | — (листинг даёт `localEnv`) | — |
| `AcpServerConfig.workspaceRoots` | — | — | корни D2 | корни D2 |
| `fileListing` | on | off | on | on |
| `mcp` (`stdio`, `http`) | on | off | on | on |
| `projectFiles`, `skillFiles` (`ProjectFilesLoader`) | да | нет, `project_files.skipped` | да | да |
| `hostFiles` (корни навыков только для чтения) | да | нет | да | да |
| `projectConfig` (папка сессии) | да | нет | да | да |
| `configCommand` (`/config`) | да | нет | нет | да |
| `execOnHost` сессии | нет | нет | да (ветка `localEnv`) | да |

- `/config` по WebSocket остаётся выключенной. Для цели она не нужна, а её ответ несёт пути и тексты проблем машины агента (R0-3). Включить её — отдельное решение.
- Фабрика `localEnv` без побочных эффектов (требование agent-acp-server «Локальное окружение сессии от хоста»): `LocalExecutionEnv(cwd:)` не трогает ФС в конструкторе, как во встроенном агенте.
- Пути защиты конфигурации (PERM-11, `agentConfigPaths`) хост передаёт уже сейчас. В режиме `--local-exec` это главная защита от правки `$CODELAB_HOME` машины агента моделью. `agentConfigPaths` строится от корня запуска (`agent_host.dart`, `agentConfigPathsFor`). `.codelab/config.yaml`, `config.local.yaml`, `agents/`, `prompts/`, `skills/` папки сессии защищает список §7.6.1, который рантайм разрешает от `cwd` каждой сессии (agent-permissions «Критические пути правок конфигурации агента»: «защита действует для сессии с любым `cwd`»). Поэтому включение `projectConfig` по WebSocket новой дыры не открывает. Тест задачи 6.1 это закрепляет.
- Навыки. Спецификация `agent-skills` («Навыки в хостах») сейчас запрещает `skillFiles` и `hostFiles` по `--ws`. Дельта change переписывает её как MODIFIED: исключение для `--local-exec` и сценарий. С `execOnHost` команда `exec` с `cwd` в каталоге навыка (`$CODELAB_HOME/skills/…`, `~/.agents/skills/…`) идёт вне корней `--workspace-root`, как во встроенном агенте. Корни навыков доступны только для чтения файловыми инструментами, но команда в них — обычная команда оболочки. Это описывается в `execution-sides.md` и `operations.md` (задача 9).
- Ядро не меняется: `buildAgentCore` уже умеет всё это для встроенных профилей.

Отвергнуто: новое состояние capability (`shellExec: local` уже есть); отдельный класс хоста для удалённого режима (дублирование `AgentHost.build`).

### D6. Возможности клиента и `initialize`

Как во встроенном агенте (change `add-embedded-agent-mode`, D4): объявленные клиентом `fs.readTextFile`, `fs.writeTextFile` и `terminal` разрешают агенту звать эти методы, но не обязывают (`09-File System.md`, `10-Terminal.md`). При `localEnv` агент их не зовёт. Клиент без `fs` и `terminal` получает рабочие `read` и `exec`.

`initialize` не меняется. `mcpCapabilities.http` по существующему правилу берётся из плана ядра (`_mcpHttp`). По `--ws --local-exec` capability `mcp` не выключена, поэтому объявляется `http: true`, как у `--stdio`. Это прежнее правило на новом входе, а не новое поле. `_meta.codelab` не расширяется: клиенту режим знать не нужно, он видит те же кадры, что от встроенного агента.

### D7. Разрешения и разрыв соединения

- Вопрос остаётся у клиента: `AcpPermissionGate` → `session/request_permission` с `toolCallId` вызова (PERM-4). Решение «спрашивать ли» — `PermissionPolicy` ядра. Headless-клиент (`codelab -p --approve …`) отвечает по своей политике, как сейчас.
- `detachGrace` остаётся `Duration.zero`. Разрыв переводит сессию в `detached`, ход отменяется, ожидающие вопросы завершаются `cancelled`. `exec` получает отмену, и `LocalExecutionEnv` завершает дерево процессов не позже 5 с (ENV-5). Без клиента команды на машине агента не продолжаются. Клиент CodeLab уже помечает прерванный ход после `session/load` (change `cancel-turn-on-ws-disconnect`, D2), это совпадает с правдой и здесь.
- `waitForReconnect` моста при нулевом grace не ждёт. Возобновление хода с повтором вопроса на новом соединении — отдельный change: он меняет и клиента (D2 того change).

Отвергнуто: `detachGrace` 30 с под `--local-exec`. Ход шёл бы без наблюдателя (в `bypass` — без вопросов), а клиент ошибочно пометил бы его прерванным.

### D8. Окружение команд

`LocalExecutionEnv.exec`: `/bin/sh -c` (`cmd.exe /d /s /c` на Windows), `includeParentEnvironment: false`, только базовый набор ENV-6 (`PATH`, `HOME`, `USER`, `LANG`, `LC_ALL`, `TMPDIR`, `SHELL`, `TERM=dumb`, `PAGER=cat`, `GIT_PAGER=cat`, `GIT_TERMINAL_PROMPT=0`), кольцевой буфер вывода, завершение дерева по таймауту и отмене. Таймаут — аргумент `timeout` инструмента `exec` (по умолчанию 120 с, максимум 3600 с), как во встроенном агенте. Секреты процесса агента (`CODELAB_SECRET_*`, ключи провайдеров) командам не передаются.

`exec.shell`, `exec.default_timeout`, `exec.max_timeout`, `exec.env`, `exec.secrets` в этом change не применяются. Они меняют поведение всех хостов с локальным исполнением, и встроенного агента тоже. Их место — отдельный change, ключи остаются с `config.key.not_applied`.

### D9. Что видит модель и клиент

**Модель.**
- Появляются `ls`, `search`, инструменты MCP, секция `project_context`, каталог навыков и инструмент `skill`.
- Платформа в промпте (`Platform.operatingSystem` процесса агента) теперь совпадает с машиной, где идут команды. Сейчас по WebSocket она расходится: процесс агента на одной ОС, а `terminal/*` у клиента на другой.
- Новых текстов промпта нет: для модели это просто машина, на которой она работает.

**Клиент.** Кадры такие же, как у встроенного агента:
- `tool_call` с `locations` и `diff`: старое содержимое `present` читает из `localEnv`;
- вывод команды приходит чанками `ToolCallProgress` с `TextContent`, то есть `tool_call_update.content` с текстом, а не `{type: "terminal"}`;
- `terminal/*` и `fs/*` нет.

Это desktop, REPL и TUI `codelab` уже показывают во встроенном режиме (профили `embedded-*` по умолчанию). Код клиентов не меняется. Пути в карточках относятся к машине агента. При совпадающих путях (D2) это незаметно. Иначе ссылки «открыть файл» в desktop ведут в локальное дерево, в другое содержимое (риск R4, Q2).

## Risks / Trade-offs

- **R1. Токен WebSocket = оболочка на машине агента.** Владелец токена может переключить режим сессии на `bypass` (`session/set_mode`) и запускать команды без вопросов, а `exec` ограничен только `cwd`. → Флаг явный. Только loopback (D3). Предупреждение `serve.local_exec`. В `operations.md` прямо сказано, что такой токен равен SSH-доступу пользователя процесса агента. Пол режима разрешений, заданный оператором, — возможный отдельный change.
- **R2. MCP-серверы клиента запускаются на машине агента** (Q3). Описание stdio-сервера из `session/new` становится процессом на машине агента без вопроса о разрешении: так ведёт себя и `--stdio`. Команда клиента может не существовать у агента (`mcp.server.failed`, сессия живёт). В `env` сервера клиент может передать свои секреты удалённой машине. → Документировано. Альтернатива — вариант (б) Q3.
- **R3a. TOCTOU между `_checkCwd` и сборкой сессии.** Между проверкой и `_canonicalCwd` рантайма каталог на пути `cwd` можно подменить ссылкой наружу, и `BoundedEnv` получит корень вне `--workspace-root`. `BoundedEnv` второй линией по корням не служит: он ограничивает файловые операции корнем сессии, каким бы тот ни раскрылся, а о корнях оператора не знает. Подменить каталог внутри корня может только тот, кто уже пишет в ФС машины агента. Держатель токена делает это через `exec`, а `exec` и так не ограничен корнями (R1). Поэтому окно новой возможности не даёт. Закрыть его до конца можно передачей раскрытого `cwd` в сессию, но тогда изменятся пути в карточках и журнале. Это не делается.
- **R3. Гонки.** Проверка `cwd` идёт до `reattach` и не разделяет атомарную пару «проверка занятости + `reattach`» (agent-acp-server «session/load и реплей»). Проверка владельца синхронна в обработчике, до любого `await`. Поздний `session/cancel` старого соединения после `session/load` нового отбрасывается проверкой владельца, а не отменяет ход нового владельца. Это исправление, а не регрессия. Разрыв во время `exec` → отмена → `LocalExecutionEnv` убивает дерево (ENV-5). Разрыв во время вопроса → `cancelled` (D7).
- **R4. Пути на двух машинах.** Пока клиент не умеет удалённую папку (Q2), режим полезен только при совпадающих путях. Desktop при расхождении показал бы локальное дерево с другим содержимым. Сессию с несуществующим у агента `cwd` агент не создаст (`-32602`), так что тихой порчи нет.
- **R5. Регистр букв и Windows.** `realpath` не приводит регистр, поэтому `/Users/Me/proj` при корне `/Users/me/proj` получит отказ. Ошибка в безопасную сторону. Признак ФС без учёта регистра у `agentConfigPaths` можно переиспользовать позже. На Windows сервер принимает `cwd` только POSIX-путём ядра (`_isAbsolute`: путь начинается с `/`; отступление записано в §13.15), то есть уже в виде `/c/proj`. Корни хост приводит к тому же виду `toCorePath`, так что `normalizePath` и `isInside` сравнивают однородные пути. Путь `C:\proj` от клиента отклоняется шагом 1, как сейчас.
- **R6. Корень `/` или `$HOME`.** Оператор может задать слишком широкий корень. Явный выбор не запрещается, `serve.local_exec` печатает корни.
- **R7. Forward compatibility ACP.** Новых полей нет. Клиент, который не знает `reason`, видит стандартные `-32602`/`-32002` с текстом. Неизвестные поля `data` клиенты CodeLab игнорируют.
- **R8. Web-безопасность.** `codelab_agent_acp` и `codelab_agent_core` остаются без `dart:io` (PKG-3, `web-compile`). Экспорт чистых функций пути её не меняет.
- **R9. Allowlist ядра (PKG-2).** Не меняется.

## Migration Plan

Новый флаг, умолчание прежнее. Конфигурации и профили клиентов не мигрируют. Ключ `exec.local_fallback` остаётся в схеме и по-прежнему даёт `config.key.not_applied`.

Правило владельца (D4) меняет ответ на запросы к чужой сессии для всех серверов. Клиенты CodeLab этого не замечают (D4, «Влияние»). Откат — удалением флага и проверки, данных не трогает.
