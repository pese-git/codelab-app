## Context

CodeLab порождает процессы ровно в одном месте сегодня: `StdioAcpTransport` запускает бинарник агента через `Process.start` со структурированным stdio (stdout парсится как ACP-протокол, stderr — как diagnostics stream). Это **не** интерактивный псевдотерминал — нет TTY, нет resize-семантики, нет job control. В проекте нет ни одной зависимости, связанной с терминальным рендерингом или PTY (`xterm`, `pty`, `ffi` — проверено, отсутствуют в `pubspec.yaml`).

Approval-safety модель CodeLab (`openspec/changes/define-codelab-mvp/specs/approval-safety/spec.md`) целиком построена вокруг того, что **агент** запрашивает разрешение на рискованные действия (`readOnly`/`localWrite`/`network`/`shell`/`destructive`). Интерактивный терминал — это действия **человека**, не агента: он структурно вне этой модели, и это нужно явно зафиксировать, а не оставить как неочевидный побочный эффект.

## Goals / Non-Goals

**Goals:**
- Интерактивный терминал (реальный shell, не просто pipe stdout/stderr) с несколькими вкладками, доступный из нижней панели workbench.
- Терминал стартует в cwd активного transport-профиля.
- Явные, задокументированные границы: вне approval-safety, вне `SecretRedactor`.
- Корректный lifecycle: процессы терминала убиваются при закрытии вкладки/панели/приложения.

**Non-Goals:**
- Полный паритет функциональности с системным терминалом (ligatures, продвинутые escape-последовательности, полная поддержка всех платформенных PTY-фич) — best-effort, не заявляется как "производственный терминал".
- Синхронизация `cd` внутри терминала с `stdioCwd` — сознательно однонаправленная связь (терминал берёт cwd при старте, не отдаёт обратно).
- Отправка вывода терминала агенту как context — не в этом MVP-объёме; естественное будущее расширение через уже существующий `ContentBlock`/Add Context механизм, но не требование этого change.
- Полный паритет Windows ConPTY vs POSIX pty — см. Risks.

## Decisions

- **Рендер терминала — пакет `xterm` (pub.dev, чистый Dart, ANSI-парсинг + виджет).** Не пишем свой ANSI-парсер — это отдельная большая задача с богатой поверхностью для багов (escape-последовательности, wide chars, scrollback), а `xterm` уже решает это и не тянет платформенно-зависимый native-код сам по себе.
- **PTY-бэкенд — отдельное решение, не включённое в этот design.md как окончательное.** Кандидаты: (a) community-пакет с FFI-биндингами к нативному PTY (macOS/Linux через `openpty`, Windows через ConPTY) — даёт наиболее полную интерактивность, но добавляет платформенно-зависимый native-код и разную зрелость на разных ОС; (b) fallback на `Process.start` без настоящего PTY (проще, без новых нативных зависимостей, но интерактивные полноэкранные программы вроде `vim`/`htop` будут работать некорректно — нет TTY). **Рекомендация**: начать с (b) для MVP (нулевая новая native-зависимость, покрывает 80% реальных сценариев — `git`, `melos`, `dart run`, скрипты), явно задокументировать ограничение ("full-screen interactive programs are not supported"), перейти к (a) отдельным change, если станет реальной проблемой в использовании.
- **Terminal-процессы не участвуют в approval-safety.** `AcpApprovalPanel`/permission modes применяются только к tool calls агента. Комментарий/пометка в UI терминала (например, в футере при первом открытии) должна явно сказать: "commands here run directly as you, not through the agent's approval flow" — предотвращает ложное чувство защищённости.
- **`SecretRedactor` не применяется к выводу терминала.** Он спроектирован для структурированных `DiagnosticEntry`/protocol payload, а не для произвольного текстового потока стороннего процесса. Явно не пытаемся "патчить" редактор под это — вместо этого предупреждение в UI при первом открытии панели.
- **cwd — снимок на момент создания вкладки**, не live-привязка к `stdioCwd`. Каждая новая вкладка терминала берёт текущее значение `state.stdioCwd` (или `WorkingDirectoryProvider.currentPath`, если stdio ещё не сконфигурирован) в момент создания, дальше живёт независимо.
- **Терминал — новая строка в layout workbench, не пятый слот `AcpWorkbenchLayout`.** Слот-система (`commandBar`/`sessionsPane`/`mainPane`/`inspectorPane`) остаётся неизменной; терминал — collapsible строка под существующим `Row`, управляемая отдельным ephemeral UI state (открыт/закрыт, активная вкладка) — не в `CodeLabShellState`, если не требуется переживать пересборку виджета (вероятно требуется для UX — тогда как минимум флаг "открыта ли панель" и список ID вкладок в state, а сам процесс/буфер вывода — presentation/infrastructure уровень, не state).

## Risks / Trade-offs

- [Секреты в выводе терминала (например, `cat .env`) видны без всякой защиты] → явное предупреждение в UI при первом открытии панели за сессию; не решается техническим редактированием вывода (ломало бы интерактивность).
- [PTY-паритет между Windows/macOS/Linux разный при выборе варианта (a) в будущем] → начинаем с варианта (b) (без native PTY) — работает одинаково на всех платформах, пусть и с меньшей интерактивностью.
- [Осиротевшие дочерние процессы при крэше/принудительном закрытии приложения] → `TerminalSession.dispose()` обязан убивать процесс; предусмотреть explicit kill в `WidgetsBindingObserver`/аналоге при закрытии приложения (см. `docs/architecture/concurrency.md`).
- [Пользователь может решить, что команды в терминале "безопасны", раз CodeLab в целом построен вокруг approval-safety] → явное предупреждение (см. Decisions) снимает эту путаницу, но полагается на то, что пользователь его прочитает — принимаем этот риск для MVP.
- [Новая внешняя зависимость (`xterm` + возможный PTY-пакет) увеличивает поверхность обновлений/уязвимостей] → `xterm` — популярный, поддерживаемый пакет; вариант (b) для PTY не требует новой native-зависимости вовсе, снижая риск на старте.

## Open Questions

- Точный выбор PTY-стратегии (вариант (a) vs (b) из Decisions) — (b) рекомендован для MVP, но финальное решение — за архитектурным ревью перед началом реализации `tasks.md` раздела 1.
- Нужно ли ограничивать terminal-панель каким-либо collapsed-by-default поведением при первом запуске приложения (сейчас предполагается: свёрнута по умолчанию) — подтвердить при реализации.
