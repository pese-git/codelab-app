## Context

§7 принятого документа ядра описывает политику разрешений целиком: контракт, таблицу `mode × tier`, алгоритм `decide`, шаблоны «разрешить всегда», лексер и критические шаблоны, поведение без gate, инварианты PERM-1…PERM-11.

Этот change реализует её в `codelab_agent_core` поверх цепочки `beforeToolCall` и единой точки исполнения из change `add-agent-core-loop-and-tools`. Ниже — только решения, которых в документе ядра нет:
- состав этапа 2;
- тексты для модели там, где документ даёт русскую формулировку;
- связь с хостом без конфигурации;
- итерации.

## Goals / Non-Goals

**Goals:**
- Ни один инструмент, зарегистрированный любым способом, не исполняется без решения политики (PERM-1).
- «Разрешить всегда» действует только на свой ключ `(tool, pattern)` (PERM-3, P-03).
- Критические команды спрашиваются даже в `bypass` и после `allow_always`, а в `autopilot` отклоняются (PERM-2, PERM-9, P-07).
- Отказ — данные для модели, ход продолжается (PERM-7).
- Без интерфейса одобрения «спросить» = отказ (PERM-5).

**Non-Goals:**
- `AcpPermissionGate` и проекция в `session/request_permission` (этап 4);
- конфигурация `permissions.*` и флаги запуска (этапы 4, 8);
- субагенты, `narrow`, хранение решений между сессиями, `prepare`-представления `lsp` (после MVP).

## Decisions

### D1. Раскладка

`lib/src/permissions/`:

| Файл | Содержимое |
|---|---|
| `gate.dart` | `PermissionGate`, `PermissionRequest`, `PermissionDecision` |
| `modes.dart` | `PermissionMode`, `ToolPolicy`, `ModeId`, таблица `mode × tier`, отображение `ModeId → PermissionMode` |
| `pattern.dart` | `PermissionKey`, `PermissionDecisionStore` |
| `policy.dart` | `PolicyRules`, `PolicyOutcome`, `PermissionPolicy` |
| `shell_lexer.dart` | лексер команд |
| `critical_patterns.dart` | критические шаблоны и `findCritical` |

`permissionPattern` реализуют сами инструменты (`AgentTool`, §6.2). Таблица §7.5 переносится в их реализации, а тест шаблонов лежит здесь.

### D2. `ModeId` этапа 2

`ModeId` — extension type над `String` с константами `plan`, `ask`, `standard`, `acceptEdits` (`accept-edits`) и `bypass`. Отображение на `PermissionMode` — по таблице §13.6 документа ядра.

У режима `plan` есть запрет на уровни `write` и `exec`. Он проверяется вторым правилом алгоритма (рядом с «запретом на ход») с причиной `plan mode: changes are not allowed`. Документ ядра (§13.6) даёт эту причину по-русски, но текст уходит модели, а тексты для модели в ядре английские (§11.7). Документ ядра правится в той же итерации.

Синонимы на входе (`architect`, `debug`, `code`, `acceptEdits`) нормализует ACP-адаптер этапа 4. `ModeId.parse` этапа 2 принимает только основные id, остальное — `ArgumentError`.

### D3. `autopilot` без конфигурации

`autopilot` не входит в `ModeId` и в этапе 2 включается только явно. Хост передаёт в `CoreConfig.permissions` поле `modeOverride: PermissionMode?`. Оно перекрывает отображение режима сессии и в этапе 4 будет заполняться флагом `--permission-mode autopilot` (§10.5). `setMode` при заданном `modeOverride` меняет `ModeId` сессии и событие `ModeChanged`, но эффективный `PermissionMode` остаётся переопределённым.

### D4. Ожидание gate и бюджет хода

`ask()` измеряет длительность `PermissionGate.request` по `Clock` хоста и добавляет её в `ToolServices.approvalWait` (design.md change `add-agent-core-loop-and-tools`, D6). Отмена токена хода во время ожидания даёт решение `cancelled`, поздний ответ gate игнорируется (PERM-4).

### D5. Наблюдаемость

Записи `Logger`:
- `permission.asked` (debug: `toolCallId`, `tool`, `tier`, `critical`);
- `permission.decided` (debug: `toolCallId`, `decision`);
- `permission.denied` (info: `toolCallId`, `tool`, `reason`).

Значения аргументов в лог не попадают: команда `exec` может содержать секрет, а редактор секретов появляется на этапе 3 (`AGENTS.md` §16).

### D6. Лексер — свой код без сторонних пакетов

Разбор §7.6 написан вручную в `shell_lexer.dart`: allowlist PKG-2 не меняется, а нужное подмножество (сегменты, вложенные подстановки, `sh -c`, here-document, лаунчеры, перенаправления) не совпадает ни с одним готовым парсером shell. Таблица критических шаблонов и регулярное выражение fork-бомбы взяты из §7.6. Они написаны для CodeLab и не копируются из стороннего кода (`AGENTS.md` §5). Ошибка разбора и глубина больше 4 дают шаблон `unparsable command`: лучше спросить, чем пропустить.

### D7. Итерации

| Итерация | Содержание | PR |
|---|---|---|
| 1 | режимы и уровни, `ModeId`, gate, `decide` без критических шаблонов, ключ «всегда» и шаблоны §7.5, headless, grants на ход | вместе с итерацией 2 change `add-agent-core-loop-and-tools` |
| 2 | лексер, критические шаблоны, критические пути правок §7.6.1 | вместе с итерацией 4 того change |

Шаг 3 алгоритма `decide` (критический шаблон) в итерации 1 объявлен, но `findCritical` возвращает `null`. Итерация 2 подключает настоящую функцию без изменения сигнатуры `decide`.

## Risks / Trade-offs

- **[Ложные срабатывания критических шаблонов]** → цена ложного срабатывания — один лишний вопрос (§7.10). Таблица «Срабатывает / Не срабатывает» §7.6 — табличный тест, включая `git commit -m "rm -rf /"` и `echo sudo`.
- **[Пропуск разрушительной команды формой, которую лексер не разбирает]** → незакрытая кавычка, глубина больше 4 и неизвестная конструкция дают `unparsable command` и вопрос. Граница рабочей папки (`BoundedEnv`) остаётся отдельным рубежом для путей инструментов. Содержимое команды он не ограничивает, это зона политики (§4.4, шаг 7).
- **[Текст причины plan-режима отличается от документа ядра]** → D2. Документ ядра правится в той же итерации.
- **[Расхождение двух change этапа 2]** → сквозной сценарий 2.10 и `policy_is_first_hook_test.dart` проверяют их вместе; итерации сливаются общим PR (D7).
