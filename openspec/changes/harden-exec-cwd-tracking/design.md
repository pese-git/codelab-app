## Context

### Угроза

Модель — недоверенный автор команд: её может вести prompt injection из файла, страницы или вывода инструмента. PERM-11 не даёт ей править конфигурацию агента без человека:
- проектный `.codelab/**`;
- пути хоста `$CODELAB_HOME`, `~/.codelab`;
- корни навыков `.codelab/skills/**`, `.agents/skills/**`.

Правка навыка или `config.yaml` действует со следующего шага и может ослабить разрешения или подменить инструкции (Q9, Q16, Q30 change `add-agent-skills`). Для `exec` защита опирается на текстовый разбор. Если разбор уверенно считает каталогом `/tmp`, а оболочка стоит в каталоге навыка, `touch SKILL.md` проходит без вопроса даже в `autopilot`.

### Как было до change (сверено с `develop`, `cdd41d00`)

Ветка change после перебазирования стоит на `develop` `8277295c`. Там уже есть итерация 2 change `add-agent-skills`: исключения E1–E3, разрешённый список Q47 и разбор опций `sh -c`. Стыковка с ними описана в D11, отступления реализации от первой редакции этого design — в D2, D6, D8–D11 и в разделе «Risks / Trade-offs».

- `parseShell` (`shell_lexer.dart`) даёт плоское дерево: `ShellScript.pipelines` — список конвейеров. Связки `&&`, `||`, `;`, `&` и перевод строки одинаково вызывают `endPipeline()`, и после разбора их не различить. Скобки `( … )` и `{ … }` тоже уплощаются: подоболочка и группа неотличимы от последовательности. Зарезервированные слова остаются словами (`then cd x` → команда `then`). Снятые лаунчеры не сохраняются, кроме `privileged`, `launcherDir`, `launcherOutputs`. Вложенный текст (`segment.nested`) не помечает, откуда взят.
- `_walk` (`critical_patterns.dart`) держит одну строку `current`. Сдвигает её только `cd` и `pushd` через `ConfigCheck.cdTarget`. Неизвестная цель оставляет прежний каталог (`?? current`). Вложенные тексты обходятся с копией.
- `ConfigCheck.cdTarget` (`agent_config_rules.dart`) отбрасывает любые слова на `-` (так теряется `cd -`). Без аргумента берёт `HOME`, с переменной даёт `null`.
- Исполнитель — новый `/bin/sh -c <command>` на каждый вызов: `LocalExecutionEnv` (`codelab_agent_io`) с окружением из allowlist (`PATH`, `HOME`, `USER`, `LANG`, `LC_ALL`, `TMPDIR`, `SHELL`) и `AcpClientEnv` (`codelab_agent_acp`, `terminal/create` с `command: '/bin/sh'`). Терминал клиента CodeLab (`terminal_process_runner.dart`) наследует **всё** окружение клиента. Сторонний клиент ACP — как решит сам.

Проверка на `develop` (временный скрипт вне репозитория, `findCritical(cmd, cwd: '/w')`) дала `null` для всех примеров 1–11 из proposal и для `if true; then rm -rf /; fi`, `while true; do rm -rf /; done`, `! rm -rf /`, `trap 'rm -rf /' EXIT`.

### Расхождения документов с кодом

- В `07-permissions.md` §7.6.1 у E2 сказано, что «`cd`, `pushd` и `popd` меняют рабочий каталог последующих команд». В коде `popd` не обрабатывался. Исправляет этот change (D3); строка E2 теперь ссылается на §7.6.2.
- В doc-комментарии `_walk` было сказано, что «ошибка в оценке `cd` (неизвестная переменная) каталог не меняет». Это и есть пробел 5. `_walk` заменён обходом `ExecDirWalk` (`exec_dir_walk.dart`, D14).

## Не входит

Возможные уточнения, если ложные срабатывания будут мешать. Сейчас они дают лишний вопрос, а не пропуск:
- `exit`: `cd X || exit 1; make` проверяет `make` и в прежнем каталоге (D12);
- ветви `then`/`else` как `&&`/`||` от условия (D6);
- значение `CDPATH` как список кандидатов (D5).

Точка расширения — переходы `dirCommandFlow` (`shell_dir_state.dart`) и разбор блока `_block` (`exec_dir_walk.dart`). Лексер уже даёт для них всё нужное: связки, отрицание и тело блока `if` (D2, D6).

## Goals / Non-Goals

**Goals:**
- Закрыть пробелы 1–11 proposal без ложной уверенности: каталог, в котором разбор не уверен, учитывается консервативно.
- Не делать критичной обычную работу: `cd sub && make`, `cd sub; make`, `pushd a; popd; make`, чтение в любом каталоге.
- Починить зарезервированные слова и `trap` для всей таблицы §7.6: модели каталога нужен тот же разбор.
- Дать человеку понятную причину вопроса.

**Non-Goals:**
- Интерпретатор shell. Значения переменных, `case`, арифметика, `source`.
- Переменная вместо пути и переприсваивание `HOME`/`CODELAB_HOME` — известные пределы (D12).
- Исключения навыков E1–E3 — только правило стыковки (D11).

## Decisions

### D1. Состояние — множество вариантов с «неизвестно»

Вариант — `(каталог, OLDPWD, стек)`. `OLDPWD` — известный абсолютный путь или «неизвестен». Стек — список абсолютных путей. Множество вариантов может содержать ещё вариант «неизвестно» (⊤): любой каталог, любой стек.

Начальное состояние строки: `{(cwd вызова, OLDPWD неизвестен, [])}`. Стек пуст, потому что каждый `exec` — новый `/bin/sh -c`, а bash и dash стек из окружения не берут. `OLDPWD` неизвестен: окружение клиента ACP его передаёт.

Сегмент проверяется существующими предикатами (`touchesConfig`, `writesViaBroadDirectory`, `replacesConfigAncestor`, `hardLinksConfig`, проверки целей записи) для каждого известного каталога. Правило ⊤ — D9. Предел — 32 известных варианта; сверх него множество схлопывается в `{⊤}`. Так время разбора остаётся ограниченным (`pushd` с `;` даёт 2ⁿ стеков). Одной команде с ≤ 32 вариантами и глубиной вложения ≤ 4 хватает существующей стоимости предикатов.

Альтернативы:
- **(а) Одна строка, а при сомнении — «неизвестно».** Отклонена. Неудачный `cd` (пример 6) и стадия конвейера дают ровно два известных варианта. Схлопывание в ⊤ сделало бы критичными `cd sub; make` и любую команду после `cd X;`.
- **(б) Только каталог, без `OLDPWD` и стека.** Отклонена. Тогда `cd -` и `popd` всегда давали бы ⊤, а пример «`pushd a; popd; make` не критичен» стал бы ложным срабатыванием.
- **(в) Полный перебор без предела.** Отклонена: экспоненциальный рост на строке из модели. Встроенный агент работает в UI-изоляте desktop (`07-permissions.md`, известная проблема `forkBomb`).

### D2. Связки `&&`, `||`, `;`, `!` и неудачная смена каталога

Лексер строит рядом с плоскими `ShellScript.pipelines` дерево `ShellScript.commands`. Его узел `ShellCommand` — конвейер: стадии `ShellStage`, связка со следующим `next` (`ShellConnector`: `sequence` для `;`, перевода строки и конца блока, `and`, `or`, `background`) и отрицание `negated` (`!`). Плоские конвейеры остаются для правил таблицы §7.6 (`curl … | sh`) и существующих тестов. Оба вида строятся из одних событий разбора и делят одни объекты `ShellSegment`, поэтому не расходятся. Поля `ShellPipeline.next` и `ShellPipeline.negated` из первой редакции не вводились: плоский конвейер теряет блоки, и связку пришлось бы восстанавливать заново. Обход (`ExecDirWalk._commands`) ведёт два множества: варианты после успеха и после неуспеха (`DirFlow`).
- Встроенная смена каталога — `cd`, `pushd`, `popd` одной стадией, без лаунчера или под `command`/`builtin`. Успех означает новый каталог, неуспех — неизменное состояние.
- Об успехе прочих команд обход ничего не знает: оба исхода из входных вариантов.
- `A && B`: `B` идёт из успеха `A`. Итог: успех — успех `B`, неуспех — неуспех `A` ∪ неуспех `B`.
- `A || B` — зеркально.
- `;`, перевод строки, конец блока объединяют успех и неуспех.
- `&` уводит в фон весь and-or список, а не последний конвейер: `A && B &` — это `{ A && B; } &` (POSIX, «Asynchronous Lists»). Состояние после `&` — как до начала списка (D16, B2).

Так `cd X && touch f` проверяет только `X`, а `cd X; touch f` — `X` и прежний каталог (пример 6). `cd build && cd - && make` идёт точно. `pushd` в dash не существует (команда не найдена): это неуспех, и модель покрывает его без отдельного правила.

Альтернативы:
- **(а) Всегда объединять.** Лексер не трогается. Отклонена: ложное срабатывание на `cd /tmp && make`, когда `cwd` вызова — каталог конфигурации или навыка (E2 разрешает чтение там, и агент оттуда уходит). `cd X && cd - && make` давал бы ⊤ через ветку неуспеха.
- **(б) Проверять существование цели `cd` через `PathResolver`** (второй проход уже знает `_existing`) и считать `cd` в существующий каталог успешным. Отклонена: та же строка может удалить каталог или снять права до `cd` (`rm -rf b; cd b`, `chmod 000 b`). Это TOCTOU внутри строки, которым управляет модель.

### D3. `cd`, `pushd`, `popd`, `dirs`

- Опции `-L`, `-P`, `-e`, `-@` пропускаются, `--` завершает опции. Неизвестная опция при успехе даёт ⊤: оболочки расходятся.
- `-` — `OLDPWD` варианта: известный даёт точный каталог, неизвестный — ⊤.
- Без аргумента — `HOME` из `expansions`, без него — ⊤.
- Успех любой из трёх команд записывает прежний каталог в `OLDPWD`.
- `pushd DIR`: успех — каталог `DIR`, прежний — на вершину стека.
- `pushd` без аргумента: каталог ↔ вершина стека; пустой стек — неуспех (bash: `no other directory`).
- `popd`: каталог ← вершина, вершина снимается; пустой стек — неуспех (bash: `directory stack empty`; в dash команды нет). Это точный ответ, а не ⊤: начальный стек известен (D1). Рекомендация «popd с пустым стеком → неизвестно» отклонена как ложное срабатывание без выигрыша в безопасности.
- `pushd ±N`, `popd ±N` дают ⊤ в каталоге. `dirs` с опциями (`-c`, `+N`) даёт ⊤ в стеке. Это редкие формы, и точное вращение стека не стоит кода.
- `cd -P`/`pushd -P` с компонентой `..`, а также `set -P`/`set -o physical` в строке и `..` в цели дают ⊤. Физический `..` идёт от цели ссылки, а нормализация лексическая. Логический `cd` (по умолчанию) нормализуется лексически, кроме `..` после обычной компоненты (`cd sub/../b`): она даёт ⊤ (D17, A5). Ведущие `..` (`cd ../b`) точны. Ссылки в цели раскрывает второй проход (`canonicalizeSeen`): проверенный путь `<ссылка>/SKILL.md` канонизируется, как сейчас.

### D4. Источники «неизвестно»

Успешная смена каталога даёт ⊤, если в цели:
- переменная, кроме `HOME`/`CODELAB_HOME` из `expansions` (`ConfigCheck._absolute` вернул `null`);
- подстановка;
- `~user`.

Также ⊤ дают:
- `cd -` без известного `OLDPWD`;
- `CDPATH` или `OLDPWD`, упомянутые в строке (D5);
- формы D3;
- `launcherDir` (`env -C`, `sudo -D`) с такой целью — для одной простой команды.

Неуспех оставляет прежнее, поэтому `cd "$X"; make` даёт `{прежний, ⊤}`.

Ещё ⊤ дают динамическая команда и `eval` с нелитеральным текстом (D16, H4), `enable`, `DIRSTACK`, `cdable_vars` в строке (D16, H6), `trap` с действием (D16, H3).

Блоки и вложенные тексты — D6–D8.

### D5. `CDPATH` и `OLDPWD`: в строке — «неизвестно», из окружения — предел

**В строке.** Признак — подстрока `CDPATH` (или `OLDPWD`) в исходной строке команды или в любом слове разбора после снятия кавычек и раскрытия `$'…'`. Признак `CDPATH` делает ⊤ относительную цель `cd`/`pushd` без `./`, `../` и не равную `.`/`..`. POSIX не применяет `CDPATH` к таким целям и к абсолютным. Признак `OLDPWD` делает ⊤ `cd -`.

Подстрока, а не разбор присваиваний, выбрана сознательно. Она ловит все формы:
- префикс `CDPATH=… cd`;
- присваивание `CDPATH=…;`;
- `export`, `declare`, `typeset`, `readonly`, `local`;
- `read CDPATH`, `printf -v CDPATH`, `: ${CDPATH:=…}`;
- `eval`, `sh -c`.

Ложное срабатывание (`echo $CDPATH; cd sub && make`) стоит одного вопроса и на практике не встречается.

Значение `CDPATH` можно было бы разобрать точно, как список кандидатов. Отклонено: законного применения в однострочной команде агента нет, а код и спецификация росли бы.

**Из окружения исполнителя** — известный предел. `LocalExecutionEnv` не передаёт `CDPATH` (allowlist окружения хоста). Терминал клиента ACP наследует окружение клиента, где пользователь мог экспортировать `CDPATH`. Модель задать его не может. Обход требует, чтобы запись `CDPATH` пользователя указывала внутрь каталога конфигурации (`CDPATH=~/.codelab/skills`). Типичные значения (`.:~:~/projects`) дают кандидатов, которые и так критичны, если цель называет каталог конфигурации.

Альтернатива — fail closed: любая относительная цель без `./` — это `{разрешённый путь} ∪ ⊤`. Тогда `cd sub && make` и любая команда не из белого списка после `cd sub` становятся критическими. Это главный сценарий работы агента, а в `autopilot` — отказ. Отклонена, вынесена в вопрос Q1.

`OLDPWD` из окружения покрыт без предела: `cd -` без известного `OLDPWD` строки уже даёт ⊤.

Подстрока не видит имя, собранное при исполнении: признаки ставятся также при `eval` с нелитеральным текстом и при записи переменной с динамическим именем (D16, H5).

### D6. Блоки: подоболочка, группа, конвейер, фон, `if`, цикл, функция, `alias`

Блок — стадия дерева `ShellScript.commands` (D2): `ShellBlock(kind, body)` рядом с простой командой `ShellSimple(segment)` в sealed-иерархии `ShellStage`. Вид — `ShellBlockKind`: `subshell`, `group`, `conditional`, `loop`, `function`. Тело `body` — список `ShellCommand` со своими связками. Перенаправления после закрывающего слова хранятся у блока (`ShellBlock.redirections`, D10). `{ a; } | c` — конвейер из двух стадий, блока и простой команды, поэтому связь `}` с `|` не теряется. Стек открытых блоков (`_Frame`) живёт только в построителе лексера, у сегмента его нет.

Отступление от первой редакции: там предлагался стек объемлющих блоков у сегмента, а вход и выход обход восстанавливал бы по смене стека между соседними сегментами. Отклонено при реализации: обход по дереву рекурсивен и проще, а sealed-стадия заставляет обход разобрать оба вида (новый вид без ветки — ошибка компиляции, а не пропуск проверки).

| Конструкция | Состояние после | Почему |
|---|---|---|
| `( … )` | как до блока | подоболочка (точно) |
| and-or список с `&` (`A && B &`, `cd X; cd /tmp && true &`) | как до начала списка | фоновое задание — подоболочка для всего списка, не только для последнего конвейера (точно; D16, B2) |
| стадия конвейера из ≥ 2 стадий, в том числе блок | объединение до и после | bash и dash исполняют стадии в подоболочках, zsh и `lastpipe` — последнюю в текущей; объединение верно для обоих |
| `{ … }` вне конвейера | как в конце блока | текущая оболочка (точно) |
| `if … fi` | объединение до блока и в конце | ветки могут не выполниться; `then` и `else` последовательно проходят одно множество (надмножество) |
| цикл | тело обходится один раз; если состояние после него отличается от входа, тело обходится повторно от «вход ∪ конец ∪ ⊤»; после — «вход ∪ конец» | повтор относительного `cd` не перечислить; тело может не выполниться; признак берётся из потока, а не из имён команд (D17, A1) |
| тело функции | копия с ⊤; наружу не выходит | тело выполнится при вызове, в неизвестном состоянии |
| после определения функции, `alias` или `trap` с непустым действием | до конца строки добавляется ⊤ | любая команда может быть вызовом; `alias` в dash раскрывается на следующей строке; действие `trap` исполнится позже в той же оболочке (D16, H3) |
| `case … esac` | `unparsable command` (как сейчас: `)` ветки) | — |

Альтернатива для циклов — итерация до неподвижной точки с пределом. Точнее для абсолютных целей, но сложнее. Отклонена: циклы со сменой каталога в однострочниках агента редки, а ⊤ безопасен.

Альтернатива для `if` — понимать `then` как `&&` от условия, `else` как `||`. Отклонена ради простоты. Возможное уточнение, если `if cd X; then …` в каталоге конфигурации будет мешать (раздел «Не входит»).

**Блоки и E1 навыков (Q47).** Пока лексер не знал блоков, слова `{`, `}`, `if`, `do` и другие были сегментами-командами. Разрешённый список Q47 (§7.6.1, E1(4)) их не содержит, поэтому они отключали E1 для следующих сегментов. Теперь эти слова в дерево не попадают. Обход сам ставит признак «E1 отключён» (`ConfigCheck.environmentAssigned`) на входе в группу `{ … }`, `if … fi`, цикл и на `!`. Поэтому `{ python3 <скрипт>; }` и `{ cat /dev/null; }; python3 <скрипт>` критичны. Подоболочка `( … )` признак не ставит: скобки — операторы, а не зарезервированные слова, и Q47 их не перечисляет. Изменения окружения внутри подоболочки наружу не выходят, поэтому `(cat /dev/null); python3 <скрипт>` остаётся под E1. Тело функции E1 не нужно: определение функции и так отключает E1 (признак по тексту строки в `findCritical`).

### D7. Лаунчеры

Лексер сохраняет имена снятых лаунчеров (`ShellSegment.launchers`).
- `command` и `builtin` — встроенный `cd`, как без лаунчера. `command -v`/`command -V` ничего не исполняют, каталог не меняется (D16, H2).
- `time` — ключевое слово bash и внешняя программа в dash. Даёт объединение прежнего и нового без сужения по `&&`/`||`.
- `env`, `sudo`, `doas`, `nohup`, `nice`, `timeout`, `stdbuf`, `xargs`, `exec` запускают внешнюю программу. Она каталог оболочки не меняет: на macOS `/usr/bin/cd` — скрипт-пустышка с кодом 0, на Linux его обычно нет. Состояние не меняется ни при успехе, ни при неуспехе. Это точно: внешний процесс не может сменить каталог родителя.

### D8. Вложенные тексты

Лексер помечает происхождение вложенного текста полем `ShellScript.origin` (`ShellOrigin`: `root`, `substitution`, `command`, `eval`, `foreign`).

| Происхождение | Состояние вложенного обхода | После |
|---|---|---|
| `substitution`: `$( … )`, `` ` … ` ``, `<( … )`, `>( … )` | копия всех вариантов | без изменений (подоболочка) |
| `command`: `sh -c`/`bash -c`/…, `env -S`, `watch`, `script -c`, `find -exec`/`-ok`, `rg --pre` | копия каталогов (с учётом `env -C`/`sudo -D`), пустой стек, `OLDPWD` неизвестен | без изменений (новый процесс) |
| `eval` без внешнего лаунчера | продолжение текущего состояния | изменения действуют дальше (текущая оболочка) |
| `eval` под внешним лаунчером (`env eval …`) | как `command` | без изменений |
| `foreign`: `git -c …` (в том числе `alias.*=!…`), `--config-env`, переменные-команды (`GIT_PAGER`, `PAGER`, `GIT_EXTERNAL_DIFF`, `GIT_EDITOR`, `EDITOR`, `VISUAL`, `GIT_SEQUENCE_EDITOR`, `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_ASKPASS`, `SSH_ASKPASS`, `LESSOPEN`, `LESSCLOSE`), `find -execdir`/`-okdir`, `trap` | известные варианты как у `command` **∪ ⊤** | без изменений |

Отступление от первой редакции: у `foreign` было `{⊤}`. Реализация оставляет известные варианты и добавляет к ним ⊤. Проверка не слабее: правило ⊤ (D9) действует так же. Зато когда git или `find -execdir` идёт из `cwd` в каталоге конфигурации, человек видит знакомую метку `write to agent configuration`, а не только `write in unknown working directory` (`git -c alias.x='!touch SKILL.md' x` в каталоге навыка).

**Переменная-команда в объявлении.** `export`, `declare`, `typeset`, `readonly`, `local` сами ничего не исполняют. Значение переменной-команды из объявления (`export EDITOR=vim`) обход откладывает и проверяет на первом следующем сегменте, который не объявление, кем бы тот ни был. Варианты — «известные ∪ ⊤» этого сегмента, как у `foreign`. Это консервативно: срабатывание наступает раньше настоящего потребителя (`export EDITOR=vim; ls; git commit` спросит уже на `ls`). Если следующего сегмента нет, проверки нет: каждый `exec` — новый `sh -c`, и значение никому не достанется. Признак «E1 отключён» ставится на самом объявлении, как прежде (Q47). Префиксное присваивание (`EDITOR=vim git commit`) проверяется сразу у своего сегмента. Поэтому:
- не критичны `export EDITOR=vim`, `readonly EDITOR=vim`, `local EDITOR=vim`, `export EDITOR=vim GIT_PAGER=less`, `export EDITOR=true; git commit`;
- критичны с меткой `write in unknown working directory` `export EDITOR=vim; git commit`, `export EDITOR=vim && git commit`, `declare -x GIT_EDITOR=vim; git rebase --continue`.

Альтернатива — проверять значение на самом объявлении. Отклонена: тогда `export EDITOR=vim` в одиночку критичен, хотя ничего не исполняет. Альтернатива — искать настоящего потребителя (`git`, `less`). Отклонена: список программ, читающих эти переменные, неполон по построению, а первый следующий сегмент — безопасная сторона.

Почему ⊤ у строки `foreign`:
- git запускает алиасы `!…` и, после `setup_git_directory`, пейджер и редактор из корня рабочего дерева, а он может быть выше `cwd` (например, `~/.codelab`, если пользователь держит его в git);
- `-execdir` идёт в каждом каталоге, найденном `find`, в том числе в `.codelab/skills/*` под корнем;
- `trap` исполняется позже, в неизвестном состоянии.

Альтернатива — копия каталога для git. Отклонена: пример `git -c alias.x='!touch SKILL.md' x` в подкаталоге каталога навыка-репозитория пишет в навык.

Цена — `git -c core.pager=delta log`, `EDITOR=vim git commit` и `LESSOPEN="|lesspipe %s" less x` становятся критическими: `delta`, `vim`, `lesspipe` не из белого списка чтения. Пейджер и редактор обычно задают в `~/.gitconfig` или окружении, а не в команде. `true`, `false` и `:` — в белом списке чтения (D9), поэтому `GIT_EDITOR=true git rebase --continue`, `EDITOR=: git commit` и `GIT_EDITOR=false git commit` не критичны; `PAGER=less git log`, `GIT_PAGER=cat git log` — тоже.

### D9. Проверка при «неизвестно» и метка

Простая команда при варианте ⊤ критична, если выполнено одно из условий:
1. она не из белого списка чтения (`_isReadOnly` с учётом опций записи и исполнения). Неизвестный каталог может быть `~/.codelab` или каталогом навыка: тогда работает «команда в каталоге конфигурации» (`isConfigWorkingDir`), «широкий приёмник по умолчанию» (`writesViaBroadDirectory`), и любой относительный аргумент может быть защищаемым путём;
2. у неё есть перенаправление записи с относительной целью;
3. относительный `launcherOutputs` (`time -o out`).

Абсолютные цели, `~`, `$HOME`, `$CODELAB_HOME` проверяются, как сейчас, — от каталога они не зависят. Цель с другой переменной (`> $F`) — известный предел, как и раньше.

Правило проще, чем прогонять каждый предикат с «любым каталогом». Пункт 1 покрывает все предикаты: любой из них срабатывает только у команды не из белого списка. Пункты 2–3 — то, что критично даже у команды из белого списка (перенаправление в защищаемый путь критично всегда).

Белый список чтения §7.6.1 дополнен `true` и `false` (`:` в нём уже был как встроенная без записи). Они ничего не пишут, а без них значение переменной-команды `GIT_EDITOR=true` давало бы вопрос (D8). Перенаправление у них проверяется как прежде: `true > SKILL.md` после `cd <навык>` критичен.

Абсолютные цели проверяются для ⊤ прогоном тех же правил с условным каталогом `unknownWorkingDirectory` (`/.unknown-working-directory`): относительная цель от него не попадает ни в корень сессии, ни в пути хоста, а абсолютная проверяется как есть.

**Недостижимое состояние** — D16, M1.

**Метки складываются.** Правило ⊤ — строка таблицы, как остальные. Сегмент получает все метки своих строк: `sudo -D "$X" make` — `privileged command; write in unknown working directory`, `trap 'cd "$X"; rm -rf /' EXIT` — `recursive delete of a protected path; write in unknown working directory`. Действие `trap`, которое каталог не меняет (`trap 'rm -rf /' EXIT`), получает только свою метку (D17, A8).

Метка `write in unknown working directory` ставится строкой таблицы сразу после `write to agent configuration` (`_tableOrder`), если сегмент не совпал с `write to agent configuration` ни для одного известного варианта и ни для абсолютного пути. Иначе метка прежняя. Если путь конфигурации виден, человек видит знакомую причину. Если не виден, он видит, почему спрашивают про `cd "$DIR" && npm test`. Реакция — как у любой критической строки: вопрос без `allow_always`, в `autopilot` отказ (PERM-9).

Альтернативы:
- **(а) Прежняя метка `write to agent configuration`.** Отклонена: человек не найдёт в команде путь конфигурации и не поймёт вопрос; ложное срабатывание выглядело бы ошибкой.
- **(б) Отдельная метка, но не критическая (обычный вопрос уровня `exec`, `allow_always` разрешён).** Отклонена: в `bypass` и `autopilot` вопроса не было бы, и пример 5 остался бы открыт. Это противоречит fail closed (Q34, Q37).

Текст метки — английский, как остальные метки §7.6. Он уходит в `reason` и `_meta.codelab.label` (`acp_permission_gate.dart`) без изменения формы.

### D10. Зарезервированные слова и `trap`

Лексер снимает в позиции команды — только в пустом сегменте, без слов и перенаправлений (D16, H1), — `if`, `then`, `elif`, `else`, `while`, `until`, `do` и `!`. `!` отмечает отрицание конвейера (D2). Заголовок `for NAME [in WORDS]` и `select …` — не команда; его закрывает незакавыченное `do` после имени или после списка `in` (D16, B1): слова заголовка не проверяются как аргументы. Подстановки в `WORDS` остаются вложенными командами. `fi`, `done` и `}` закрывают блок. Перенаправление после `done`/`fi`/`}` (`done < in.txt`, `} > out`) относится к блоку и проверяется с состоянием на выходе. `function NAME` и `NAME()` открывают тело функции (D6). Первый аргумент `trap` разбирается как вложенный текст (D8).

Новые ошибки разбора — `unparsable command` (правило 8, fail closed): если структура блоков не сходится, обход не знает, какие команды и в каком каталоге выполнятся:
- лишние `then`, `elif`, `else`, `do` (вне своего блока), `fi`, `done`, `}`, `)`;
- незакрытые `{`, `(`, `if`, цикл;
- арифметический `for ((…))`: его `;` оборвали бы заголовок;
- слово без разделителя после закрытого блока (`{ a; } b`, `fi x`) и блок сразу за блоком.

Побочный эффект — `time { …; }` даёт `unparsable command`. `time` снимается как лаунчер-слово, поэтому `{` после него не в позиции команды, а `}` закрывает неоткрытый блок. Принятая цена: форма редка в командах агента, а ошибка — вопрос, а не пропуск. Разбирать `time` как ключевое слово перед составной командой отклонено: это второй путь разбора лаунчеров ради редкой формы.

Это чинит всю таблицу §7.6: `if true; then rm -rf /; fi`, `while true; do rm -rf /; done`, `! rm -rf /`, `trap 'rm -rf /' EXIT` сейчас не критичны. Отдельный change отклонён: модель каталога опирается на те же слова (`then cd X`), а порознь две правки лексера разошлись бы.

### D11. Исключения навыков E1–E3

E1–E3 и разрешённый список Q47 change `add-agent-skills` уже в `develop` (`8277295c`, итерация 2). Этот change влился вторым и перенёс их на обход по вариантам.

Правило стыковки:
- E1 и E3 проверяются по известным вариантам, как раньше.
- E2 (рабочий каталог навыка) — только для известного варианта каталога навыка. У ⊤ его нет (fail closed).
- E1 не снимает пункт 1 D9 у варианта ⊤: неизвестный каталог может быть `~/.codelab`, а E2 там не действует и при известном каталоге.
- Признак «E1 отключён» (Q47) обход ведёт в порядке записи, как прежний плоский обход. Блоки ставят его сами (D6): группа, `if`, цикл, `!` — да, подоболочка — нет. Подстановка, `eval`, `env -S` и вложенный текст не `sh|bash|dash -c` тоже его ставят, как в `add-agent-skills`.

Примеры:
- `cd "$X" && python3 <скрипт навыка>` — `write in unknown working directory`: E1 действует для абсолютного пути скрипта, но `python3` не из белого списка чтения, а каталог ⊤.
- `cd "$(mktemp -d)" && python3 <скрипт навыка>` — `write to agent configuration`. Подстановка в `cd` отключает E1 по Q47, и путь скрипта в защищаемом корне навыков виден в команде. Метка конфигурации вытесняет метку каталога (D9). В первой редакции здесь стояла метка `write in unknown working directory`: она писалась до Q47.
- `python3 <скрипт навыка>` с известным `cwd` — как в `add-agent-skills`.
- `cd $pdf && python3 scripts/x.py` — известный вариант (успех `cd`), E2 действует.
- `pushd $pdf && npm install && popd` — критичен.

Документ: абзац E1–E3 и строка E2 в §7.6.1 ссылаются на §7.6.2. В спецификацию `add-agent-skills` этот change не вмешивается. Требование «Критические пути правок конфигурации агента», которое она MODIFIED, здесь не меняется — добавлено отдельное требование.

### D12. Известные пределы

- `CDPATH` из окружения исполнителя (D5, Q1).
- Переменная вместо пути: `f=…; echo > $f`, `rm $F` (§7.6.1).
- Переприсваивание `HOME`/`CODELAB_HOME` в строке: `HOME=/x; cd; touch f`, `HOME=/w/.codelab; echo > ~/config.yaml`. Это тот же класс «значение переменной неизвестно». Признак, как у `CDPATH`, сделал бы ⊤ каждую цель с `$HOME`. Вынесено в Q2.
- `source`/`.` со скриптом из файла — «скрипт из файла» §7.6.1.
- Исполнитель — новый `/bin/sh -c`. Если `ExecutionEnv` перейдёт на постоянную оболочку (сессионный терминал), начальные `OLDPWD` и стек перестанут быть известными. Это условие записано в §7.6.2, и его пересмотр обязателен.
- `/bin/sh` — zsh. Тогда последняя стадия конвейера исполняется в текущей оболочке. Объединение D6 это покрывает, но `cd a b` (подстановка в zsh) — нет: такой `cd` даёт `a` или прежний каталог. Требует проверки, если такой исполнитель появится.
- Подстановка в теле here-document без кавычек (`cat <<EOF` … `$(touch …)` … `EOF`) исполняется оболочкой, а разбор считает тело данными. Пробел был до change и касается всей таблицы §7.6: правило 4 документа («строки до `WORD` — данные») верно только для `<<'EOF'`/`<<"EOF"`/`<<\EOF`. Правило 4 здесь не меняется — отдельная задача (вне этого change, как и запрет записи на уровне ОС).
- Shell через stdin: `sh <<X`, `bash < file`, `. /dev/stdin`, `source /dev/stdin` — тело тоже не разбирается как команда. Отдельная задача вместе с предыдущим пунктом.
- Данные, которые оболочка исполняет как код: `PS4='$(…)'; set -x`, `x='a[$(…)]'; echo $((x))` (индекс массива в арифметике). Разбор видит строку в кавычках как данные.
- Окружение клиента ACP: `SHELLOPTS`/`BASHOPTS` (включают `cdable_vars`, `physical`), экспортированная функция `BASH_FUNC_cd%%` подменяет `cd`. Модель задать их не может; класс D5 «из окружения исполнителя».
- `.`/`source` как значение переменной-команды (`GIT_EDITOR=. git commit -e -F m`): программа исполняет файл сообщения как скрипт — класс «скрипт из файла».
- Расхождение bash и dash для `$'…'` внутри `${…}` вне двойных кавычек (D18, C1). C1 следует bash; найденная форма, которую dash исполняет иначе, даёт `unparsable command`. Полный перебор форм не делался.
- Пределы W7 (D18) измерены только на JIT: 245 мс на 6660 `pushd`. На AOT в UI-изоляте desktop не измерялись.
- Относительные цели `rm` и других строк таблицы §7.6 вне PERM-11 (`cd / && rm -rf usr`) считаются от корня сессии, а не от каталога варианта. Так было до change; модель каталога этот change применяет только к PERM-11.
- Запрет записи на уровне ОС, который закрыл бы все эти пределы сразу, — отдельный change `add-exec-os-write-sandbox` (pese-git/codelab-app#312).
- **Решение пользователя (2026-11-13):** D18 — последний раунд исправлений в этом change. Обходы, найденные дальше, сюда не исправляются, а записываются известными пределами этого раздела и §7.6.2. Исключение — находки уровня CRITICAL и регрессии относительно `develop`. Текстовый разбор остаётся эвристикой; надёжная защита PERM-11 для `exec` — запрет записи на уровне ОС (`add-exec-os-write-sandbox`).
- `exit` не моделируется: `cd X || exit 1; make` проверяет `make` в `X` и в прежнем каталоге (лишний вопрос, только если прежний — каталог конфигурации).

### D13. Отклонено: узнавать `git rev-parse --show-toplevel`

Можно было бы считать `cd "$(git rev-parse --show-toplevel)"` переходом в корень запуска. Отклонено:
- корень репозитория может быть выше корня запуска, в том числе `~/.codelab` или каталогом навыка-репозитория;
- ядро не видит файловую систему и не исполняет подстановку (`PathResolver` раскрывает ссылки, но не ищет `.git`);
- `GIT_DIR`, `GIT_WORK_TREE` и `-C` меняют ответ.

Принятая цена — `cd "$(git rev-parse --show-toplevel)" && make` спрашивает. Команды белого списка чтения (`… && git log`, `… && cat x`) — нет. Модель может передать каталог полем `cwd` инструмента `exec`, оно известно.

Ни методов, ни полей, ни состояний. Новая метка — строка в существующих `reason` и `_meta.codelab.label` запроса `session/request_permission`. Клиенты метки не разбирают (поиск по `apps/` и `packages/dart/codelab_client_*`). Фикстуры ACP не меняются.

### D16. Исправления по двойному ревью

Ревью нашло обходы модели каталога и разбора. Все правила — fail closed: где модель не уверена, состояние становится ⊤ или команда неразбираема.

**B1. `for|select NAME do …` без `in`.** POSIX допускает `for x do …; done` (обход позиционных параметров). Заголовок закрывает незакавыченное `do` сразу после имени или после списка `in WORDS` (в том числе на новой строке или после `;`). Любое другое слово в заголовке, кроме `in` на месте второго слова, — `unparsable command`. Без правила `do rm -rf /; done` оставался в заголовке как данные, и `for x do rm -rf /; done` не был критичен (на `develop` запись в `.codelab` там ловилась). Альтернатива — считать заголовок оконченным на первом незнакомом слове. Отклонена: граница заголовка тогда угадывается, а ошибка угадывания прячет команду.

**B2. `&` и and-or список.** `&` относится ко всему and-or списку (D2): `cd .codelab; cd /tmp && true & touch config.yaml` — `cd /tmp && true` ушёл в фон целиком, и `touch` пишет в `.codelab`. Обход возвращает после `&` состояние до начала списка, а не до последнего конвейера. Альтернатива — оставить связку `background` у последнего конвейера и восстанавливать список в обходе. Выбор формы — за реализацией; правило наблюдаемо одно.

**H1. Зарезервированные слова только в пустом сегменте.** Слово распознаётся как зарезервированное, только если в сегменте ещё нет ни слов, ни перенаправлений. `>/dev/null ! cd /tmp` — команда `!` (bash: `!: command not found`), а не отрицание; `> f if …` — команда `if`. Иначе модель видела бы отрицание или блок, которых оболочка не исполняет. Совпадает с грамматикой POSIX: зарезервированное слово — только первое слово команды.

**H2. `command -v`, `command -V`.** Только печатают, как найдена команда, и ничего не исполняют: `command -v cd /tmp` каталог не меняет, и `dirCommandFlow` не вызывается. Без правила `command -v cd /tmp` считался бы встроенным `cd` под `command` (D7), и модель «переходила» бы в `/tmp`, не покидая каталог навыка.

**H3. `trap` с непустым действием.** Действие исполняется позже в той же оболочке: по сигналу, `EXIT`, а в bash ещё `DEBUG` (перед каждой командой), `ERR`, `RETURN`. С `DEBUG` действие `cd <навык>` меняет каталог перед каждой следующей командой. Поэтому `trap` с непустым действием, которое может сменить каталог (`mayChangeDirectory` хоть для одного сегмента действия, D17), делает состояние ⊤ до конца строки, как определение функции (D6), и действие проверяется как `foreign` (D8). Иное действие (`rm -f "$tmp"`) каталог не меняет: оно проверяется в конце строки во всех состояниях, в которых строка побывала, без ⊤ (D17, A8). `trap - EXIT`, `trap '' INT` и `trap -p` действия не задают. Альтернатива — разбирать `DEBUG`/`ERR` отдельно и моделировать действие перед каждой командой. Отклонена: сложность ради формы, которой у агента нет.

**H4. Динамическая команда** (уточнено D17, A2). Если первое слово команды после лаунчеров содержит `$`, обратную кавычку или подстановку (`$CMD /tmp`, `"$(echo cd)" /tmp`) и нет буквального `/` вне подстановок и раскрытий (слово с `/` оболочка всегда исполняет как файл, поэтому `$HOME/bin/tool; make` не критично), оболочка может исполнить что угодно, в том числе `cd`. После такого сегмента состояние — ⊤ (успех и неуспех). То же для `eval` с нелитеральным текстом (`eval "$X"`, `eval "$(cat f)"`): разбор видит только литерал. Сам сегмент проверяется как раньше: не из белого списка чтения — правило ⊤ на следующих командах. Точное правило «слова-файла» и масок — D17, A2. Альтернатива — считать первое слово неизвестной внешней программой. Отклонена: функцию или встроенную оболочка выберет по значению.

**H5. Признаки `CDPATH`/`OLDPWD` при косвенной записи.** Подстрока (D5) не видит имя, собранное во время исполнения. Признаки ставятся ещё и:
- при `eval` с нелитеральным текстом;
- при `export`, `declare`, `typeset`, `local`, `readonly`, `read`, `printf -v`, `getopts`, `mapfile`, если имя переменной содержит `$`, обратную кавычку или подстановку (`export "${N}PATH=…"`, `read "$V"`).

**H6. Состояние bash, которое меняет `cd`.** На macOS `/bin/sh` — bash 3.2 в режиме POSIX, поэтому учитываются расширения bash. Признаки — по подстроке строки команды, как в D5:
- `enable` как имя команды (после снятия лаунчеров) где угодно в строке, включая вложенные тексты: `enable -n cd` выключает встроенную, и `cd` становится внешней программой или функцией; `cd`, `pushd`, `popd` дают ⊤ при успехе. Подстрока не ищется: `./configure --enable-shared` не в счёт (уточнено D18, W5);
- `DIRSTACK` в строке: присваивание меняет стек `pushd`; стек всех вариантов становится неизвестным;
- `cdable_vars` в строке (`shopt -s cdable_vars`): относительная цель без `./`, `../` и не `.`/`..` может быть именем переменной; такая цель даёт ⊤, как при `CDPATH`.

Альтернатива для всех трёх — разбирать `enable`, `shopt` и присваивания точно. Отклонена по причине D5: формы записи многочисленны, законного применения у агента нет, ложное срабатывание стоит одного вопроса.

**M1. Недостижимое состояние** (уточнено D17, A4). Если вход команды пуст (`popd && …` при пустом стеке: `popd` гарантированно неуспешен), вместо него берётся **вход предыдущей команды того же уровня**, и вся команда идёт от него, в том числе `cd`: `popd && cd .codelab && touch config.yaml` критичен. Условный каталог для этого не используется. `popd && touch .codelab/config.yaml` в корне сессии — `write to agent configuration`; `popd && rm -rf /` — `recursive delete of a protected path`; `popd && make` в обычном корне — не критична. Отклонённая первая реализация — условный каталог `unknownWorkingDirectory`: относительная запись от него никуда не попадает, и безопасность всей таблицы зависела бы от точности модели стека. Это D9 и отвергает: если модель стека ошиблась (`DIRSTACK`, неизвестный `pushd`), `popd` мог и удаться. Альтернатива — ⊤. Отклонена: лишние вопросы на `popd && make`, а входные варианты — уже надмножество достижимого.

**M2. Пределы разбора.** Глубина вложенности блоков — не больше 64. Длина команды до разбора — не больше 128 KiB. Превышение любого — `unparsable command` (правило 8). Без предела рекурсия по блокам давала `StackOverflowError` вместо метки, а строка в 600 КБ — около 4 с синхронной работы в UI-изоляте desktop (§12 `AGENTS.md`). Значения выбраны с запасом над реальными командами агента. Альтернатива — перенести разбор в отдельный изолят. Отклонена: проверка синхронна в `beforeToolCall`, а предел проще и закрывает обе причины. Третий предел — бюджет проверок обхода (D17, A6).

**L1. Переменная-команда через косвенную запись.** `printf -v EDITOR …`, `read EDITOR`, `mapfile`/`readarray` с таким именем, `getopts … EDITOR`, `declare -n R=EDITOR` пишут переменную-команду (список `_commandEnvironment`, D8) значением, которого разбор не видит. Следующий сегмент-необъявление проверяется как отложенный `foreign` с неизвестным значением: известные варианты ∪ ⊤ и правило D9 к нему самому. Альтернатива — игнорировать. Отклонена: `read EDITOR <<< 'touch SKILL.md'; git commit` иначе проходил бы. Полный перечень способов записи и разбор `variableWrites` — D17, A5.

### D17. Исправления по повторному ревью

Второй раунд ревью нашёл обходы реализации D16. Решение пользователя: N1, N2 и N9 включены в этот change. Принцип прежний — fail closed.

**Предикат `mayChangeDirectory`** (`exec_dir_walk.dart`). Одно определение «сегмент может сменить каталог текущей оболочки» для перехода сегмента, цикла (A1) и `trap` (A8). Истинен для `cd`/`pushd`/`popd`/`dirs`, `eval`, `trap` с действием и динамического имени команды (A2). Ложен для внешнего лаунчера, `lookupOnly` (A3) и сегмента без слов. Почему один предикат: три места решали одно и то же по-разному, и `$C "$d"` с `C=cd` проходил через цикл.

**A1. Цикл по потоку.** Тело обходится один раз. Если состояние после тела отличается от входа, тело обходится повторно от «вход ∪ конец ∪ ⊤». Итог — «вход ∪ конец» (тело может не выполниться). Имена команд не учитываются: смену каталога видно по потоку, в том числе через `eval` и динамическое имя. Альтернатива — прежний признак «в теле есть `cd`/`pushd`/`popd`/`eval`». Отклонена: `C=cd; $C /tmp` в теле его обходил. Альтернатива — неподвижная точка с пределом итераций. Отклонена, как в D6.

**A2. Динамическое имя команды** (`shell_words.dart`, `isDynamicCommandWord`; признак разбиения на слова `commandWordSplit` у сегмента; скрытый текст — D18, W4). Первое слово после лаунчеров динамическое, если:
- в нём есть незакавыченные `*`, `?`, `[`, `{` (маска или фигурные скобки: `c[d]`, `{cd,x}`), кроме слов `[` и `[[`;
- в нём есть `$` или обратная кавычка, и оно не «файл».

«Файл» — слово, где буквальная `/` стоит до первого раскрытия или сразу после раскрытия, которое либо в двойных кавычках (`"$d"/run`), либо это `$HOME`, `$CODELAB_HOME` или `~`. Такое слово оболочка исполняет как путь, и вызвать им `cd` нельзя. Незакавыченное `$d/run` или `${d}/run` динамическое: при разбиении на слова `d='cd '` даёт встроенный `cd` и аргумент `/run`. Скобки `${…}` в префиксе должны быть сбалансированы. Альтернатива — любое слово с `/` считать файлом. Отклонена из-за разбиения на слова.

**A3. `command` и лаунчер с путём.** `-v`/`-V` у любого снятого `command` (`command -p command -v cd`) делает сегмент `lookupOnly`: каталог не меняется. Лаунчер с путём (`/usr/bin/command`, `/usr/bin/time`) — внешняя программа, а не встроенная: `cd` под ним каталог оболочки не меняет (D7).

**A4. Пустой вход.** Если вход команды пуст, берётся вход предыдущей команды того же уровня, и команда, в том числе `cd`, идёт от него (уточняет D16, M1). Состояние «последний вход» не хранится отдельно (`_lastInput` удалён): его даёт обход уровня. Пустой вход у самого первого сегмента пустого вложенного обхода проверяется с условным каталогом, чтобы не терять метки, не зависящие от каталога.

**A5. Запись переменных** (`variableWrites`, один разбор на сегмент; уточнено D18, W4 и F1). Результат — `names` (литеральные имена, записанные способом, значения которого строка не показывает), `dynamic` (имя собрано при исполнении или нелитеральный `eval`), `shoptDynamic`, `setDynamic`.
- `dynamic` ставит признаки `cdpath`, `oldpwd`, `dirstack` (D5, D16 H5, H6).
- `shopt` с нелитеральным аргументом ставит `cdpath` (может включить `cdable_vars`). `set` с нелитеральным аргументом ставит `physical`.
- Запись переменной-команды (`_commandEnvironment`) делает следующий сегмент потребителем отложенного `foreign` (D16, L1). Способы записи: `NAME=`, `NAME+=`, `NAME[i]=`, `${NAME:=…}`, `read`/`mapfile`/`readarray`/`getopts`/`printf -v`, `declare -n`, переменная заголовка `for`/`select`.
- Присваивание узнаётся по `^NAME(\[…\])?\+?=` — и в лексере (снятие префикса, N2), и здесь.
- Физический `..`: цель `cd` с `..` после обычной компоненты (`sub/../b`) даёт ⊤. Если `sub` — ссылка, физический `cd` (bash вне POSIX-режима откатывается к нему при ошибке) уходит не туда, куда лексическая нормализация. Ведущие `..` точны.

Альтернатива — отдельный разбор в `DirContext` и в обходе. Отклонена: два разбора уже разошлись в первом раунде.

**A6. Бюджет обхода.** Правила, не зависящие от каталога, проверяются один раз на сегмент. Варианты для правил с каталогом — пары (каталог, `OLDPWD`): `~-` зависит от второго (N9). На сегмент уходит «варианты + 2» единицы бюджета `maxDirWalkWork = 20000`. Сверх бюджета — `unparsable command`. Порог времени в тестах — 1 с. Альтернатива — только пределы длины и глубины (D16, M2). Отклонена: 32 варианта × тысячи сегментов строки в 128 KiB всё ещё стоили секунд.

**A7. `trap` и непотреблённое значение.** Если в строке был `trap` с действием, отложенное значение переменной-команды, которого никто не потребил, проверяется в конце строки с вариантами «все состояния строки ∪ ⊤»: ловушка (`EXIT`) может его запустить. Без `trap` непотреблённое значение не проверяется (D8).

**Потребитель неизвестного значения (A5, D16 L1).** При косвенной записи значение переменной-команды неизвестно. Поэтому первая следующая команда-необъявление получает его как команду не из белого списка чтения с вариантами «известные ∪ ⊤» — метка `write in unknown working directory`, даже если сама команда только читает (`read EDITOR …; true; git commit`). Иначе команда белого списка чтения поглощала бы признак, а настоящий потребитель шёл бы без проверки. Альтернатива — переносить признак до первой команды не из белого списка чтения. Отклонена: потребителем может быть и `less` (пейджер), и `git log` из белого списка.

**A8. `trap` без смены каталога.** `trap` даёт ⊤ до конца строки только если `mayChangeDirectory` истинен хоть для одного сегмента действия. Иначе действие проверяется в конце строки во всех состояниях, в которых строка побывала, включая состояние после последней команды (ловушка `EXIT` срабатывает там), без ⊤. `trap 'rm -f "$tmp"' EXIT; make` не критичен, `trap 'rm -rf /' EXIT` даёт только `recursive delete of a protected path`. Это сужает D16 H3 и прежний пример со сложением меток (D9). Условие «меняет состояние» расширено в D18, W3 (`alias`, функция, запись переменной-команды). Альтернатива — ⊤ для любого действия. Отклонена: типичная уборка временных файлов становилась критической.

**A9. Двойной `!`.** `! ! cmd` — `unparsable command`. bash принимает, dash — нет; разбор не угадывает.

**N1. Раскрытия.** `${…}` читается с учётом вложенности, кавычек и `\}`. `$(…)`, обратные кавычки и `${…}` внутри — вложенные команды `substitution` (`${x:-$(rm -rf /)}`). Незакрытое раскрытие — `unparsable command`. `$((…))` — арифметика, только если закрывается смежными `))` и внутри нет `$(` и обратной кавычки; иначе это `$(` и подоболочка, тело разбирается как команда (`$((rm -rf /) )`). Альтернатива — пропускать `${…}` до первой `}`. Отклонена: подстановка внутри исполняется. Кавычки внутри `${…}`, условия арифметики и предел вложенности уточнены в D18, C1–C4.

**N2. Присваивание с `+=` и индексом в префиксе.** `a+=1 rm -rf /` и `a[0]=1 rm -rf /` снимаются как присваивания, и команда `rm -rf /` проверяется (`recursive delete of a protected path`). Раньше слово не узнавалось как присваивание и становилось именем команды.

**N9. `~+`, `~-`, `~user`.** `~+` раскрывается в каталог варианта, `~-` — в `OLDPWD` варианта. `~user` и `~-` при неизвестном `OLDPWD` сравнить с защищаемыми путями нельзя: `~user` может быть текущим пользователем, `~-` — любым каталогом. Такое слово критично при записи (перенаправление, цели пишущих команд) и в аргументах команд вне белого списка чтения с меткой `write to agent configuration`, потому что путь может быть защищаемым. Чтение (`cat ~bob/x`, `ls ~-`) не критично. Альтернатива — метка `write in unknown working directory`. Отклонена: неизвестен путь, а не каталог. В правиле ⊤ (D9) `~+` и `~-` считаются относительными целями (D18, W6).

### D18. Исправления третьего раунда

Третий раунд ревью. Принцип прежний — fail closed; после этого раунда новые обходы идут в известные пределы (D12, решение пользователя).

**C1. ANSI-C внутри `${…}`.** Вне двойных кавычек `$'…'` внутри `${…}` разбирается как ANSI-C строка: `${x:-$'\x27'}` содержит кавычку, а не открывает строку. `$"` пропускается как локализуемая строка. Альтернатива — считать `'` началом обычной строки. Отклонена: граница `}` сдвигалась, и следующая команда пряталась в «строке».

**C2. Кавычки в `${…}` внутри двойных кавычек.** `'` или `$'` в `"${…}"` — `unparsable command`. bash и dash ищут закрывающую `}` по-разному: bash учитывает одинарные кавычки, dash — нет. Цена: `"${x:-'default'}"` неразбираем. Альтернатива — выбрать поведение bash. Отклонена: `/bin/sh` бывает dash, и разбор должен быть верен для обоих.

**C3. Арифметика.** Если в `$((…))` встретились `'`, `"`, `\`, `#`, обратная кавычка, `$(` или `${`, тело разбирается как подстановка `$(` с подоболочкой, а не как арифметика. `$((1+2))` остаётся арифметикой. Почему: эти символы оболочки читают в арифметике по-разному, а внутри может исполняться подстановка. Альтернатива — разбирать арифметическое выражение. Отклонена: второй парсер ради редкой формы.

**C4. Предел вложенности раскрытий.** Вложенность `${…}` не больше 64 (`_maxExpansionDepth`), иначе `unparsable command`. Причина та же, что у D16 M2: рекурсия без предела даёт `StackOverflowError` вместо метки.

**W1. Состояние каждой оболочки.** У каждой оболочки свои `_tainted`, `_enableSeen`, `_foreignNext`, `_trapSeen`, отложенные `trap`, `_pendingForeign` и `_seen` (`ExecDirWalk._shell`). Оболочки — корень, подоболочка, подстановка, фоновый and-or список (`{ …; } &`, `A && B &` — подоболочка, D16 B2) и новый процесс (`sh -c`, `env -S`, `foreign`, `eval` под внешним лаунчером). Подоболочка, фоновый список и подстановка наследуют `_tainted` и `_enableSeen` (видят функции, `alias` и `enable` родителя); новый процесс начинает чистым. На выходе из оболочки отложенные `trap` и непотреблённые значения переменных-команд проверяются в её `_seen` и её конечном состоянии; наружу состояние не выходит; снаружи фонового списка состояние остаётся входом списка. `eval` без внешнего лаунчера — та же оболочка, состояние общее. Фоновый список добавлен после финального ревью: без него `{ trap 'echo > config.yaml' EXIT; cd .codelab; } & wait` давал `null`, а dash пишет в `.codelab` — CRITICAL-регрессия относительно `develop`. Почему: `(trap 'cd <навык>' DEBUG); touch SKILL.md` — ловушка подоболочки на родителя не действует, а `sh -c 'alias …'` не задевает следующие команды. Без разделения обход либо пропускал ловушку внешнего уровня, либо делал ⊤ там, где оболочка его не даёт. Альтернатива — общий флаг на всю строку. Отклонена: ложные ⊤ и потеря конечного состояния вложенной оболочки.

**W2. Повтор тела цикла при смене состояния оболочки.** Тело цикла повторяется от «вход ∪ конец ∪ ⊤» (D17, A1) и тогда, когда каталог не изменился, но тело поставило `_tainted`, добавило `_pendingForeign` или поставило `_foreignNext`. На втором проходе определённые в теле функция или `alias` и записанная переменная-команда уже действуют на начало тела. Пример: `cd <навык>; for i in 1 2; do touch SKILL.md; f() { cd /tmp; }; done`.

**W3. Действие `trap`, меняющее состояние.** Действие меняет состояние оболочки, если в нём есть сегмент с `mayChangeDirectory`, `alias`, определение функции или запись переменной-команды либо переменной с динамическим именем. Тогда ставится `_tainted` (⊤ до конца оболочки), и действие сразу проверяется как `foreign`. Иначе действие откладывается (D17, A8). Пример: `trap 'f() { :; }' EXIT; touch SKILL.md` — `write in unknown working directory`.

**W4. Скрытый текст** (`runsHiddenText`, `shell_words.dart`). `fc`, `history -s`, `mapfile`/`readarray -C CALLBACK` исполняют текст, которого разбор не видит. Для каталога это нелитеральный `eval`: ⊤ после сегмента, сам сегмент не из белого списка чтения, `mayChangeDirectory` истинен. `declare -n R` без `=` даёт `dynamic` (цель ссылки известна только при исполнении). Альтернатива — перечислить команды истории точно. Отклонена: формы неисчислимы, у агента законного применения нет.

**W5. `enable` по имени команды и порядок.** Признак `enable` ставится, если `enable` — имя команды после снятия лаунчеров в любом месте строки, включая вложенные тексты. Подстрока больше не ищется: `./configure --enable-shared && cd build && make` не критичен. Имя, собранное при исполнении, признак не видит; поэтому после динамической команды, нелитерального `eval` или скрытого текста (W4) порядкозависимый `_enableSeen` делает последующие `cd`/`pushd`/`popd` ⊤ до конца оболочки. Альтернатива — глобальный признак при любой динамической команде в строке. Отклонена: он делал ⊤ и `cd`, стоящий раньше динамической команды, и ломал сценарий «Цикл, который меняет каталог через переменную».

**W6. `~+` и `~-` в правиле ⊤.** При варианте ⊤ `~+` (текущий каталог) и `~-` (`OLDPWD`) — относительные цели: перенаправление `> ~+/a` и `time -o ~+/out` дают `write in unknown working directory`. Раньше они считались абсолютными, как `~`.

**W7. Пределы состояния.** Стек `pushd` длиннее 64 (`maxKnownDirStack`) становится неизвестным, путь каталога длиннее 4096 (`maxDirPathLength`, `PATH_MAX`) — ⊤. Почему: `pushd a && …` тысячи раз давал квадратичное копирование списков и строк в UI-изоляте, а путь длиннее `PATH_MAX` оболочка не откроет.

**F1. Префиксное присваивание без команды.** Сегмент из одних присваиваний с литеральным значением (`GIT_EDITOR=true`, `PAGER=cat`) уже проверен: лексер разобрал значение как вложенный текст. `_foreignNext` он не ставит. Поэтому `GIT_EDITOR=true; export GIT_EDITOR; git rebase --continue` и `PAGER=cat; git log` не критичны. Нелитеральное значение (`EDITOR=$V; git commit`) по-прежнему ставит `_foreignNext` (D17, A5).

## Risks / Trade-offs

- **Ложные срабатывания (принятая цена).** Критичными станут:
  - `cd "$(git rev-parse --show-toplevel)" && make`;
  - `cd "$DIR" && npm test`;
  - `cd build; cd -; make` с `;`;
  - `for d in */; do (cd "$d" && make); done` — `cd` с переменной в подоболочке: `make` в ⊤;
  - `find . -execdir <не только чтение>`;
  - `git -c core.pager=delta log`;
  - `EDITOR=vim git commit`, `LESSOPEN="|lesspipe %s" less x` — `write in unknown working directory`: редактор и препроцессор не из белого списка чтения, а git и less запускают их не обязательно в каталоге оболочки (D8);
  - `export EDITOR=vim; ls` — значение проверяется на первом следующем сегменте-необъявлении, даже если он его не читает (D8);
  - `f() { echo hi; }; f` — после определения функции каталог неизвестен до конца строки, а вызов `f` не из белого списка чтения (D6);
  - `time { …; }` — `unparsable command` (D10);
  - `cd X || exit 1; make` в каталоге конфигурации;
  - `cd "$(dirname "$0")" && make`, `cd "$(mktemp -d)" && …` — цель с подстановкой (D4);
  - `for d in a b; do cd $d && make && cd ..; done`, `for d in packages/*; do (cd "$d" && dart test); done` — повтор тела цикла от ⊤ (D17, A1);
  - `cd sub/../b && make` — `..` после обычной компоненты (D17, A5);
  - `${d}/run && make`, `$d/run && make` — незакавыченное раскрытие перед `/` может разбиться на слова (D17, A2);
  - `'` или `$'` внутри `"${…}"` — `unparsable command` (D18, C2): `"${x:-'default'}"`, `echo "${f%'.dart'}"`, `x="${y:-'a b'}"`, `printf '%s\n' "${x:-$'\t'}"`;
  - `fc`, `history -s`, `mapfile -C` — скрытый текст (D18, W4).

  В `bypass` это вопрос, в `autopilot` — отказ. Модель может передать каталог полем `cwd` `exec` или использовать `&&`.

  Не меняются:
  - `cd sub && make`, `cd sub; make`;
  - `pushd a; popd; make`, `pushd a && pushd b && popd && make`;
  - `(cd sub && make)`;
  - чтение в любом каталоге;
  - `export EDITOR=vim`, `readonly EDITOR=vim` без следующей команды, `export EDITOR=true; git commit`;
  - `GIT_EDITOR=true git rebase --continue`, `EDITOR=: git commit`, `PAGER=less git log`;
  - существующие тесты PERM-11 с `cd X &&` и `cd ~/.codelab; …` (`config_exec_whitelist_test.dart`, `agent_config_paths_test.dart`) — проверить задачей 3.1.
- **Стыковка с `add-agent-skills`** (D11). Ветка этого change перебазирована на `develop` с итерацией 2 навыков; тесты `skill_script_exceptions_test.dart` прогоняются задачей 4.2.
- **Время разбора.** ≤ 32 варианта × предикаты × глубина ≤ 4 × блоки ≤ 64 на строке до 128 KiB (D16, M2), не больше 20 000 проверок «сегмент × вариант» (D17, A6). Задачи 2.7 и 6.x проверяют порог 1 с на длинных строках. Встроенный агент работает в UI-изоляте desktop.
- **Second pass.** `canonicalizeSeen` получит больше путей (по каждому варианту). Время растёт линейно с числом вариантов. Предел 32 его ограничивает.
- **Потеря точности W6.** В правиле ⊤ `~+` — относительная цель, поэтому и при известном каталоге путь с `~+` в цели `cd` даёт ⊤: `cd .codelab && cd ~+/agents && touch x.md` получает `write in unknown working directory` вместо `write to agent configuration`. Защиты это не снижает: команда остаётся критической, меняется только метка.
- **Неполнота текстового разбора (решение пользователя).** После трёх раундов ревью новые обходы того же класса вероятны. Этот change их больше не исправляет: они записываются известными пределами (D12, §7.6.2), кроме находок CRITICAL и регрессий относительно `develop`. Надёжная защита PERM-11 для `exec` — запрет записи на уровне ОС, change `add-exec-os-write-sandbox` (pese-git/codelab-app#312).
- **Гонки, отмена, поздние события (§9, §12)** не затронуты: проверка синхронна внутри `beforeToolCall` и не создаёт подписок. TOCTOU между проверкой и исполнением — прежний известный предел §7.6.1.
