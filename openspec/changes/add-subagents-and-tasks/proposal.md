## Why

Решение пользователя 2026-11-09: субагенты (C-06, инструмент `agent`) и список задач в стиле Claude Code переходят из пула 1.x в продукт 1.0. Конечная цель — функциональность уровня Claude Code: агент поручает части работы субагентам с отдельным контекстом, те могут поручать свои части дальше, а общий список задач показывает, кто что делает и что чего ждёт.

Сейчас этого нет:
- инструмента `agent` нет. Есть только поле `scope` у `AgentDefinition` и опаковый ключ конфига `subagents`;
- план ведёт `update_plan` (C-05, Must). Модель каждый раз присылает весь план целиком: она теряет пункты, не может назначить пункт субагенту и не может выразить «этот пункт ждёт тех двух»;
- в §17.3 документа ядра глубина субагентов зафиксирована как 1 без настройки (SUB-1, обоснование §17.3.13). Решение пользователя — глубина до 3 настройкой.

Реализация поэтапная (дорожная карта §6.4). Этот change — **базовый этап и этап 2** (решение пользователя 2026-11-10): база — только то, что дорого переделывать потом, этап 2 — шаги потомков деревом в клиентах, которые его согласовали. Решение пользователя 2026-11-12 (Q13) добавляет облегчённую панель Agents v1 в доке codelab-app — проекцию kit над уже приходящими данными, без нового протокола (design.md, D33). Базу составляют контракты ядра, формат журнала, формы расширений ACP и состояния жизненного цикла. Следующие этапы встают в его точки расширения без смены используемых сигнатур (дорожная карта §9, пункт «в»).

## What Changes

- **Имена** (решение пользователя 2026-11-10, design.md D20): как в Claude Code — субагенты запускает инструмент `agent` (параметр типа — `type`), будущие инструменты фона и продолжения — `agent_status`, `agent_cancel`, `agent_send`, `agent_resume`, `agent_observe`; инструменты списка задач — `task_create`, `task_update`, `task_list`, `task_get`. Имена инструментов модели нигде не означают субагента словом task; slash-команда фоновой работы для человека остаётся `/tasks`, как в Claude Code (решение пользователя 2026-11-10, design.md D23).
- **Ядро `codelab_agent_core`, субагенты (agent-core-architecture §17.3):**
  - инструмент `agent`;
  - `SubagentManager` на каждую сессию, у которой есть `agent`, и `SubagentTree` на корневую сессию;
  - типы — `AgentDefinition` со `scope` `subagent | both`, встроенные `general`, `explore`, `review`, `plan`;
  - вложенность до `subagents.max_depth` (1–3, по умолчанию 3); все лимиты (`max_depth`, `max_concurrent` = 3, `max_per_turn` = 10 и бюджеты) — ключи `subagents.*` реестра настроек с проверкой диапазонов;
  - лимиты считаются на всё дерево: слоты `max_concurrent`, `max_per_turn`. Ребёнок, ждущий своих детей, возвращает слот, поэтому взаимоблокировки нет (SUB-23);
  - бюджет и usage потомков входят в бюджет предков;
  - состояния хэндла `queued`, `running`, `waiting`, `completed`, `failed`, `cancelled` — сразу полные, под будущие фон и продолжение;
  - отмена через дочерние `CancelToken`;
  - события потомков в потоке корневой сессии обёрткой `SubagentActivity` с `parentToolCallId`, `path` и id субагента.
- **Ядро, навыки у субагента** (решение пользователя 2026-11-12, Q17, design.md D34; стык с change `add-agent-skills`):
  - с итерации 2 политика ребёнка использует набор защищаемых путей конфигурации агента корневой сессии, а не новый (SUB-1); `skill` у ребёнка — только при переданном снимке каталога;
  - задачи 2s (после слияния кода `add-agent-skills`; он в `develop` к началу итерации 2, поэтому 2s выполняется внутри неё): `skill` по общему правилу набора, тот же снимок каталога и та же секция `skills/catalog`, `readOnlyRoots` каталогов навыков как у родителя; активные навыки родителя не наследуются.
- **Ядро, список задач (новый §17.16):**
  - инструменты `task_create`, `task_update`, `task_list`, `task_get` заменяют `update_plan`;
  - у пункта есть id, заголовок, описание, статус `pending | in_progress | completed`, удаление, приоритет (по умолчанию `medium`), владелец (`main` или id субагента) и `blocked_by` с проверкой циклов;
  - список один на дерево; субагент меняет только статус своих пунктов;
  - `agent` корневой сессии может назначить пункт ребёнку полем `task`;
  - событие `TaskListChanged` заменяет `PlanUpdated`.
- **Журнал (`codelab_agent_core`, `codelab_agent_io`):**
  - журнал потомка любой глубины лежит в `<корневая сессия>/subagents/`, а в его заголовке есть поле `parent`;
  - в журнал прямого родителя пишется запись `subagent` с итоговым отчётом — она становится точкой восстановления (SUB-9, SUB-10);
  - вызов `agent`, прерванный сбоем, лечится без перезапуска ребёнка;
  - запись `task` по каждой операции; старые записи `plan` читаются как начальный список.
- **ACP (`codelab_agent_acp`, `codelab_acp_protocol`) — только `_meta.codelab.*`, новых методов нет:**
  - схема объявления расширений в `initialize`. Клиент объявляет `clientCapabilities._meta.codelab`, агент в ответ отдаёт `agentCapabilities._meta.codelab` с `subagents: {version, maxDepth}`, `subagentToolCalls: {version}` и `tasks: {version}`. Сторонний клиент получает ответ `initialize` без изменений;
  - запрос разрешения потомка идёт через gate корневой сессии: `toolCallId`-цепочка, префикс `title`, `toolCall._meta.codelab.subagent`, запросы дерева идут пользователю по одному;
  - `plan` со всем списком после каждой операции, у каждой entry `_meta.codelab.task` `{id, owner, blockedBy}`; у самого `plan` — `_meta.codelab.taskChange` `{op, actor, toolCallId?, changed, deleted}`: точная привязка операции к вызову `task_*` (D35);
  - вызов `agent` — стандартный `tool_call` с `kind: think`, строкой прогресса и отчётом; финальное обновление всегда несёт `_meta.codelab.subagent.summary` — вызовы, токены и длительность ребёнка вместе с потомками (решение пользователя 2026-11-10, D24);
  - **этап 2:** клиенту, объявившему `subagentToolCalls`, вызовы потомков уходят `tool_call`/`tool_call_update` с `toolCallId`-цепочкой и `_meta.codelab.parentToolCallId`; при завершении вызова `agent` висящие вызовы поддерева закрываются; `session/load` проигрывает их из журналов детей. Остальным клиентам — как в базе (SUB-12).
- **Клиенты (минимальный UI):**
  - kit `codelab_client_core` / `codelab_client_acp` объявляет `clientCapabilities._meta.codelab` и разбирает `_meta.codelab.task` и `_meta.codelab.subagent`;
  - codelab-app: строка `agent` с прогрессом и отчётом, запрос разрешения потомка с пометкой «кто спрашивает», чек-лист с id, владельцем и блокерами;
  - под статусом завершённого `agent` — строка итога `N tool calls · N.Nk tokens · время` (в TUI — глиф ✓ и сокращённый итог без «Done», как в app); без `summary` — как прежде (D24);
  - компактный вид ленты (решение пользователя 2026-11-10, артборд 30, D27): операции со списком задач — тихие строки «Tasks #1–#4 added to the plan», «Task #2 done», подряд идущие сливаются, ошибка — обычной строкой с причиной; завершённый `agent` свёрнут в одну строку с глифом и итогом «4 tool calls · 18.2k · 48s» без тега «Done»; вопрос потомка — блок под строкой `agent` корня с путём «review › explore wants to run», без раскрытия деревьев; сводка плана над композером скрыта при открытой панели Plan. Протокол и ядро при этом не меняются;
  - CLI (REPL и `--ui tui`): то же построчно; в TUI список задач — блок над композером, Ctrl+T прячет и показывает его, доска открывается только `/tasks` (D26);
  - этап 2: у работающего свёрнутого `agent` — «хвост» из трёх последних вызовов потомков и `+N more tool calls` без токенов (проекция клиента, D25; токены — только из итога, Q15); вызовы потомков вложены под строкой `agent` (app — свёрнутое дерево, CLI — отступ по глубине), запрос разрешения потомка стоит в строке своего вызова;
  - **панель Agents v1** (решение пользователя 2026-11-12, Q13, итерация 5b, D33; артборд 16): kit строит список субагентов сессии `SessionView.subagents` из `_meta.codelab.subagent`, итога, дерева вызовов, запросов потомков и владельцев пунктов списка — идемпотентно при реплее и дублях; app показывает его панелью дока: тип, заголовок, состояние, время, вызовы, токены, последнее действие, глубина, пункты `#N`, отметка «waiting for approval» с переходом к блоку одобрения, дерево шагов выбранного потомка, переход к строке `agent` в ленте. Панель есть, только пока у сессии в фокусе есть вызов `agent` с `_meta.codelab.subagent`. Протокол, ядро и CLI не меняются.
- **Матрица и дорожная карта** (уже внесены итерацией 0):
  - C-06 и новая строка C-20 входят в Should 1.0 (дорожная карта §6.1, строка 9);
  - C-05 меняет критерий: `acp/prompt-task-plan` и `acp/session-load-legacy-plan`, а `acp/prompt-update-plan` остаётся фикстурой только с ролью `client`;
  - этапы: 1 и 2 — этот change (1.0); 3 → 5 → 4 → 6 — начало пула 1.x (дорожная карта §6.2, §6.4).

**BREAKING:**
- инструмента `update_plan` больше нет: модель видит `task_*`. Сессии, записанные с `update_plan`, открываются, и их последний план становится начальным списком (решение пользователя 2026-11-10);
- golden-промпты, профили хоста и фикстуры со схемой `update_plan` меняются.

Формат ACP для сторонних клиентов не меняется: `plan` остаётся стандартным, а `_meta` они игнорируют.

## Не входит

- **Этап 3.** Фоновые субагенты: `run_in_background`, `agent_status`, `agent_cancel`, уведомления, `wake`, ожидание в headless (§17.3.8–§17.3.9, SUB-13 – SUB-16). Состояния хэндла и токены под фон закладываются, но сам режим — нет.
- **Этап 4.** Продолжение ребёнка (C-17: `agent_send`, `agent_resume`, `agent_observe`) и отчёт по JSON-схеме (`output_schema` с ремонтом).
- **Этап 5.** Доска субагентов и задач (U-21, D-25, `_codelab/subagents/*`, `/tasks`) и ответ `-32602 subagentSession` на `session/load` id ребёнка. В базе такой `session/load` даёт «сессия не найдена». Исключение — панель Agents v1 (Q13, D33): она входит в этот change, а Stop одного субагента, «Open transcript», состояния `queued`/`waiting`, шаги, токены работающего, признак «нет вывода», Background jobs, A2A и вид CLI `tasks` остаются этапами 3–6.
- **CLI в панели Agents v1** не меняется: там строка `agent` (C16) и список задач над композером (D26).
- **Этап 6.** Фоновые команды (T-10, `_codelab/jobs/*`).
- Общий список задач между сессиями; изоляция ребёнка в git worktree (решение пользователя 2026-11-09 — отложено).
- Роли моделей (L-10): модель ребёнка — `type.model`, иначе текущая модель родителя.
- Удалённые A2A-типы субагентов (E-22, §17.15.3).
- Этапы 3–6 — пул 1.x в порядке 3 → 5 → 4 → 6 (решение пользователя 2026-11-10); этот change их не реализует.
- Поле `skills` в определении типа субагента (предзагрузка навыков) и исполнение навыка в субагенте (Agent Skills, «Subagent delegation») — после 1.0, отдельным change после архивации этого change и `add-agent-skills` (Q17.3, D34).
- Право потомков создавать свои пункты списка задач — позже; формат записи `task` (`actor`) это допускает.
- Тексты, промпты и описания инструментов Claude Code не копируются (`AGENTS.md` §5, §7а `07-decision-sources.md`). Все тексты пишутся заново, источник поведения указан в §17.3.13 и §17.16.8.
