Текущее состояние: `acp_testing` даёт `FakeAcpTransport` (`autoRespondToInitialize`, `emitInbound`, `sentMessages`), `FakeTerminalProcessRunner` и `CodelabCompatibleStdioAgent`; `AcpClientApplication` принимает порты `TextFileReader`, `TextFileWriter`, `TerminalProcessRunner`. `acp_testing` зависит от `acp_client_core`, а `acp_client_core` подключает `acp_testing` как `dev_dependency`.

## Goals / Non-Goals

**Goals:**

- один формат сценария ACP, который читают и агентская (этап 4), и клиентская проверки;
- 12 фикстур этапа 0 проходят клиентский прогон на `AcpClientApplication`;
- неполная или противоречивая фикстура падает при загрузке с понятным сообщением, а не даёт ложный зелёный прогон;
- расхождение кадра показывается diff с путём JSON.

**Non-Goals:**

- агентский драйвер, `ScriptedStreamFunction` и прогон агента (этапы 1 и 4);
- прогон фикстур в `codelab_app` и `acp_client_kit` (этап 5);
- исправление клиента под фикстуры — если прогон находит расхождение со спецификацией, оно фиксируется отдельным change.

## Decisions

### D1. Корпус в `acp_testing`, прогон в пакете клиента

Фикстуры, модель, матчер и драйвер — в `acp_testing` (общий тестовый пакет обеих сторон); тест, который проигрывает корпус на конкретном клиенте, — в пакете клиента (`acp_client_core/test/fixtures/`). Так тот же корпус позже проигрывается в `acp_client_kit` и `codelab_app`, а агентский драйвер (этап 4) ложится рядом с клиентским. Путь к каталогу корпуса драйвер получает через `Isolate.resolvePackageUri('package:acp_testing/...')` либо параметром; тесты не зависят от текущего каталога.

### D2. Схема как документ, проверка — в загрузчике

`_schema.json` (draft 2020-12, `additionalProperties: false` на верхнем уровне, в `setup` и в кадре) описывает формат для авторов и редакторов. Загрузчик проверяет структуру сам: обязательные поля, типы, допустимые значения `dir`, `roles`, `repeat`, неизвестные ключи. Тест `fixtures_schema_sync_test.dart` сверяет множества ключей, которые знает загрузчик, со свойствами `_schema.json`, чтобы они не разошлись.

Альтернатива — зависимость `json_schema` для валидации по схеме: новая зависимость ради 12 файлов, а сообщения валидатора хуже, чем у загрузчика с путём поля. Отклонено; вернуться, если формат вырастет.

### D3. Нормализация и сравнение

Ожидаемый и фактический кадры проходят одну нормализацию (§14.5): подстановка переменных, `$capture`, `<ts>`, префикс `cwd` → `${cwd}`, разделители путей → `/`, правила `normalize.replace` фикстуры. Сравнение точное: лишний ключ — расхождение; порядок ключей не важен, порядок массивов важен, кроме `unordered`. `_meta` всегда сравнивается как `$partial`. Результат сравнения — список расхождений `$.params.update.status: expected "completed", got "failed"`; тест падает с этим списком.

### D4. Клиентский драйвер

`runClientFixture(fixture, clientFactory, {onBeforeExpect})` (§14.10):

1. фикстура без `client` в `roles` пропускается (`skip` с причиной), блок `llm` игнорируется;
2. `FakeAcpTransport(autoRespondToInitialize: false)`; если `skipInitialize` не задан, драйвер сам проигрывает стандартный handshake (`initialize`, `session/new`): ответы агента — стандартные ответы драйвера с учётом `setup.mode` и `setup.config`, `${sessionId}` берётся из ответа `session/new`;
3. кадр `a2c` → подстановка переменных и `emitInbound`; кадр `c2a` → ожидание следующего сообщения в `sentMessages` (таймаут 5 с), нормализация и сравнение;
4. кадры `c2a`, которые клиент шлёт по действию пользователя (`session/prompt`, ответ на `session/request_permission`, `session/cancel`), требуют вызова API клиента: драйвер вызывает `onBeforeExpect(frame)` до ожидания, тест выполняет действие (например, выбирает вариант разрешения);
5. `fs/*` клиент обслуживает через `TextFileReader`/`TextFileWriter` поверх fake fs-порта в памяти (`InMemoryFixtureFileSystem`, §14.10 допускает fake fs-порт), заполненного из `setup.files`; нарезка `line`/`limit` — как у адаптера приложения `text_file_io.dart`. `terminal/*` — через `FixtureTerminalProcessRunner` на `FakeTerminalProcessHandle`, сценарий процесса берётся из фикстуры (`setup.terminal`: строка команды `command args…` или только `command` → вывод и код выхода, процесс завершается сразу);
6. после кадров драйвер дожидается действий пользователя, зарегистрированных в хуке (`step.track`), проверяет тишину (лишний кадр клиента в течение 100 мс — провал) и сверяет `after.files` с файловой системой клиента; проверки состояния клиента пишет тест, а не фикстура.

Уточнения, найденные при реализации:

- **Кадр `a2c` превращается в конкретное значение** (`FrameMatcher.materialize`): переменные подставляются, `$capture` генерирует id `fixture-<имя>` и сохраняет его в переменную, `$contains`, `$partial` и `$oneOf` (первый вариант) дают своё значение, `$any` — строку `fixture-any`, `$absent` убирает ключ, `<ts>` — фиксированное время; `repeat: "+"` с `match.$text` отправляется одним кадром со всем текстом. `$regex` в кадре `a2c` для клиентской роли — ошибка фикстуры.
- **Стандартный handshake**: `initialize` сверяется по `$partial` с `protocolVersion: 1` (и `clientCapabilities`, если задан `setup.clientCapabilities`), ответ — версия 1 и пустые `agentCapabilities`; `session/new` — по `$partial` с `cwd`, ответ — `sessionId: fixture-session-1` и при `setup.mode` блок `modes` из одного режима. `setup.config` — конфиг агента (§15), клиентский прогон его не читает: фикстура, которой нужен конкретный ответ `session/new` (например, `configOptions`), пишет handshake сама с `skipInitialize`.
- Хук `onBeforeExpect` вызывается и для кадров handshake (`step.isHandshake`): тест выполняет там `connect` и `createSession`.

`setup.terminal` — расширение схемы §14.4 для клиентской роли: агентская проверка его не читает (вывод команды там приходит кадрами `terminal/output`). Поле описано в agent-core-architecture §14.4 (внесено вместе с этим change) и добавляется в `_schema.json`.

### D5. Инварианты корпуса на этапе 0

- FIX-1 (непустой `spec`, ссылки на существующие файлы `docs/acp/protocol/`, якорь существует в файле) и FIX-4 (без `extensions` нет `_meta.codelab`, `data.codelab`, `_codelab/*`) — в `fixtures_load_test.dart` с этапа 0 полностью.
- FIX-2 (каждый вид `sessionUpdate` и каждый метод `acp_method_codec.dart` есть в фикстуре каждой роли) — `fixtures_coverage_test.dart` с явным списком `pendingCoverage`: виды и методы, для которых фикстуры появятся на этапе 4 (`session/load`, `session/list`, `fs/write_text_file`, `terminal/kill`, `user_message_chunk`, `current_mode_update`, `session_info_update` и т. п.). Тест падает и на непокрытом элементе вне списка, и на элементе из списка, который уже покрыт, — список только сокращается. Агентская роль в FIX-2 проверяется с задачи 4.8; до неё тест проверяет клиентскую роль.
- FIX-3 — с агентским прогоном (задача 4.8).

### D6. Блок `llm` пишется сразу

Фикстуры с ролью `agent` содержат блок `llm` уже на этапе 0: сценарий пишется один раз, вместе с кадрами. На этапе 0 загрузчик проверяет его структуру по таблице §14.7 (поля шага, допустимые `stopReason`), выполнение — с этапа 4. Расхождения, найденные агентским прогоном, правятся в задаче 4.8 со ссылкой на раздел спецификации.

### D7. Правила изменения фикстур

- новая фикстура или изменение ожидаемых кадров — только со ссылкой `spec` на раздел `docs/acp/protocol/*`, который обосновывает кадр;
- правка ожидаемого кадра под поведение реализации без такой ссылки запрещена (`AGENTS.md` §17: «запрещено молча менять specification под существующую реализацию»);
- обновление вендоренной спецификации ACP → прогон корпуса, расхождения разбираются по одному;
- пункт о фикстурах — в шаблоне pull request.

### D8. TDD

Каждая часть начинается с красного теста (§9.0, правило 3): матчер — мутационные тесты (лишний ключ, другой статус, другой порядок) до реализации; загрузчик — неполные фикстуры до реализации; драйвер — фикстура `acp/prompt-text-end-turn` до реализации драйвера. Фикстуры добавляются по одной: фикстура → прогон → при расхождении с клиентом решение «фикстура ошибочна» (ссылка на спецификацию) или «клиент ошибается» (отдельный change).

## Risks / Trade-offs

- [Фикстура закрепляет неверное прочтение спецификации] → обязательный `spec` со ссылкой на раздел и якорь; ревью кадров по спецификации, а не по выводу клиента.
- [Клиент расходится со спецификацией на одной из 12 фикстур] → фикстура не подгоняется; расхождение фиксируется отдельным change, фикстура временно `skip` с id этого change — только с явной пометкой в `tasks.md`.
- [Тайм-ауты ожидания делают тест медленным или нестабильным] → таймаут 5 с только на ожидание кадра `c2a`, fake-транспорт синхронен; CI не ретраит упавшие тесты.
- [Схема и загрузчик расходятся] → `fixtures_schema_sync_test.dart` (D2).

## Migration Plan

Только новые файлы тестов и данные; поведение приложения не меняется. Откат — revert pull request.
