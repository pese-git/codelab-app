## Goals / Non-Goals

**Goals:**
- Статический сайт, который собирается из `site/` и опубликованных документов одной командой и проверяется в CI.
- Документ, который читается на GitHub, без правок читается и на сайте; ссылки работают в обоих местах.
- Правка документации, ломающая сайт, видна в pull request, где она сделана.
- Node не влияет на Dart-часть: на сторож, Melos, Dart-джобы CI и их охват.
- Хостинг подключается позже изменением конфигурации CI, без переделки сайта.

**Non-Goals:**
- Хостинг, деплой, домен, заголовки безопасности хостинга.
- `docs:screenshots` и витринные снимки.
- Первая новость.
- Поиск, английская версия, аналитика, RSS.
- Новые документы продуктов.

## Decisions

### D1. `site/` — изолированный Node-проект; правило сторожа не нужно

Состав каталога:

```text
site/
├── .nvmrc               точная версия Node (LTS на момент реализации)
├── .npmrc               save-exact=true, engine-strict=true, fund=false, audit=false
├── package.json         private, type: module, engines.node = версия из .nvmrc
├── package-lock.json
├── astro.config.mjs
├── tsconfig.json
├── src/
│   ├── content.config.ts      коллекции docs и news (D3, D10)
│   ├── content/news/          новости
│   ├── lib/                   чистые функции: адреса, публикация, навигация (D3, D4, D9)
│   ├── plugins/               remark/rehype-плагины (D5, D7, D11)
│   ├── components/, layouts/, pages/, styles/
│   └── scripts/               клиентские скрипты: тема, mermaid (D7, D8)
├── scripts/check-links.mjs    проверка собранного сайта (D6)
└── test/                      тесты vitest (D14)
```

- **Где Node.** Node, npm и JavaScript-зависимости живут только в `site/`. `.nvmrc` лежит в `site/`, а не в корне: всё, что относится к сайту, попадает под один префикс пути. Это нужно для охвата CI (D13) и для понятной зоны `site-engineer`.
- **Скрипты `package.json`:**
  - `check` — `astro check`;
  - `test` — vitest;
  - `build` — `astro build`;
  - `check:links` — `node scripts/check-links.mjs dist`;
  - `verify` — все четыре по порядку плюс проверка точных версий (сценарий «Диапазон версии отклоняется»; это короткая проверка в `check-links.mjs` или отдельной функции `src/lib/`, без новой зависимости).
- **Телеметрия Astro выключена** (`ASTRO_TELEMETRY_DISABLED=1` в скриптах): сборка не отправляет данные наружу.
- **`.gitignore` корня:** `site/node_modules/`, `site/dist/`, `site/.astro/`.
- **`analysis_options.yaml` корня:** `site/**` добавляется в `analyzer.exclude`. Тогда `fvm dart analyze` из корня не обходит `node_modules`. `dart format .` исключений `analysis_options` не читает, но `.dart`-файлов в `site/` нет. Задача 2.4 проверяет, что `check-format` проходит, и замеряет время с установленным `node_modules`.
- **Сторож.** Правило в `rules.dart` не нужно: сторож обходит только члены workspace и каталоги своих правил (Context). Проверять ему в `site/` нечего — Dart-импортов там нет. Отрицательное правило «`site/` не член workspace» тоже не нужно. Член workspace без `pubspec.yaml` невозможен, а `package_naming_test.dart` упадёт на любом новом члене, имя которого не по схеме ADR-0002. Граф пакетов в `README.md` не меняется: сайт не пакет. В таблицу «Структура» `README.md` добавляется строка `site/`.

Альтернативы:
- **Node в корне** (`package.json` корня, npm workspaces). Корень стал бы Node-проектом. `node_modules` в корне задел бы все Dart-команды. Охват CI пришлось бы описывать списком файлов, а не одним префиксом.
- **Правило сторожа «каталоги вне workspace не содержат `pubspec.yaml`»** — защита от несуществующей угрозы. Не выбрано (§13).

### D2. Версии и цепочка поставок

- **Версии точные:** `save-exact`, проверка в `verify`. Lock-файл коммитится вместе с изменением `package.json`. Установка — только `npm ci`, локально и в CI.
- **Astro** — актуальная стабильная мажорная версия на момент реализации. Конкретная версия фиксируется в `package.json`, в документах не дублируется (`AGENTS.md` §4).
- **Прямые зависимости — минимум:**
  - `astro`, `@astrojs/check`, `typescript` — сборка и проверка типов;
  - `mermaid` — D7;
  - `vitest` — D14;
  - `@astrojs/markdown-remark` — конвейер unified для Markdown. В Astro 7 Markdown по умолчанию обрабатывает Sätteri, на котором remark- и rehype-плагины не работают, а `markdown.remarkPlugins` и `rehypePlugins` объявлены устаревшими. `astro.config.mjs` явно задаёт `markdown.processor: unified({ remarkPlugins, rehypePlugins })`, и плагины D5, D7, D11 работают в том же конвейере, что их тесты (D14);
  - `@types/node` — типы `process.env` и модулей `node:` для `site.config.ts`, плагинов и `scripts/check-links.mjs`; без них `astro check` не проходит;
  - пакеты unified, которые плагины импортируют напрямую (например, `unist-util-visit`), — объявляются явно, даже если уже пришли транзитивно с Astro;
  - интеграции Astro (sitemap, MDX), UI-фреймворки (React, Vue), CSS-фреймворки (Tailwind) не добавляются. Сайт — статический HTML и CSS с двумя небольшими клиентскими скриптами (D7, D8).
- **Лицензии** проверяются при добавлении и при обновлении lock-файла. Разрешены MIT, BSD, ISC, Apache-2.0, BlueOak-1.0.0, CC0-1.0, Unlicense, 0BSD. Двойная лицензия с разрешительным вариантом допустима: например, DOMPurify в зависимостях mermaid — `MPL-2.0 OR Apache-2.0`. Copyleft без разрешительного варианта не распространяется посетителям: такой код НЕ ДОЛЖЕН попадать в `dist/`.
  - **Инструменты сборки** с copyleft-лицензией допустимы, если работают только при сборке и в `dist/` не попадают. На момент реализации это `lightningcss` (MPL-2.0) и `@img/sharp-libvips-*` (LGPL-3.0), транзитивные зависимости Astro.
  - **`elkjs`** (`EPL-2.0 OR GPL-3.0`) приходит с `mermaid` для раскладки ELK. Сайт эту раскладку не регистрирует, и её чанк исключается из сборки (D7). `scripts/check-links.mjs` падает, если код `elkjs` оказался в `dist/` (D6).
  - Сторонний код, шаблоны и темы не копируются (`AGENTS.md` §5).
- **Install-скрипты.** CI ставит зависимости через `npm ci --ignore-scripts`. Если сборке нужен install-скрипт зависимости, исключение и причина записываются в skill `codelab-site`, а флаг для этой зависимости снимается явно (`npm rebuild <пакет>`). Задача 2.2 это проверяет.

Альтернатива — **pnpm или Yarn**. Быстрее и строже к фантомным зависимостям, но это ещё один инструмент, который надо ставить (corepack). Пользователь выбрал npm.

### D3. Публикуемые источники — allowlist, одна коллекция `docs`

Коллекция `docs` в `src/content.config.ts` использует загрузчик `glob` Astro с базой в корне репозитория (`../`). Шаблоны — ровно список из спецификации («Публикуемые источники документации»). Список шаблонов — одна константа в `src/lib/publish.ts`. Её используют загрузчик, плагин ссылок (D5) и тесты: определение «опубликован ли файл» существует в одном месте.

- **Allowlist, а не denylist.** Новый каталог в `docs/` (например, следующий `docs/backlog/`-подобный) не публикуется, пока его не добавят в список осознанно. Это защищает от публикации внутренних отчётов (`AGENTS.md` §2, приоритет 1).
- **Только `.md`.** `AGENTS.md` исключён явно, даже если окажется внутри `doc/`.
- **Отложено: `docs/integrations/claude-code.md` и `docs/codelab-spec.md`.** Пользователь пока не решил, публиковать ли их. По умолчанию не публикуются — они не в allowlist. Чтобы опубликовать, достаточно одной строки в константе `src/lib/publish.ts` и строки в требовании спецификации; группу навигации D9 они получат как `docs/**` вне `user` и `ops` — её нужно будет добавить той же правкой.
- **Frontmatter в документах не нужен.** Документы читаются на GitHub, а frontmatter там отображается таблицей. Заголовок страницы — первый `#`; если его нет, сборка падает. Описание страницы (`<meta name="description">`) — первый абзац после заголовка, обрезанный по границе слова.
- **Файлы вне `site/`.** Сборка читает Markdown и изображения вне корня проекта Astro, поэтому Vite нужно явно разрешить корень репозитория (`vite.server.fs.allow`). Разрешается корень целиком, а не отдельные каталоги: публикацию ограничивает allowlist загрузчика, а не файловый доступ Vite. Доступ dev-сервера ограничен `127.0.0.1` (настройка Astro по умолчанию).

Альтернативы:
- **Коллекция на каждый источник** (`user`, `ops`, `apps`). Три загрузчика и три схемы с одинаковыми полями. Группировка нужна только навигации (D9), и её проще вывести из пути.
- **Символические ссылки из `site/src/content/` в каталоги документации.** Хрупко на Windows и в git. Ссылки и ошибки указывают на путь symlink, а не на исходный файл.

### D4. Адрес страницы выводится из пути файла

`pageUrl(repoPath)` — чистая функция в `src/lib/urls.ts`:

| Путь в репозитории | Адрес на сайте |
|---|---|
| `docs/user/README.md` | `<base>docs/user/` |
| `docs/user/configuration.md` | `<base>docs/user/configuration/` |
| `apps/codelab_cli/README.md` | `<base>docs/apps/codelab_cli/` |
| `apps/codelab_cli/doc/user-guide.md` | `<base>docs/apps/codelab_cli/doc/user-guide/` |
| `packages/dart/codelab_setup/README.md` | `<base>docs/packages/dart/codelab_setup/` |

- Правила: префикс `docs/` у источников `docs/*` не дублируется; `README.md` даёт адрес каталога; регистр и подчёркивания сохраняются.
- Отображение обратимо и механично. По адресу видно, какой файл править. Переименование файла меняет адрес — это осознанная цена.
- Конечный слэш у всех адресов: `trailingSlash: 'always'`, `build.format: 'directory'`. Так статический хостинг отдаёт `index.html` без настроек.

Альтернатива — **человекочитаемые слаги из frontmatter** (`/docs/cli/`). Нужен frontmatter (D3), нужна таблица соответствия, и появляется второй источник правды об адресе.

### D5. Перевод ссылок — remark-плагин `repoLinks`

Плагин (`src/plugins/repo-links.ts`) обходит узлы `link`, `image` и `definition` mdast каждого документа коллекции `docs`. Путь исходного файла от корня репозитория берётся из `file.path`.

1. **Не трогаются** ссылки со схемой (`http:`, `https:`, `mailto:`) и якоря `#…`.
2. **Ошибка сборки** (`file.fail` с позицией, D11): `file:`; абсолютный путь (`/…`, `C:\…`); путь, который после нормализации выходит за корень репозитория; путь к несуществующему файлу или каталогу. В сообщении — путь документа, строка и исходная ссылка.
3. **Изображение** (`image`) с пустым `alt` — ошибка сборки. Существующее изображение остаётся относительным путём: Astro обрабатывает относительные изображения в Markdown коллекций сам — копирует их в сборку и оптимизирует. Ссылка (`link`) на изображение — как на неопубликованный файл.
4. **Опубликованный файл** (D3) → `pageUrl()` + якорь.
5. **Существующий неопубликованный файл** → `${repoUrl}/blob/${repoRef}/${path}#якорь`; каталог → `${repoUrl}/tree/${repoRef}/${path}`.

Настройки:
- `repoUrl` и `repoRef` — в `src/site.config.ts`. `repoUrl` — `https://github.com/pese-git/codelab-app`, совпадает с `origin`.
- **`repoRef` — параметр конфигурации** (ответ на Q2). Порядок: `SITE_GITHUB_REF`, если задан; иначе `GITHUB_SHA` (CI); иначе `git rev-parse HEAD` при сборке. Если ни одно не доступно (сборка вне git без переменных) — ошибка сборки с подсказкой задать `SITE_GITHUB_REF`, а не молчаливая ветка.
  - Почему коммит сборки: ссылка указывает ровно на ту версию файла, из которой собран сайт, и не бывает 404 на файлы, которых ещё нет в `master`. В pull request `GITHUB_SHA` — merge-коммит `refs/pull/<N>/merge`; это приемлемо, потому что сборки pull request не публикуются.
  - Окончательная цель (`master`, `develop` или коммит) выбирается вместе с хостингом и задаётся одной переменной в джобе публикации.
- Регистр пути проверяется точно, а не по правилам файловой системы. Иначе ссылка, рабочая на macOS (регистронезависимая ФС), ломается на GitHub и в CI на Linux.
- Якорь в адресе GitHub не проверяется: GitHub строит якоря неопубликованных файлов сам. Якоря опубликованных страниц проверяет D6.

Альтернативы:
- **rehype на HTML.** Позиция в Markdown-исходнике теряется. Ошибка указывала бы на HTML, а не на строку документа.
- **Переписывать ссылки в самих документах на адреса сайта.** Ломает чтение на GitHub. Противоречит решению пользователя.

### D6. Проверка ссылок собранного сайта — свой скрипт без зависимостей

`scripts/check-links.mjs` (только `node:fs`, `node:path`) читает каждый `*.html` из `dist/` и проверяет:
- каждый `href` и `src` с префиксом `base`: целевой файл существует (`…/` → `…/index.html`);
- якорь целевой страницы есть среди её `id`.

Внешние адреса не запрашиваются: проверка без сети детерминирована и не зависит от чужих серверов. Тот же скрипт ищет в `dist/` абсолютные пути домашних каталогов (D11) как вторую линию после плагина. Ловит пути, пришедшие не из документов, а из страниц сайта.

Разбор HTML — регулярными выражениями по атрибутам `href`, `src` и `id`. Выход Astro предсказуем, а скрипт проверяет только свою сборку. Тесты (D14) фиксируют разбор на образцах выхода Astro.

Альтернативы:
- **lychee** (Rust) — бинарь в CI и локально, лишний инструмент.
- **Пакет npm `linkinator` или аналог** — зависимость ради 100 строк. Сетевые проверки пришлось бы отключать.
- **Только проверка в плагине (D5).** Якоря целевых страниц плагин не видит: заголовки другого файла ещё не разобраны. Ссылки страниц сайта (главная, возможности, новости) плагин не проходит вовсе.

### D7. Mermaid — remark-плагин и ленивый клиентский скрипт

- **Плагин** `src/plugins/mermaid-blocks.ts` заменяет `code` с `lang === 'mermaid'` обычным узлом дерева, а не сырым HTML: элемент `pre` с классом `mermaid-source` и атрибутом-меткой `data-mermaid` (через `data.hName` и `data.hProperties`), внутри — исходный текст схемы как текстовый узел. Экранирование делает сериализатор. Узел не сырой HTML, поэтому защита D11 его не видит и не отвергает; Shiki его не подсвечивает. Без JavaScript виден исходный текст (сценарий «Без JavaScript»).
- **Клиентский скрипт** `src/scripts/mermaid.ts`:
  1. Подключается из макета документа. Если на странице нет `[data-mermaid]`, он ничего не загружает.
  2. Если блоки есть — `import('mermaid')`. Модуль собирается Vite в отдельный чанк сборки: никакого CDN.
  3. Вызывает `mermaid.initialize({ startOnLoad: false, securityLevel: 'strict', theme })`. Тема — `default` для светлой темы сайта и `dark` для тёмной.
  4. Отрисовывает каждый блок через `mermaid.render` в соседний контейнер. При первой отрисовке скрипт сохраняет `textContent` блока `pre` в памяти; `data-mermaid` — только метка блока, исходник в атрибуте не дублируется.
  5. Подписывается на событие смены темы (D8) и перерисовывает все схемы из сохранённого исходника.
- **Без раскладки ELK.** Скрипт не регистрирует раскладку ELK (`mermaid.registerLayoutLoaders` не вызывается для `elk`), и сборка не содержит чанк `elkjs`: его лицензия `EPL-2.0 OR GPL-3.0` не проходит D2. Если Vite всё равно выпускает чанк из динамического импорта внутри `mermaid`, модуль `elkjs` подменяется в `vite.resolve.alias` заглушкой, которая бросает ошибку. Схемы документации ELK не используют. Отсутствие чанка проверяет `check-links` (D6).
- **Ошибка синтаксиса схемы** не ломает страницу. Исходный текст остаётся видимым, под ним — сообщение «Схему не удалось отрисовать», ошибка пишется в `console.error`.
- **Цвета.** Тема mermaid не настраивается под токены сайта цвет в цвет. Встроенные `default` и `dark` читаются в обеих темах, а схемы документации цветов не задают (`codelab-docs` §6).

Альтернативы:
- **Отрисовка при сборке** — отклонена пользователем (ADR-0003, Alternative 5).
- **Подключать mermaid на всех страницах.** Скрипт большой, а схемы есть в 8 документах из 15.

### D8. Оформление: токены Fluent, системные шрифты, тема без вспышки

- **Токены.** `src/styles/tokens.css` объявляет custom properties с теми же именами и значениями, что `.fx` и `.fx.dark` в `docs/design/claude-design/fluent.css`: `--mica`, `--layer`, `--card`, `--stroke`, `--text`, `--text2`, `--ok`, `--warn`, `--bad`, `--code-bg`, `--syn-*`, тени. Акцент — производные `#0078D4`: `--accent` и `--on-accent`. `--accent-text` — `#005FB8` в светлой теме и `#60CDFF` в тёмной (`Appearance.dc.html`, встроенные темы Fluent Light и Fluent Dark).
  - Источник каждого значения записан в skill `codelab-site`.
  - Это наш собственный экспорт макетов, а не сторонний код. Записи в `THIRD_PARTY_NOTICES.md` не требуется.
  - Расхождение токенов сайта с `fluent.css` — дефект ревью.
- **Шрифты — системные стеки** из `fluent.css`. Текст: `'Segoe UI Variable Text', 'Segoe UI', -apple-system, BlinkMacSystemFont, system-ui, sans-serif`. Код: стек `codelab_ui` (`Menlo`, `SF Mono`, `Consolas`, `Cascadia Mono`, `DejaVu Sans Mono`, `monospace`). Веб-шрифты не загружаются. Segoe UI нельзя распространять, сторонние шрифты потребовали бы записи в `THIRD_PARTY_NOTICES.md`. Без запросов страница быстрее.
- **Типографика** — шкала Fluent из `fluent.css`: caption 12/16, body 14/20, body large 18/24, subtitle 20/28, title 28/36, title large 40/52. Радиусы — 4 px у контролов и 8 px у карточек.
- **Тема.**
  - По умолчанию — `prefers-color-scheme`. Переключатель в шапке сохраняет выбор в `localStorage` (`codelab-site-theme`: `light`, `dark` или отсутствие ключа — «как в системе»).
  - Короткий встроенный скрипт в `<head>` ставит класс темы на `<html>` до первой отрисовки. Это единственный встроенный скрипт сайта.
  - При смене темы скрипт отправляет событие `codelab-theme-change` на `document`. Его слушает mermaid (D7).
- **Подсветка кода** — Shiki (встроен в Astro) с двумя собственными темами `src/styles/shiki-light.json` и `shiki-dark.json`, собранными из токенов `--syn-*` и `--code-*`. Режим двух тем Astro переключает их по классу темы через CSS-переменные.

Альтернативы:
- **Готовые темы Shiki** (`github-light`, `github-dark`). Код на сайте выглядел бы иначе, чем в приложении.
- **CSS-фреймворк Fluent** (Fluent UI Web Components). Тянет компонентную библиотеку ради нескольких кнопок и карточек.

### D10. Новости — коллекция `news` со схемой

- **Файл** — `site/src/content/news/<version>.md`.
- **Схема** — zod в `content.config.ts`:
  - `title` — строка;
  - `date` — `YYYY-MM-DD`;
  - `version` — `MAJOR.MINOR.PATCH` с необязательным суффиксом пре-релиза;
  - `summary` — строка до 200 символов.
- **Проверки сборки.** Неполная запись — ошибка сборки (стандартная проверка схемы Astro). Две записи с одной `version` — ошибка из `src/lib/news.ts`, в сообщении оба пути.
- **Порядок** — по `date`, от новой к старой; при равных датах — по `version`. На главной — три последние.
- **`CHANGELOG.md` в корне** (ответ на Q4) — источник фактов о выпуске:
  - на русском; сверху — описание формата, затем разделы выпусков от нового к старому: `## <version> — YYYY-MM-DD`, подразделы «Добавлено», «Изменено», «Исправлено», «Удалено», «Безопасность» (пустые не пишутся); пункт — одна строка о видимом изменении со ссылкой на архив change, если он есть;
  - ведётся в `release/<version>`: раздел выпуска пишется при подготовке выпуска, а не в каждом `feature/*`;
  - не публикуется на сайте (не в allowlist); новость ссылается на него на GitHub;
  - для CI — документация в корне (`*.md`), Dart-джобов и `site` не запускает.
- **Кто пишет новость.** `docs-writer` в `release/<version>`, после раздела `CHANGELOG.md`. Источники: раздел выпуска `CHANGELOG.md` и `proposal.md` архивированных changes выпуска (`openspec/changes/archive/`, даты между предыдущим выпуском и текущим). Правила текста — skill `codelab-site`: что изменилось для пользователя, ссылки на документы, без обещаний. Пункты «раздел `CHANGELOG.md`» и «новость на сайте» добавляются в чек-лист выпуска `AGENTS.md` §22, пункт о новости — в агента `docs-writer`; зона записи агента расширяется на `site/src/content/news/**`. Сам `CHANGELOG.md` — корневой файл вне зоны `docs-writer`: раздел выпуска пишет тот, кто готовит `release/*` (оркестратор), `docs-writer` его читает.
- **Ссылки.** Новость лежит в `site/`, поэтому ссылки на документы в ней — адреса сайта от корня без `base` (`/docs/user/configuration/`). Markdown не может вызвать `withBase`, а Astro не добавляет `base` к ссылкам Markdown, поэтому remark-плагин `src/plugins/news-base.ts` добавляет `base` к корневым ссылкам и изображениям файлов коллекции `news` (D12). Схемы ссылок в новостях — только `http:`, `https:`, `mailto:` и корневые адреса; остальное — ошибка сборки. Итоговые адреса проверяет D6, а не D5.

### D11. Безопасность публикации

Слои защиты:

1. **Allowlist источников** (D3) — главный рубеж. `docs/backlog/` и подобное не публикуются, пока их не добавят осознанно.
2. **Сырой HTML в документах.** rehype-плагин `src/plugins/raw-html-guard.ts` — ошибка сборки на любой элемент вне `details`, `summary`, `br`, `kbd`, `sub`, `sup`. Разрешённые элементы пишутся без атрибутов; единственное исключение — `open` у `details`. Любой другой атрибут, в том числе обработчик события (`<kbd onclick=…>`), — ошибка сборки с позицией. Проверяется только сырой HTML авторов документов: узлы плагинов (D7) сырым HTML не являются. HTML-комментарии удаляются. GitHub сам вырезает `script`, `iframe`, `style` и обработчики событий при отображении, поэтому документ, которому они нужны, и так неправилен. На сайте они бы выполнились.
3. **Личные пути.** Remark-плагин находит абсолютные пути домашних каталогов в тексте и коде документов: `/Users/<имя>/`, `/home/<имя>/`, `C:\Users\<имя>\`. Это ошибка сборки с позицией. Маски `user` и `me` разрешены: `docs/user/configuration.md` уже показывает вывод `codelab config check` с `/home/me/.codelab/config.yaml`, а `codelab-docs` §7 маскирует имя пользователя как `user`. Список масок — одна константа, её же читает `check-links.mjs`, который повторяет поиск по `dist/` (D6).
4. **Секреты.** Отдельного сканера нет. Документы маскируют токены по `codelab-docs` §7, а сайт публикует только то, что уже публично в репозитории (он публичный).
5. **Сторонние запросы и аналитика.** Не подключаются: ни шрифтов, ни CDN, ни счётчиков (D2, D8). CSP-заголовки — забота будущего хостинга. Встроенный скрипт темы (D8) — единственный, его хэш можно будет внести в CSP.

Альтернатива — **санитайзер `rehype-sanitize` вместо ошибки**. Молча меняет содержимое: документ на сайте и на GitHub выглядит по-разному, а автор не узнаёт об этом.

### D12. `base` и `site` из окружения

`astro.config.mjs` читает `SITE_URL` (по умолчанию не задан) и `SITE_BASE` (по умолчанию `/`, нормализуется к виду `/…/`).

- Внутренние адреса строит одна функция `withBase()` в `src/lib/urls.ts`: компоненты, плагин ссылок (D5), навигация. Адреса вида `href="/docs/…"` вручную не пишутся. Нарушение ловит сборка с непустым `base` в CI (D13) и `check-links.mjs`.
- Без `SITE_URL` не формируются `canonical` и карта сайта. Интеграция sitemap добавляется вместе с хостингом.
- GitHub Pages для проекта — это `SITE_URL=https://pese-git.github.io`, `SITE_BASE=/codelab-app/`. Другой хостинг в корне домена — `SITE_BASE=/`.

### D13. CI: признак `site` в `ci_scope.dart` и джоб `site`

**`tool/ci/ci_scope.dart`:**
- у `CiScope` появляется поле `site` (`bool`);
- полный прогон (`fullReason`, файл вне пакетов) → `site: true`;
- файл с префиксом `site/` — файл сайта: он ставит `site: true`, не считается «вне пакетов» и не попадает в Dart-матрицу;
- файлы `docs/**`, `openspec/**`, `apps/*/README.md`, `apps/*/doc/**`, `packages/**/README.md`, `packages/**/doc/**` ставят `site: true`. Их прежняя классификация для Dart-матрицы не меняется: `docs/**` и `openspec/**` — документация, `apps/*/doc/**` — файл пакета, как сейчас;
- предикат «влияет ли файл на сайт» — одна функция `_affectsSite` рядом с `_isDocumentation`. Шаблоны — path-фильтр из решения пользователя плюс `openspec/**` (ответ на Q6, ниже).

**Почему весь `openspec/**`, а не только файлы, на которые ссылается документация (Q6).** Точный вариант потребовал бы в `ci_scope.dart` разбирать Markdown опубликованных документов и разрешать относительные ссылки — второй реализации D5 на Dart. Она бы расходилась с плагином сайта, а ошибка в ней молча пропускала бы поломки. Удалённый или перенесённый файл (архивирование change) к тому же нужно сверять со ссылками документов на `HEAD`, а не с изменёнными файлами — ещё одна ветка логики. Цена простого варианта — джоб `site` на pull request только с `openspec/` (около 1–2 минут на `ubuntu-latest`, параллельно; Dart-джобов такие pull request по-прежнему не запускают). Она меньше, чем стоимость и риск второй реализации.

**`tool/ci/affected.dart`** пишет `site=<true|false>` в `$GITHUB_OUTPUT`, а в summary — строку `site: yes/no`.

**`.github/workflows/ci.yml`:**

```yaml
  site:
    needs: scope
    if: needs.scope.outputs.site == 'true'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    defaults: { run: { working-directory: site } }
    env:
      ASTRO_TELEMETRY_DISABLED: '1'
      SITE_BASE: /codelab-app/
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: site/.nvmrc
          cache: npm
          cache-dependency-path: site/package-lock.json
      - run: npm ci --ignore-scripts
      - run: npm run verify
```

- Джоб `site` идёт параллельно с `checks`, а не после него. Права — `contents: read` уровня workflow. Секретов нет. Артефакт сборки не загружается: публикации нет, предпросмотр — локальной командой.
- `checkout` без `fetch-depth: 0`: сайту история не нужна.
- **Итоговый джоб `ci` ждёт `site`** (ответ на Q1): `site` в `needs`, проверка `success|skipped`, как у `checks`. Красный `site` блокирует merge в `develop`; пропущенный (`skipped`, ничего сайтового не менялось) — нет. Защита ветки не меняется: обязательным статусом остаётся один `ci` (`testing.md` §74). Задача 5.3.
- **AGENTS.md §21.** Джоб на `ubuntu-latest`, без устройства и симулятора, поэтому правило «никаких device- и simulator-джобов в PR в `develop`» не нарушается. Локальная проверка: `npm run verify` в `site/` — если изменён `site/**`, и СЛЕДУЕТ при правке опубликованных документов, если Node установлен. Без Node check-runner пишет «НЕ ЗАПУСКАЛСЯ: нет Node», и это ловит CI.

Альтернативы:
- **`on.pull_request.paths` в отдельном workflow** — второй workflow со своей логикой охвата. Не учитывает полный прогон (push в `develop`, ночь, `workflow_dispatch`) так же, как `scope`. Path-фильтры workflow на pull request к тому же скрывают статус: пропущенный workflow не даёт проверки вовсе.
- **`dorny/paths-filter`** — стороннее действие ради того, что `ci_scope.dart` уже делает и тестирует.
- **Сайт как ещё одна строка Dart-матрицы `checks`.** Шаг `prepare` ставит FVM и Flutter, а сайту они не нужны.

## Risks / Trade-offs

- **R1. Красный `site` из-за чужой правки документации блокирует merge.** `docs-writer`, исполнитель или автор change меняет ссылку в `docs/user/` или переносит файл в `openspec/`, а сборка падает — и `ci` красный. Смягчение: правило в `codelab-docs`; сообщение с путём, строкой и ссылкой; локальная `npm run verify` (check-runner запускает её по D13); исправление — правка одной ссылки в том же pull request. Отключать джоб ради merge нельзя: битая ссылка — дефект документации (`codelab-docs` §9).
- **R2. Ссылки в `openspec/changes/` устаревают при архивировании.** Один опубликованный документ ссылается на активный change. Архивирование переносит каталог, и ссылка ломается. Теперь `openspec/**` запускает `site` (D13), поэтому поломка видна в pull request архивирования и блокирует его. Смягчение: правило в `codelab-docs` — из документов ссылаться на `openspec/specs/`, а не на активные changes; исправление при архивировании — ссылка на архивный путь.
- **R3. Ссылки на GitHub на коммит сборки** устаревают для читателя: сайт, собранный давно, ведёт на старую версию файла. Репозиторий публичный, 404 нет. Вопрос снимается вместе с выбором цели ссылок на этапе хостинга (D5).
- **R4. Рост времени CI.** `npm ci` с кэшем и сборка 15–30 страниц — порядка минуты-двух на `ubuntu-latest`, параллельно с Dart-джобами. Итоговое время pull request почти не растёт; pull request только с `docs/` или `openspec/` получает один джоб вместо нуля. Задача 5.2 замеряет фактическое время.
- **R5. Цепочка поставок npm.** Сотни транзитивных пакетов. Смягчение: точные версии, lock, `npm ci --ignore-scripts`, без публикации и секретов в джобе. Обновление зависимостей — отдельные pull request с проверкой лицензий.
- **R6. Слаги якорей.** Якоря Astro (`github-slugger`) и GitHub совпадают для обычных заголовков, в том числе кириллических. Расхождения возможны на редких символах. Смягчение: D6 проверяет каждый якорь опубликованных страниц.
- **R7. HTML-подобный текст вне кода** (`<id>` в обычном абзаце) на сайте станет тегом и вызовет ошибку D11. В текущих документах такие места внутри кода. Если встретится — исправление документа (обернуть в `код`). Так он отображается правильно и на GitHub.
- **R8. Скриншоты с баннером DEBUG** на витрине. Осознанно до `docs:screenshots`.
- **R9. `dart format .` обходит `site/node_modules`** локально. Время растёт, ошибок нет. Задача 2.4 замеряет; если заметно — отдельный вопрос о скрипте `check-format` (вне этого change).
