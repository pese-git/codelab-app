## Context

Исследование `docs/architecture/session-lifecycle.md`, `streaming.md`, `concurrency.md` перед этим change (обязательно по AGENTS.md §9) дало точную картину.

**Уже существующий, но неиспользуемый механизм:**
- `ClientConnectionState` (`packages/dart/acp_client_core/lib/src/domain/domain_models.dart:39-60`) — sealed-класс с вариантами `disconnected/connecting/initializing/ready/failed`. Вариант `failed` уже несёт `reason: ConnectionFailureReason`.
- `ConnectionFailureReason` (`domain_models.dart:27-37`): `startFailed, sendFailed, receiveFailed, protocolViolation, unsupportedProtocolVersion, disconnected, closed, timeout, unknown`. Причины `sendFailed/receiveFailed/disconnected/closed/timeout` сегодня нигде не используются ни одним call site — выглядят подготовленными именно под транспортные сбои.
- `ConnectionStateMachine._fail` (`state_machines.dart:260-278`) уже разрешает переход `ready → failed` (и вообще любой, кроме `disconnected → failed`, который явно отклоняется с сообщением "disconnected connection cannot fail again"). То есть reducer не требует изменений — просто никто не вызывает `fail` event для транспортных сбоев.
- `StdioAcpTransport._handleProcessExit` (`stdio_acp_transport.dart:223-234`) уже корректно различает намеренное закрытие (`if (_isClosed || _state == failed) return;`) и неожиданный exit (`_fail(AcpTransportException(code: disconnected, ...))`), что эмитит и `AcpTransportEvent.stateChanged(failed)`, и `AcpTransportEvent.failure(...)` (`_fail`, строки 289-296).
- `AcpClientApplication._bindTransport` (`acp_client_application.dart:545-559`) уже фильтрует по generation (`boundGeneration != _generation`) на уровне подписки на `_transport.events` — событие от старого, замёненного при reconnect транспорта физически не может дойти до `_handleTransportEvent`. Это уже решает race "old connection callback vs new connection" (`concurrency.md` §68) без каких-либо изменений с моей стороны.
- Единственный реальный пробел: `_handleTransportEvent`'s `case AcpTransportFailure(:final error):` (`acp_client_application.dart:724-731`) только вызывает `_recordDiagnostic(...)` и никогда — `_transitionConnection(...)`.

## Goals / Non-Goals

**Goals:**
- Спонтанный отказ транспорта (в первую очередь — неожиданное завершение stdio-процесса) должен доходить до `AcpClientApplication.connectionStateChanges` как `ClientConnectionFailed`.
- `CodeLabShellCubit` должен честно отразить это в `CodeLabShellState`: `connectionStatus: failed`, и очистить поля, описывающие состояние активного запроса, которое больше не может считаться достоверным (per `session-lifecycle.md` §51 — нельзя показывать turn running без подтверждения, если resume не гарантирован).
- Explicit `connect()`/`reconnect()`-failures должны продолжать работать ровно как сегодня, без дублирования диагностики от нового кода.
- Race "событие от старого/заменённого транспорта" не должно влиять на текущее соединение — используя уже существующий generation-механизм, не изобретая новый.

**Non-Goals:**
- **Никакой auto-reconnect/retry-политики.** `session-lifecycle.md` §35-37 и `concurrency.md` §28-30 прямо запрещают придумывать retry/backoff policy ad hoc в feature-коде, если она нигде не утверждена (а она нигде не утверждена). Пользователь видит `Failed` и жмёт уже существующую кнопку `Reconnect` сам — этот UX не меняется.
- **Не вводится новый вариант `ClientConnectionState`** (например, отдельный `connectionLost`/`reconnecting`, который упоминается в документации как концептуально анticipated, но не как обязательный). Переиспользуется уже существующий `failed` с уже существующими, просто неиспользуемыми причинами — по AGENTS.md §13 (пропорциональность архитектуры): abstraction оправдана, если решает конкретную задачу, а не "на будущее". Если впоследствии понадобится полноценный `ConnectionLost → Reconnecting` flow с retry — это отдельный, самостоятельный change.
- **Не очищаются** `transcriptEntries`, `agentCommands`, `configOptions`, список сессий. Это либо локальная история (не "live session trust", а исторический контент, который пользователь вправе увидеть), либо данные, которые естественным образом пересоздаются при следующем `Reconnect` + создании новой сессии через уже существующую логику (`_handleSessionChange`/`createSession`).
- **Не решается** сценарий "resume активного запроса после восстановления соединения" — ACP/используемый агент не гарантирует resume, поэтому turn считается безвозвратно потерянным при потере соединения (что и требует §51), а не "приостановленным в ожидании reconnect".
- **Не трогается** `AcpTransportStateChanged` case — он уже no-op и остаётся таковым: `AcpTransportFailure` эмитится синхронно с `stateChanged(failed)` в том же `_fail()` вызове транспорта, так что достаточно реагировать только на `AcpTransportFailure`, не дублируя логику для `stateChanged`.

## Decisions

- **Переиспользовать `ClientConnectionState.failed` + существующие `ConnectionFailureReason`**, не вводить новый sealed-вариант. Маппинг `AcpTransportErrorCode → ConnectionFailureReason` — тривиальный 1:1 switch (оба enum почти идентичны: `startFailed, sendFailed, receiveFailed, protocolViolation, closed, timeout, disconnected, unknown`; у `ConnectionFailureReason` есть дополнительный `unsupportedProtocolVersion`, используемый только для собственной проверки версии протокола при `initialize`, транспортным кодам не соответствует).
- **Guard в `_handleTransportEvent`**: `if (_connectionState is! ClientConnectionDisconnected) { _transitionConnection(ConnectionStateEvent.fail(...)); }` — тот же паттерн, что уже используется в `_establishConnection` (`acp_client_application.dart:320`) перед намеренным disconnect. Это единственный переход, который `ConnectionStateMachine._fail` отклоняет (`state_machines.dart:262-264`, "disconnected connection cannot fail again") — без guard'а вызов `.stateOrThrow` на отклонённом переходе бросил бы исключение прямо внутри callback'а `_eventSubscription.listen`, что недопустимо.
- **В кубите — guard по `state.connectionStatus == AcpConnectionStatus.connected`**, а не просто "любой `ClientConnectionFailed`". Explicit `connect()`/`reconnect()` уже переводят `connectionStatus` в `connecting`/`reconnecting` ДО await, и сами же обрабатывают итоговую неудачу в своих catch/`result.match` блоках (`shell_cubit.dart:421-526`) — значит, если `ClientConnectionFailed` прилетает, пока `connectionStatus` уже `connecting`/`reconnecting`, это НЕ спонтанная потеря, а часть уже обрабатываемого explicit-flow, и новый подписчик обязан промолчать, чтобы не задваивать diagnostic-записи и не гонять state в конфликтующие стороны. Только `connectionStatus == connected` однозначно означает "мы ни на что не давили — оно умерло само".
- **Что именно очищается** — не общий "sweep всего state", а точечно то, что описывает *активный процесс, за достоверность которого больше нельзя ручаться*: `pendingApproval` (агент никогда не ответит на подтверждение), `isPromptSubmitting`/`canCancel` (turn не может ни завершиться, ни быть отменённым штатно), `isRespondingToApproval`/`isRespondingToConfigOption` (аналогичные in-flight флаги). Список конкретно взят из документированного анти-паттерна "нельзя оставлять `isLoading = true` навсегда" (`concurrency.md` §64) и прямого требования §51 про turn running.
- **Diagnostic вместо тихой очистки** — записывается запись severity error с сообщением из `ConnectionFailureReason`/исходного transport-сообщения, чтобы пользователь понимал, что произошло, а не просто увидел, что композер внезапно "остыл".

## Risks / Trade-offs

- [Агент может упасть буквально в момент, когда пользователь одновременно жмёт `Cancel`/`Reconnect`] → race "disconnect vs completion"/"cancel vs disconnect" уже покрыт существующим generation-механизмом на уровне транспорта/`_bindTransport`; на уровне кубита новый код только *читает* `state.connectionStatus` синхронно в момент получения события (Dart event loop, без промежуточных await), так что параллельный клик не может создать промежуточное несогласованное состояние.
- [Пользователь мог начать новый `connect()` практически одновременно с получением спонтанного `ClientConnectionFailed` от предыдущего соединения] → как только `connect()` выполнит `emit(connectionStatus: connecting)`, guard в кубите (`connectionStatus == connected`) перестанет пропускать более старое, теперь неактуальное событие потери — но событие от **старого** транспорта физически не может прийти позже, чем `_generation` уже увеличен в `_replaceTransport`/новом `connect()`, потому что `_bindTransport` фильтрует по generation на уровне подписки до вызова `_handleTransportEvent`.
- [Маппинг `AcpTransportErrorCode → ConnectionFailureReason` может в будущем разойтись, если один из enum'ов получит новое значение без другого] → switch без `default` (exhaustive), анализатор сам укажет на несоответствие при добавлении нового варианта в любой из enum'ов.
