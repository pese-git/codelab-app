## Context

`SessionUpdate.plan({required List<PlanEntry> entries})` (`packages/dart/acp_protocol/lib/src/acp/session_update.dart:191-195`) — один из вариантов sealed class `SessionUpdate`, наравне с уже обрабатываемыми `userMessageChunk`/`agentMessageChunk`/`toolCall`/`toolCallUpdate`. `CodeLabShellCubit` уже обрабатывает `SessionUpdate` для построения транскрипта и инспектора (см. `_handleSessionChange`/маппинг session updates) — `plan` в этой обработке отсутствует полностью.

`PlanEntry` (`session_update.dart:130-165`) несёт `priority: PlanEntryPriority` (`high`/`medium`/`low`) и `status: PlanEntryStatus` (`pending`/`in_progress`/`completed`) плюс контентное поле (описание шага).

**Референс: Zed.** Реальная реализация в Zed (`crates/acp_thread/src/acp_thread.rs`, `crates/agent_ui/src/conversation_view/thread_view.rs`) размещает эквивалент чеклиста не над транскриптом, а в единой пристыкованной "activity bar" **под** транскриптом, вплотную над композером (`render_activity_bar`, `thread_view.rs:3084-3187`, вызывается сразу после рендера транскрипта — `thread_view.rs:12462`), где план — одна из нескольких секций (наравне с edited files/message queue), разделённых полосой-разделителем. Этот change сознательно перенимает точечные решения этого паттерна (см. Decisions), но **не** переносит весь unified bar целиком — секции "Edited files"/"Queue" здесь не реализуются, см. Non-Goals.

## Goals / Non-Goals

**Goals:**
- Обработка `SessionUpdate.plan` в кубите — последний полученный `Plan` для активной сессии хранится в state.
- `AcpProgressChecklist` рендерит список `PlanEntry` 1:1 по протокольным `priority`/`status`, без изобретения новых промежуточных статусов; приоритет-бейдж показывается явно (сознательное расхождение с Zed, который приоритет не отображает вообще — у нас это поле уже смоделировано в протоколе, скрывать его без причины не стали).
- Компактная сводка встроена в `AcpActivityBar` — новый переиспользуемый docked-контейнер под транскриптом, вплотную над композером; полный список — по клику на всю строку сводки (не только по отдельной иконке).
- Чеклист отсутствует (не рендерится вообще, и `AcpActivityBar` не занимает место), если `plan` update ещё не приходил для сессии — не показываем пустую заглушку.

**Non-Goals:**
- Не добавляется возможность пользователю самому редактировать/переупорядочивать план — это read-only отражение того, что прислал агент.
- Не решается, как несколько последовательных `plan` updates за одну сессию визуально анимируются/сравниваются — на MVP просто заменяем текущий список новым (в отличие от Zed, который мержит по индексам — см. Decisions, это заведомо не переносим).
- **Секции "Edited files" и "Queued messages" в `AcpActivityBar` не реализуются в этом change.** `AcpActivityBar` проектируется расширяемым (список секций с разделителями), но в этом change регистрируется единственная секция — Plan. "Edited files" не заспецирован нигде в проекте; "Queued messages" — предмет отдельного `add-prompt-queue`, который при реализации сможет зарегистрировать свою секцию в том же контейнере вместо отдельной плавающей панели — это координационная заметка для того change, не работа, которую делает этот.
- Не переносится Zed'овское поведение "снапшот завершённого плана в транскрипт" (`snapshot_completed_plan`, `acp_thread.rs:3602-3607`) — план не становится частью истории сообщений после завершения; наше поведение при завершении плана проще (см. Decisions), это сознательный выбор, а не пробел.
- Не связывается с `session/cancel`/`stopReason` напрямую — план остаётся видимым независимо от того, продолжается ли prompt turn.

## Decisions

- **Один `Plan` на сессию, полная замена по каждому update.** `SessionUpdate.plan` несёт полный список entries (не diff/patch) — так что state просто хранит последний полученный `List<PlanEntry>` целиком, без попытки мержить/diff'ить предыдущий список вручную (в отличие от Zed's `update_plan`, `acp_thread.rs:3577-3598`, который зипует по индексам — не переносим, см. Non-Goals).
- **Статус/приоритет — прямой проброс enum, без промежуточного UI-enum** (в отличие от `add-approval-option-kinds`, где потребовался отдельный `AcpApprovalOptionKind` в `acp_ui`, чтобы не тянуть протокольный пакет в UI-слой) — здесь `AcpProgressChecklist` в `acp_ui` получит свои собственные presentation-enum'ы (`AcpPlanEntryStatus`/`AcpPlanEntryPriority`), 1:1 зеркалящие протокольные, по той же причине разделения границ пакетов.
- **Размещение: `AcpActivityBar` под транскриптом, вплотную над композером** (не над транскриптом, как в исходной версии этого design.md), карточка в общем стиле остальных панелей main pane (полная рамка/радиус 6, тот же ритм отступов `SizedBox(height: 12)`, что и между остальными блоками колонки) — без попытки визуально "слить" её границу с композером пиксель-в-пиксель (это была деталь черновика-сравнения, не самостоятельное требование; трогать декорацию `AcpPromptComposer` ради этого не станем, см. §13 AGENTS.md). Причина смены решения о позиции: сверено с реальным кодом Zed, эта позиция читается как "статус следующего действия", а не как ещё один персистентный блок наверху main pane.
- **`AcpActivityBar` — новый переиспользуемый organism** (docked-контейнер, список секций, разделённых горизонтальной линией; заголовок секции кликабелен целиком и разворачивает/сворачивает её тело). В этом change регистрируется только секция Plan — см. Non-Goals про Edited files/Queue.
- **Компактная сводка секции Plan — по алгоритму Zed, адаптированному под наши поля**: если есть entry со статусом `in_progress` и секция свёрнута → `"Current: <текст шага>"` (одна строка, `TextOverflow.ellipsis` — тот же способ обрезки, что и везде в проекте; Zed использует градиентный fade, но заводить для этого единственного места отдельную технику ради визуального нюанса непропорционально, см. AGENTS.md §13) + справа, если остались `pending`, — `"N left"`; иначе (нет `in_progress`, или секция развёрнута) → `"Plan"` слева и агрегированный статус справа: `"N Tasks"` (ничего ещё не `completed`) или `"N/M"` (частичный прогресс). Это заменяет прежнее решение "показываем текст последнего pending-шага" — теперь для состояния "план получен, ничего не начато" показывается обобщённый счётчик, а не название конкретного шага.
- **Прогресс-бар убирается** — сводка полностью текстовая (`"3/7"`/`"N left"`), без визуальной полоски. Следствие принятия сводки в стиле Zed; при необходимости это обратимо в отдельном follow-up.
- **Когда все entries `completed` — сводка скрывается полностью** (не показываем Zed'овское `"All Done"`). У Zed `"All Done"` — переходное состояние перед автоматическим "снапшотом" плана в транскрипт (см. Non-Goals); раз мы этот снапшот-механизм не переносим, оставляем более простое и уже согласованное поведение: пустая секция = не занимает место. Полный список остаётся доступен, пока `currentPlan` не `null`.
- **Разворачивание по клику на всю строку сводки** (не только по иконке-шеврону) — шеврон остаётся как визуальная подсказка, но hit-area — вся строка.
- **Кнопка "✕ Clear Plan" в сводке** — новое клиентское действие: `CodeLabShellCubit.dismissPlan()` очищает `currentPlan` (ставит `null`), секция скрывается. Это **не** протокольная операция и не сообщается агенту — чисто локальное "убрать с экрана"; следующий `SessionUpdate.plan` (если придёт) покажет секцию заново с новыми данными.
- **Развёрнутый список — фиксированная максимальная высота с внутренним скроллом** (а не безусловно растущий список) — длинный план не расталкивает transcript/composer; список скроллится сам в своих границах.
- **State — `CodeLabShellState.currentPlan: List<AcpPlanEntry>?`** (маппинг протокольного `PlanEntry` → `acp_ui`-фасадный `AcpPlanEntry` в кубите). Не заводим промежуточный `CodeLabPlanEntry`: `AcpPlanEntry` уже presentation-safe (свои enum'ы, не протокольные) — тот же паттерн, что уже используется для `configOptions`/`agentCommands` (`_configOptionsFor`/`_agentCommandsFor` возвращают `acp_ui`-типы `AcpConfigOption`/`AcpCommandAction` напрямую, без промежуточного app-level DTO), а не паттерн `CodeLabInspectorEntry` — добавлять третий слой ради одного и того же трёхполейного record было бы лишней абстракцией (AGENTS.md §13).

## Risks / Trade-offs

- [Агент может не присылать `plan` updates вовсе — это опционально по ACP] → секция Plan просто не появляется и `AcpActivityBar` не рендерится (Goals), не считается ошибкой/отсутствующим состоянием.
- [Долгий план с большим числом entries] → решено фиксированной высотой + внутренним скроллом развёрнутого списка (см. Decisions), а не только "сворачиваем по умолчанию".
- [Несколько последовательных `plan` updates подряд (агент часто уточняет план) могут создать "мерцание" UI при каждой полной замене списка] → не решается сложной diff-анимацией в этом MVP; если станет реальной проблемой после использования — предмет отдельного follow-up change.
- [Обобщённая сводка ("N Tasks" вместо названия конкретного следующего шага, пока ничего не `in_progress`) — небольшая потеря информативности по сравнению с прежним решением этого же design.md] → осознанный компромисс ради упрощения алгоритма сводки и согласованности с уже разведанным паттерном; полный список с названиями всех шагов всё равно на расстоянии одного клика.
- [`AcpActivityBar` спроектирован под несколько секций, но использует его пока только Plan] → если `add-prompt-queue` в итоге не станет регистрировать свою секцию в этом контейнере (а сделает отдельную панель), контейнер останется с одной секцией — не проблема (интерфейс `List<Section>` работает и с одним элементом), но абстракция в этом случае будет использована не полностью; решение подтверждать boundary-ценность абстракции — за `add-prompt-queue` в момент его реализации, не сейчас.
