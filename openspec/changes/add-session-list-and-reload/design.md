## Context

После `extract-acp-client-kit` клиентская логика живёт в `codelab_client_core` (`ClientWorkspace`, `SessionHandle`, `TranscriptProjector`). `codelab_desktop` только отображает её через пять Cubit-ов.

Что уже есть:
- `codelab_client_acp` умеет `loadSession` с реплеем (`add-client-session-load-replay`). Ожидающие запросы завершаются ошибкой при сбое транспорта (`_failPendingRequests`).
- Dart-агент (`codelab_agent_acp`) объявляет `loadSession` и `sessionCapabilities.list` для хранилища на диске и отвечает на `session/list` и `session/load`.

Чего нет:
- `session/list` в клиенте;
- таймаута запросов;
- загрузки сессий в рабочем пространстве и UI;
- восстановления после переподключения и перезапуска.

Сейчас `reconnect()` — одна попытка без `session/load` (`acp-client-kit`, «Явный автомат соединения»). Открытые сессии после неё указывают на id, которых новый процесс агента не знает.

Источники:
- `09-10-stage-5-client-kit.md`: задачи 5.2, 5.10, 5.12, алгоритмы переподключения и восстановления;
- ACP: `docs/acp/protocol/04-Session List.md`, `03-Session Setup.md`;
- матрица паритета, строка D-03.

## Goals / Non-Goals

**Goals:**
- `listSessions` в `codelab_client_acp` с курсором по ACP и таймаут исходящих запросов.
- Список сессий проекта в рабочем пространстве и сайдбаре, подгрузка страниц, загрузка выбранной сессии через `session/load`.
- После `reconnect()` открытые сессии загружаются заново, иначе — `detached` с уведомлением.
- Восстановление после перезапуска app: проект, сайдбар, транскрипт активной сессии.
- Scripted-агент `withSessionList` и интеграционный тест `session_list_load_flow_test.dart` (D-03).

**Non-Goals:**
- Повторы переподключения с паузами, отмена попыток, номер попытки в UI. `Reconnecting` по-прежнему `attempt: 1`; это change автопереподключения.
- Автоподключение при старте, `ProfileStore` в app и шаг `routes` сторожа запуска — change `add-app-boot-watchdog` (задача 5.11).
- Закрытие сессии, поиск по сессиям, `session/resume` и `session/fork`.
- Список сессий в CLI (этап 6) — API kit для него готов, экраны там.

## Decisions

### D1. `listSessions` в `codelab_client_acp`

`AcpClientApplication.listSessions({String? cwd, String? cursor}) → SessionListPage(sessions, nextCursor)`. Элемент — `SessionInfo` протокола (`sessionId`, `cwd`, `title`, `updatedAt`): это DTO результата запроса, долгоживущим состоянием он не становится. Без `sessionCapabilities.list` в ответе `initialize` метод бросает `AcpClientApplicationException` и запрос не отправляет (ACP: Clients MUST NOT attempt).

Курсор только передаётся обратно: не разбирается и не сохраняется. Отсутствие `nextCursor` — конец списка. Use case в `use_cases.dart` не добавляется: kit use case-ы не использует (design D3 `extract-acp-client-kit`).

Альтернатива — отдавать сразу все страницы. Отклонена: размер страницы задаёт агент (SHOULD enforce page sizes), а у сайдбара проекта с сотнями сессий первая страница должна появиться сразу.

### D2. Таймаут запросов клиента

`AcpClientApplication(requestTimeout: Duration(seconds: 60))` — таймер на каждый исходящий запрос, кроме `session/prompt`: ход длится сколько угодно, его прерывает `session/cancel`. По таймауту ожидающий запрос снимается и завершается `AcpRequestTimeoutException(method, timeout)` — наследник `AcpClientApplicationException`, событие лога `request_timeout` с `request_id`. Поздний ответ на снятый запрос логируется как ответ на неизвестный id и не меняет состояние. `session/load` подчиняется тому же таймауту: буфер реплея отбрасывается, как при ошибке.

Альтернатива — таймаут на уровне транспорта. Отклонена: транспорт не знает, какой кадр — ответ на какой запрос, а `session/prompt` должен быть исключением.

### D3. Список сессий в `WorkspaceState`

`AgentBackend` получает `listSessions` и `loadSession` вместе с потребителями (правило D3 прошлого change). `WorkspaceState.sessions` становится списком сайдбара проекта в порядке:
1. сессии, открытые в этом запуске (созданные или загруженные), — как сейчас;
2. затем сессии из `session/list`, ещё не открытые, — в порядке агента.

`SessionSummaryView` получает `title` и `updatedAt`. `SessionStatusView` получает два значения:
- `notLoaded` — сессия есть у агента, но не открыта;
- `detached` — сессия была открыта, но новое соединение её не знает (D5).

`WorkspaceState.hasMoreSessions` — есть следующая страница. Сам курсор kit держит закрытым полем и наружу не отдаёт.

Первая страница запрашивается `listSessions(cwd: projectDirectory)` после каждого успешного `connect`/`reconnect`, если агент объявил `list`. При смене проекта следующий запрос идёт уже с новым `cwd`. `ClientWorkspace.loadMoreSessions()` берёт следующую страницу и игнорирует повторный вызов, пока запрос в полёте. Ошибка списка — диагностика `Failed to list ACP sessions: …`; сайдбар остаётся с уже открытыми сессиями.

Альтернатива — отдельная коллекция `listedSessions` рядом с `sessions`. Отклонена: сайдбар показывает одну ленту, а слияние «открыта — показать один раз» — политика kit, а не каждого хоста.

### D4. Загрузка сессии

`ClientWorkspace.loadSession(SessionId id, {required String cwd}) → SessionHandle`. Последовательность:
1. `AgentBackend.loadSession`;
2. проекция транскрипта с нуля по реплею;
3. регистрация `SessionHandle`;
4. перенос строки из `notLoaded` в открытые.

Повторный вызов для той же сессии, пока загрузка в полёте, возвращает тот же `Future`. Без `loadSession` у агента — `ClientWorkspaceException`. В app выбор строки `notLoaded` в сайдбаре вызывает `loadSession`, затем `activate` и показ сессии. Ошибка загрузки — диагностика `Failed to load ACP session <id>: …`; строка остаётся `notLoaded`, выбранная сессия не меняется.

`TranscriptProjector` сбрасывает проекцию сессии, когда её `AcpSession` загружен заново: id ходов реплея могут совпасть с прежними (`turn-1`). Сброс определяется по событию загрузки, а не по сравнению ходов.

### D5. Переподключение загружает открытые сессии

`reconnect()` (одна попытка, D4 прошлого change) после успешного `initialize` выполняет:
- если агент объявил `loadSession` — `loadSession(id, cwd)` для каждой открытой сессии, сначала для активной;
- иначе, а также при ошибке загрузки, — сессия получает статус `detached`, в её транскрипт добавляется `NoticeItem(kind: detached)`.

Тексты уведомления:
- `The agent cannot restore sessions after reconnecting.` — агент не умеет загружать;
- `Session <id> could not be restored after reconnecting.` — загрузка не удалась.

Чего `detached` сессия не делает:
- не отправляет промпты: `send()` даёт `PromptFailed` с текстом `Session <id> is detached from the agent.`;
- не сливает свою очередь: очередь сохраняется до конца запуска;
- одобрения прежнего соединения закрываются как отменённые — ядро уже сбрасывает их при замене транспорта.

Список сессий запрашивается заново (D3).

Почему по одной сессии, сначала активная: пользователь видит её транскрипт первым, а загрузки фоновых сессий не задерживают его. Почему без автоматического `session/new`: открытая сессия — работа пользователя, и подменять её новой без спроса нельзя. `detached` честно показывает, что связь потеряна (`AGENTS.md` §2, «нельзя скрывать protocol error»).

### D6. Восстановление после перезапуска — при первом подключении

Решение владельца продукта: без автоподключения и `ProfileStore`. Это уточняет алгоритм `09-10`.

**Снимок.** Порт kit `WorkspaceSnapshotStore` (`read`, `write`, `clear`) и модель `WorkspaceSnapshot`:

```json
{"version": 1, "windows": {"main": {
  "projectDirectory": "/work/app",
  "activeSessionId": "sess_42",
  "openSessions": [{"id": "sess_42", "cwd": "/work/app"}, {"id": "sess_17", "cwd": "/work/app"}]
}}}
```

От формата `09-10` снимок отличается тем, что в нём нет `profileId`: подключается текущая форма. Курсоры, транскрипт, очередь, секреты и профиль не сохраняются.

Запись идёт после успешных `newSession`, `loadSession`, `activate` и смены проекта: kit сравнивает снимок из `WorkspaceState` с последним записанным. Записи не накладываются. Синхронная серия изменений даёт одну запись, потому что запись стартует со следующей микрозадачи. Изменения во время записи склеиваются в одну следующую запись с последним снимком, а `dispose` дожидается последней записи. Таймера «не чаще раза в секунду» нет: в widget-тестах графа он оставался бы висящим `Timer`, а при сбое терялась бы отложенная запись (уточнение при реализации). До `restoreProject()` снимок не пишется, иначе пустое рабочее пространство стёрло бы снимок прошлого запуска. Ошибка записи — диагностика, а не отказ операции. Реализация в app — `SharedPreferencesWorkspaceSnapshotStore`, ключ `codelab.workspace.snapshot`.

**API.** Восстановление — часть `ClientWorkspace`, его включает `snapshots: WorkspaceSnapshotStore`:
- `restoreProject()` — шаг 1;
- `selectProject(path)` — проект в `WorkspaceState` и снимке;
- `flushSnapshot()` — дождаться записи.

Шаги 2–4 выполняются внутри первого успешного `connect()`. Алгоритм — `WorkspaceRestorer` в `lib/src/restore/`. Нужные ему закрытые операции (сессии снимка в список, новая сессия с уведомлением) он получает через внутренний `RestoreHost`, не экспортируемый из бареля. Отдельный публичный объект восстановления потребовал бы открыть эти операции хостам.

**`WorkspaceRestorer` (kit).**

1. При старте app до подключения: прочитать снимок. Нет ключа — обычный старт. Неизвестная версия или битый JSON — диагностика `Workspace snapshot is invalid; starting fresh.`, ключ удаляется. Проект снимка выбирается: `SettingsCubit` получает его как выбранный проект, если пользователь ещё не выбрал свой.
2. При первом успешном `connect()` в этом запуске:
   - если агент объявил `list` — первая страница списка (D3);
   - сессии снимка, которых нет в списке, добавляются строками `notLoaded`: агент мог не объявить `list`;
   - если агент объявил `loadSession` — загрузить `activeSessionId` (D4) и сделать её активной; остальные открытые сессии снимка загружаются лениво, при выборе, и до загрузки остаются в снимке;
   - агенту без `loadSession` сессии снимка в список не добавляются: открыть их нельзя ни сейчас, ни по выбору.
3. Агент без `loadSession` — `newSession(cwd)` и `NoticeItem(kind: reconnected)` с текстом `The agent cannot restore sessions; a new session was started.`. Ошибка `session/load` — `newSession(cwd)` с текстом `Session <id> could not be restored; a new session was started.`, id удаляется из снимка.
4. Ничего не отправляется автоматически: восстановление не повторяет промпты и не отвечает на одобрения.

Восстановление срабатывает один раз за запуск. Последующие `connect`/`reconnect` идут по D3 и D5.

Почему при первом подключении, а не при старте: app стартует без подключения, а форма подключения не сохраняется между запусками. Переход к автоподключению на шаге `routes` сторожа запуска меняет только момент вызова шага 2; модель и порт остаются.

Почему `newSession` в шаге 3, а не `detached`, как в D5: после перезапуска у пользователя нет живой сессии, в которой можно показать отрыв. Новая сессия с уведомлением — та, в которой он продолжит работу (`09-10`, шаг 6).

### D7. UI

`CodeLabSessionSidebar` (`codelab_ui`) получает:
- статусы `notLoaded` («not loaded», нейтральный тон) и `detached` («detached», тон предупреждения);
- `onLoadMore` с кнопкой `Load more sessions` (ключ `sessions-load-more`), видимой при `hasMoreSessions`.

Логики в виджете нет: что показывать, решает `SessionsCubit` через `ui_mappers.dart`.

`SessionsCubit` берёт из `WorkspaceState.sessions` неоткрытые сессии (`notLoaded`), признак `detached` и `hasMoreSessions`. Строки открытых сессий он по-прежнему строит из `sessionChanges` (уточнение при реализации): статус «ждёт одобрения» (бейдж `Approval`, R-21) есть только в `AcpSession`, а `SessionStatusView` kit объединяет его с ходом. Порядок «последняя изменившаяся открытая сессия первой» сохраняется. Чтобы на изменение статуса открытой сессии не было второго состояния, `WorkspaceState` учитывается только при изменении видимого сайдбару отпечатка: строки `notLoaded`, `detached`, `hasMoreSessions`. Когда `detached` меняется у показываемой сессии, её лента перерисовывается тем же пакетом изменений: уведомление меняет `SessionView` без нового `AcpSession`. Выбор строки `notLoaded` сначала вызывает `ClientWorkspace.loadSession`, затем показывает сессию; при ошибке выбранная сессия не меняется. Уведомления `NoticeItem` `detached` и `reconnected` отображаются в ленте как `CodeLabTranscriptEntryKind.diagnostic`.

### D8. Тестовый агент и e2e

Режим scripted-агента `with_session_list` (`CodelabCompatibleStdioAgentMode.withSessionList`):
- объявляет `loadSession` и `sessionCapabilities.list`;
- хранит сессии в файле рядом со скриптом, чтобы пережить перезапуск процесса;
- отдаёт `session/list` страницами по 2 с курсором;
- на `session/load` повторяет историю `user_message_chunk` / `agent_message_chunk`.

`session_list_load_flow_test.dart` проверяет три сценария:
- две сессии в сайдбаре после переподключения, и выбор восстанавливает транскрипт;
- `Reconnect` при открытой сессии загружает её заново;
- «перезапуск»: корневой scope закрывается и создаётся заново с теми же `SharedPreferences`, и после `Connect` активная сессия загружена с прежним транскриптом (D-03).

Режима `dart` у теста нет, тест помечен `scripted-only`. Бинарь `codelab-agent` со сценарием `--llm-script` выключает сохранение сессий (`agent_host.dart`, `CapabilityOff('--llm-script: сессии в памяти')`) и потому не объявляет `loadSession` — по ACP клиент не вправе вызывать `session/load`. Сценарий D-03 и задача 5.6 против Dart-агента требуют, чтобы агент со `--llm-script` хранил сессии на диске; это изменение агента, вне объёма этого change (найдено при реализации). Хранение на диске добавил change `add-llm-script-session-store` (флаг `--sessions-dir`), после чего тег `scripted-only` с теста снят.

Снимок пишется в `shared_preferences`, а на macOS e2e-тесты делят `NSUserDefaults`. Поэтому `integration_test/flutter_test_config.dart` удаляет снимок перед каждым тестом — Flutter подхватывает этот файл для всех тестов каталога, и текст 8 тестов не меняется. Иначе снимок прошлого теста запустит восстановление в следующем. Очистка появляется вместе с записью снимка, в итерации 4.

## Risks / Trade-offs

- **[Снимок прошлого запуска меняет поведение существующих тестов и сценариев]** → восстановление действует только при наличии снимка; widget-тесты используют пустые `SharedPreferences`, e2e очищают ключ (D8); восстановление не отправляет ничего агенту, кроме `session/list`, `session/load`, `session/new` (D6, шаг 4).
- **[Новый процесс агента не знает id из снимка]** → `session/load` даёт ошибку → новая сессия с уведомлением, id удаляется из снимка (D6, шаг 3).
- **[Повторы id ходов в реплее ломают инкрементальную проекцию]** → сброс проекции по событию загрузки (D4) и тест «реплей с теми же id ходов».
- **[Длинный реплей упирается в таймаут 60 с]** → таймаут настраивается конструктором; превышение — типизированная ошибка, а не зависание (D2).
- **[Сайдбар с открытыми и незагруженными сессиями путает пользователя]** → статус `notLoaded` и порядок «сначала открытые» (D3, D7).
- **[Ход пережил переподключение]** → Dart-агент держал ход `detachGrace` (30 с) после закрытия WebSocket и продолжал его после `session/load`, а ядро клиента считает ходы реплея завершёнными, поэтому поздние `session/update` хода терялись. Change `cancel-turn-on-ws-disconnect` (задача 5.6) выбирает для MVP отмену хода при обрыве: `detachGrace` ноль и для WebSocket, клиент показывает прерванный ход отменённым. `session/cancel` перед заменой транспорта kit не шлёт: при нулевом `detachGrace` агент отменяет ход сам.
- **[Отложенная запись снимка теряется при выходе]** → `dispose` дожидается последней записи (D6).

## Migration Plan

Хранимых данных до этого change нет: ключ `codelab.workspace.snapshot` появляется при первой записи. Неизвестная версия снимка или битый JSON — обычный старт (D6, шаг 1). Откат — revert PR: оставшийся ключ app без этого change не читает.
