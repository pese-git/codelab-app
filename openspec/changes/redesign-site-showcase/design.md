## Goals / Non-Goals

**Goals:**
- Посетитель за первые секунды видит главную идею продукта: агент спрашивает разрешение, решение за пользователем.
- Всё, что показывает демо, существует в продукте. Рассинхрон строки интерфейса или документа с витриной ломает сборку в том pull request, где он возник.
- Без JavaScript, с `prefers-reduced-motion` и с клавиатуры витрина остаётся полной и понятной.
- Ни фреймворков, ни новых npm-зависимостей, ни запросов к чужим хостам. Встроенный скрипт — по-прежнему один.

**Non-Goals:** хостинг и публикация (H1–H3 `add-astro-site`), новые снимки экрана, английская версия, видео, аналитика, браузерные e2e-тесты.

Демо добавляется в начало страницы, если оно объясняет продукт: app — сценарий первого экрана в клиенте app; `codelab` — клавиши ответа; `codelab-agent` — режимы разрешений. Демо в каждой карточке не ставится: демо там, где текст хуже (`AGENTS.md` §13).

Альтернативы:
- **Отдельная страница «Демо».** Посетитель первого экрана её не увидит, а главная идея должна быть видна сразу.
- **Мини-демо в каждой карточке, как у Amperic.** Шесть демо на страницу — шесть сценариев, которые надо держать в соответствии с продуктом. Цена правдивости (D6) растёт быстрее пользы.

### D2. Скрипты витрины: модули Astro, собранные Vite; встроенный по-прежнему один

**Правило** заменяет пункт skill §6 «Клиентских скриптов два»:
1. Скрипт витрины — `<script>` в компоненте Astro. Логика вынесена в модули `src/scripts/showcase/*.ts`, которые Vite собирает в файлы `/_astro/*.js`. Astro подключает модуль только на страницах, где есть компонент: на страницах документации скриптов витрины нет.
2. **Встроенный скрипт — только тема** (`ThemeInit.astro`), его текст неизменен (D11 `add-astro-site`). Чтобы Astro не встроил маленький модуль в HTML сам, сборка запрещает встраивание скриптов (`vite.build.assetsInlineLimit` в форме функции: `0` для `.js` и `.ts`, прежний порог для остального). Итог проверяет `check-links` (D12). Так CSP хостинга остаётся вида `script-src 'self' 'sha256-<тема>'` без `'unsafe-inline'`.
3. **Без UI-фреймворков, без новых npm-зависимостей,** без `eval`, `new Function`, `innerHTML` со строками сценария. Узлы создаются через `textContent` и `createElement`, а лучше берутся из готовой разметки.
4. **Чистая логика отдельно от DOM.** Состояние демо — конечный автомат в `src/lib/showcase/*.ts` без обращения к `document`: переходы, таймеры через переданный планировщик. Его покрывает vitest (D13). Модуль в `src/scripts/showcase/` только связывает автомат с разметкой: находит корни `[data-demo="…"]`, вешает обработчики, отражает состояние в атрибутах. Это продолжает образец `theme.ts` и `theme-state.ts` (`AGENTS.md` §14).
5. **Прогрессивное улучшение.** Сервер отрисовывает полное осмысленное состояние без JavaScript (D3–D5). Скрипт ставит на корень `data-live` и только тогда скрывает лишнее и показывает элементы управления. Элементы управления, которые без скрипта ничего не делают, получают `hidden` в разметке, как кнопка темы.
6. **Движение.** При `prefers-reduced-motion: reduce` нет автопроигрывания, печати по символам и анимированных переходов. Состояния сменяются только по действию посетителя и сразу. Автопроигрывание:
   - идёт, только пока демо видно (`IntersectionObserver`);
   - останавливается при наведении и фокусе внутри демо;
   - имеет видимую кнопку «Пауза» / «Продолжить» (WCAG 2.2.2): движение дольше 5 секунд.

   Пауза (наведение, фокус, невидимость, кнопка) останавливает **только автопроигрывание**, то есть то, что демо делает само. Показ последствий действия посетителя — не автопроигрывание: он идёт и при паузе. В макете D3 это переход `allowed|rejected → done` после ответа. Причина: курсор остаётся над кнопкой после клика, и при паузе по наведению исход замирал бы, а «Ещё раз» не появлялась (замечание ручной приёмки 6.2).
7. **Доступность:**
   - все элементы управления — `<button>` или ссылки;
   - переключатели (клиенты, шаги, режимы) — шаблон вкладок WAI-ARIA: `role="tablist"`, стрелки, Home и End;
   - меняющийся итог (исход разрешения, ответ режима) объявляется в области `aria-live="polite"`. Поток ответа по символам не объявляется — объявляется готовая фраза;
   - фокус не переносится скриптом без действия посетителя. Перенос фокуса как прямое следствие действия посетителя допустим, если иначе фокус потерялся бы: элемент, на котором он стоял, скрывается. Таких случаев в макете D3 два: ответ на карточку запроса (фокус уходит на карточку, затем на «Ещё раз») и нажатие «Ещё раз» (кнопка скрывается, фокус уходит на окно макета `.wb-window` с `tabindex="-1"`, `src/scripts/showcase/workbench.ts`);
   - элемент управления, на котором может стоять фокус, не получает `disabled`, когда действие временно недоступно: браузер сбросил бы фокус на `body` (focus fixup). Кнопка «Пауза» при недоступной паузе получает `aria-disabled="true"`, остаётся в порядке табуляции, а её нажатие игнорируется.
8. **Бюджет:** весь JavaScript витрины на странице — не больше 12 КБ после gzip, без учёта темы и mermaid. Проверяет `check-links` (D12).
9. **Тема.** Демо раскрашены токенами `tokens.css` и меняют тему вместе со страницей, без своего слушателя `codelab-theme-change`.

Альтернативы:
- **Встроенные скрипты в каждом демо (`is:inline`), как у Amperic.** Каждый встроенный скрипт — свой хэш в CSP. TypeScript и `astro check` их не проверяют, vitest не тестирует. При правке текста хэш меняется молча.
- **Web Components (custom elements).** Встроены в браузер и подходят по размеру. Но в проекте их нет, а модуль с `data-*` корнями уже используется (`theme.ts`). Без выигрыша это второй способ.
- **Preact или Alpine.js.** Новая зависимость и фреймворк, запрещено skill §6 и `AGENTS.md` §4.

### D3. Живой макет рабочего места

Сценарий первого экрана — правка файла с запросом разрешения. Это поведение режима `standard` по умолчанию (`05-permissions.md#режимы`).

Состояния автомата (`src/lib/showcase/workbench-demo.ts`):

```text
idle → prompt → streaming → awaiting → allowed → done
                                     ↘ rejected → done
done → idle (кнопка «Ещё раз»)
```

- **промпт стоит в ленте с первого кадра** (`promptShown: true` во всех состояниях, `src/lib/showcase/workbench-view.ts`), отдельного поля ввода с набираемым промптом нет. Первый экран не пуст и без JavaScript, и до первого таймера;
- `idle` → `prompt` — стартовой задержки нет (0 мс): первый шаг сразу после `start`;
- `prompt` — визуально совпадает с `idle` и только задерживает начало ответа на 700 мс, чтобы посетитель успел прочитать промпт. Состояние сохранено ради явной последовательности автомата и тестов, а не ради отдельного вида;
- `streaming` — ответ агента появляется по частям, затем строка вызова инструмента записи с путём файла;
- `awaiting` — карточка запроса: тег риска, путь, выбор «Только сейчас» или «Всегда», кнопки «Разрешить» и «Отклонить». **Автопроигрывание здесь останавливается всегда:** решение принимает посетитель, демо не отвечает за него;
- `allowed` — строка вызова получает исход, агент пишет итог; `rejected` — исход «отклонено», агент сообщает, что правку не сделал;
- `done` — кнопка «Ещё раз».

**После ответа посетителя** (согласовано с D2 п. 6–7):
- переход `allowed|rejected → done` — показ последствий ответа, он идёт и при паузе любой причины. Пауза останавливает только автопроигрывание до ответа;
- заголовок карточки меняется на «Решено» — ключ `workbenchApprovalResolved` из `apps/codelab_desktop/lib/l10n/app_ru.arb` (вид `ui`, D6). Выбор «Только сейчас» / «Всегда» и кнопки ответа скрываются: ответ дан, повторное нажатие ничего не меняет (R4);
- фокус переходит на карточку (`role="group"`, `tabindex="-1"`, заголовок — её `aria-labelledby`). Иначе он пропал бы на `body` вместе со скрытой кнопкой. Когда появилась «Ещё раз», фокус переходит на неё, если посетитель за это время не увёл его с карточки. Перенос вызван действием посетителя (D2 п. 7);
- нажатие «Ещё раз» переносит фокус на окно макета (`.wb-window`, `tabindex="-1"`) и запускает повтор: кнопка скрывается, и без переноса фокус пропал бы на `body`. Это второй и последний случай переноса фокуса скриптом (D2 п. 7);
- «Ещё раз» — явная просьба повторить: наведение на неё не ставит повтор на паузу.

Без JavaScript сервер отрисовывает ленту до карточки запроса включительно, без кнопок. Под ней — оба исхода текстом: «Если разрешить, …», «Если отклонить, …».

Альтернативы для промпта:
- **Печать промпта в поле ввода, как было задумано.** Первый кадр пуст до первого таймера и без JavaScript. Посетитель первого экрана видит пустой макет как раз тогда, когда решает, читать ли дальше.
- **Убрать состояние `prompt`.** Ответ начинался бы сразу, и промпт не успевали бы прочитать. Длительность можно было бы задать стартовой задержкой `idle`, но тогда задержка у первого кадра снова была бы.

Альтернатива для паузы после ответа — **держать паузу и для последствий**. Исход замирает под курсором, «Ещё раз» не появляется, посетитель видит «зависшее» демо.

Каркас макета — шапка сессии, лента, поле ввода. Взят по смыслу с артбордов `docs/design/claude-design/Main.dc.html` и `Turn.dc.html`, свёрстан заново токенами сайта. Код артбордов и рантайм Claude Design не копируются (`AGENTS.md` §5). Это иллюстрация, а не снимок: подпись под макетом говорит «Схема рабочего места; ответ модели и файл — пример».

Альтернатива — **живой снимок (GIF или видео)**. Тяжелее, без клавиатуры и текста для чтения с экрана. Рассинхрон с продуктом не ловится сборкой.

### D4. Один агент — три клиента

Переключатель над макетом: «CodeLab app», «`codelab`», «Zed». Сценарий один (промпт, вызов, путь, исход), вид — по клиенту:
- **CodeLab app** — карточка одобрения Fluent со строками русского каталога `codelab_ui_ru.arb` (D6);
- **`codelab`** — блок терминала (токены `--term-*` из `fluent.css`). Подсказки клавиш `y`, `a`, `n` — из таблицы `02-repl.md#разрешения`. Текст блока одобрения — только из текстового снимка в документе CLI. Пока снимка нет, вкладка показывает таблицу клавиш и подпись «вид блока — в руководстве», а `docs-writer` добавляет снимок (задача 1.3);
- **Zed** — интерфейс Zed не изображается: это чужой продукт, его вид меняется между версиями, и проверить его по нашему источнику нельзя. Вкладка показывает нейтральную схему: «Zed запускает `codelab-agent` и показывает вопрос в своём интерфейсе; правила вопроса — те же». Рядом ссылка на `docs/user/zed.md` и оговорка из него о непроверенном примере настроек.

Без JavaScript три представления идут подряд, у каждого свой заголовок.

Альтернатива — **отрисовать панель агента Zed.** Убедительнее, но это изображение чужого интерфейса, которое мы не можем проверить. Оно устареет без сигнала.

### D5. «Как это работает» и мини-демо

- **Четыре шага** (`src/lib/showcase/steps.ts`) — каждый с заголовком, фразой и ссылкой на раздел руководства app:
  1. открыть папку проекта — `02-projects-and-sessions.md`;
  2. подключить провайдера модели — `07-providers-and-models.md`;
  3. попросить агента — `03-conversation.md`;
  4. ответить на запрос разрешения — `04-permissions.md`.

  Иллюстрация шага — существующий снимок из `apps/codelab_desktop/doc/images/` или фрагмент макета D3. Автопроигрывание — по правилам D2 п. 6, шаг держится 6 секунд. Без JavaScript — нумерованный список всех шагов.
- **Режимы разрешений** (страница агента и карточка главной). Вкладки `plan`, `ask`, `standard`, `accept-edits`, `bypass`, три строки: чтение, правка файлов, команды и MCP-инструменты. Ячейка — «без вопроса», «вопрос» или «запрещена без вопроса». Значения берутся при сборке из строк таблицы `05-permissions.md#режимы` (D6), а не набираются руками. `autopilot` показывается сноской словами документа: селектором его не включить. Без JavaScript — таблица целиком.
- **Клавиши `codelab`** (страница CLI и карточка главной). Кнопки с `<kbd>` `y`, `a`, `n`, `N`, `?`; нажатие показывает ответ из таблицы `02-repl.md#разрешения` в области `aria-live`. Клавиатурный перехват — только когда фокус внутри демо. Без JavaScript — таблица.

### D6. Правдивость витрины: строки из источников, проверка при сборке

Правило заменяет запрет skill §2 «текстовые снимки терминала и команды не копируются». Смысл запрета сохраняется: один факт — одно место, и витрина не расходится с продуктом. Но рассинхрон теперь ловит сборка, а не память автора.

**Виды строк в данных витрины** (`src/lib/showcase/scenarios.ts`, `facts.ts`, `steps.ts`):

| Вид | Что это | Как получается | Если источник изменился |
|---|---|---|---|
| `ui(каталог, ключ)` | строка интерфейса app | значение ключа из `*.arb` при сборке | нет ключа — ошибка сборки с каталогом и ключом |
| `quote(документ, текст)` | короткая цитата документа: клавиша, имя режима, строка таблицы, сообщение | сборка ищет текст в документе (пробелы нормализуются) | нет совпадения — ошибка с путём и цитатой |
| `snippet(документ#якорь, n)` | текстовый снимок терминала | n-й блок кода раздела, отрисованный как есть | нет раздела или блока — ошибка |
| `example(текст)` | промпт, ответ модели, содержимое файла | пишется в данных | не проверяется; на странице помечен «пример» |
| `docRef(документ#якорь)` | «подробнее» у шага, факта, демо | адрес через `pageUrl` | якорь проверяет `check-links` (D6 `add-astro-site`) |

- **Закрытый список источников** — одна константа `showcaseSources` в `src/lib/showcase/sources.ts`:
  - опубликованные документы (allowlist `publish.ts`);
  - `packages/flutter/codelab_ui/lib/src/l10n/codelab_ui_ru.arb` и `apps/codelab_desktop/lib/l10n/app_ru.arb`;
  - изображения: `apps/*/doc/images/**` (как сейчас) и `docs/design/brand/**` (D10).

  Исходники Dart (`lib/**/*.dart`) в список не входят. Строка, которой нет ни в каталоге, ни в документе, на витрину не попадает; сначала её документирует `docs-writer`.
- **Чтение источников — при сборке, в node.** Функции `ui`, `quote`, `snippet` вызываются из frontmatter страниц и компонентов. В клиентский JavaScript попадают уже готовые строки как данные разметки (`data-*` или скрытые узлы), а не пути к источникам.
- **Каждый шаг сценария и каждый факт** имеет `docRef`: витрина не показывает поведение, которого нет в руководстве.
- **Пример помечен.** Под каждым демо с `example` — подпись «Ответ модели и файл — пример». Промпт и ответ не обещают качества модели: «добавь проверку пустой строки», а не «перепиши проект».
- **Охват CI.** Правка каталога `*.arb` без этого не запустила бы джоб `site` (`ci_scope.dart`, D13 `add-astro-site`), и рассинхрон прошёл бы pull request. Поэтому `_affectsSite` получает только файлы `*.arb` в `packages/flutter/codelab_ui/` и `apps/codelab_desktop/` (константа `_siteL10nDirs`). Существующий предикат `_isL10nFile` не переиспользуется: он ловит ещё `pubspec.yaml`, `l10n.yaml` и сгенерированный код локализации. Они не служат источниками витрины, а с ним джоб `site` запускался бы на каждую правку `pubspec.yaml` этих пакетов. `docs/design/brand/**` отдельного правила не получает: он лежит под `docs/**`, который уже в охвате. Синхронность `showcaseSources` с `_affectsSite` проверяет тест vitest: каждый путь из `showcaseSources`, кроме опубликованных документов, сопоставляется с фиксированным списком шаблонов, который повторяет Dart-тест `ci_scope_test.dart`. Расхождение двух списков — пункт чек-листа skill §9.
- **Корень репозитория — `process.cwd()/..`.** Экспортируемые `ui`, `quote`, `snippet` создаются как `createShowcaseSources(resolve(process.cwd(), '..'))`; тесты передают в `createShowcaseSources(корень)` каталог фикстур. Корень не выводится из `import.meta.url`: в собранном серверном бандле Astro модуль лежит уже не в `src/lib/showcase/`, и путь от него ненадёжен. Условие решения — `astro build` и vitest запускаются из `site/`; так делают npm-скрипты `site/package.json` и джоб `site` в CI. Запуск из другого каталога даёт ошибку «источник не найден» с путём, а не тихо неверные строки (риск R9).
- **Кто проверяет.** Механическую сверку делает сборка. Смысл проверяет `docs-writer` (`codelab-docs` §8): шаг сценария соответствует руководству, пример не создаёт ложного впечатления, ограничения названы. Правки вносит `site-engineer`.

Альтернативы:
- **Набирать строки руками и сверять на ревью.** Так сейчас работает skill §2 для прозы, но строки интерфейса меняются чаще, а ошибка не видна.
- **Цитировать исходники Dart.** Строки CLI собираются интерполяцией, и подстрока кода — не то, что видит пользователь. Кроме того, это расширило бы охват `site` на `lib/` приложений.
- **Снимать демо с работающего приложения** (запись событий ACP и воспроизведение). Точнее всего, но это инструмент записи, формат и хранение фикстур ради витрины — непропорционально.

### D7. Факты, бейджи, цифры, плашка версии

- Бейджи первого экрана и цифры — записи `facts.ts`: текст + `docRef`; при числе — `quote` из источника, где это число стоит. Кандидаты: «Без телеметрии», «Ключи API — вне настроек клиента», «Файловые инструменты — только в папке проекта», «Код под лицензией MIT» (`LICENSE`), «Три клиента одного агента». Окончательный список утверждает проверка фактов `docs-writer`.
- Бейдж МОЖЕТ вести не на руководство, а на блок главной (поле `homeAnchor` записи). Так бейдж файловых инструментов («Файловые инструменты агента CodeLab — в папке проекта») ведёт на блок доверия `#trust` (D8), где гарантия читается вместе с ограничениями; `docRef` остаётся для проверки раздела и ссылки «Подробнее». Бейдж без ограничений рядом создавал бы впечатление более сильной гарантии (`AGENTS.md` §2, приоритет 1).
- Цифра без источника, сравнения с другими продуктами и оценочные слова (skill §2) не пишутся.
- **Плашка версии** — `version` и `date` последней новости коллекции `news`, ссылка на новость. Новостей нет — плашки нет (сейчас её нет: выпусков нет).

### D8. Блок «Ваш код и ключи»

Четыре утверждения, у каждого — ссылка на раздел и, где есть, ограничения в том же пункте:

| Утверждение | Ограничение рядом | Источник |
|---|---|---|
| Без телеметрии, отчётов о сбоях и аналитики; промпты и файлы уходят только провайдеру и инструментам, которые вы настроили | — | `apps/codelab_desktop/doc/user/09-settings.md#конфиденциальность` |
| Ключ API берётся из переменной окружения или хранилища секретов; значения секретов агент не логирует | журналы сессий до 1.0 хранят тексты промптов и вывод инструментов без редактирования; файловый бэкенд секретов (`secrets.backend: file`) хранит значения открытым текстом в `secrets.yaml` с правами `0600`, хранилища ОС в этой версии нет | `docs/user/configuration.md#шаг-2-задайте-ключ-api`, `#что-попадает-в-логи-и-журналы` |
| У встроенного агента и `codelab-agent` файловые инструменты работают только внутри папки проекта: путь наружу отклоняется до обращения к файлу | для команд ограничен только каталог запуска, а не содержимое; ОС-песочницы нет — выполненная команда работает с правами пользователя, может читать и писать вне рабочей папки и обращаться к сети; исключение только для чтения — каталоги загруженных навыков; в `serve --stdio` `ls` и `search` идут по symlink наружу (для `read`/`write`/`edit` ссылки раскрывает клиент); `stdio`-сервер MCP получает права пользователя | `apps/codelab_agent/doc/user/05-permissions.md#рабочая-папка`, `08-mcp.md#какие-бывают-серверы` |
| В режиме по умолчанию агент спрашивает разрешение перед правкой файла и запуском команды | ответ «разрешать всегда» действует на такие же вызовы до конца сессии; правило `permissions.tools.<инструмент>: allow` снимает вопрос, кроме критических команд и режима `plan`; `bypass` спрашивает только о критических командах и правках конфигурации агента; `autopilot` там, где `bypass` спросил бы, отказывает, но правило `ask` в нём по-прежнему задаёт вопрос | `05-permissions.md#режимы`, `#вопрос-и-четыре-ответа` |

Ограничений у пункта может быть несколько: каждое — отдельная запись `limits` пункта `trustItems` в `src/lib/showcase/facts.ts` со своим `docRef`, подтверждённая цитатой документа (`quote`). Субъект пункта о файловых инструментах назван явно: у внешнего агента в app действуют его собственные правила.

Гарантия без ограничения рядом создаёт ложное впечатление о безопасности (`AGENTS.md` §2, приоритет 1). Поэтому ограничения обязательны и проверяются тем же `docs-writer`.

### D10. Мета-данные, favicon, логотип

- **Логотип в шапке** — `docs/design/brand/codelab-logo.svg` и `codelab-logo-dark.svg` по теме, без копии в `site/`. Надпись нарисована линиями, шрифты не нужны (`docs/design/brand/README.md`).
- **Favicon** — `docs/design/brand/launcher/web-favicon.svg` (`<link rel="icon" type="image/svg+xml">`). PNG 180×180 для `apple-touch-icon` собирает endpoint `src/pages/apple-touch-icon.png.ts` из `launcher/web-icon.svg` (растеризация — ниже).
- **Картинка для ссылок** 1200×630 PNG — одна на сайт, `dist/og.png`. Её собирает endpoint `src/pages/og.png.ts` из SVG-карточки `src/lib/og-card.ts`: знак и надпись бренда (`codelab-logo.svg`) на плашке. Текста шрифтом в картинке нет, поэтому результат не зависит от шрифтов машины сборки.
- **Растеризация SVG — сервис изображений Astro напрямую, флаг SVG — только у двух вызовов.** `getImage` из `astro:assets` не растеризует SVG без `image.dangerouslyProcessSVG: true`: Astro по умолчанию защищает сборку от чужих SVG. Глобально флаг не включается. Модуль `src/lib/raster-svg.ts` берёт сервис `getConfiguredImageService()` (sharp из зависимостей Astro, новой npm-зависимости нет) и вызывает его `transform` с конфигурацией `{ ...imageConfig, dangerouslyProcessSVG: true }`. Адреса `og.png` и `apple-touch-icon.png` стабильны, без хэша `_astro/`: на них ссылаются мета-теги и проверка D12 п. 4. Запасной закоммиченный PNG не понадобился, `site/public/` не создаётся.
- **Граница флага:**
  - вызывающих ровно два — `src/pages/og.png.ts` (1200×630) и `src/pages/apple-touch-icon.png.ts` (180×180). Новый вызов `rasterizeSvg` — изменение этого решения;
  - вход — только SVG из `docs/design/brand/`, импортированные как `?raw` при сборке. Это файлы репозитория, они проходят ревью;
  - ввода посетителя нет: endpoint статический и выполняется только при `astro build`. Во время работы сайта сервера нет;
  - остальные изображения сайта (`astro:assets`, снимки из `apps/*/doc/images/`) идут через `getImage` без флага.
- **Цвета карточки.** SVG-карточка отдаётся сервису изображений, а не странице, и CSS-переменные `tokens.css` в ней не видны. Поэтому `--mica` и `--accent` светлой темы продублированы в `og-card.ts` hex-константами с именами токенов. Расхождение с `tokens.css` ловит тест `site/test/og-card.test.ts` («цвета плашки совпадают с токенами светлой темы»): он читает светлое значение `light-dark(...)` из `tokens.css`.
- Альтернативы растеризации:
  - **`image.dangerouslyProcessSVG: true` в `astro.config.mjs`.** Флаг распространился бы на все изображения сайта, включая будущие SVG из документов. Защита Astro снята целиком ради двух файлов бренда;
  - **закоммиченный PNG в `site/public/` с SVG рядом** (прежний запасной путь). Вторая копия бренда в `site/` и ручная пересборка при правке знака;
  - **`getImage` с растровым исходником.** Растрового исходника бренда нет, его пришлось бы завести — та же копия;
  - **своя npm-зависимость для SVG → PNG** (`resvg`, `sharp` напрямую). Запрещено D2 п. 3 и `AGENTS.md` §4, а sharp уже даёт Astro;
  - **CSS-переменные внутри SVG-карточки.** Сервис изображений их не разрешает, цвета вышли бы по умолчанию.
- **Мета-теги каждой страницы:** `og:type`, `og:title`, `og:description`, `og:locale` (`ru_RU`), `og:site_name`, `twitter:card` = `summary_large_image`.
  - `og:image`, `og:url` и `twitter:image` требуют абсолютного адреса. Они пишутся только при заданном `SITE_URL`, как `canonical` (D12 `add-astro-site`). Без `SITE_URL` их нет.
  - `hreflang` не пишется: язык один.
- **Карта сайта** — с хостингом (D12 `add-astro-site`), не здесь.

### D12. Проверка сборки: скрипты, обработчики, бюджет, картинка

`scripts/check-links.mjs` уже разбирает все теги `dist/`. Он получает новые правила, с тестами на мини-`dist/`:
1. **Встроенный скрипт.** На каждой странице не больше одного `<script>` без `src`, и его текст одинаков на всех страницах (хэш для CSP, D2 п. 2). Встроенный скрипт с `type="application/ld+json"` не добавляется: структурированных данных в change нет.
2. **Обработчики событий.** Нет атрибутов `on*` ни у одного элемента, нет `javascript:` ни в одном атрибуте (схемы ссылок уже проверяются, D6/D11 `add-astro-site`).
3. **Бюджет.** Сумма gzip (`node:zlib`) модулей `<script type="module" src>` страницы и их статических импортов, кроме чанков темы и mermaid, — не больше 12 КБ. Чанки темы и mermaid определяются по исходным модулям, а не по имени чанка: имя с хэшем меняется при любой правке.
   - **Манифест чанков — свой плагин Vite.** Astro 7 не пишет манифест Vite в `dist/`: `vite.build.manifest: true` в статической сборке ничего не создаёт. Поэтому плагин `site/src/plugins/build-chunks.ts` (подключается в `vite.plugins` `astro.config.mjs`) при клиентской сборке пишет `site/.astro/build-chunks.json`: для каждого чанка — его статические импорты и исходные модули. Пути — от корня репозитория, без абсолютных путей машины сборки (D11 `add-astro-site`). Файл лежит в `site/.astro/`, который уже в `.gitignore`, и в `dist/` не попадает — посетителю он не публикуется. Чистую часть плагина (`chunksFromBundle`) покрывает `site/test/build-chunks.test.ts`.
   - `check-links.mjs` (`isEntryExcluded`) исключает из бюджета входной чанк, только если **все** его исходные модули — `site/src/scripts/theme.ts` или `site/src/scripts/mermaid.ts`; общий (статически импортируемый) чанк — если все его модули относятся к теме или mermaid, включая `site/src/scripts/theme-state.ts` (`isSharedExcluded`). Смешанный чанк считается кодом демо и входит в бюджет. Причина: Rolldown/Vite может слить модуль демо с модулем темы в один чанк, и правило «есть модуль темы — исключить» вывело бы код демо из бюджета молча — ложный проход проверки. Ошибка в обратную сторону (лишние байты темы в сумме) видна как превышение и безопасна.
   - Нет файла манифеста — CLI `check-links` падает с сообщением собрать сайт (`astro build`), а не считает бюджет без исключений: иначе тема и mermaid попали бы в сумму, и ошибка выглядела бы как превышение бюджета демо.
   - Альтернативы: **манифест Vite** (`build.manifest`) — в Astro 7 не создаётся; **узнавать чанки по имени** (`theme.*.js`) — Vite выносит общий код в чанки с произвольными именами, и правило сломалось бы молча; **сканировать текст чанка** на признаки mermaid — хрупко и неявно.
4. **Картинка для ссылок.** Если в `<head>` есть `og:image`, файл существует в `dist/`, это PNG, а размер из заголовка `IHDR` — 1200×630. Если `og:image` нет, значит не задан `SITE_URL`; для этого случая проверяется сам файл картинки по известному адресу.

Альтернатива — **отдельный скрипт `check-showcase.mjs`**. Второй проход по тем же тегам и второй разбор HTML. Правила относятся к безопасности и ресурсам сборки — той же зоне, что D6.

## Risks / Trade-offs

- **R1. Демо обещает больше, чем продукт.** Смягчение: D6 — строки из источников, `docRef` у каждого шага, подпись «пример», проверка фактов `docs-writer`; D4 — чужой интерфейс не изображается; D8 — ограничения рядом с гарантиями.
- **R2. Красный `site` от правки каталога локализации или документа.** Строка интерфейса берётся по ключу, поэтому новый перевод витрина подхватывает сама. Джоб `site` падает только при удалённом или переименованном ключе в pull request `codelab_ui` или `codelab_desktop`. Так задумано: витрина узнаёт о правке. Цитаты документов (`quote`) ломаются чаще — при любой переформулировке, — поэтому они короткие: клавиша, имя режима, строка таблицы. Исправление — правка цитаты в данных витрины в том же pull request.
- **R3. Язык.** Демо app — на русском (каталог `ru`), снимки галереи — на английском. Посетитель увидит два языка интерфейса. Смягчение: подпись галереи; полное решение — русские снимки (`docs:screenshots`), вопрос Q2.
- **R4. Таймеры и состояние.** Автопроигрывание, пауза, видимость и ручной выбор могут гоняться: поздний таймер переключает шаг после выбора посетителя. Смягчение: автомат получает планировщик и отменяет таймер при каждом переходе. Нажатие на устаревшую кнопку (исход уже выбран) не меняет состояние. Это покрыто тестами D13 (аналог правила о поздних событиях, `AGENTS.md` §9, §12).
- **R5. Бюджет и производительность.** Анимации на первом экране тормозят слабые устройства. Смягчение: только CSS `opacity` и `transform`, без layout-анимаций; бюджет D2 п. 8; остановка вне экрана.
- **R6. Без JavaScript страница длиннее.** Три представления клиентов и все шаги подряд. Это осознанная цена прогрессивного улучшения.
- **R7. Ручная проверка доступности.** Без e2e регресс фокуса или `aria-live` пройдёт CI. Смягчение: чек-лист в skill §9, правило пересмотра D13.
- **R8. OG-картинка без `SITE_URL`.** Мессенджеры не покажут превью, пока нет хостинга. Это ожидаемо: абсолютный адрес появится с хостингом.
- **R9. Корень репозитория от рабочего каталога.** `ui`, `quote`, `snippet` считают корень как `process.cwd()/..` (D6). Сборка или vitest, запущенные не из `site/` (например, `npx astro build --root site` из корня), ищут источники не там. Смягчение: npm-скрипты и джоб `site` запускаются из `site/`; ненайденный источник — ошибка сборки с путём, поэтому сбой громкий, а не тихий. Пересмотреть, если появится запуск сборки из другого каталога.
- **R10. Манифест чанков — своя договорённость с Vite.** Плагин `build-chunks.ts` читает поля пакета Rollup/Rolldown (`imports`, `modules`). Обновление Astro или Vite может их изменить. Смягчение: тест `build-chunks.test.ts`; без файла манифеста `check-links` падает; сумма бюджета на реальной сборке проверяется в CI.

## Migration Plan

Миграции данных нет. Порядок — `tasks.md`: источники и проверки → автоматы → компоненты → страницы → мета-данные → проверка фактов → skill. Откат — возврат `site/` и `ci_scope.dart` к прежнему состоянию; продукты и документы от витрины не зависят.
