**Что уже есть в цикле.**

`agent_loop.dart` (строки 248–275) вызывает хук, только если шаг закончился без вызовов, ответ непустой и нет ожидающего ввода:
- `Revise` при `revisions < maxResponseRevisions` кладёт заметку последним `user`-сообщением payload следующего шага и не пишет её в транскрипт (LOOP-7);

После вердикта цикл проверяет отмену и опрашивает steering. Исключение хука даёт `AgentError(hook)` и `TurnEnded(failed)` (LOOP-1). Тест цикла `test/loop/final_response_hook_test.dart` уже есть.

Два дефекта цикла, которые станут видимыми, как только гейт заработает:

Если после `Hold` пришёл steering (`_pollSteering`) или follow-up (`followUp.takeOne`), начинается новый шаг. Ход заканчивается с `held` прежнего кандидата, даже если новый ответ принят. Возможна и пара `held` и `budgetExceeded`.
- **Два `assistant` подряд в истории.** Заметка `Revise` живёт только в payload следующего шага. Поэтому в транскрипте и журнале за кандидатом сразу идёт следующий ответ модели, и в следующих ходах и после `session/load` история содержит два `assistant` подряд. Адаптеры провайдеров (`lib/src/llm/providers/`):

## Goals / Non-Goals

**Goals:**
- корневая сессия собирает финальный гейт из включённых в конфиге проверок; без проверок поведение MVP не меняется;
- две детерминированные встроенные проверки, которые ловят частые «ложно готовые» ответы: незакрытая задача и «тесты прошли» без запуска;
- лимит ревизий и политика на исчерпание, ограниченная ценой: ревизия — обычный шаг в `TurnBudget`;
- клиент видит удержанный ответ: на проводе `_meta.codelab.held`, в транскрипте заметка, в headless код `1`;
- проект без доверия не может ослабить проверки, заданные пользователем;
- диагностика без текста ответа в логах.

**Non-Goals:** модель-судья; одобрение ответа человеком (`/approve`, журнал, реплей); регистрация проверок хостом; проверка секретов в ответе; перепроверка действия после паузы. Причины — в proposal.md «Не входит» и в D4, Q1–Q3.

## Decisions

### D1. Составной хук собирает рантайм корня; проверка — внутренний синхронный интерфейс

`lib/src/loop/final_checks.dart` (новый, внутренний, барель его не экспортирует):

```dart
/// Одна проверка финального ответа (§17.12.4; D1, D2 change).
abstract interface class FinalResponseCheck {
  String get id;                                     // ^[a-z][a-z0-9_]{0,31}$
  /// Замечание для модели или `null` — замечаний нет.
  String? review(AssistantMessage message, TurnInfo turn);
}

BeforeFinalResponseHook composeFinalChecks({
  required List<FinalResponseCheck> Function() checks,   // снимок на вызов
  required FinalResponseSettings Function() settings,     // max_revisions, on_revise_limit
  required Logger logger,
  required SessionId sessionId,
});
```

`AgentRuntime` при сборке `AgentLoopConfig` корневой сессии (`agent_runtime.dart:1837`):
- всегда передаёт `beforeFinalResponse: composeFinalChecks(...)`;
- ставит `maxResponseRevisions` равным верхней границе схемы `5`.

Список проверок и фактический лимит берутся при каждом вызове гейта из снимка конфигурации **этой сессии**. Сессия в корне запуска читает применённый снимок процесса. Сессия другой папки читает конфигурацию своей папки, а без порта папки — `CoreConfig.withoutProject` (`agent-runtime` «Конфигурация сессии вне корня запуска», «Живая перезагрузка конфигурации»). Проверки, включённые проектным конфигом корня, на сессию чужой папки не действуют. Так перезагрузка действует со следующего вызова, а `AgentLoopConfig` не пересобирается (CFG-16, как функция модели в той же сборке). Хук ставится всегда, а не только при непустом `checks`: иначе проверки, включённые перезагрузкой в уже открытой сессии, не заработали бы до новой сессии. С пустым списком в снимке хук сразу возвращает `Accept`. Наблюдаемое поведение совпадает с MVP (LOOP-13), ход отличается одним синхронным вызовом без побочных эффектов.

Почему синхронный `review`, а не асинхронный `check` с таймаутом 30 с из §17.12.4. Обе встроенные проверки читают данные в памяти: `TurnInfo`, `TaskList.items`. Таймаут потребовал бы таймера, а ядро не создаёт таймеры ожидания само (PKG-6). Асинхронный интерфейс без асинхронных проверок — абстракция «на вырост» (`AGENTS.md` §13). Если появится проверка с вводом-выводом или модель-судья, интерфейс расширится тем change, который её введёт (Q1).

Почему `String?`, а не `ResponseVerdict`. `Hold` от отдельной проверки нужен только встроенной проверке одобрения (`require_approval`), а она не входит в change (Q2). Вердикт решает составной хук по лимиту (D3).

**Альтернативы:**
- (а) Порт `SessionSpec.finalResponseChecks` для хоста, как в §17.12.4. Ни `apps/codelab_agent`, ни `codelab_embedded` своих проверок не имеют: это публичный API без потребителя. Отклонено.
- (б) Проверки цепочкой хуков, как `beforeToolCall`. У финального гейта ровно одна точка и сводный вердикт, а цепочка с первым победившим теряет замечания остальных проверок. Отклонено.
- (в) Пересобирать `AgentLoopConfig` на каждый ход. `Agent` живёт всю сессию, и пересборка затронула бы очереди steering и follow-up. Отклонено.

### D2. Встроенные проверки: `open_tasks` и `unverified_success`, порядок фиксирован

Каталог в `final_checks.dart`. Проверки идут в порядке каталога, а не в порядке списка `checks`: список — множество, порядок заметки детерминирован.

1. **`open_tasks`.** В `TaskList` корневой сессии есть пункты со `status == in_progress` и `owner == TaskOwner.main`.
   - Пункты `pending` не считаются: план на будущее — законный итог хода.
   - Пункты субагентов не считаются: ребёнок закрывает их сам, а к финальному ответу корня все вызовы `agent` хода уже завершены.
   - Без списка задач (инструменты `task_*` недоступны агенту сессии) проверка молчит.

   Замечание:

   ```text
   Tasks still in progress: #<id>, #<id>. Finish them, or update their status with task_update before you answer.
   ```

   Не больше пяти id по возрастанию, после пятого — `and <n> more`. `subject` пункта в заметку не попадает. Это текст модели, а заметка — `user`-сообщение вне ограды TOOL-10 (D10): подставлять туда текст модели значит повышать его до «слов обвязки». Номер пункта модель сопоставит сама через `task_list`.

2. **`unverified_success`.** Текстовые блоки ответа-кандидата (без `thinking`) содержат утверждение об успехе проверки, а за ход не было попытки проверить. Попытка — вызов `exec` с исходом `completed` или `failed` (команда исполнялась) либо вызов `agent` с исходом `completed` (проверка делегирована субагенту, его отчёт — недоверенный вывод, SUB-7). Вызов с исходом `rejected` (отказ разрешения, режим `plan`) или `cancelled` попыткой не считается. Исход берётся из нового аддитивного поля `TurnInfo.toolOutcomes`: отображение `toolCallId → ToolOutcome` вызовов хода. Цикл заполняет его из итогов пакета. В `ToolResultMessage` исхода нет, только `isError`. Утверждения — одно регистронезависимое выражение, написанное для этого change: английские и русские формы «tests pass / passed / are passing / succeed(ed)», «build passes / succeeded», «тесты прошли / проходят», «сборка прошла / проходит». Источник — не сторонний список (`AGENTS.md` §5).

   Замечание:

   ```text
   The answer says that tests or the build pass, but no command ran in this turn. Run the check with exec, or say plainly that it was not verified.
   ```

   Признак попытки грубый: исполненный `exec` любой командой, в том числе с ошибкой. Проверка ловит именно ответ без попытки проверить, а не неверную интерпретацию вывода. Разбор вывода команды — задача модели-судьи (Q1).

**Альтернативы:**
- (а) Проверки по умолчанию включены. Меняет исход ходов у всех пользователей, а headless с `on_revise_limit: hold` начнёт выходить с кодом `1`. Решение отдано пользователю (Q5).
- (б) `open_tasks` по `pending` тоже. Ложные срабатывания на ходах «составь план». Отклонено.
- (в) `unverified_success` сопоставляет текст команды с `test` или `build`. Хрупко: `melos run check`, `make`, `just ci`. Отклонено.
- (г) Проверка «обещал правку, но не сделал» по ключевым словам. Без разбора смысла много ложных срабатываний. Вынесено в Q1.

### D3. Вердикты, лимит ревизий и политика

Алгоритм составного хука на один вызов:

```text
 1  s := settings(); active := catalog ∩ s.checks (в порядке каталога)
 2  notes := []
 3  для c из active:
 4    try r := c.review(message, turn)
      on Object e: log loop.final_check.error (warning: session_id, turn_id, check, error_class, stack); continue
 5    if r != null: notes.add("[<c.id>] <r>")
 6  if notes пуст: return Accept()
 7  if turn.revisions < s.maxRevisions:
        log loop.final_check.revise (info: session_id, turn_id, step_index, revisions, checks)
        return Revise(reviseText(notes))
 8  log loop.final_check.limit (info: session_id, turn_id, revisions, checks, policy)
 9  return s.onReviseLimit == hold
        ? Hold(truncateRunes("revision limit reached: " + notes.join("; "), 500))   # обрезка по рунам с `…`
        : Accept()
```

Текст заметки `Revise` цикл добавляет в транскрипт `user`-сообщением с `LoopNudgeOrigin(finalCheck, n)` (D10):

```text
[Final answer check] Your answer was not accepted:
<note 1>
<note 2>
Revise the answer. If you need to verify something, use the tools first.
```

Что делает каждый вердикт:

| Вердикт | Цикл | Провод | Журнал |
|---|---|---|---|
| `Accept` | ход завершается `TurnEnded(completed)` | `end_turn` | как сейчас |
| `Revise(note)` | заметка в транскрипт, ещё один обычный шаг | для клиента ничего особенного: продолжаются `agent_message_chunk`, `tool_call`; заметка не проецируется | запись `message` заметки с `origin: "loop_nudge"`, `nudge: "final_check"`, `attempt`; записи шага |
| `Hold(reason)` | `TurnEnded(completed, held: reason)`, если после него ход не продолжился (D11) | `end_turn` с `_meta.codelab.held` (D6) | как сейчас; `response_hold` не пишется (Q2) |

Правила:
1. Исключение проверки не валит ход: проверка пропускается с логом. В отличие от LOOP-1 для хуков хоста, встроенная проверка — вспомогательный рубеж, и её дефект не должен превращать каждый ход в `failed`.
2. Шаг ревизии — обычный шаг. Он входит в `TurnBudget` (`maxSteps`, `maxTokens`, `maxCost`, `maxDuration`), в `TurnEnded.usage`, в журнал usage и в уведомление `_codelab/session/usage`. Отдельного учёта нет: модель вызывается обычным запросом, а не судьёй.
3. Бюджет, исчерпанный на границе после `Revise`, завершает ход `budgetExceeded` без `held` и без нового вызова гейта (§17.12.4 п. 2).
4. Отмена побеждает: цикл проверяет отмену после вердикта (`agent_loop.dart`), `Revise` при отменённом ходе даёт `cancelled`.
5. Steering той же границы и заметка `Revise` идут в один шаг (§17.7.3.2): заметка добавляется в транскрипт до опроса steering.
6. Пустой ответ и заметка цикла гейт не вызывают (§5.4.1, LOOP-13 — без изменений).
7. `max_revisions: 0` — первое же замечание сразу идёт по политике.

**Альтернативы:**
- (а) Повтор без лимита до `Accept`. Бесконечная цена при ложном срабатывании. Отклонено.
- (б) `Hold` как отдельный `stopReason`. В ACP такого значения нет (`05-Prompt Turn.md#stop-reasons`), выдумывать нельзя (§3.4). Отклонено.
- (в) Повтор с заменой ответа: стереть кандидата из транскрипта. Кандидат уже отправлен клиенту и записан (SES-8), стирание нарушило бы целостность журнала и реплея. Отклонено.

Длина причины `Hold` везде считается в рунах (Unicode code points), а не в единицах UTF-16: обрезка не разрывает суррогатную пару. То же правило у клиента (D7).

### D4. Секреты в ответе финальный гейт не проверяет

Ответ-кандидат к моменту вызова гейта:
- уже ушёл клиенту дельтами `agent_message_chunk`;
- записан в журнал записью `message`: `SessionWriter` пишет `MessageEnded` до перехода цикла к следующему действию (SES-8).

Гейт не может ни скрыть текст, ни отменить запись. `Revise` только попросил бы модель «не повторять» секрет, который пользователь уже видел. Правильные рубежи:
- редакция до журнала и перед провайдером (P-10, после 1.0);
- маскирование клиента (`codelab_client_acp/doc/redaction.md`).

Дублировать их эвристикой в гейте — ложное чувство защищённости. Отклонённая альтернатива — проверка `secrets` с точными значениями известных секретов и `Revise`: польза только в том, что модель не повторит секрет в следующих ответах. Если такая потребность появится, её место — P-10.

### D5. Конфигурация и доверие к проекту

Схема `loop.final_response` вместо `_opaque` становится разделом:

| Ключ | Тип | По умолчанию | Ограничения |
|---|---|---|---|
| `checks` | список строк | `[]` | id каталога D2 |
| `max_revisions` | int | `2` | `0..5` |
| `on_revise_limit` | `hold` \| `accept` | `hold` | |

Все три ключа применяются: потребитель — составной хук (CFG-5). Неизвестный id в `checks` даёт предупреждение валидации (`ConfigIssue` вида `semantic` с ключом `loop.final_response.checks`) и пропускается, а не ошибку. Так конфиг, написанный для более новой версии агента, не ломает запуск. `config check` предупреждение показывает. `require_approval` в схему не входит (Q2): как любой неизвестный ключ, он даёт обычное предупреждение о неизвестном ключе.

Реестр настроек: `_opaque('loop.final_response')` заменяется дескриптором `_fileOnly` раздела `Advanced` «Final answer checks». Ключи не `restartRequired` и действуют со следующего вызова гейта (D1).

Доверие (`trust.dart`, по образцу `_lowerSubagents`). Недоверенный проект только ужесточает:
- `checks` объединяется со списком нижних слоёв, проект не может убрать проверку пользователя;
- `on_revise_limit: accept` поверх `hold` нижних слоёв (или умолчания) отбрасывается;
- `max_revisions` больше нижнего значения (или умолчания `2`) отбрасывается: репозиторий не может увеличить число оплачиваемых шагов ревизии;
- `max_revisions` меньше нижнего значения отбрасывается, если итоговая политика после правил доверия — `accept`. При `accept` уменьшение лимита до `0` фактически снимает проверки пользователя: первое же замечание принимается без ревизии. При `hold` уменьшение — ужесточение (ответ раньше удерживается), и оно применяется.

Каждое отбрасывание даёт `config.project.untrusted_key`. У доверенного проекта ограничений нет. Слои `extra`, окружения и флагов правилам не подчиняются: их задаёт тот, кто запускает.

**Альтернативы:**
- (а) Список `checks` проекта заменяет нижний, как при обычном слиянии списков. Недоверенный репозиторий снял бы проверку пользователя. Отклонено.
- (б) Ключи на каждую проверку (`open_tasks: true`). Больше ключей без выгоды. Список короче и расширяется без новых ключей схемы. Отклонено.

### D6. Провод: `_meta.codelab.held` в ответе `session/prompt`

`turnResponse` (`event_projection.dart`): `TurnEndReason.completed`, `budgetExceeded == null`, `held != null` → `PromptResponse(stopReason: endTurn, meta: {'codelab': {'held': held}})`.

Почему так:
- `stopReason` остаётся стандартным: ход закончился штатно, ответ есть;
- расширение лежит в `_meta`, который ACP отводит под это (`15-Extensibility.md`);
- оно уже перечислено в §13.12 документа ядра;
- `PromptResponse` в `codelab_acp_protocol` уже несёт `_meta` (`prompt.dart`), протокольный пакет не меняется.

Сторонний клиент видит обычный `end_turn`, клиент CodeLab старой версии тоже. Совместимость вперёд сохраняется.

Приоритеты не меняются: признак отмены от клиента даёт `cancelled` раньше всего, бюджет — `max_turn_requests`. `held` и `budgetExceeded` в одном ходе невозможны: при остановке бюджетом гейт не вызывается, а `held` прежнего кандидата сбрасывается в начале нового шага (D11).

`_meta.codelab.turnEnded` после переподключения `held` не несёт, как не несёт и `budgetExceeded` (R4).

### D7. Клиенты: итог хода, заметка транскрипта, headless

- **`codelab_client_acp`.** `PromptTurn.held: String?` заполняется из ответа `session/prompt` по образцу `_budgetExceededOf`. Поле читается только при `stopReason: end_turn` и только строкой длиной больше нуля. Переводы строк заменяются пробелом, длина ограничена 500 рунами с `…`. Иное значение даёт `null` без ошибки разбора. Строка от агента — недоверенный текст, но не более недоверенный, чем сам ответ модели в ленте.
- **`codelab_client_core`.** Ход с `held` даёт `NoticeItem` вида `turnStopped`: «агент остановил ход по причине, которую пользователь иначе не увидит» — смысл вида подходит. Параметры заметки:
  - id `<turnId>/stopped`;
  - новая причина `ResponseHeldReason(reason)` в sealed `NoticeReason`;
  - текст `The answer did not pass the final checks: <reason>`.

  Инкрементальная проекция и проекция с нуля дают равные причины. У ходов реплея `session/load` ответа на `session/prompt` нет, поэтому и заметки нет. Требования `acp-client-kit` «Инкрементальная проекция транскрипта» и «Типизированная причина заметки транскрипта» меняются (MODIFIED): до change `end_turn` заметку `turnStopped` не давал. REPL и TUI показывают `text` без правок.
- **`apps/codelab_cli` headless.** `end_turn` с `held` даёт код `1` и строку `Response held: <reason>` в stderr. Ответ модели остаётся в stdout: это реальный ответ, CI решает по коду. Модуль кодов выхода — прежний `exit_codes.dart` и `headless/outcome.dart`.
- **`apps/codelab_desktop`** (spec `agent-workbench-ui` «Заметка исхода хода в ленте»). `ui_mappers.dart` получает ветку `ResponseHeldReason` с локализованным префиксом `workbenchNoticeResponseHeld(reason)`. Причина подставляется как есть и не переводится, как значение провода в D7 change `add-desktop-localization`. Язык — по spec `app-settings` «Язык интерфейса app». Ветка обязательна: новый подтип sealed-класса ломает исчерпывающий `switch`, поэтому `[client]` и `[desktop]` идут одним PR.

**Альтернатива:** новый `NoticeKind.responseHeld`. Затронул бы все `switch` по виду в CLI, TUI и desktop без выгоды: вид `turnStopped` уже означает «итог хода, который иначе не виден». Отклонено.

### D8. Наблюдаемость

Логи ядра через логгер сессии, уровень и поля:

| Событие | Уровень | Поля |
|---|---|---|
| `loop.final_check.revise` | info | `session_id`, `turn_id`, `step_index` (шаг кандидата), `revisions`, `checks` (id сработавших) |
| `loop.final_check.limit` | info | то же и `policy` (`hold` \| `accept`) |
| `loop.final_check.error` | warning | `session_id`, `turn_id`, `check`, `error_class` (`runtimeType`), `stack` |

Текст ответа, текст замечаний, `subject` задач и текст исключения (`error`) в логи не пишутся: в тексте исключения проверки может оказаться фрагмент ответа, а в ответе — всё, что модель прочитала (`AGENTS.md` §10, §16). Стек содержит только имена кода и номера строк. Причина `held` уходит клиенту в ответе `session/prompt`. Клиентский журнал кадров маскирует её как любой текст (`SecretRedactor`).

### D9. Субагенты, headless и встроенный агент

- **Субагенты.** Гейт есть только у корневой сессии. Ребёнок (`agent_runtime.dart:583`) хука не получает. У отчёта ребёнка свой ремонт по схеме отчёта (§17.3, правило 4 §17.12.4). Отчёт ребёнка для корня — недоверенный результат инструмента в ограде (SUB-7), а не финальный ответ. Пункт `in_progress`, оставленный ребёнком, принадлежит ему (`owner != main`) и `open_tasks` корня не задевает.
- **Headless.** Одобрять некому, `held` — сигнал CI: код `1` (D7). Политика `--approve` на гейт не влияет: гейт не спрашивает человека.
- **Встроенный агент** (`codelab_embedded`) идёт тем же `AgentRuntime` и тем же `AcpAgentServer`: поведение совпадает с `codelab-agent serve`.

### D10. Заметка `Revise` — сообщение транскрипта с `origin: "loop_nudge"`

Цикл при `Revise` добавляет `UserMessage([TextContent(note)])` с `LoopNudgeOrigin(LoopNudgeReason.finalCheck, revisions)` в транскрипт тем же `_append`, что подсказку после пустого ответа (§5.4.1). Отдельная вставка заметки в payload (§5.2, шаг 4) удаляется.

Почему. История остаётся чередующейся: кандидат, заметка, следующий ответ. Решение снимает проблему адаптеров (Context): OpenAI-совместимые серверы со строгими шаблонами больше не получают два `assistant` подряд, а Anthropic не склеивает два ответа с блоками `thinking` в одно сообщение. Следующий ход и `session/load` видят ту же историю, что модель видела живьём: SES-8, как у подсказки пустого ответа (`08-sessions.md` §8.2.3).

Следствия:
- журнал: запись `message` с `origin: "loop_nudge"`, `nudge: "final_check"`, `attempt` (номер ревизии с 1). Новое значение `nudge` — новое значение поля записи, а не новый `origin`. `isUserWords` для `loop_nudge` уже даёт `false` (SES-14), заголовок сессии и счёт ходов пользователя не меняются;
- реплей `session/load` подсказки цикла пропускает (§13.5), клиент её не видит ни живьём, ни после загрузки. Живая проекция сообщений `user` не отправляет;
- сжатие: заметка — обычное сообщение истории, суммаризатор видит её как служебную;
- `TurnInfo.turnMessages` следующего вызова гейта содержит прежние заметки: проверки на них не опираются.

**Альтернативы:**
- (а) Оставить заметку только в payload, а в адаптерах склеивать соседние `assistant`. Это правка каждого адаптера и потеря причины ревизии в истории. Модель следующего хода видит два ответа без объяснения. Отклонено.
- (б) Писать заметку в журнал, но не в транскрипт `Agent`. Тогда история живого хода и после `session/load` разошлась бы, а SES-8 нарушен. Отклонено.

### D11. `held` относится к последнему кандидату

Цикл сбрасывает `held` в `null` в начале каждого нового шага: после решения продолжать и до проверки бюджета. Поэтому:
- `Hold`, за которым steering или follow-up открыли новый шаг, на итог хода не влияет. Итог определяет вердикт последнего кандидата;
- пара `held` и `budgetExceeded` невозможна: бюджет проверяется только перед новым шагом, а `held` к этому моменту сброшен;
- `revisions` не сбрасывается: лимит ревизий — на ход (§17.12.4).

Поэтому задачи 1.1–1.2 меняют цикл, а не только характеризуют его.

## Направление зависимостей и пакеты

Пакеты по ADR-0002:
- `codelab_agent_core` (ядро, слой `core`): `loop/final_checks.dart`, сборка в `runtime/`, конфиг;
- `codelab_agent_acp` (проекция агента): одна ветка `turnResponse`;
- `codelab_client_acp`, `codelab_client_core` (клиент): итог хода и заметка;
- `apps/codelab_cli`, `apps/codelab_desktop`: показ.

Новых зависимостей и пакетов нет, направление прежнее: `final_checks.dart` в `loop/` зависит от `tools/tasks/task_list.dart` через порт `TaskList`, который рантайм передаёт замыканием. Цикл о списке задач не знает (LOOP-6). Новое правило сторожа в `codelab_architecture_tests/test/support/rules.dart` не нужно: импорты между пакетами не меняются. Граф в `README.md` не меняется. Web-безопасность: `codelab_agent_core`, `codelab_client_acp` и `codelab_client_core` получают только `RegExp` и строки, новых импортов нет.

## Risks / Trade-offs

- **R1. Ложные и пропущенные срабатывания `unverified_success`.**
  - Ложные: «not all tests passed», цитата пользователя, тесты, запущенные в прошлом ходе, проверка, сделанная внуком через субагента с исходом `failed` у вызова `agent`.
  - Пропущенные: `exec` с любой командой (`ls`) засчитывается как попытка, а завершённый вызов `agent` — как делегированная проверка, даже если ребёнок тестов не запускал. `exec`, отклонённый разрешением или режимом `plan`, попыткой не считается (D2).

  Цена ложного срабатывания — до `max_revisions` лишних шагов, а при `hold` — код `1` в CI. Смягчение: проверка выключена по умолчанию; замечание разрешает модели прямо сказать «не проверено»; политика `accept` доступна.
- **R2. Цена ревизий.** Каждая ревизия — полный запрос к модели. Ограничение: `max_revisions ≤ 5`, `TurnBudget`, недоверенный проект не увеличивает лимит (D5).
- **R3. Проект включает проверки.** Недоверенный репозиторий может добавить проверки и тем самым увеличить число шагов (в пределах лимита пользователя) или чаще давать код `1` в CI. Это не расширение прав агента, а ужесточение. Отключить проверки для прогона можно слоем флагов или окружения.
- **R4. `held` теряется после переподключения.** Итог хода новому соединению идёт в `_meta.codelab.turnEnded` только со `stopReason`. Это тот же пробел, что у `budgetExceeded`, и закрывать его следует одним change для обоих.
- **R5. Ответ виден до проверки.** Пользователь видит кандидата, затем новые шаги модели без объяснения. Q4.
- **R6. Гонки.** Гейт работает на границе шага, когда вызовы шага завершены, а новые не начаты. `TaskList.items` читается без замка: в этот момент операций над списком в корне нет. Детские операции идут только внутри вызова `agent`, а он завершён. Отмена во время гейта побеждает (D3 п. 4). Steering после `Hold` сбрасывает устаревший `held` (D11). Перезагрузка конфига посреди хода меняет лимит со следующего вызова. Если новый лимит меньше уже сделанных ревизий, срабатывает политика.
- **R7. Late events.** Гейт не создаёт подписок и фоновых операций. Новых владельцев и отписок нет.

## Migration Plan

- Журналы: новых типов записей нет. Появляется значение `nudge: "final_check"` у записи `message` с `origin: "loop_nudge"` (D10). Старый читатель принимает `nudge` строкой и оставляет сообщение в контексте модели. Журналы до change заметок не содержат.
- Конфиг. Значения под `loop.final_response` раньше молча игнорировались (`_opaque`, `applied: false`). Теперь ключи схемы применяются, а неизвестные ключи раздела (`require_approval`) дают обычное предупреждение о неизвестном ключе. По умолчанию `checks: []`, поведение не меняется.
- Откат: удалить ключ `checks` или задать `[]`.
- Документы (задачи в tasks.md):
  - §17.12.4: синхронный `review` вместо асинхронного `check`; внутренний интерфейс без `SessionSpec.finalResponseChecks`; встроенные проверки; `require_approval`, `/approve` и записи журнала помечены «после change, Q2»;
  - §13.10 — строка stderr;
  - §5.2 и §5.4 (`05-agent-loop.md`) — заметка `Revise` в транскрипте, сброс `held`; §8.2.3 (`08-sessions.md`) — значение `nudge: "final_check"`;
  - `turn.md`, L21 — гейт достижим;
  - `docs/user/configuration.md`.

## Open Questions

Ответы пользователя 2026-11-26: по всем вопросам принята рекомендация design.md (Q1–Q5 — рекомендованные варианты). Вопросы ниже закрыты, текст сохранён как обоснование.

- **Q1. Модель-судья.** Нужна ли проверка отдельным вызовом модели: «обещал правку, но не сделал», «ответ не отвечает на вопрос», разбор вывода тестов? Цена — ещё один запрос на каждый финальный ответ, задержка, недетерминизм, отдельная строка usage (REV-43 учит учёт новым источникам), выбор модели через роли (§17.10.5). **Рекомендация:** не сейчас. Сначала собрать по логам `loop.final_check.*` частоту срабатываний детерминированных проверок. Судья — отдельный change с асинхронным интерфейсом, таймаутом от `Clock` хоста и своим ключом usage.
- **Q2. Одобрение ответа человеком.** Делать ли `require_approval`, `/approve`, записи журнала `response_hold` и `response_review` и пометку реплея из §17.12.4? **Рекомендация:** отдельный follow-up после этого change, и только если есть сценарий использования. Пользователь и так реагирует следующим промптом, а CI получает код `1`.
- **Q3. Перепроверка действия после паузы.** Мысль из обсуждения: после ожидания (вопрос о разрешении, замок пути) перед необратимым действием перепроверять, что оно всё ещё верно и разрешено. Место — единая точка исполнения `ToolCallExecutor` между цепочкой `beforeToolCall` и `execute`, а не финальный гейт: к финальному ответу действие уже сделано. Сейчас после хуков и после ожидания замка перепроверяется только отмена (`executor.dart`, шаг 6). Перепроверять стоит:
  - режим сессии: пользователь переключил `plan` во время вопроса;
  - правила `deny` после перезагрузки конфига;
  - `preflight` путей.

  Повторного вопроса пользователю не нужно. Это пробел безопасности: режим или `deny` могут смениться, пока висит вопрос. **Рекомендация:** отдельный change `agent-permissions`, например `add-post-wait-recheck`, с инвариантом «решение применяется, только если политика на момент исполнения его допускает». В этот change не включать.
- **Q4. Показывать ли клиенту факт ревизии.** Например, заметкой транскрипта по `_meta` у первого `agent_message_chunk` шага ревизии. **Рекомендация:** нет, пока нет жалоб. Нужно новое расширение, а лог `loop.final_check.revise` с `step_index` уже даёт диагностику: по нему шаг ревизии сопоставляется с кадрами хода.
- **Q5. Умолчания.** Включать ли `open_tasks` по умолчанию? **Рекомендация:** оставить `checks: []` в этом change. После одного выпуска с логами `loop.final_check.*` решить, включать ли `open_tasks` по умолчанию: ложных срабатываний у неё почти нет, но она меняет исход ходов в headless.
