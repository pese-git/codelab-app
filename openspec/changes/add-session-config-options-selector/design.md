## Context

ACP определяет два способа, которыми агент сообщает клиенту конфигурируемые параметры сессии: устаревший `SessionModeState`/`session/set_mode` (`docs/acp/protocol/12-Session Model.md`) и предпочитаемый `SessionConfigOption[]`/`session/set_config_option` (`docs/acp/protocol/13-Session Config Options.md`, категории `mode`/`model`/`thought_level`). Сам протокол явно требует: «Clients that support config options SHOULD use them exclusively and ignore `modes`».

В `acp_protocol` уже полностью смоделированы входящие DTO: `SessionConfigOption`/`SessionConfigId`/`SessionConfigValueId`/`SessionConfigSelectOption` (`packages/dart/acp_protocol/lib/src/acp/session.dart:281-429`), `SessionUpdate.configOptionUpdate`/`currentModeUpdate` (`session_update.dart:201-207`). `AcpClientApplication.createSession()`/`loadSession()` уже кладут `response.configOptions` в `AcpSession.configOptions` при создании/загрузке сессии (`acp_client_application.dart:123-168`).

Чего нет вообще:
- исходящего метода `session/set_config_option` в `acp_method_codec.dart`/`session.dart` — нет ни модели запроса/ответа, ни записи в `acpMethodRegistry`;
- обработки `SessionUpdate.configOptionUpdate`/`currentModeUpdate` в `SessionStateMachine._applyUpdate` (`state_machines.dart`) — `grep` не даёт ни одного совпадения, обновления этого типа сегодня просто не долетают до `AcpSession.configOptions` после первого `session/new`;
- какого-либо UI в `AcpPromptComposer`/`CodeLabShellCubit`.

## Goals / Non-Goals

**Goals:**
- Добавить исходящий `session/set_config_option` (request: `sessionId`, `configId`, `value`; response: полный `configOptions[]`, по спеке — «always contains the complete configuration state»).
- Применять `SessionUpdate.configOptionUpdate` к `AcpSession.configOptions` **независимо от наличия активного turn** — агент может прислать его «at any point during a session, whether idle or generating a response» (дословно из `12-Session Model.md`, тот же принцип верен и для config options). Это та же архитектурная проблема, что уже была найдена и исправлена для `AvailableCommandsUpdate` в `wire-command-palette` — `SessionStateMachine._applyUpdate` получает точно такой же второй `case`, специально session-scoped, а не turn-gated.
- Показать в `AcpPromptComposer` ряд chip-селекторов — по одному на каждый `SessionConfigOption` из `AcpSession.configOptions`, в порядке, присланном агентом (порядок значим по спеке). Выбор в dropdown вызывает `session/set_config_option` и обновляет чип из ответа.
- Если `configOptions` пуст или `null` (агент не предоставляет ни одного) — ряд селекторов не рендерится вообще. Не «disabled»/«coming soon» — там просто нечего показывать, это не незавершённая фича CodeLab, а объективное отсутствие данных от конкретного агента.

**Non-Goals:**
- **Не реализуется UI для собственного (client-side) `permissionMode` CodeLab** (`readOnly`/`ask`/`plan`/`autoEdits` из `approval-safety` спеки). Это не связанное с ACP wire-protocol понятие — оно определяет исключительно локальную политику подтверждений и не имеет отражения в протоколе. Design-канвас (`SessionOptionsRow.dc.html`) визуально изображает «Permission mode» чип с этими самыми значениями (Read only/Ask) — это конфликтует по смыслу c `SessionConfigOption.category == "mode"`, которая означает нечто, объявленное *агентом*, а не режим клиента. Здесь взят только agent-driven путь (`SessionConfigOption`); UI для client-side `permissionMode` — отдельная, никак не связанная будущая фича, если вообще будет нужна.
- **`session/set_mode`/`SessionModeState` не реализуются и не получают UI.** Строго по протоколу: агент, предоставляющий `configOptions`, не должен ожидать, что клиент также использует `modes`, а клиент, поддерживающий config options, обязан их игнорировать. Смешивать оба канала — источник рассинхронизации, которую сама спека явно предостерегает не создавать.
- Не вводится persistence/кэш выбранных опций между сессиями — `configOptions` целиком приходит от агента при каждом `session/new`/`session/load`, значение по умолчанию всегда его.
- Не решается вопрос иконок/специфичного стиля под каждую `category` (`mode`/`model`/`thought_level`) — в этой итерации все опции рендерятся одним универсальным chip-виджетом с общей иконкой; кастомизация по категории — возможное будущее расширение, не блокирующее MVP.

## Decisions

- **`session/set_config_option` — request-response метод**, как `session/new`/`session/prompt`, а не notification: агент обязан вернуть полный обновлённый список `configOptions` синхронно (`13-Session Config Options.md`, "The Agent MUST respond with the complete list"). Модели `SetSessionConfigOptionRequest{sessionId, configId, value}`/`SetSessionConfigOptionResponse{configOptions}` добавляются в `session.dart` по образцу `NewSessionRequest`/`NewSessionResponse`; метод регистрируется в `acp_method_codec.dart` как `acpSessionSetConfigOption` в `acpMethodRegistry`.
- **`SessionStateMachine._applyUpdate` получает pattern-case для `ConfigOptionUpdate`**, применяющий `session.copyWith(configOptions: update.configOptions)` до проверки `activeTurn` — идентично уже существующему `case AvailableCommandsUpdate(...)` (`state_machines.dart`), включая тот же fallthrough: если активный turn есть, обновление *также* записывается в него (для истории/инспектора), но сессия обновляется в любом случае. `CurrentModeUpdate` (устаревший канал) намеренно не обрабатывается вообще — Non-Goal выше.
- **`AcpClientApplication` получает `Future<AcpSession> setSessionConfigOption(SetSessionConfigOptionCommand command)`** — тонкая обёртка: `_sendRequest<SetSessionConfigOptionResponse>(...)`, затем `session.copyWith(configOptions: response.configOptions)` через `_storeSession`, тем же паттерном, что `createSession`/`loadSession`. Use case `SetSessionConfigOption` в application-слое — тонкая, но самостоятельная (координирует `AcpClientApplication` + маппинг command/failure), по аналогии с `CreateSession`/`SendPrompt`.
- **`CodeLabShellCubit.setSessionConfigOption(String configId, String value)`** вызывает use case и полагается на уже существующий путь `sessionChanges`/`_handleSessionChange` для отражения нового `configOptions` в `CodeLabShellState` — отдельного поля в state не заводится, `state.activeSession?.configOptions` (или эквивалент, уточняется в tasks.md) читается напрямую, тем же способом, каким уже читаются `agentCommands` из `AcpSession.availableCommands`.
- **UI — новый опциональный параметр `AcpPromptComposer.configOptions`/`onConfigOptionSelected`**, ряд chip-виджетов над toolbar'ом (между текстовым полем и рядом Send/Cancel, либо отдельной строкой сверху — уточняется в реализации по месту, визуальный референс `SessionOptionsRow.dc.html`/`Main.dc.html`). Каждый chip — `Button` с текущим `name`/значением и dropdown-меню (`FlyoutTarget`/аналог, уже использующийся в проекте для похожих меню, если есть, иначе `MenuFlyout` из `fluent_ui`) со списком `options`. Выбор синхронно вызывает `onConfigOptionSelected(configId, value)`.
- **Ряд не рендерится при пустом списке** — не «visually disabled», а полностью `null`/`SizedBox.shrink()`, зеркально decision из `wire-command-palette` про честное отсутствие вместо fake-интерактивности, но здесь дело не в недоделанной фиче CodeLab, а в объективном отсутствии данных конкретного агента.

## Risks / Trade-offs

- [Агент может прислать `configOptions` с большим количеством записей, переполняя toolbar] → не вводится лимит/скролл в этой итерации; ряд просто оборачивается по ширине (`Wrap`), как и в остальном UI проекта — если станет проблемой на практике, это отдельный будущий change.
- [Гонка между двумя быстрыми последовательными выборами одной и той же опции пользователем] → `session/set_config_option` — request-response; пока предыдущий запрос не завершился, повторный выбор в том же чипе можно временно дизейблить (`isRespondingToConfigOption`-подобный флаг, аналогичный `isRespondingToApproval`), решение по месту в tasks.md.
- [Путаница между agent-driven `SessionConfigOption.category == "mode"` и client-side `approval-safety` `permissionMode`] → явно описано в Non-Goals; в UI выбрана нейтральная формулировка чипа (название берётся из `option.name`, присланного агентом, а не захардкожено как «Permission mode»), чтобы не создавать ложное впечатление, что это переключатель `readOnly`/`ask`/`plan`/`autoEdits`.
