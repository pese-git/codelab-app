## Context

**Как app выходит сейчас.** `CodeLabBootstrap` (`apps/codelab_desktop/lib/app/app_scope.dart`) создаёт root scope CherryPick и закрывает его в `dispose`: `closeCodeLabRootScope()` → `CodeLabRootLifecycle.dispose()` и `CodeLabLoggingLifecycle.dispose()`. При штатном завершении (macOS `terminate:` по Cmd+Q и после закрытия последнего окна) движок останавливается без размонтирования дерева, и этот `dispose` не выполняется (`add-integrated-terminal`, D4 «Выход из app», D15 п. 9).

Единственная точка, которая гарантированно вызывается до выхода, — `AppLifecycleListener.onExitRequested`. Её обрабатывает `AppExitHandler` (`lib/app/app_exit_handler.dart`):
1. `app.exit_requested`;
2. `TerminalTabsCubit.closeAll()` — `hangUp` всем вкладкам, через 3 с `kill`;
3. сброс файловых журналов не дольше 500 мс;
4. всегда `AppExitResponse.exit`.

Остальное закрытие обработчик сознательно не вызывал: «может ждать долго и не нужно для выхода» (doc-комментарий `AppExitHandler`). Этот change пересматривает это решение: закрытие нужно, чтобы не оставлять процессов-сирот.

**Владельцы процессов и их закрытие (код на `develop` 4c71d949).**

| Процесс | Владелец | Как закрывается | Сколько ждёт |
|---|---|---|---|
| Вкладки панели Terminal | `TerminalTabsCubit` | `closeAll()`: `hangUp` → 3 с → `kill`, без ожидания выхода после `kill` | ≤ 3 с |
| ACP `terminal/*` внешнего агента | `AcpClientApplication` (реестр `SessionId → TerminalId`), адаптер `IoTerminalProcessRunner` | `dispose()` → `_killAllTerminalProcesses()` → `handle.kill()` = один `SIGTERM` корню, без ожидания; затем `_transport.close()` | 0 с; игнорирующий `SIGTERM` процесс живёт дальше |
| Внешний stdio-агент | `AcpClientApplication` — текущий транспорт после `connect`; транспорт — `StdioAcpTransport` | `close({timeout})`: закрыть stdin → ждать `timeout` (по умолчанию 5 с) → `process.kill()` (`SIGTERM`) → `await exitCode` **без предела** | 5 с + неограниченно |
| Встроенный агент: `exec` | ядро агента (`LocalExecutionEnv`, `codelab_agent_io`) | `EmbeddedAgent.dispose()` → `server.shutdown(grace: 5 s)` отменяет ходы → токен отмены → `terminateTree`: `SIGTERM` дереву, 2 с, `SIGKILL` | ≤ 2 с после отмены |
| Встроенный агент: MCP stdio | сессии рантайма (`StdioProcessTransport`, `codelab_agent_io`) | `runtime.dispose()` после `shutdown`: EOF → 2 с → `SIGTERM` дереву → 5 с → `SIGKILL`; потомки — `SIGTERM`, 5 с, `SIGKILL` | обычно мгновенно, худший случай ~14 с; сессии закрываются по очереди |
| Встроенный агент целиком | `EmbeddedTransportResolver` (app) | `close()` ждёт открытие в полёте и `dispose` агента; `CodeLabRootLifecycle` ограничивает 10 с (`embedded.close_timeout`) | ≤ 10 с |

**Порядок `CodeLabRootLifecycle.dispose()` сейчас**, строго последовательно, без изоляции шагов:
1. `closeAll()` и `close()` терминала;
2. остальные Cubit-ы;
3. `ClientWorkspace.dispose()` (сброс снимка);
4. `EmbeddedTransportResolver.close()` (≤ 10 с);
5. `SecretMigrationOffer.close()`;
6. `_transport.close()` — синглтон начального транспорта;
7. `AcpClientApplication.dispose()`.

Повторный вызов возвращается сразу по флагу `_isDisposed`, даже если первый ещё идёт.

**Одновременно работает только один агент.** Текущий транспорт ядра клиента — либо встроенный (`InProcessAcpLink`), либо внешний (stdio или WebSocket). Процессы `terminal/*` бывают только у внешнего агента: встроенный исполняет команды сам (`embedded-agent` «Локальное исполнение и containment»). При замене транспорта `terminal/*` прежнего соединения убиваются (`_transitionConnection` → `_killAllTerminalProcesses`). Поэтому при выходе долгий хвост даёт либо ветка встроенного агента, либо ветка внешнего, но не обе сразу.

**ACP.** `16-Transports.md` для stdio описывает завершение одной строкой диаграммы: «Close stdin, terminate subprocess». `session/cancel` (`05-Prompt Turn.md`, «Cancellation») — это `MAY` клиента для отмены хода, а не шаг закрытия соединения. Методов закрытия сессии или соединения в схеме (`17-Schema.md`) нет.

## Goals / Non-Goals

**Goals:**
- После штатного выхода из app не остаётся дочерних процессов клиента: вкладок Terminal, `terminal/*`, `exec` и MCP stdio встроенного агента, внешнего stdio-агента. Исключение — процессы, которые пользователь сам намеренно отвязал (`nohup`, `disown`, `platform-integration.md` §23).
- Выход не зависает: ответ `exit` уходит не позже общего предела, отмены выхода нет.
- В журнале видно, как прошло закрытие: уложилось ли оно в предел, какие шаги не успели или упали. Путей, команд и текстов ошибок в событиях нет.
- Встроенный агент дописывает журнал сессии, рабочее пространство сбрасывает снимок — как при обычном закрытии root scope.

**Non-Goals:**
- Завершение дерева потомков `terminal/*` (Q2).
- Укорочение grace встроенного агента и закрытия MCP при выходе (Q3).
- Изменения ACP, `codelab_embedded`, ядра агента, `codelab_client_core`, CLI.
- Индикатор «Quitting…» и блокировка ввода на время закрытия.

## Decisions

### D1. Владелец «закрыть всё клиентское» — `CodeLabRootLifecycle`, вызывает его обработчик выхода

`AppExitHandler` вызывает `CodeLabRootLifecycle.dispose()` — функцию `closeRoot`, которую передаёт composition root. Прямой вызов `TerminalTabsCubit.closeAll()` из обработчика убирается. `dispose()` уже описывает упорядоченное закрытие всех владельцев процессов в composition root (`session-lifecycle.md` §42, `concurrency.md` §45). Выход должен идти тем же путём, а не вторым списком шагов.

Почему `CodeLabRootLifecycle` (app, `lib/app/`), а не общий пакет:
- Владельцы процессов распределены по app и пакетам. `EmbeddedTransportResolver` и `TerminalTabsCubit` живут в app, `AcpClientApplication` — в `codelab_client_acp`. Связать их может только composition root.
- `ClientWorkspace.dispose` в `codelab_client_core` по контракту не закрывает бэкенд («бэкенд закрывает его владелец»). Узнать о встроенном агенте он не может: `codelab_client_core` не зависит от `codelab_embedded` (allowlist сторожа, D3 `add-embedded-agent-mode`).
- У CLI свой владелец — `CliRuntime.dispose`, и он уже вызывается при выходе `codelab`. Общий тип ради одного потребителя был бы абстракцией «на вырост» (`AGENTS.md` §13).

Отклонённые альтернативы:
- **Новый метод `CodeLabRootLifecycle.releaseProcesses()`** только для процессов, без закрытия Cubit-ов и рабочего пространства. Отклонено. Процессы `terminal/*` и stdio-агента закрывает `AcpClientApplication.dispose`, а его вызывают последним, после рабочего пространства и встроенного агента (D9 `add-embedded-agent-mode`). Отдельный метод повторил бы этот порядок во втором месте. Кроме того, закрытие Cubit-ов — это и есть шаг «stop new operations» из `concurrency.md` §45.
- **Метод `ClientWorkspace.shutdown(deadline)` в `codelab_client_core`.** Отклонено по причинам выше: пакет не знает встроенного агента и терминал пользователя.
- **Закрывать root scope целиком (`closeCodeLabRootScope()`) из обработчика.** Отклонено. Scope закрывает и `CodeLabLoggingLifecycle`, в том числе HTTP-выход журнала, а журнал нужен до самого ответа `exit`. Сброс журнала — отдельный шаг обработчика, как сейчас.

### D2. Общий предел — 5 с от запроса выхода; терминал и клиентская цепочка — параллельно

`AppExitHandler` ждёт `closeRoot()` не дольше `exitTimeout` = **5 с**, затем сбрасывает журнал (≤ 500 мс, как сейчас) и возвращает `exit`. Худшее время от Cmd+Q до выхода — около 5,5 с.

Внутри `CodeLabRootLifecycle.dispose()` две ветки идут параллельно:
- **ветка терминала:** `TerminalTabsCubit.closeAll()` (≤ 3 с), затем `close()`;
- **клиентская ветка:** остальные Cubit-ы → `ClientWorkspace.dispose()` → `EmbeddedTransportResolver.close()` (≤ 10 с, прежний предел) → `SecretMigrationOffer.close()` → закрытие начального транспорта → `AcpClientApplication.dispose(closeTimeout: 2 с)`.

> **Уточнено по ревью (D11).** Клиентская ветка после `ClientWorkspace.dispose()` делится на две параллельные: агентская (`embedded` → `migration_offer`) и ACP (`transport` → `client`). Последовательный вариант выше оставлял сигналы `terminal/*` и stdio-агенту за зависшим закрытием встроенного агента.

`dispose()` ждёт обе ветки. Терминал пользователя и ACP-сторона друг о друге не знают (`add-integrated-terminal`, D10), поэтому порядка между ветками нет. `closeAll()` с первого вызова запрещает новые вкладки (`concurrency.md` §45), поэтому `close()` Cubit-а терминала может прийти после `ClientWorkspace.dispose()`.

Бюджет клиентской ветки в худшем ожидаемом случае укладывается в 5 с:

| Активный агент | Хвост ветки |
|---|---|
| Внешний stdio | `terminal/*`: `SIGTERM` → 2 с → `SIGKILL` (D4) **параллельно** с транспортом: EOF → 2 с → `SIGTERM` → 2 с → `SIGKILL` (D3). Итого ≈ 4 с |
| Встроенный | отмена ходов → `terminateTree` `exec` ≤ 2 с; MCP: EOF, обычно мгновенный выход. Худший случай (ход не завершился за grace, MCP-сервер игнорирует EOF и `SIGTERM`) выходит за 5 с — Risks, Q3 |
| WebSocket | закрытие сокета, процессов нет |

Почему 5 с:
- Нижняя граница — 4 с: столько нужно эскалации stdio-агента (D3) плюс накладные расходы. Терминал (3 с) идёт параллельно и укладывается.
- 3 с, как у терминала, мало: внешний агент, игнорирующий EOF, не получил бы даже `SIGTERM`.
- 10 с, как `defaultEmbeddedCloseTimeout`, слишком много для Cmd+Q. В типичном случае закрытие занимает доли секунды, и большой предел защищает только от редкого зависшего хода встроенного агента. Пользователь заметит паузу в 10 с как зависание app.

Последовательный вариант «терминал, потом остальное» отклонён: 3 с + 4 с не укладываются в разумный предел.

**Что происходит по истечении предела.** Обработчик пишет `app.exit_timeout` (D6) и возвращает `exit`. Незавершённые шаги продолжают работать до остановки VM. Отдельного прохода «убить всех оставшихся» из обработчика нет. У обработчика нет реестра pid, и заводить второй реестр рядом с владельцами — конкурирующий механизм (`AGENTS.md` §14). Предел действует, если шаги, посылающие сигналы, начинаются достаточно рано, а эскалация каждого из них укладывается в остаток предела (D3, D4).

Утверждение «к пределу каждый владелец уже послал свои сигналы» верно не всегда (уточнено по ревью, D10, D11). Шаг, который к пределу не начался, не послал ничего. Поэтому:
- `pending` в `app.exit_timeout` перечисляет и не начатые шаги (D10) — по журналу видно, кто остался без сигналов;
- шаги с сигналами (`terminal`, `client`) не стоят в очереди за закрытием встроенного агента (D11). Перед ними остаются только `cubits` и `workspace` (сброс снимка, локальная запись файла) и `transport` (закрытие начального транспорта, который никогда не запускается, — мгновенно).

Остаточный путь, когда сигналы не уходят, — зависший `ClientWorkspace.dispose()`. Его ожидание без предела — это ожидание записи снимка в локальный файл (`WorkspaceRestorer.flush()`); принято (Risks).

Предел — параметр конструктора `AppExitHandler` (`exitTimeout`, по образцу `flushTimeout`). Это шов тестов, а не настройка пользователя.

### D3. `StdioAcpTransport.close` — ограниченная эскалация до `SIGKILL`

Сейчас `close({timeout})`:
1. закрывает stdin;
2. ждёт выхода `timeout` (по умолчанию 5 с);
3. шлёт `process.kill()` (`SIGTERM`);
4. делает `await exitCode` без предела.

Агент, игнорирующий `SIGTERM`, держит `close()` вечно — и вместе с ним `AcpClientApplication.dispose`, `CliRuntime.dispose` и замену транспорта при Reconnect.

Новое поведение:
1. закрыть stdin;
2. ждать выхода `timeout`;
3. `SIGTERM`;
4. ждать ≤ 2 с;
5. `SIGKILL` без дальнейшего ожидания кода выхода.

`close()` завершается не позже `timeout + 2 с` плюс отписка потоков. Значение 2 с совпадает с `terminateTree` агента (`agent-core-architecture` §4.6). Внутренняя константа транспорта, не параметр.

При выходе из app `CodeLabRootLifecycle` передаёт `AcpClientApplication.dispose(closeTimeout: 2 с)`, а тот — `_transport.close(timeout:)`. Параметр повторяет существующий образец `connect(transport, closeTimeout:)` и `ReconnectCommand.closeTimeout` (`_replaceTransport`). Значение 2 с — константа `lib/app/` рядом с `defaultEmbeddedCloseTimeout`. Без параметра остаётся прежнее значение 5 с, поэтому CLI и тесты пакета не меняются.

Это соответствует ACP: «Close stdin, terminate subprocess» (`16-Transports.md`). Сколько ждать и чем завершать, ACP не определяет. Для `codelab-agent serve --stdio` `SIGTERM` после EOF не прерывает начатое безопасное завершение: первый сигнал считается первым (`signals.dart`), и выхода «сразу» нет. Если агент не уложился в 4 с, `SIGKILL` может оборвать дописывание журнала (Risks).

> **Уточнено по ревью (D13).** `close()` мемоизирован: повторный вызов ждёт идущее закрытие, а более ранний предел повторного вызова сокращает ожидание EOF. `close()` во время `start()` дожидается запуска и закрывает запущенный процесс.

Отклонено:
- `SIGKILL` сразу после `timeout`: лишает агента обработчика `SIGTERM` (у `codelab-agent` он дописывает журнал).
- Оставить неограниченное ожидание и полагаться на предел обработчика: тогда Reconnect и CLI зависают на таком агенте по-прежнему, а при выходе агент остаётся сиротой.

### D4. `IoTerminalProcessRunner.kill()` — `SIGTERM`, через 2 с `SIGKILL`; в `dispose` — параллельно с транспортом

`kill()` адаптера:
1. если процесс уже вышел — no-op, как сейчас;
2. иначе `SIGTERM`, ждать кода выхода ≤ 2 с;
3. не вышел — `SIGKILL`;
4. `Future` завершается после выхода или после отправки `SIGKILL`, то есть не позже чем через ~2 с.

В статусе выхода `signal` — фактически приведший к выходу сигнал: `SIGTERM` или `SIGKILL`. Сейчас там всегда `SIGTERM`.

> **Уточнено по ревью (D14).** Сигнал выводится из кода выхода процесса, а не из того, какой сигнал послан последним; `exitCode` при выходе по сигналу — `null`. Прежняя формулировка давала в провод `exitCode: -15` (схема ACP: `minimum: 0`) и `signal: SIGTERM` у процесса, вышедшего сам.

Контракт порта `TerminalProcessHandle.kill()` («Terminates the process») не меняется, уточняется только его doc-комментарий. Изменение видно агенту: ответ на `terminal/kill` для процесса, игнорирующего `SIGTERM`, приходит до 2 с позже, но процесс к этому моменту действительно завершён. ACP требует, чтобы `terminal/kill` «terminates a command» (`10-Terminal.md`, «Killing Commands»). Сейчас такой процесс после ответа продолжал работать.

`AcpClientApplication.dispose` запускает `_killAllTerminalProcesses()` и `_transport.close(timeout: closeTimeout)` параллельно и ждёт оба. Последовательно это 2 с + 4 с, что выходит за предел D2. Порядок между ними ACP не задаёт. Входящая подписка снимается до обоих шагов, так что агент уже не может прислать `terminal/*`. Путь `_transitionConnection` (разрыв соединения) по-прежнему вызывает `_killAllTerminalProcesses()` через `unawaited` и получает эскалацию бесплатно.

Отклонено:
- **Таймер `SIGKILL` внутри адаптера при немедленном возврате `kill()`.** При выходе VM может остановиться раньше таймера, и процесс останется сиротой. Тогда `dispose` пришлось бы дополнительно ждать `waitForExit()`, а он включает дочитывание вывода (до 2 с).
- **Новый метод порта `forceKill()`.** Лишний public API: эскалацию нигде не нужно отделять от `kill`.

### D5. Изоляция шагов и идемпотентность `CodeLabRootLifecycle.dispose()`

- `dispose()` возвращает один и тот же `Future` при повторных вызовах (`_disposing ??= _dispose()`). Второй вызов ждёт тот же проход, а не возвращается сразу, как при флаге `_isDisposed`. Это закрытие scope после выхода (тесты, hot restart) и второй запрос выхода от ОС.
- Каждый шаг выполняется через локальный помощник `_step(name, body)`:
  - сбой шага → `app.shutdown_step_failed {step, error_type}`, следующие шаги выполняются;
  - имена шагов — закрытый набор: `terminal`, `cubits`, `workspace`, `embedded`, `migration_offer`, `transport`, `client`;
  - помощник ведёт множество незавершённых шагов `pendingSteps` — для события `app.exit_timeout` (D6). **Уточнено по ревью (D10):** множество заполняется целиком в начале прохода, `_step` только удаляет имя.

  Образец — `_step` в `EmbeddedAgent.dispose` (`assemble.dart`) и цепочка `try/finally` в `CliRuntime.dispose`. Сейчас исключение из `workspace.dispose()` пропустило бы закрытие агента и ядра клиента.
- Повторных сигналов нет за счёт самих владельцев:
  - `closeAll()` мемоизирован;
  - `_killAllTerminalProcesses()` очищает реестр до `kill`;
  - `kill()` вышедшего процесса — no-op;
  - `StdioAcpTransport.close()` мемоизирован (D13; раньше — флаг `_isClosed`, и повторный вызов не ждал первый);
  - `EmbeddedTransportResolver.close()` мемоизирован;
  - `EmbeddedAgent.dispose()` идемпотентен.
- `AppExitHandler.onExitRequested` тоже мемоизирован (`_exit ??= _handle()`). Предел D2 отсчитывается от первого запроса, второй запрос ждёт тот же ответ.

Отклонено: вести общий флаг «идёт выход» в app. Его роль уже выполняют мемоизированные `Future` владельцев. Флаг стал бы mutable global state (`concurrency.md` §72).

### D6. События журнала — только типы, счётчики и длительности

По образцу D9 `add-integrated-terminal`: путей, команд, аргументов, окружения, `toString()` исключений и текста ошибок нет. Ключ `error_type` — `runtimeType`.

Логгер `codelab_desktop.app`, компонент `app` (как у `app.exit_requested`):

| Событие | Уровень | Поля | Когда |
|---|---|---|---|
| `app.exit_requested` | info | — | без изменений |
| `app.exit_closed` | info | `duration_ms` | `closeRoot()` завершился в пределе |
| `app.exit_timeout` | warning | `timeout_ms`, `pending` — список имён шагов из закрытого набора D5 | предел истёк |
| `app.exit_close_failed` | error | `error_type` | без изменений; теперь — `closeRoot()` бросил целиком (страховка: шаги изолированы) |
| `app.shutdown_step_failed` | error | `step`, `error_type` | шаг `CodeLabRootLifecycle.dispose()` бросил — и при выходе, и при закрытии scope |

`codelab_client_acp`, логгер ядра клиента, слой `application`:

| Событие | Уровень | Поля | Когда |
|---|---|---|---|
| `terminal_processes_killed` | info | `count`, `reason` (`connection_closed` \| `dispose`) | `_killAllTerminalProcesses()` с непустым реестром |

`session_id` и `terminal_id` в событие не пишутся: оно агрегирует все сессии, а по одному событию на процесс при выходе не нужно. Имя без префикса — как `connection_state_changed` и `turn_interrupted` этого логгера.

Существующие события не меняются:
- `terminal.close_all`, `terminal.tab_closed {forced}` (терминал);
- `embedded.close_timeout` (10 с — внутри закрытия root scope; при выходе, как правило, не успевает, его заменяет `app.exit_timeout` с `pending: [embedded]`);
- `connection_state_changed` (ядро клиента).

Отклонено: событие на каждый `SIGKILL` транспорта и адаптера. `codelab_acp_transports` и `codelab_client_io` не логируют, а заводить логгер в транспорт ради одного события непропорционально. Факт эскалации виден по длительности `app.exit_closed` и по `pending` в `app.exit_timeout`.

### D7. ACP: перед закрытием агенту ничего не отправляется

`session/cancel` перед выходом не отправляется:
- ACP делает его `MAY` для отмены хода пользователем (`05-Prompt Turn.md`, «Cancellation»), а не шагом закрытия соединения;
- ответа на `session/prompt` клиент при выходе ждать не будет, а сам `session/cancel` — уведомление без подтверждения;
- агент CodeLab отменяет ход при закрытии соединения сам: встроенный — через `server.shutdown`, `codelab-agent --stdio` — по EOF (`agent-binary` «Жизненный цикл процесса»);
- так же решено для замены транспорта (change `cancel-turn-on-ws-disconnect`, D1, отклонённая альтернатива).

Ожидающие `session/request_permission` при `dispose` по-прежнему снимаются без ответа: обязанность ответить `cancelled` ACP связывает с отправкой `session/cancel` (`05-Prompt Turn.md`), а соединение закрывается. Для stdio-агента завершение — «Close stdin, terminate subprocess» (`16-Transports.md`), D3 только ограничивает его по времени. Новых методов, полей и semantics ACP change не вводит.

## Решения по ревью реализации (2026-11-13)

Двойное ревью реализации нашло проблемы. Каждая находка проверена по коду ветки. Решения D10–D15 уточняют D2–D6 и имеют приоритет над ними там, где расходятся. Отклонённые находки — в конце раздела.

### D10. `pending` в `app.exit_timeout` — все незавершённые шаги, включая не начатые

Сейчас `_step(name, body)` добавляет имя в `_pendingSteps` при старте шага и удаляет в `finally`. Шаги клиентской ветки идут друг за другом. Если к пределу ветка стоит, например, на `embedded`, то `migration_offer`, `transport` и `client` в `pending` не попадают, хотя не выполнены. Именно они посылают сигналы `terminal/*` и stdio-агенту. Журнал говорит «не успел только `embedded`», а без сигналов остались процессы — диагностика вводит в заблуждение (`AGENTS.md` §16).

Решение:
- `_dispose()` первым синхронным действием заполняет `_pendingSteps` всем закрытым набором в его порядке: `terminal`, `cubits`, `workspace`, `embedded`, `migration_offer`, `transport`, `client`;
- `_step` только удаляет имя в `finally`;
- `pendingSteps` до вызова `dispose()` — пустой список, после завершения прохода — тоже пустой.

Набор и порядок имён не меняются, меняется только смысл: «не завершён», а не «начат и не завершён». Формулировка требования agent-workbench-ui («имена незавершённых шагов») уже это покрывает. Сценарий в дельте уточняет: не начатые шаги тоже перечислены.

Отклонено:
- **Два поля — `pending` и `not_started`.** Отдельной ценности нет: из порядка набора и текущей структуры ветвей видно, какие шаги ещё не стартовали. Лишнее поле — лишний контракт журнала.

### D11. Клиентская ветка после рабочего пространства — две параллельные: агентская и ACP

**Проблема (находка E).** Сигналы `terminal/*` и stdio-агенту посылает только последний шаг клиентской ветки, `client`. Перед ним стоит `embedded`, ограниченный 10 с — больше общего предела 5 с. Пример: выход во время открытия встроенного агента (Reconnect со stdio-профиля на встроенный), пока ещё активен внешний stdio-агент с `terminal/*`. `EmbeddedTransportResolver.close()` ждёт открытие в полёте (`_tail`), а открытие встроенного агента (конфигурация, MCP-серверы) может длиться секунды. К пределу 5 с `client` не начался, и stdio-агент с `terminal/*` остаются сиротами.

**Решение.** После `workspace` клиентская ветка делится на две параллельные:

```text
dispose()
├─ terminal:  closeAll() → close()
└─ cubits → workspace ─┬─ embedded → migration_offer
                       └─ transport → client
```

Порядок `cubits` → `workspace` сохраняется: Cubit-ы отписываются до закрытия рабочего пространства, а оно отписывается от ядра клиента до его `dispose`. `migration_offer` остаётся после `embedded`: резолвер до конца пишет в источник предложения.

**Почему порядок «встроенный агент до ядра клиента» (D9 `add-embedded-agent-mode`) можно ослабить.** Проверено по требованиям и коду:
- если клиентский конец `InProcessAcpLink` закрывается первым, агент запускает тот же идемпотентный `EmbeddedAgent.dispose()`: `shutdown` отменяет ходы, дожидается `TurnEnded` и дописывает журнал (embedded-agent «Жизненный цикл встроенного агента»: «Закрытие клиентского конца клиентом SHALL запускать тот же `dispose`»; сценарий «Клиент закрыл соединение»). `EmbeddedTransportResolver.close()` ждёт тот же `Future` `dispose`, поэтому предел 10 с и событие `embedded.close_timeout` сохраняются;
- журнал сессии пишет ядро агента в файл, а не через соединение. Потеряны только последние `session/update` отменённого хода, а их при выходе уже никто не читает: рабочее пространство закрыто;
- открытие в полёте: `close()` резолвера синхронно поднимает поколение (`_generation++` до первого `await`), открытие становится устаревшим и само освобождает агента; `reconnect` получает `EmbeddedOpenCancelledException` до `_replaceTransport`, и новый транспорт к ядру клиента не привязывается. Остальные окна гонки закрывает D12;
- закрытие ядра клиента не зависит от резолвера встроенного агента, и наоборот: общих объектов у них нет, кроме клиентского конца, а его закрытие идемпотентно с обеих сторон.

Требование agent-workbench-ui «Закрытие root scope SHALL ждать остановки встроенного агента не дольше 10 s … и продолжать освобождение транспорта и `AcpClientApplication`» остаётся выполненным: освобождение не ждёт остановки встроенного агента вовсе.

Цена: если активен встроенный агент, ядро клиента может закрыть клиентский конец раньше, чем `shutdown` агента закончит ход. Тогда в журнале может появиться `embedded.agent.late_error` уровня `warning` от записи в закрытый конец. Это ожидаемое по спецификации поведение «ошибки во время уже начатой остановки», не сбой.

**Бюджет.** Перед шагами с сигналами остаются только `cubits`, `workspace` и `transport`:
- `cubits` — закрытие Cubit-ов, мгновенно;
- `workspace` — `ClientWorkspace.dispose()`: `_restorer?.flush()` ждёт уже начатую запись снимка в локальный JSON-файл, затем отписки и закрытие потоков. Предела нет, но ожидание — это одна запись маленького файла. Принято (Risks);
- `transport` — закрытие начального транспорта-синглтона. Ядро клиента подключается через `connect(transport)` с новым транспортом и закрывает начальный при замене, поэтому начальный никогда не запускается и закрывается мгновенно.

Худший ожидаемый хвост ACP-ветки — ≈ 4 с (D2), в предел укладывается.

Отклонено:
- **Ограничить `embedded` остатком бюджета при выходе.** Не помогает: эскалации stdio-агента нужно ≈ 4 с, и при любом разумном остатке `embedded` + `client` больше 5 с.
- **Выбирать порядок по тому, какой агент активен** (`EmbeddedTransportResolver.currentAgent`). `_running` остаётся заполненным после переключения на внешний агент, пока агент сам не остановится, поэтому признак не равен «встроенный — текущий транспорт ядра клиента». Точный признак потребовал бы нового публичного геттера транспорта у `AcpClientApplication`, а параллельная структура безопасна в обоих случаях.
- **Отдельный ранний шаг «послать сигналы» до `embedded`.** Нужен новый публичный метод ядра клиента — то же, что отклонённый в D1 `releaseProcesses()`.

### D12. Закрытие ядра клиента во время Connect и Reconnect

**Проблема (находка B, клиентская часть).** `AcpClientApplication.dispose()` закрывает текущий `_transport`, но не мешает операциям, уже идущим в другом `Future`:
1. `reconnect()` ждёт фабрику транспорта, а `dispose` в это время закрывает старый транспорт. Затем `_replaceTransport` ставит новый транспорт, `_bindTransport()` заново подписывается на потоки, а `_establishConnection()` вызывает `start()` и порождает процесс stdio-агента. Владельца у него уже нет — сирота. То же, если `dispose` пришёл, пока `_replaceTransport` ждёт `_transport.close` старого транспорта: старый `close` уже идёт, а новый транспорт запустится после `dispose`;
2. `terminal/create`: между `await runner.start(...)` и регистрацией handle в `_terminals` вызывается `dispose` (или замена транспорта). `_killAllTerminalProcesses` видит пустой реестр, процесс регистрируется потом и не завершается никем. Ответ уходит в закрытый или в новый транспорт.

**Решение.**
- `dispose()` мемоизирован (`_disposing ??= _dispose()`); первым синхронным действием ставит приватный флаг `_disposed`. Повторный вызов ждёт тот же проход — как `CodeLabRootLifecycle.dispose()` (D5).
- Проверка «ядро закрыто» после каждого `await`, за которым операция подключения меняет состояние:
  - `reconnect()` после фабрики: закрыт → закрыть полученный транспорт (`close()` не запущенного транспорта мгновенный) и бросить `AcpClientApplicationException('ACP application disposed.')`;
  - `_replaceTransport()` после `await _transport.close(...)` старого: закрыт → закрыть новый, не привязывать его (`_bindTransport` не вызывается) и бросить то же исключение;
  - `_establishConnection()` после `await _transport.start()`: закрыт → бросить то же исключение. Сам процесс завершает транспорт (D13): `dispose` к этому моменту уже вызвал его `close()`.
- `terminal/create`: поколение запоминается до `await runner.start(...)`. После него, если ядро закрыто или поколение сменилось, handle не регистрируется, процесс завершается `handle.kill()`, ответ не отправляется, пишется `event_ignored {reason: stale_generation, kind: terminal_create_result}` (`_logStaleEvent`). Старт и такое завершение образуют один `Future`. Он лежит в приватном множестве незавершённых стартов, и `dispose` ждёт его вместе с `_killAllTerminalProcesses` и закрытием транспорта (`Future.wait`, D4). Ожидание ограничено: `Process.start` плюс `kill()` ≤ 2 с.

Почему исключение, а не тихий возврат: вызывающий (`ClientWorkspace` или CLI) ждёт результат подключения. Тип `AcpClientApplicationException` и текст уже используются для ожидающих запросов при `dispose`. Новых типов и публичного API нет.

Отклонено:
- **Сериализовать `dispose` с идущим `reconnect`** (ждать его завершения). Reconnect может ждать открытие агента и `initialize` до `requestTimeout`, а выход ограничен 5 с.
- **Отменять фабрику транспорта.** У `ReconnectCommand.transportFactory` нет отмены. Встроенный агент уже отменяется своим резолвером (D11), а stdio-фабрика синхронна по сути: она только создаёт объект.

### D13. `StdioAcpTransport`: мемоизированное `close`, сокращение срока и закрытие во время `start`

**Проблема (находка B, транспортная часть).**
1. Повторный `close()` возвращается сразу по `_isClosed`, не дожидаясь идущего закрытия и не применяя свой `timeout`. Сценарий: `reconnect` закрывает старый stdio-транспорт с пределом по умолчанию 5 с (`ClientWorkspace` предел не передаёт), и в этот момент приходит выход. `dispose(closeTimeout: 2 с)` вызывает `close` того же транспорта, получает мгновенный возврат и считает транспорт закрытым. Фактически `SIGTERM` уйдёт только через 5 с — уже после выхода из app.
2. `close()` во время `start()`: `Process.start` в полёте, `_process` ещё `null`. `close` ставит `_isClosed`, закрывает контроллеры и завершается. Потом `Process.start` возвращает процесс, `_setState(connected)` бросает `StateError` (контроллер закрыт), а процесс живёт без владельца.

**Решение** (всё внутри транспорта, сигнатуры `start`/`close` не меняются):
- `close({timeout})` мемоизирован: `_closing ??= _close(...)`. Повторный вызов возвращает тот же `Future`.
- Срок ожидания EOF — абсолютный дедлайн. Повторный вызов с более ранним дедлайном (`now + timeout` раньше текущего) сокращает его, если закрытие ещё в фазе ожидания EOF. Если `SIGTERM` уже послан, повторный вызов ничего не меняет. Срок только сокращается: более поздний предел не продлевает идущее закрытие. Фазу «после `SIGTERM` → 2 с → `SIGKILL`» ничто не сокращает, иначе агент лишился бы обработчика `SIGTERM` (D3).
- `start()` хранит свой `Future` запуска. `close()` сначала дожидается его, игнорируя ошибку, и только потом закрывает stdin и эскалирует. Ожидание ограничено `Process.start`, то есть `fork`/`exec`.
- `start()` после `Process.start`: если транспорт уже закрывается, процесс сохраняется в `_process`/`_exitCode`, чтобы `close` провёл обычную эскалацию. Подписки на stdout и stderr не создаются, событий не публикуется, и `start` бросает `AcpTransportException(code: AcpTransportErrorCode.closed)` — существующий код ошибки.

ACP и spec «Stdio transport» это не меняет: «Close stdin, terminate subprocess» (`16-Transports.md`) выполняется и для процесса, запущенного во время закрытия. Агент получает EOF без единого сообщения и обычную эскалацию.

Отклонено:
- **`SIGKILL` сразу процессу, запущенному после `close`.** Лишает агента обработчика `SIGTERM` без причины: эскалация и так ограничена.
- **Публичный метод `forceClose()`.** Лишний API; сокращение срока повторным `close(timeout:)` решает задачу существующим контрактом порта.

### D14. Статус выхода terminal-процесса выводится из кода выхода ОС

**Проблема (находка C, ACP).**
- На POSIX `Process.exitCode` в Dart для процесса, завершённого сигналом, — отрицательный номер сигнала: `-15`, `-9`. Адаптер кладёт его в `TerminalProcessState.exited(exitCode:)`, и в ответ `terminal/wait_for_exit` или `terminal/output` уходит `exitCode: -15`. В схеме ACP `TerminalExitStatus.exitCode` — `integer | null` с `Minimum: 0` (`17-Schema.md`, `TerminalExitStatus`); `10-Terminal.md`: «may be null if terminated by signal».
- `_lastSignal` ставится до доставки сигнала. Процесс, который в момент `SIGTERM` вышел сам с кодом 0 или обработал `SIGTERM` через `trap 'exit 0' TERM`, получает `signal: SIGTERM` — сигнал его не завершал.

**Решение** — в адаптере `IoTerminalProcessRunner` (`codelab_client_io`), где известна семантика кода выхода ОС:
- код выхода ≥ 0 → `exited(exitCode: code, signal: null)`;
- код выхода < 0 → `exited(exitCode: null, signal: <имя>)`, где номер сигнала — `-code`;
- имя сигнала: для номеров, одинаковых на Linux и macOS, — POSIX-имя: 1 `SIGHUP`, 2 `SIGINT`, 3 `SIGQUIT`, 6 `SIGABRT`, 9 `SIGKILL`, 11 `SIGSEGV`, 13 `SIGPIPE`, 14 `SIGALRM`, 15 `SIGTERM`; для остальных номеров — `SIG` и десятичный номер (`SIG10`). Номера прочих сигналов различаются между платформами (`SIGUSR1` — 10 на Linux, 30 на macOS), и угадывать имя по номеру нельзя;
- поле `_lastSignal` удаляется.

Формат строки `signal` ACP не задаёт: тип `string | null`, без перечня значений. Таблица имён выше — решение CodeLab, а не значения ACP. Перечень сигналов — стандартные номера POSIX, сторонний код не копируется.

На Windows `kill()` даёт неотрицательный код (`TerminateProcess`), поэтому `signal` — `null`, `exitCode` — код ОС. Это соответствует ACP: сигналов на Windows нет. Тесты адаптера — `testOn: '!windows'`, как в D9.

`_terminalExitStatus` в `codelab_client_acp` остаётся передачей полей. Порт `TerminalProcessState` не меняется, уточняется только doc-комментарий: `exitCode` при выходе по сигналу — `null`. Защитная проверка `exitCode < 0` в ядре клиента не добавляется: она скрыла бы ошибку адаптера, а не исправила бы её. Проверяет тест адаптера.

Отклонено:
- **Оставить `_lastSignal` как подсказку при отрицательном коде.** Номер сигнала в коде выхода точнее: процесс мог умереть от постороннего сигнала (OOM killer — `SIGKILL`).
- **Отдавать в `signal` номер (`"15"`).** ACP описывает поле как сигнал, а для распространённых сигналов имя однозначно и привычнее агенту.

### D15. Ответ на `terminal/*` уходит только в своё соединение; журнал после сигналов

**Проблема (находка D).** `_sendTracedMessage` берёт текущий `_transport`. Обработчики `terminal/kill` и `terminal/release` теперь ждут `kill()` до 2 с, а `terminal/wait_for_exit` — выхода процесса без предела. За это время Reconnect может заменить транспорт, и ответ с JSON-RPC id старого соединения уйдёт новому агенту. Нумерация id у нового агента начинается заново, поэтому такой ответ может совпасть с id запроса нового агента и подменить его результат. Это нарушает «ровно один ответ на запрос в своём соединении» (`AGENTS.md` §9: поздние события старого соединения не меняют актуальное состояние). После `dispose` ответ уходит в закрытый транспорт, а ошибка отправки попадает в диагностику закрытого ядра.

**Решение.** Обработчики `terminal/create`, `terminal/output`, `terminal/wait_for_exit`, `terminal/kill`, `terminal/release` запоминают `_generation` при входе. Перед отправкой ответа — и результата, и ошибки — проверяется, что ядро не закрыто (D12) и поколение не сменилось. Иначе ответ не отправляется, пишется `event_ignored {reason: stale_generation, kind: terminal_response}` через `_logStaleEvent` с поколением запроса. Проверка — один приватный помощник, а не копия условия в каждом обработчике.

Почему не отвечать: соединение, которому принадлежит запрос, закрыто. ACP не определяет доставку ответа в другое соединение. Агент старого соединения уже получил EOF или закрытие сокета и ответа не ждёт. Это не новая semantics ACP, а отказ от отправки в чужое соединение — так же поступает `respondToPermission` (`_requireCurrentGeneration`).

`fs/*` имеет то же окно, но короче (одна файловая операция) и этим change не затронут. Отдельная задача, если понадобится (Risks).

**Журнал после сигналов (находка F).** В `_killAllTerminalProcesses` событие `terminal_processes_killed` пишется после очистки реестра, но до `kill()`. Сбой логгера оставил бы процессы живыми: реестр уже пуст, повторный вызов их не найдёт. Кроме того, исключение вышло бы из `dispose`. Решение: сначала запустить все `kill()` (собрать `Future`), затем записать событие в `try`, сбой которого игнорируется (писать о сбое журнала некуда, как в `_step` D5), затем ждать `kill()`. Второй `_terminals.clear()` убирается. `reason` становится приватным enum с двумя значениями (`connectionClosed` → `connection_closed`, `dispose` → `dispose`) вместо строки.

### Отклонённые находки ревью

- **G. Сигнал stdio-агенту без проверки, что код выхода уже пришёл (повторное использование pid).** В `_waitForProcessExit` сигнал посылается только в ветке `TimeoutException` от `await exitCode.timeout(...)`. Если код выхода был доставлен до таймера, `timeout` завершился бы значением, и сигнала не было бы. Между срабатыванием таймера и продолжением после `await` выполняются только микрозадачи, а доставка кода выхода — событие порта. Флаг «код выхода получен», выставляемый из `exitCode.then`, в этой точке всегда равен `false` и ничего не добавляет. Проверка `_exitCodeReceived` в ветке таймаута адаптера `IoTerminalProcessRunner` по той же причине избыточна, но безвредна. Реальное окно — процесс уже собран `waitpid` VM, а код выхода ещё не доставлен в isolate — флагом уровня Dart не закрывается вовсе. Окно — микросекунды, а pid за это время должен ещё и переиспользоваться. Принято как остаточный риск, задачи нет.
- **H. `await process?.stdin.close()` может висеть, если агент не читает stdin.** Проверено по `dart:io` (`_StreamSinkImpl`, SDK 3.38): `send()` всегда ждёт `flush()`, поэтому неотправленных данных в буфере `IOSink` к моменту `close()` нет. Если `flush()` идущего `send` ещё не завершён (труба полна), `close()` синхронно бросает `StateError('StreamSink is bound to a stream')`. Его ловит существующий `try`, а эскалация `timeout` → `SIGTERM` → `SIGKILL` идёт дальше. EOF при этом не доставляется, но агент, не читающий stdin, его и не увидел бы. Зависания нет, задачи нет. Описано в Risks.

## Risks / Trade-offs

- **Встроенный агент с зависшим ходом.** `server.shutdown(grace: 5 s)` ждёт `TurnEnded` до 5 с, и только потом `runtime.dispose()` закрывает MCP-серверы. При пределе 5 с MCP-сервер, игнорирующий EOF, может остаться сиротой. Процессы `exec` при этом завершаются: отмена хода приходит в начале `shutdown`, `terminateTree` укладывается в 2 с. Смягчение — Q3 (параметр grace у `EmbeddedAgent.dispose`).
- **`SIGKILL` внешнему агенту через 4 с** может оборвать дописывание его журнала. Для `codelab-agent` это 2 с на EOF плюс 2 с после `SIGTERM`, а безопасное завершение по EOF ждёт ход до 5 с. Принято: предел выхода важнее, ход всё равно отменяется. Если журнал важнее — Q1 (предел больше).
- **Потомки `terminal/*` и stdio-агента.** Сигнал получает только корень. Внук, который сам не завершается при смерти родителя, остаётся сиротой. Так было и до change, но теперь это единственный остаточный путь (Q2).
- **UI во время закрытия (до 5 с).** Cubit-ы закрываются в начале клиентской ветки. Действие пользователя в окне, которое ещё видно, может бросить `StateError` (emit после `close`). Ошибка попадёт в обработчик Flutter, данных не портит. Принято на время закрытия; индикатор «Quitting…» — отдельная задача.
- **Гонки (`AGENTS.md` §9, §12).**
  - Запрос выхода во время Connect или Reconnect: `EmbeddedTransportResolver.close()` делает открытие в полёте устаревшим и сам закрывает вернувшегося агента. Прежнее утверждение «вызовы закрытия транспорта идемпотентны, поколение растёт» оказалось недостаточным (ревью): новый транспорт привязывался и запускался после `dispose`. Теперь — флаг `_disposed` и проверки после `await` (D12), мемоизированный `close` с сокращением срока и закрытие во время `start` (D13).
  - Старт `terminal/create` против `dispose` или замены транспорта: процесс, стартовавший после очистки реестра, завершается, не регистрируется и не получает ответа; `dispose` ждёт такие старты (D12).
  - Ответ `terminal/*` после замены транспорта не уходит новому агенту (D15). `fs/*` имеет то же окно на время одной файловой операции и этим change не меняется — отдельная задача при необходимости.
  - Позднее событие процесса после `kill`: адаптер не меняет зафиксированный статус выхода.
  - Отмена против завершения: `kill()` вышедшего процесса — no-op (§24).
  - Таймеры эскалации принадлежат `Future` `kill()` и `close()` и не переживают их.
- **Закрытие клиента не ждёт встроенного агента (D11).** Если активен встроенный агент, клиентский конец может закрыться раньше, чем `shutdown` агента закончит ход. Журнал сессии дописывается (агент запускает тот же `dispose`, embedded-agent «Жизненный цикл встроенного агента»), но в журнале app возможны `embedded.agent.late_error` уровня `warning`. Принято.
- **`ClientWorkspace.dispose()` без предела.** Перед шагами с сигналами стоит ожидание записи снимка рабочего места (`WorkspaceRestorer.flush()`). Это запись маленького локального JSON-файла; зависнуть она может только на неисправной файловой системе. Тогда сигналы `terminal/*` и stdio-агенту не уйдут до выхода, и `pending` покажет `workspace`, `transport`, `client` (D10). Ограничивать предел внутри `codelab_client_core` ради этого не стали: пакет не знает о выходе app (D1).
- **Проверка профиля при выходе.** Риска больше нет: change `remove-test-connection` удалил «Test connection» и `ProfileProbe`, процессов проверки профиля в app не осталось.
- **Закрытие stdin при полной трубе (находка H).** Если `send` ещё ждёт `flush()`, `stdin.close()` бросает `StateError` (пойман), и EOF агенту не доставляется. Эскалация `SIGTERM` → `SIGKILL` выполняется, зависания нет (раздел «Отклонённые находки ревью»).
- **Повторное использование pid (находка G).** Окно между сбором процесса `waitpid` VM и доставкой кода выхода в isolate флагом уровня Dart не закрывается. Остаточный риск — микросекунды.
- **Permissions и containment (§10).** Не меняются. Выход не обходит одобрения: ожидающие одобрения снимаются, ход отменяется. Новых путей запуска процессов нет.
- **Forward compatibility ACP.** Новых сообщений нет. Поведение со сторонними агентами меняется в трёх местах:
  - агент, игнорирующий EOF и `SIGTERM`, через 2 с после `SIGTERM` получает `SIGKILL`;
  - статус выхода terminal-процесса соответствует схеме: `exitCode` не бывает отрицательным, при выходе по сигналу он `null` (D14). Агент, который раньше разбирал `exitCode: -15`, теперь видит `exitCode: null, signal: SIGTERM`;
  - ответ на `terminal/*` запрос прежнего соединения не отправляется (D15).
- **Web-безопасность.** `codelab_client_acp` и web-барель `codelab_acp_transports` процессов не касаются; `StdioAcpTransport` — в `io.dart`. `web-compile` нужен только как проверка затронутого `codelab_client_acp`.
- **Allowlist зависимостей ядра (PKG-2).** Ядро агента не меняется, зависимостей не добавляется.

## Migration Plan

Миграции нет: состояние в памяти, форматы файлов не меняются. Откат — возврат `AppExitHandler` к вызову только `closeAll()`.
