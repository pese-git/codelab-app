Отвергнуто: проверке `model` нужен каталог ядра, а бюджет и проверка полей — чистая логика, которую встроенный и мобильный хосты получат без повторной реализации. Разделение «хост разбирает, ядро проверяет» — тот же паттерн, что `ConfigTree` → `CoreConfig.fromLayers` (D3 change `add-agent-configuration`; `AGENTS.md` §14).
- (в) Три порта (контекст, шаблоны, агенты). Отвергнуто: один момент чтения, один запрос, одна диагностика (`AGENTS.md` §13).

### D2. Какая файловая система и граница чтения

Файлы читаются с **локальной файловой системы процесса агента**, а не через env сессии. Загрузчик получает `LocalExecutionEnv` хоста, а каждое чтение идёт через `BoundedEnv.wrap(local, root)` корня своей области:

| Область | Корень области | Корень `BoundedEnv` для файлов | Что читается |
|---|---|---|---|
| контекст проекта | корень git-репозитория (D5) или `cwd` | тот же | `AGENTS.md`/`CLAUDE.md` уровней от корня до `cwd` |
| шаблоны проекта | `cwd` | реальный путь `<cwd>/.codelab/prompts` | `*.md` первого уровня |
| агенты проекта | `cwd` | реальный путь `<cwd>/.codelab/agents` | `*.md` первого уровня |
| пользователь | `$CODELAB_HOME` | `$CODELAB_HOME` для `AGENTS.md`; реальный путь `prompts/`, `agents/` для шаблонов и агентов | `AGENTS.md`, `prompts/*.md`, `agents/*.md` |

**Граница каталогов шаблонов и агентов двухступенчатая** (решение по ревью итерации 2):
1. Каталог (`.codelab/prompts`, `$CODELAB_HOME/prompts`; в итерации 3 — `agents/`) раскрывается `realpath` и проверяется по корню своей области (`cwd` или `$CODELAB_HOME`). Каталог-symlink за пределы области — `outside_root`, каталог не читается.
2. Файлы каталога читаются через `BoundedEnv` с корнем в **реальном пути каталога**, а не в корне области. Поэтому файл-symlink за пределы каталога — `outside_root`, даже если цель лежит внутри `$CODELAB_HOME` или `cwd` (например, `prompts/x.md` → `$CODELAB_HOME/config.yaml`).

Почему не один `BoundedEnv` с корнем области: шаблон — это `*.md` первого уровня своего каталога (§17.2.2). Symlink на соседний файл области превращал бы в шаблон файл, который пользователь шаблоном не делал, и его тело уходило бы модели.

Единственная операция вне границы — проверка существования `<каталог>/.git` у предков `cwd` при поиске корня. Содержимое не читается, `.git` может быть каталогом или файлом (worktree, submodule). Путь, чей `realpath` выходит за корень области (symlink наружу, `..`), отклоняется `BoundedEnv` до чтения. Файл пропускается с диагностикой `outside_root`.

**Чтение префикса файла.** `ExecutionEnv.readText` читает файл целиком построчно, а файлу контекста нужны только первые `max_bytes + 1` байт (D5, п. 4). Поэтому:
1. Канонический путь даёт `BoundedEnv.realpath` корня области: он раскрывает symlink и отклоняет путь вне корня (`outside_root`).
2. Загрузчик требует окружение с `PathResolver` — `LocalExecutionEnv` хоста. Окружение без `PathResolver` не даёт канонического пути, поэтому файлы не читаются вовсе: одна диагностика `unreadable` на область, без обращения к файлу.
3. Префикс `max_bytes + 1` байт читается `dart:io` (`RandomAccessFile`) по этому каноническому пути, а не по исходному.
4. После открытия загрузчик повторно проверяет путь: `realpath` того же исходного пути совпадает с прочитанным каноническим и лежит внутри корня, а запись — обычный файл. Иначе файл закрывается без использования прочитанного, диагностика `outside_root` (путь ушёл наружу) или `unreadable` (путь или тип изменились, ошибка ввода-вывода).

Остаточный риск TOCTOU — подмена между повторной проверкой и чтением — того же класса, что у `BoundedEnv` для инструментов: `dart:io` не даёт открыть файл с `O_NOFOLLOW` и проверить открытый дескриптор (`agent-core-architecture` §4.4). Повторная проверка сужает окно, но не закрывает его. Для этого нужен процесс, который пишет в дерево проекта во время `session/new`; такой процесс и так может менять файлы, которые агент читает инструментами.

Тот же остаточный риск есть у шаблонов и определений агентов: их файлы проходят ту же двухступенчатую проверку (каталог, затем файл) и то же чтение по каноническому пути. Отдельный случай — подмена файла на FIFO после `stat`: чтение блокируется до появления писателя, и его прерывает таймаут фазы 5 с (D6) с диагностикой `timeout`; сессия открывается без файлов этой фазы. Запись с `.md`, которая уже при перечислении не обычный файл (FIFO, сокет, устройство), не открывается — `unreadable` (D3).

**`serve --ws` файлы проекта не читает** (решение пользователя 2026-10-30). Клиент WebSocket выбирает `cwd` и может быть на другой машине. Чтение шло бы с файловой системы машины агента: держатель токена получал бы в промпт, а значит и в ответы модели, инструкции любого каталога этой машины и `$CODELAB_HOME/AGENTS.md` её владельца. Это то же рассуждение, что выключает MCP по WebSocket (D3 change `add-agent-mcp-client`). Хост по `--ws` не передаёт порт (D16), поэтому не читается ничего: ни контекст, ни шаблоны и агенты проекта, ни файлы `$CODELAB_HOME`. В `serve --stdio` агент и клиент на одной машине, и клиент — локальный хозяин процесса.

Почему не env сессии (§11.5 предполагал «через `ExecutionEnv` сессии»):
- чтение происходит внутри `createSession`, до ответа `session/new`. Запрос `fs/read_text_file` до ответа нёс бы `sessionId`, которого клиент ещё не знает (ACP-8);
- в ACP нет `stat` и листинга каталога (`09-File System.md`), поэтому через клиента нельзя ни найти корень git, ни перечислить `*.md`;
- `$CODELAB_HOME` лежит на машине агента; §17.2.3 по той же причине берёт для skills `localFs`, а не env сессии;
- клиент показывал бы эти чтения пользователю как действия агента.

Альтернатива — читать через `AcpClientExecutionEnv` после ответа `session/new` и пересобирать промпт. Отвергнута: первый ход мог бы уйти без инструкций (гонка с первым `session/prompt`), а корень git и листинг всё равно недоступны.

### D3. Разбор: хост отделяет frontmatter, ядро проверяет поля

1. `frontmatter.dart` (`_io`):
   - первая строка файла (после BOM) равна `---` → frontmatter до следующей строки `---`;
   - CRLF читается как LF;
   - текст между строками разбирается `readYamlTree` в строгом профиле CFG-21: один документ, без якорей и тегов, без повторяющихся ключей, логические значения — только `true`/`false`;
   - позиции сдвигаются на номер строки внутри файла.

   Результат — `MarkdownFile {path, scope, frontmatter: ConfigTree?, body, bodyLine}`. Нарушение профиля или незакрытый `---` дают диагностику `error` с путём, строкой и столбцом, файл в `ProjectFiles` не попадает.
2. Ядро (`parseCommandTemplates`, `parseAgentDefinitions`) проверяет ключи, типы, имена и лимиты тела. Результат — определения и `ExtensionDiagnostic {path, line?, column?, level, code, message}` (тип §17.2.3; `column` добавлен для единообразия с `ConfigIssue`). Коды: `invalid_name`, `unknown_key`, `invalid_value`, `empty_body`, `too_large`, `duplicate`, `shadowed`, `reserved_name`, `untrusted_project`, `limit_exceeded`, `outside_root`, `not_utf8`, `unreadable`, `syntax`, `profile`; два кода ставит runtime, а не загрузчик: `unexpected` и `timeout` (D6).

   Уровни кодов файлового доступа и runtime (решение по ревью итерации 1):

   | Код | Уровень | Когда |
   |---|---|---|
   | `outside_root` | warning | `realpath` пути вне корня области (D2) |
   | `not_utf8` | warning | файл не в UTF-8 |
   | `unreadable` | warning | файл не открылся или не прочитался; у окружения нет `PathResolver`; после открытия путь или тип изменились (D2) |
   | `timeout` | warning | загрузка не уложилась в таймаут фазы (D6) |
   | `shadowed` | info | файл перекрыт другим: `CLAUDE.md` при `AGENTS.md`, пользовательский шаблон или определение при проектном |
   | `limit_exceeded` | warning | больше 100 `*.md` в каталоге шаблонов или агентов: лишние отброшены (D6) |
   | `limit_exceeded` | info | предел 64 уровней обхода к корню git: корень = `cwd` (D6) |
   | `unexpected` | error | непредвиденное исключение порта (D6) |

   Почему `unreadable` отдельно от `outside_root`: пользователю в `config check` важно различать «symlink наружу» (правило границы) и «нет прав или файл исчез» (окружение). Почему у `limit_exceeded` два уровня: отброшенные шаблоны и агенты пользователь должен увидеть в `config check` (D13 печатает `warning`, а из `info` — только `untrusted_project` строкой `note:`), а предел обхода — штатное ограничение поиска корня, без потери файлов, которые пользователь положил сам. Коды проверки содержимого получают уровни по таблицам: шаблонов — ниже в этом решении, определений агентов — в D10.

   Уровни кодов содержимого шаблонов (решение по ревью итерации 2; определения агентов — D10):

   | Код | Уровень | Когда |
   |---|---|---|
   | `unknown_key` | error | ключ frontmatter вне `description`/`argument-hint`: файл пропущен (D7) |
   | `invalid_value` | error | значение не строка или длина вне 1–200 / 1–80 символов (D7) |
   | `empty_body` | error | тело пустое или только из пробельных символов |
   | `too_large` | error | файл больше 64 КиБ: не читается (§17.2.2) |
   | `invalid_name` | warning | имя файла не по правилу D7 |
   | `reserved_name` | warning | имя встроенной команды или `skill` (D7) |
   | `shadowed` | info | пользовательский шаблон перекрыт проектным |
   | `untrusted_project` | info | каталог шаблонов недоверенного проекта не читается (D4) |
   | `unreadable` | warning | запись `*.md`, которая не обычный файл (FIFO, сокет, устройство): не открывается (D2) |

   Почему `invalid_name` и `reserved_name` — warning, а ошибки содержимого — error: в первом случае файл, возможно, и не задуман шаблоном (`README.md`, заметка), во втором пользователь явно написал шаблон, и он не заработал.

Почему `ConfigTree` для frontmatter: позиции и сообщения строит тот же код, что для `config.yaml`. Одна модель ошибок для конфига и frontmatter — довод §15.11 в пользу YAML.

### D4. Доверие к файлам проекта

| Файл | Недоверенный проект | Доверенный проект |
|---|---|---|
| `AGENTS.md`/`CLAUDE.md` от корня git до `cwd` | читается | читается |
| `<cwd>/.codelab/prompts/*.md` | не читается; есть каталог → одна диагностика `info` `untrusted_project` | читается |
| `<cwd>/.codelab/agents/*.md` | не читается; есть каталог → одна диагностика `info` `untrusted_project` (CFG-6) | читается, заменяет пользовательское определение с тем же `name` |
| `$CODELAB_HOME/*` | читается | читается |

**Доверие сравнивается с каноническим `cwd` сессии**, а не с `projectRoot` запуска. `CoreConfig` получает поле `trustedProjects` — канонические корни из глобального слоя; их уже канонизирует `ConfigLoader` (D7 change `add-agent-configuration`). Runtime вычисляет `projectTrusted = trustedProjects.any((r) => samePath(r, canonicalCwd))` тем же `realpath`, что и для выбора снимка (D9 того change). Почему: сессия в другом `cwd` получает снимок без проектных слоёв, но её собственный проект может быть доверенным. И наоборот, сессия по symlink на доверенный корень не должна терять доверие. Сравнивается равенство путей, а не вложенность, — как при выборе снимка (D9 того change): подкаталог доверенного репозитория со своим `.codelab/` доверия не наследует, пользователь добавляет его в `trusted_projects` явно.

**Fail-closed.** Если `cwd` не раскрылся — у базового env нет `PathResolver` или `realpath` вернул ошибку, — `projectTrusted = false` (решение по ревью итерации 1). Нераскрытый путь мог бы совпасть с доверенным корнем текстом, но указывать на другой каталог (symlink, который не удалось раскрыть), а ошибка канонизации не должна давать права шире (приоритет 1). Выбор снимка конфигурации при этом не меняется: он по-прежнему сравнивает путь как есть (D9 change `add-agent-configuration`), снимок без проектных слоёв для такого пути и так недоверенный.

**Почему `AGENTS.md` читается без доверия.** E-01 (Must) и все сопоставимые агенты читают инструкции репозитория. Это основной способ передать правила проекта, а не расширение прав:
- текст не меняет ни режим, ни правила разрешений, ни набор инструментов — это делает код (PERM-1, CFG-3);
- обёртка `project_context` прямо говорит модели, что инструкции не отменяют правил безопасности и решений пользователя (§11.7);
- по силе воздействия это тот же недоверенный текст, что `README.md`, прочитанный инструментом `read`. Худший случай — модель попросит опасное действие, и его остановит политика одобрения.

Шаблоны и определения агентов — другое дело. Шаблон — это текст, который пользователь отправляет одним словом, не читая. Определение агента выбирает модель, режим, инструменты и пишет текст в системный промпт. Поэтому из недоверенного проекта они не загружаются (SKL-1, CFG-6). Подтверждено решением пользователя 2026-10-30 (OQ4).

Альтернативы:
- (а) `AGENTS.md` только для доверенного проекта. Отвергнуто: ломает E-01 для каждого нового клона. Защиту прав это не повышает: права охраняет код, а не текст;
- (б) шаблоны проекта без доверия. Отвергнуто: SKL-1, команда-ловушка `/review` с «удали всё» в теле.

### D5. Инструкции проекта: обход, бюджет, усечение, секции

**Обход** (`ProjectFilesLoader`):
1. `cwd` канонический (D4). От `cwd` вверх ищется первый каталог с записью `.git`, не больше 64 уровней. Найден → корень; не найден → корень = `cwd`, читается только `cwd`.
2. На каждом уровне от корня до `cwd` берётся `AGENTS.md`. Если его нет — `CLAUDE.md` (алиас; решение пользователя 2026-10-30, OQ2). Есть оба → только `AGENTS.md`, `CLAUDE.md` даёт диагностику `info` с кодом `shadowed`.
3. `$CODELAB_HOME/AGENTS.md` — пользовательский файл (без алиаса `CLAUDE.md`: каталог наш).
4. Файл читается не больше `contextMaxBytes + 1` байт средствами `dart:io` по каноническому пути, проверенному `BoundedEnv.realpath`, с повторной проверкой после открытия (D2, «Чтение префикса файла»); полный размер `M` — из `stat` открытого файла. Лишний байт нужен, чтобы отличить файл ровно в бюджет от длинного. `contextMaxBytes == 0` → контекст не читается вовсе.

**Сборка** — чистая функция ядра `assembleProjectContext(List<ContextFile> files, int maxBytes) → ProjectContext?`:
1. Порядок в промпте — от общего к частному: пользовательский, затем от корня к `cwd` (ближайший — последним, E-01).
2. Бюджет раздаётся в обратном порядке: сначала `cwd`, затем вверх, пользовательский — последним.
3. Файл помещается целиком → как есть. Не помещается → усекается по последней границе строки в оставшемся бюджете; в конец ставится строка `[file truncated: showing N of M bytes]`, где `N` — байты UTF-8 оставленного текста. Если первая строка длиннее остатка (границы строки в остатке нет), она режется по последней границе символа UTF-8 в остатке: символ посередине не режется, `N` может быть меньше остатка на 1–3 байта. Строка пометки в бюджет не входит, чтобы бюджет оставался числом из конфига.
4. После усечения бюджет считается исчерпанным, даже если от остатка осталось несколько байт (хвост строки или символа). Оставшиеся, более дальние файлы, включая пользовательский, пропускаются; их число попадает в `project_context.loaded.omitted`. Почему: короткий дальний файл, вставленный после усечённого ближнего, нарушил бы правило «ближний получает бюджет первым» — модель видела бы общий файл целиком, а частный — нет.
5. Пустой файл (после обрезки пробельных символов) пропускается.
6. Путь в секции: для файлов проекта — относительный от корня обхода (`AGENTS.md`, `pkg/AGENTS.md`), для пользовательского — литерал `$CODELAB_HOME/AGENTS.md`. Абсолютный путь домашнего каталога в промпт не идёт, поэтому промпт одинаков на разных машинах и в golden-тестах.

**Секции промпта.** `prompts/project_context.md` (`id: project_context`, `vars: [files]`) — заголовок `# Project instructions` и текст §11.7 во множественном числе. `prompts/project_context_file.md` (`vars: [path, content]`) — блок `<project-instructions path="{{path}}">…</project-instructions>`. Экранирование (решение по ревью итерации 1):
- **Теги в содержимом.** Каждое вхождение открывающего или закрывающего тега блока получает `\` сразу после `<`. Тег ищется без учёта регистра ASCII и с необязательными пробельными символами после `<` и после `/`: `<\s*/?\s*project-instructions`. Примеры: `</project-instructions` → `<\/project-instructions`, `</PROJECT-INSTRUCTIONS` → `<\/PROJECT-INSTRUCTIONS`, `< / project-instructions` → `<\ / project-instructions`, `<project-instructions` → `<\project-instructions`. Почему так широко: модель читает разметку не как парсер XML, и `</PROJECT-INSTRUCTIONS>` или `< /project-instructions>` для неё такой же конец блока. Файл не может ни закрыть свой блок и выдать продолжение за текст агента, ни открыть ложный блок с чужим `path`. Регистр сравнивается только для ASCII, как `RegExp(caseSensitive: false)` без `unicode`: `ı` и `ſ` с `i` и `s` не сравниваются.
- **Атрибут `path`.** Символы `"`, `<`, `>`, `\r`, `\n` заменяются на `_`. Имя каталога с кавычкой иначе закрыло бы атрибут и дописало бы свои. Поэтому путь в промпте МОЖЕТ отличаться от пути в логе `project_context.loaded` и в диагностиках: там путь не экранируется, по нему файл находят на диске.

Экранирует сборка блока в `compose.dart` (`Prompts.projectContextFile.render`), а не `assembleProjectContext`: бюджет считается по байтам файла, а не по байтам после экранирования, и `ProjectContext` хранит текст как в файле (D15). Секция встаёт шагом 10 §11.5, до `agent_profile` (D11). Почему два шаблона, а не литерал блока в коде: PR-2 запрещает многострочные литералы промптов вне `prompts.g.dart`.

**Ключ** `tools.project_context.max_bytes`: целое `0..262144`, по умолчанию `32768`. Из проектных слоёв недоверенного проекта принимается только уменьшение — правило «только уменьшение», как у `budget.*` (§15.3). Увеличение отбрасывается с `config.project.untrusted_key`. Почему: репозиторий не должен раздувать каждый запрос мегабайтом своего текста.

Альтернативы:
- (а) весь бюджет ближнему файлу без сохранения дальних. Это и есть выбранное правило: ближний получает бюджет первым (E-01);
- (б) поровну на файл. Отвергнуто: короткий корневой файл «тратит» долю, а длинный ближний режется без причины.

### D6. Лимиты, ошибки файлов, отмена

| Лимит | Значение | Нарушение |
|---|---|---|
| файлов `*.md` в одном каталоге шаблонов или агентов | 100, в байтовом порядке имён | лишние пропущены, одна диагностика `warning` `limit_exceeded` (D3) |
| размер файла шаблона или определения | 64 КиБ | файл не читается, `too_large` |
| тело шаблона или определения | 1 байт … 32 КиБ UTF-8 | `empty_body` / `too_large` |
| уровней обхода к корню git | 64 | дальше не ищется, корень = `cwd`, диагностика `info` `limit_exceeded` |
| файл контекста | `max_bytes + 1` байт читается, остальное — усечение (D5) | — |
| вся загрузка файлов проекта сессии | 5 с | сессия без файлов проекта, диагностика `warning` `timeout` |

- Файл не в UTF-8 → `not_utf8`, файл пропущен. Файл не открылся или не прочитался → `unreadable`, файл пропущен. Подкаталоги в `prompts/` и `agents/` не обходятся (без рекурсии, §17.2.2). Файлы и каталоги на `.` пропускаются молча.
- Любая ошибка файла — диагностика, а не исключение. `createSession`/`loadSession` не падают из-за файлов проекта. Непредвиденное исключение порта ловится runtime: лог `project_files.diagnostic` (`error`, `code: unexpected`, тип исключения), сессия без файлов проекта.
- **Отмена, таймаут и гонки (§9, §12).** Загрузка — одна фаза внутри `_open`, до возврата сессии и до ответа `session/new`, как подключение MCP (D6 change `add-agent-mcp-client`). Сессии ещё нет, поэтому `close()` её отменить не может: токен запроса — дочерний от токена фазы, а тот — от `_shutdown` рантайма (`dispose()`). `_loadProjectFiles` ждёт первым из трёх событий:
  - результат порта — проверка ядром (D1), как раньше;
  - отмена (`dispose()` рантайма) — результат выбрасывается, сессия не создаётся (то же поведение, что у MCP при `dispose`);
  - таймаут фазы 5 с — токен запроса отменяется, чтобы загрузчик остановился между файлами; сессия создаётся без файлов проекта, лог `project_files.diagnostic` с `code: timeout` (warning). Поздний результат порта выбрасывается, а его исключение ловится и не теряется (§12): оно уходит в лог `debug` без текста.

  Почему таймаут, хотя чтение локальное: порт ждут до ответа `session/new`, а `stat` и `open` на зависшем сетевом диске (NFS, SMB, FUSE) не прерываются токеном — загрузчик проверяет токен только между файлами. Без предела один зависший `stat` держал бы `session/new` без ответа бесконечно. Почему 5 с: штатная загрузка — до 64 `stat` обхода и несколько файлов до 256 КиБ, а с итерациями 2–3 — до 200 файлов по 64 КиБ; на локальном диске это миллисекунды, поэтому 5 с не срабатывают в штатной работе, но укладываются в типичное ожидание клиентом ответа на `session/new` и меньше подключения MCP-сервера, которое идёт следом. Величина — константа ядра, не ключ конфигурации: настраивать её незачем, пока нет запроса (`AGENTS.md` §13).

  Подписок и поздних событий нет: файлы читаются один раз при открытии сессии. Повторный `session/load` уже открытой в процессе сессии файлы не перечитывает (§17.2.1: изменения — со следующей сессии): ACP-адаптер переподключает такую сессию (`reattach` в `agent_server.dart`) без `AgentRuntime.loadSession`, поэтому требование и тест — у ACP-слоя (agent-acp-server «session/load и реплей», задача 6.4).

### D7. Шаблоны команд: имена, резервирование, публикация

- Имя — имя файла без `.md` по правилу `^[a-z0-9][a-z0-9-]{0,63}$`. Другое имя (`Review.md`, `my_cmd.md`) — `warning` `invalid_name`, файл пропущен.
- Frontmatter необязателен; ключи — только `description` (1–200 символов) и `argument-hint` (1–80). Другой ключ — `error` `unknown_key`, файл пропущен. Без `description` берётся первая непустая строка тела, обрезанная до 200 символов.
- **Резервные имена.** Сразу резервируется весь список встроенных команд §13.4: `compact`, `mode`, `model`, `status`, `usage`, `redact`, `config`, `mcp`, `rename`, `branches`, `branch`, `rewind`, `fork`, `label`, `approve`, `timer`, `memory`, `tasks`, `help`, а также `skill`. Шаблон с таким именем — `warning` `reserved_name`, файл пропущен. Почему уже сейчас, хотя встроенных команд ещё нет (OQ1): иначе шаблон `status.md` работал бы до change встроенных команд и молча перестал бы после. Так встроенная команда никогда не меняется от файла в репозитории (SKL-7).
- Одно имя в проекте и у пользователя → побеждает проект (доверенный), у пользовательского — `info` `shadowed`.
- `SlashCommand {name, description, inputHint, source: template}`. Подсказка — `argument-hint`, иначе `"arguments"`, если тело использует `$ARGUMENTS` или `$1`…`$9`, иначе подсказки нет. Порядок — по имени (байтово). Список `AgentSession.commands` строится при открытии сессии и не меняется до её закрытия.

### D8. Разворачивание `/<имя> <аргументы>` в ядре

Место — `AgentSession.prompt`, до записи сообщения пользователя. Тогда ACP, встроенный режим и CLI ведут себя одинаково (§17.2.6, диаграмма). Алгоритм — `expandCommand` §17.2.6 в объёме шаблонов:
1. Разбирается только первый текстовый блок промпта. Он начинается с `/`, а слово до первого пробельного символа соответствует `^[A-Za-z0-9][A-Za-z0-9:_-]*$` → имя команды; `raw` — остаток после ведущих пробелов без завершающего `\r?\n` (CRLF присылают клиенты на Windows; иначе `\r` попал бы в `$ARGUMENTS` и последний `$N`).
2. Есть шаблон с этим именем → `Expanded`. Тело с подставленными аргументами заменяет первый текстовый блок, остальные блоки (картинки, ресурсы) идут после него в исходном порядке.
3. Иначе — `NotACommand`: промпт уходит модели как есть. Это нынешнее поведение; ответ «Unknown command» без вызова модели — в change встроенных команд (OQ1).

**Подстановка** — один проход слева направо по таблице §17.2.6:
- `$ARGUMENTS` → `raw`;
- `$1`…`$9` → аргументы `splitArguments`;
- `$$` → `$`;
- `$10` → `$1` и `0`;
- `$` перед другим символом остаётся литералом;
- в теле нет плейсхолдеров, а `raw` не пуст → дописывается `\n\nARGUMENTS: <raw>`.

Подставленное значение не сканируется повторно. Синтаксис `{{…}}` в теле не обрабатывается.

**Безопасность подстановки.**
- Frontmatter разобран при загрузке, а подстановка касается только тела, поэтому аргументы не могут изменить ни описание, ни ключи.
- Результат — сообщение с ролью `user`, а не системный промпт: шаблон не получает силы системной инструкции.
- Разбор не исполняет shell и не читает файлы (SKL-8).

**Незакрытая кавычка** — отступление от §17.2.6. Там `CommandFailed` и ответ без вызова модели, но механизма «ответ агента без модели» в ядре ещё нет: его вводит change встроенных команд вместе с `/help` и `/status`. Здесь незакрытая кавычка закрывается концом ввода: `/review "error handling` → `$1 = error handling`. Поведение детерминировано и ничего не теряет. Change встроенных команд МОЖЕТ вернуть `CommandFailed` — это изменение поведения, его записывает тот change.

**Журнал.**
- Запись `message` развёрнутого сообщения получает поле записи `command: {"source": "template", "name", "args"}` (§8.2.3; поле уже описано «после MVP», здесь оно вводится для `template`). Модель поля не видит, как `toolMeta`.
- Реплей (§13.5) для такой записи отдаёт первым блоком `user_message_chunk` с текстом `/<name>` или `/<name> <args>`, затем остальные блоки, кроме развёрнутого текста.
- Если журнал читает старое ядро, поле уходит в `extra` записи. Реплей тогда покажет развёрнутый текст, и данные не теряются.
- **Заголовок сессии** (решение по ревью итерации 2) — `summarize`, `session/list` и автоматический `session_info` с `source: "auto"` (а за ним `session_info_update`) — для записи с полем `command` строится по исходному тексту `/<name>[ <args>]`, как реплей, а не по развёрнутому телу. Почему: пользователь видит в списке сессий то, что набрал сам; тело шаблона одинаково у всех сессий с этой командой и не различает их. Запись с неизвестным `source` даёт заголовок по тексту сообщения, как и реплей.

Лог `command.expanded` (info): `session_id`, `name`, `source`, `args_bytes`. Текст аргументов в лог не пишется: пользователь мог вставить туда секрет (§16).

### D9. Публикация команд в ACP

- После ответа `session/new` — `available_commands_update` с `session.commands` (а не с пустым списком). В реплее `session/load` — тот же список на прежнем месте последовательности (`agent-acp-server`, «session/load и реплей»).
- Элемент — `AvailableCommand {name, description, input: {hint}?}` (`14-Slash Commands.md`). Поле `input` есть только при подсказке. `_meta` не добавляется.
- События `CommandsChanged` (§5.3) этот change не вводит: список не меняется за жизнь сессии (D7). Событие и повторное `available_commands_update` при изменении набора добавит change, у которого набор меняется (MCP prompts, `/config reload`).
- Инструменты модели в список не попадают ни при каком составе (R-07). Это проверяет фикстура с fake MCP-сервером.

Совместимость: фикстуры этапов 0 и 4 сверяют список через `$any` (§14.2); клиенты уже применяют `available_commands_update` (`acp-protocol-client`).

### D10. Определения агентов: формат и проверка

Формат и поля — §15.8:
- `name` — `^[a-z][a-z0-9-]{0,47}$`, `default` зарезервировано;
- `description` — 1–200 символов;
- `model` — `<provider>/<model>` каталога; модели нет в каталоге → `error` `invalid_value`, определение пропущено;
- `mode` — `plan`, `ask`, `standard`, `accept-edits`, `bypass`; синонимы §13.6 не принимаются; `autopilot` → ошибка (CFG-4);
- `tools` — список строк `^[A-Za-z0-9_-]+\*?$` (`*` только в конце — префиксный шаблон), пустой список допустим;
- `scope` — `session` | `subagent` | `both`, по умолчанию `both`;
- тело — 1 байт … 32 КиБ.

Неизвестный ключ — `error` `unknown_key`, файл пропущен (как CFG-1). Frontmatter обязателен.

Уровни кодов содержимого определений (решение по ревью итерации 3; коды файлового доступа и разбора frontmatter — D3):

| Код | Уровень | Когда |
|---|---|---|
| `invalid_value` | error | `name` вне правила или `default`; нет `name` или `description`; нет frontmatter; значение не того типа или длины; `mode: autopilot` или синоним режима §13.6; модель вне каталога; элемент `tools` вне правила (`*` не в конце) |
| `unknown_key` | error | ключ frontmatter вне списка §15.8 |
| `empty_body` | error | тело пустое или только из пробельных символов |
| `too_large` | error | файл больше 64 КиБ или тело больше 32 КиБ |
| `duplicate` | error | одно `name` у двух файлов одного каталога: диагностика на каждый файл, в сообщении оба пути |
| `shadowed` | info | пользовательское определение перекрыто проектным с тем же `name` |
| `untrusted_project` | info | каталог агентов недоверенного проекта не читается (D4) |

Почему у определений нет `invalid_name` и `reserved_name`, как у шаблонов: имя берётся из поля `name`, а не из имени файла. Файл в `agents/` пользователь положил как определение, поэтому любое нарушение — `error`, а не `warning` «возможно, это не определение». По той же причине отсутствие frontmatter — `error`: тело без полей определением быть не может.

- Одно `name` в одном каталоге → оба файла пропускаются с `duplicate` (по диагностике на файл, в сообщении оба пути). Проектное определение (только доверенный проект) заменяет пользовательское с тем же `name`, у пользовательского — `info` `shadowed`.
- `scope: subagent` загружается, но в опцию `agent` не входит (инструмента `task` ещё нет, §17.3). `info`-диагностики нет: это не ошибка.
- Имена инструментов при загрузке не проверяются: MCP-инструменты появляются после подключения серверов. Шаблон, не совпавший ни с одним инструментом, — не ошибка. В `agent.selected` пишется число доступных инструментов.

### D11. Применение агента

`AgentSession` получает члены `agents` (определения со `scope` `session` или `both`, по имени), `agent` (имя текущего, `default` без профиля) и `setAgent(String name)`. `name` не из списка и не `default` → `ArgumentError` (адаптер отвечает `-32602` до вызова).

**Очередь смен конфигурации** (решение по ревью итерации 3). `setMode`, `setModel`, `setEffort` и `setAgent` сессии исполняются строго по одной, в порядке вызова: каждый вызов встаёт в очередь сессии (цепочка `Future`), и новое значение — база, пол, итоговые режим и модель — вычисляется уже под очередью, от состояния после предыдущей смены, а не в момент вызова. Итоговое состояние сессии равно результату последнего вызова. Записи журнала (`config_change`, `mode_change`, `model_change`) и события `ModeChanged` идут в порядке очереди. Почему: `setAgent` читает текущие `(mode, model)` для базы и меняет их несколькими шагами; без очереди параллельный `setMode` мог встать между чтением и записью, и тогда база запоминала бы промежуточный режим, а итог зависел бы от планировщика. Почему очередь в ядре, а не только в адаптере: прямой API (встроенный режим, CLI) вызывает те же методы без ACP. Ошибка одного вызова (`ArgumentError`) не ломает очередь: следующий вызов исполняется. `dispose()`/`close()` сессии ждёт текущей смены и отклоняет оставшиеся в очереди `StateError`.

Альтернатива — блокировка только на `setAgent`. Отвергнута: `setMode` после `setAgent` всё равно должен видеть результат `setAgent`, иначе «последний запрос выигрывает» не выполняется.

**База.** При переходе `default → X` сессия запоминает базу — текущие `(mode, model)`. Действующее состояние — база, перекрытая полями определения. Переход `X → Y` считает от той же базы. `default` возвращает базу и снимает профиль. Если пользователь при активном агенте сменил режим или модель, меняется только текущее значение: база остаётся прежней (так возврат к `default` предсказуем). После `session/load` база — режим и модель, восстановленные из журнала до записи выбора агента. Если найти её нельзя — режим и модель конфигурации сессии.

**Зажим восстановленной базы** (решение по ревью итерации 3). Режим базы, восстановленный из журнала, зажимается полом текущей конфигурации сессии: если он мягче пола, база получает режим пола. Почему: запись `mode_change` не несёт источника, и по журналу не различить «пользователь сам смягчил режим селектором» и «конфиг тогда был мягче, а сейчас строже». Без зажима возврат к `default` после `session/load` дал бы режим мягче конфига, хотя пользователь этого в текущей конфигурации не выбирал — тот же обход OQ3, только через журнал. При неразличимости решение fail-closed (приоритет 1). Цена: пользователь, явно смягчивший режим до выбора агента, после загрузки и возврата к `default` получает режим конфига и смягчает его снова одним явным выбором. Режим сессии без агента при загрузке восстанавливается, как раньше: зажим касается только базы, которую неявно применяет `setAgent('default')`. Если в будущем `mode_change` получит источник (`source: user`), явный выбор пользователя зажимать не придётся — это отдельное изменение формата журнала.

**Промпт.** Секция `agent_profile` (`prompts/agent_profile.md`, `vars: [name, body]`, заголовок `# Agent profile: {{name}}`) встаёт шагом 10b §11.5, последней секцией. Базу, правило ограды и секции инструментов она не заменяет (CFG-8). Тело вставляется значением с обрезкой пробельных символов по краям и шаблоном не обрабатывается (§11.4): `{{…}}` в теле остаётся литералом. Обрезка краёв убирает пустые строки после frontmatter и в конце файла, чтобы промпт не зависел от них. Смена агента меняет промпт и стоит одного промаха кеша провайдера.

**Режим — только не мягче режима конфига** (решение пользователя 2026-10-30, OQ3). Пол — режим конфигурации сессии: `settings.permissions.mode ?? profile.defaultMode` с `extraDeniedTiers`. Режим определения применяется, если он не мягче пола по порядку `bypass → accept-edits → standard → ask` (`plan` строже всех по запретам записи и команд). Мягче → режим не меняется, лог `agent.mode.not_applied {session_id, agent, mode, floor}`, остальные поля определения применяются. `extraDeniedTiers`, `permissions.deny`, критические шаблоны и PERM-11 не затрагиваются ни при каком определении. Почему пол — конфиг, а не текущий режим: пользователь мог сам перейти в `accept-edits` селектором, и агент `accept-edits` не должен тогда отказывать. Смягчить режим ниже конфига можно только явным выбором режима — селектором клиента или `session/set_mode`. Выбор агента — один клик в списке, и он не должен расширять права шире, чем пользователь настроил.

**Мягкость режима.** `ModeId.softness` перечисляет все пять режимов явными ветками, включая `standard`; ветки «по умолчанию» для известного режима нет. Неизвестное значение (новый режим, который ядро ещё не знает) — fail-closed: считается мягче любого известного, поэтому режим определения с ним не применяется (`agent.mode.not_applied`), а пол с неизвестным значением не пропускает ни одного режима определения. Почему: молчаливое `_ => standard` сделало бы новый мягкий режим «не мягче» пола `standard`, и выбор агента смягчил бы права.

**Модель** из определения — через `setModel` (каталог проверен при загрузке, D10).

**Инструменты** (CFG-7). Набор схем = инструменты сессии ∩ список `tools` (шаблоны по префиксу). Без `tools` — все инструменты сессии; `tools: []` — ни одного. Инструменты, появившиеся позже (MCP `tools/list_changed`), фильтруются тем же списком. Вызов инструмента вне набора разрешается на шаге поиска инструмента, до `beforeToolCall`, как неизвестный инструмент: результат-ошибка `Tool not available for agent <name>: <tool>`, без запроса разрешения и без исполнения. Такой вызов считается в `MisuseBreaker` так же, как вызов неизвестного инструмента (TOOL-11): модель, упорно зовущая выключенный агентом `write`, получает предупреждение и блокировку ключа, а не тратит весь бюджет хода. Почему до политики: иначе пользователь одобрял бы вызов, который всё равно не выполнится. Политика по-прежнему первое звено для доступных инструментов (PERM-1).

Секции промпта считаются по доступному набору (PR-6): секция с `tools` входит, только если все её инструменты в наборе агента. Секция `mcp` при заданном `tools` перечисляет только серверы, у которых есть хотя бы один доступный инструмент; сервер, все инструменты которого вне набора, в секции не упоминается — как сервер с выключенными инструментами (§11.10, `prompt_sections_tools_test.dart`). Почему: модель не должна знать о префиксе сервера, вызвать который не может.

**Посреди хода** (решение по ревью итерации 3) все поля агента — режим политики разрешений, модель, промпт и набор инструментов — действуют со следующего шага через `prepareNextStep` (`StepUpdate.systemPrompt`, `tools`, `model`, режим политики); идущий вызов не прерывается (§15.8, шаг 7). Вызовы пакета текущего шага, в том числе ещё не начатые, решаются по прежнему режиму и прежнему набору инструментов. Почему не «со следующего вызова», как у `setMode`: агент меняет режим вместе с набором инструментов и промптом, и модель сформировала пакет под прежний профиль. Решать часть пакета по новому режиму, а набор оставлять прежним дало бы сочетание, которого нет ни у одного агента. Явный `setMode` сохраняет своё правило — со следующего вызова инструмента (agent-runtime «Смена режима посреди хода»).

Значения `mode` и `model` сессии, опции `configOptions`, событие `ModeChanged` и записи журнала меняются сразу при `setAgent`, под очередью: ответ ACP и `current_mode_update` не ждут границы шага. Отложено только применение к идущему ходу. Если после `setAgent` в том же шаге пришёл явный `setMode`, он выигрывает (последний запрос, очередь выше): отложенный режим агента отменяется, а режим `setMode` действует со следующего вызова по своему правилу. Вне хода изменения действуют сразу.

**Журнал.** `setAgent` пишет `config_change {optionId: "agent", value: <name>}`, а смена режима и модели — свои обычные `mode_change` и `model_change`. `loadSession` восстанавливает агента по последней `config_change` с `optionId: "agent"` на ветке. Определения с этим именем больше нет → `default`, лог `agent.definition.missing {session_id, agent}` и запись `config_change {optionId: "agent", value: "default"}` — как `session.model.not_restored` дописывает `model_change` модели по умолчанию (agent-runtime «Модели журнала нет в каталоге»). Режим и модель — из своих записей, как сейчас. Почему дописывать: иначе каждая следующая загрузка снова искала бы пропавшее определение и снова писала бы предупреждение, а если файл вернут, сессия неожиданно сменила бы профиль без действия пользователя.

### D12. ACP-опция `agent`

```json
{"id":"agent","name":"Agent","type":"select","currentValue":"default",
 "options":[{"value":"default","name":"Default"},
            {"value":"reviewer","name":"reviewer","description":"Reviews the current changes and reports defects"}]}
```

- **Без `category`.** Пример §15.8 с `"category":"other"` противоречит ACP: имена категорий без `_` зарезервированы спецификацией, а их список — только `mode`, `model`, `thought_level` (`13-Session Config Options.md`, «Option Categories»). Своя категория `_codelab_*` — расширение протокола; по `codelab_agent_acp/AGENTS.md` §2 его вводит отдельный OpenSpec change, а UX она не улучшает: клиенты CodeLab показывают опцию без категории. Документ исправляется задачей 0.1.
- **Порядок** — `mode`, `model`, `effort`, `agent` (§13.6: важные первыми). Изменение порядка существующих опций сломало бы фикстуры и привычку клиентов.
- Опция есть, только если у сессии есть хотя бы одно определение со `scope` `session` или `both` (§15.8). Без определений список опций и фикстуры прежние.
- `session/set_config_option {configId: "agent"}`:
  - неизвестное значение → `-32602`;
  - иначе `setAgent`, ответ — полный список опций, в том числе изменённые `mode` и `model`;
  - если режим изменился — перед ответом `current_mode_update` (как при `configId: "mode"`) для клиентов на устаревшем `modes`;
  - `config_option_update` в ответ на запрос клиента не дублируется (ACP-11). Шаг 6 §15.8 («разослать `config_option_update`») расходится с §13.6, п. 4, и исправляется задачей 0.1;
  - смена модели через агента (выбор или возврат к `default`) ставит ту же заметку §2.12.3, что `configId: "model"`: переход с модели с рассуждением на модель без него — заметка первым `agent_message_chunk` следующего хода, переход на модель с рассуждением — заметка снимается. Почему: пользователь меняет модель одним кликом в другой опции и должен узнать, что его `effort` перестал действовать, так же, как при прямой смене модели.
- **Очередь запросов и эхо режима** (решение по ревью итерации 3). Мост сессии обрабатывает `session/set_config_option` (любой `configId`) и `session/set_mode` одной сессии строго по очереди, в порядке прихода, и вызывает методы ядра под этой очередью (D11). Поэтому в каждый момент у моста не больше одного клиентского запроса смены, и эхо `ModeChanged` однозначно принадлежит ему: событие проецируется только в `current_mode_update` (без `config_option_update`), а ответ уходит после этого кадра. На каждый запрос — ровно один ответ; ответ несёт снимок опций после своей смены, а итоговое состояние сессии — результат последнего запроса. `ModeChanged`, пришедшее без клиентского запроса в очереди (смена самим агентом), проецируется, как раньше, и `current_mode_update`, и `config_option_update`. Почему очередь в мосте, хотя ядро уже сериализует: общий слот ожидания эха (`_clientModeChange`) у двух параллельных запросов перезаписывался — второй запрос забирал эхо первого, а первый ждал вечно или отвечал до своего `current_mode_update`. Альтернатива — метка операции в `ModeChanged` — отвергнута: она меняет публичное событие ядра ради адаптера, а очередь моста даёт тот же результат локально (`AGENTS.md` §13). Ошибка запроса (`-32602`) не останавливает очередь.
- Реплей `session/load`: `config_option_update` с опцией `agent` и восстановленным значением — на прежнем месте последовательности.

### D13. `config check` показывает диагностику файлов проекта

`ConfigCommands.check` после успешной загрузки конфига вызывает тот же `ProjectFilesLoader` для `--cwd` с доверием и `max_bytes` загруженного конфига. Затем ядро проверяет шаблоны и определения (`parseCommandTemplates`, `parseAgentDefinitions` с каталогом конфига). Невалидный конфиг → файлы проекта не проверяются (каталога моделей нет). Строк `Sources:`/`Config:` это не меняет. `codelab config check` получает то же через мост `codelab_setup` без кода в CLI.

**Канонический `cwd`.** Загрузчик и проверка доверия получают ту же форму `cwd`, что в runtime: `LocalExecutionEnv.realpath` (D4). Почему: иначе `config check` по symlink на доверенный корень показал бы «не доверен», а сессия в том же каталоге читала бы шаблоны проекта — проверка разошлась бы с тем, что видит агент. Нераскрытый путь — недоверенный, как в runtime (fail-closed, D4).

**Вывод** (перед последней строкой, в общем формате `config check`):

| Источник | Строка |
|---|---|
| диагностика `error` или `warning` | `warning: <path>[:<line>[:<column>]]: <message>` |
| `untrusted_project` (`info`), по строке на каталог `.codelab/prompts` / `.codelab/agents` | `note: <каталог>: the project is not trusted; add it to trusted_projects` (решение пользователя 2026-10-30) |
| прочие `info` (`shadowed`, `limit_exceeded` обхода и т. п.) | не печатаются |
| непредвиденное исключение загрузчика (например, `CODELAB_HOME` — относительный путь к несуществующему каталогу; до D17 так падал и `CODELAB_HOME='~/x'`) | `warning: <cwd>: project files could not be read: <runtimeType>` — как диагностика `unexpected` в runtime (D6) |
| загрузка дольше 5 с (лимит фазы D6) | `warning: <cwd>: project files were not read within 5 s`; загрузка отменяется |

- Сообщения — фиксированные тексты кодов D3/D10: имя ключа, значение и фрагменты файла в них не попадают (D14). Сценарии спецификации проверяют путь, позицию и префикс сообщения, а не текст целиком, — уточнение текста кода не ломает сценарий.
- Почему `note:` только для `untrusted_project`: это единственный `info`, после которого файлы пользователя молча не работают, и у него есть действие — добавить каталог в `trusted_projects`. Остальные `info` — штатное поведение (перекрытие, предел поиска корня), их печать была бы шумом. Альтернатива — печатать все `info` с префиксом `note:` — отвергнута по тому же доводу.
- Диагностики, заметки, сбой и таймаут проблемами не считаются: коды выхода прежние, файлы проекта не мешают запуску (D6). Сбой загрузчика не превращается в исключение команды — иначе `config check` падал бы там, где сессия работает без файлов проекта.

**Асинхронность.** Порт `ProjectFilesSource.load` асинхронный, поэтому `ConfigCommands.check` возвращает `Future<ConfigCommandResult>`. Вызывающие — `config` обоих бинарей (`apps/codelab_agent`, `apps/codelab_cli`) и мост `codelab_setup` (`io.dart`); они ждут результат до печати и выхода. Альтернатива — синхронное чтение файлов в `check` — отвергнута: второй путь чтения разошёлся бы с загрузчиком runtime (границы, лимиты, диагностики D2/D6).

Почему здесь, а не только в логе: R-15 требует «битый YAML — диагностика с именем файла», а пользователь, у которого агент не появился в списке, смотрит в `config check`, а не в лог.

- Содержимое файлов, тела шаблонов и определений, аргументы команд в лог не пишутся. `message` диагностики строится из фиксированных текстов, без фрагментов файла (как `ConfigIssue.message`, D3 change `add-agent-configuration`).
- Пишет логгер сессии (correlation `session_id`, §16).

### D16. Хост

- `AgentHost.build` для `--stdio` создаёт `ProjectFilesLoader(home: codelabHomeOf(environment), local: <LocalExecutionEnv хоста>)` и передаёт его в `AgentCoreServices.projectFiles`.
- **`--llm-script`.** Сценарий не трогает `$CODELAB_HOME` (`agent-binary`, «Конфиг бинаря…»), поэтому загрузчик получает `home: null`: пользовательская область не читается. Глобальный слой конфига под `--llm-script` тоже не читается, значит проект недоверенный, и шаблоны и агенты проекта не загружаются. Читается только контекст проекта (`AGENTS.md` дерева `cwd`) — это вход сценария, его создаёт тест. Так прогон детерминирован и не зависит от файлов разработчика.
- **`serve --ws`.** Порт не передаётся (`projectFiles: null`), файлы проекта и `$CODELAB_HOME` не читаются (D2; решение пользователя 2026-10-30). Это сужение по транспорту по образцу MCP (D3 change `add-agent-mcp-client`): хост один раз при запуске, рядом с `host.config.loaded`, пишет `project_files.skipped` (info) с полями `transport: ws` и `reason: "project files are not read over WebSocket"`. Почему событие хоста, а не на каждую сессию, как `mcp.server.skipped`: серверы MCP приходят в каждом `session/new` и пропускаются поштучно, а файлы проекта выключены для всего процесса одним решением хоста. Альтернатива — новая `HostCapability.projectFiles` с `CapabilityOff` и событием на сессию — отвергнута: она меняет публичный enum ядра ради того, что уже выражает `null` порта (D1), а диагностике хватает одной строки при запуске (`AGENTS.md` §13). `config check` транспорта не знает и файлы проверяет как раньше (D13).

### D17. Раскрытие `~` в `CODELAB_HOME`

**Проблема.** Тильду раскрывает оболочка, и только без кавычек. В unit launchd/systemd, в `env` профиля IDE и в `CODELAB_HOME="~/x"` она приходит буквально. Сейчас `codelabHomeOf` и `CodelabHome.resolve` возвращают такое значение как есть: загрузчик конфига молча читает `./~/x/config.yaml` относительно текущего каталога процесса, а `ProjectFilesLoader` падает в `BoundedEnv.wrap` на несуществующем корне (`config check` печатает `project files could not be read`). Хуже всего — запись: журналы сессий и история CLI оказались бы в каталоге `~` внутри рабочей копии и могли бы попасть в коммит.

**Решение** (решение пользователя 2026-10-30):
- `CODELAB_HOME`, равный `~` или начинающийся с `~/`, раскрывается в домашний каталог: `HOME`, а если он не задан или пуст, `USERPROFILE`. Остаток пути приклеивается как есть, без нормализации — так же `ConfigLoader` уже раскрывает `trusted_projects` (`_canonicalEntry`); правило одно для обоих мест.
- Агент: раскрытие внутри `codelabHomeOf` (`codelab_agent_io/lib/src/config/config_loader.dart`). Это единственная точка: её зовут загрузчик конфига (слой 2, поиск `codelab.toml`), `ConfigCommands.check` и `AgentHost` (журналы сессий, `ProjectFilesLoader`, D16) — отдельных правок потребителей нет.
- CLI: то же правило в `CodelabHome.resolve` (`apps/codelab_cli/lib/src/home.dart`). Общей функции у двух сторон нет и не вводится: клиенту запрещено импортировать `package:codelab_agent_*` (§5), а выносить четыре строки в мост `codelab_setup` или в `codelab_acp_*` — абстракция без второй причины (§13). Совпадение двух реализаций держат тесты обеих сторон с одинаковыми входами.
- Любое другое значение с `~` в начале (`~user/…`, `~\…` на Windows) — ошибка использования, код `64`, текст `CODELAB_HOME: ~user is not supported, use an absolute path`. Почему: «как есть» оставляет тот же дефект (`./~user/…` в текущем каталоге), а раскрыть `~user` нечем — базы пользователей ОС (`getpwnam`) в `dart:io` нет, на Windows форма не определена. `~\…` не раскрывается, как в `trusted_projects`, и попадает в ту же ошибку, а не в относительный путь.
- `~` или `~/…` без домашнего каталога (`HOME` и `USERPROFILE` нет или пусты) — ошибка использования, код `64`, текст `CODELAB_HOME: cannot expand ~ without HOME or USERPROFILE, use an absolute path`. Одинаково у обоих бинарей: значение с тильдой — явная просьба о домашнем каталоге, и молча подставить вместо него текущий каталог нельзя. Умолчание без `CODELAB_HOME` не меняется (агент — от `.`, CLI — `UsageError`): это отдельное поведение вне change.
- Агент: `codelabHomeOf` бросает `ConfigUsageException` (тот же тип, что у `checkConfigFileName`), поэтому хост `serve` и `config` обоих бинарей отображают его в код `64` уже существующей обработкой; ошибка — до чтения файлов и до создания каталогов. CLI: `CodelabHome.resolve` бросает `UsageError`. Тексты ошибок одинаковы.
- `--llm-script`: `$CODELAB_HOME` не читается (D16, `home: null`), поэтому хост в этом режиме `codelabHomeOf` не вызывает: значение не раскрывается и не проверяется, неверное значение не даёт `64`. Почему: проверять значение, которое прогон не использует, — ломать детерминированные сценарии из-за окружения разработчика; ошибка нужна только там, где путь действительно пошёл бы в работу. `~\…` остаётся ошибкой использования (fail-closed, без относительного каталога).

**Альтернативы.**
- *Не раскрывать, документировать «только абсолютный путь».* Отвергнуто пользователем: ошибка тихая, а результат — данные в рабочей копии.
- *Требовать абсолютный `CODELAB_HOME` (ошибка использования для любого относительного).* Сильнее и закрывает весь класс, но ломает тех, кто уже задаёт относительный путь (тесты, скрипты), и выходит за рамки change. Кандидат отдельного change (OQ5, вариант (в) не выбран).
- *`~user/…` и `~` без домашнего каталога — «как есть».* Отвергнуто пользователем 2026-10-30 (OQ5, вариант (б)): тихий относительный путь — тот же дефект, который исправляет D17.
- *Раскрывать `$VAR`/`${VAR}` в `CODELAB_HOME`.* Не входит: жалоба только на тильду, а подстановка окружения уже есть у значений конфига (§15.5).
- *Раскрывать `~\…` на Windows.* Отвергнуто пользователем 2026-10-30: `trusted_projects` раскрывает только `~/`, правило держится одним. Расширение — правкой обеих функций и этого решения.

**Тесты.** `codelab_agent_io/test/config/codelab_home_test.dart` и `apps/codelab_cli/test/home_test.dart` — одинаковые входы и тексты ошибок: `~`, `~/x`, `USERPROFILE` при пустом `HOME`, `~bob/x` и `~\x` (ошибка), `~/x` без домашнего каталога (ошибка); плюс сквозной тест загрузчика (слой 2 из раскрытого пути) и `config check` с `CODELAB_HOME='~/x'` и шаблоном в `$HOME/x/prompts/` без строки `could not be read`. Сценарий «Сбой загрузчика» (D13) больше не опирается на `~/x`: в тестах — относительный путь к несуществующему каталогу или фейковый `ProjectFilesSource`.

## Risks / Trade-offs

- **[Prompt injection через `AGENTS.md` недоверенного репозитория]** → текст не меняет прав (политика в коде). Обёртка `project_context` говорит модели, что правила безопасности и решения пользователя главнее. Блок нельзя закрыть или открыть изнутри: теги экранируются без учёта регистра и пробелов, атрибут `path` — тоже (D5). Любое опасное действие идёт через одобрение. Остаточный риск — модель попросит одобрить вредное действие; он тот же, что у `README.md` под `read`. Подтверждено решением пользователя 2026-10-30 (OQ4).
- **[Модель правит `AGENTS.md` и влияет на следующую сессию]** → правка `AGENTS.md` — обычная правка файла с одобрением по режиму. В `bypass` она без вопроса, как правка любого кода. Включать `AGENTS.md` в критические пути PERM-11 этот change не стал: это задело бы обычную работу над документацией проекта. `.codelab/agents/**` и `.codelab/prompts/**` уже критические.
- **[Symlink из `$CODELAB_HOME` в dotfiles]** → единое правило границы (D2) отклоняет файл, чей `realpath` вне `$CODELAB_HOME`. Пользователь видит диагностику `outside_root` в `config check`. Symlink на весь `$CODELAB_HOME` работает: корень канонизируется. Расслабить правило для пользовательской области — отдельное решение, если появится запрос.
- **[Шаблон с тем же именем, что клиентская команда CLI]** → CLI уже даёт команде агента имя `/agent:<имя>` (`codelab-cli`, «Slash-меню»). Агентская сторона ничего не делает.
- **[`CLAUDE.md` с импортами `@AGENTS.md`]** → алиас (OQ2): при `AGENTS.md` на том же уровне `CLAUDE.md` не читается, поэтому строки `@…` в промпт не попадают и правила не дублируются.
- **[Гонка выбора агента и хода]** → `setAgent` применяется к идущему ходу со следующего шага через `prepareNextStep`, включая режим политики: вызовы пакета текущего шага решаются по прежнему режиму и набору (D11). Тест — смена агента во время первого из двух вызовов пакета и между шагами.
- **[Гонка параллельных смен конфигурации]** → очередь смен в сессии и очередь запросов в мосте (D11, D12): новое значение считается под очередью, эхо `ModeChanged` принадлежит одному запросу, итог — последний запрос. Тест — параллельные `set_config_option agent` и `set_mode` без ожидания ответов.
- **[Режим мягче конфига через журнал]** → восстановленная база зажимается полом текущего конфига (D11), неизвестный режим — fail-closed (`ModeId.softness`).
- **[Медленная файловая система (сетевой диск) задерживает `session/new`]** → лимиты числа и размера файлов (D6), чтение только первого уровня каталогов, отмена по `dispose()` рантайма и таймаут фазы 5 с: по таймауту сессия создаётся без файлов с диагностикой `timeout`. Остаток — зависший системный вызов продолжает висеть в фоне до ответа ОС; его результат выбрасывается.
- **[Удалённый клиент WebSocket читает инструкции машины агента]** → по `--ws` порт не передаётся, файлы проекта и `$CODELAB_HOME` не читаются, событие `project_files.skipped` (D2, D16; решение пользователя 2026-10-30). Цена — E-01 не работает по WebSocket; включение явным флагом хоста — отдельный change, как у MCP.
- **[`CODELAB_HOME` с буквальной тильдой]** → раскрывается в домашний каталог одинаково у агента и CLI (D17). `~user/…`, `~\…` и тильда без домашнего каталога — ошибка использования `64`. Остаток — прочие относительные значения без тильды по-прежнему считаются от текущего каталога процесса (OQ5 (в) — отдельный change).
- **[TOCTOU при чтении префикса]** → канонический путь от `BoundedEnv.realpath`, чтение по нему, повторная проверка пути и типа после открытия (D2). Остаточное окно — тот же класс, что у `BoundedEnv` (нет `O_NOFOLLOW` в `dart:io`).
- **[Доверие при нераскрытом `cwd`]** → fail-closed: `projectTrusted = false` (D4).
- **[Forward compatibility ACP]** → новых полей нет. Опция `agent` без `category`, поэтому клиенты, которые знают только `mode`/`model`, её просто показывают или игнорируют (`13-Session Config Options.md`, «Default Values and Graceful Degradation»).
- **[Allowlist ядра (PKG-2), web-безопасность]** → ядро получает только чистую логику; `yaml` и файловый доступ — в `_io`. `melos run web-compile` и сторож — в проверках затронутого.

## Migration Plan

1. **Итерация 0** — правки документов (выполнены при подготовке change и после решений OQ 2026-10-30).
2. **Итерация 1** — инструкции проекта (8.6): порт, сборка, секция промпта, загрузчик контекста, ключ `max_bytes`, `trustedProjects`, хост. Без файлов поведение прежнее.
3. **Итерация 2** — шаблоны команд (8.7): ядро, загрузчик шаблонов, разворачивание, журнал `command`, ACP-публикация и реплей, фикстуры.
4. **Итерация 3** — определения агентов (8.8): ядро, загрузчик, `setAgent`, опция `agent`, фикстура.
5. **Итерация 4** — `config check` с диагностикой файлов проекта (D13).
6. **Итерация 5** — матрица, DoD, сверка документов.

**Откат.** Каждая итерация — отдельный PR. `AgentCoreServices.projectFiles = null` возвращает прежнее поведение без отката кода. Журналы с полем `command` читаются и старым ядром (поле в `extra`). Пользовательских файлов change не пишет.
