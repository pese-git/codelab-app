## Context

`CodeLabShellCubit` уже хранит state приложения (`CodeLabShellState`) и управляет единственным экраном `CodeLabShell` через `BlocBuilder`. `AcpCommandPaletteSurface` (organism в `acp_ui`) — самодостаточный виджет с поиском/фильтрацией по `AcpCommandAction.filter()`, но нигде не смонтирован в дереве `apps/codelab_app`. `openCommandPalette()` — единственный метод, который должен переключать видимость палитры, сейчас no-op.

## Goals / Non-Goals

**Goals:**
- Палитра открывается по `Ctrl/Cmd+K` и закрывается по `Esc` или после выбора команды; все шесть команд видны и выбираемы.
- `/new`, `/reconnect`, `/logs` выполняют реальное действие через уже существующие методы `CodeLabShellCubit` (`createSession()`, `reconnect()`, раскрытие `AcpDebugLogPanel`) — новых use cases не создаётся.
- `/plan`, `/permissions`, `/compact` при выборе явно показывают "недоступно" вместо тихого no-op — честное отражение реального состояния, а не имитация готовности.
- Видимость палитры — часть `CodeLabShellState`, а не отдельный boolean флаг вне state machine (см. `docs/architecture/state-management.md`).
- Палитра открывается двумя независимыми триггерами — `Ctrl/Cmd+K` (по центру, с собственным полем поиска) и `/` как первый символ нового слова в композере (inline, без переключения фокуса) — оба ведут к одному и тому же состоянию/списку команд.
- Палитра показывает и шесть client-native команд, и команды, объявленные агентом через `AvailableCommandsUpdate`, — визуально разделённые секции, единый список для фильтрации по `AcpCommandAction.filter()`.

**Non-Goals:**
- Не реализуется permission-mode selector, plan-mode или compact-transcript механизм — в кубите/state для них нет ни одного поля (проверено: `grep` по `permissionMode|planMode|compact` в `shell_cubit.dart` не дал совпадений), это отдельные фичи вне scope палитры. Каждая — предмет собственного будущего OpenSpec change.
- Не меняется набор из шести client-native команд и не добавляются новые client-native команды — единственное расширение набора видимых команд идёт извне, от агента через `AvailableCommandsUpdate` (см. Goals), а не от нового захардкоженного клиентского действия.
- Агентские команды не выполняются как отдельный RPC — у `AvailableCommand` нет метода "invoke" в протоколе; выполнение агентской команды — это отправка обычного `session/prompt` с текстом, который агент разбирает сам (см. Decisions). Не вводится никакой новый исходящий метод в `acp_protocol`.
- `AcpCommandPaletteSurface`/`AcpCommandAction` в `acp_ui` меняются минимально — новый опциональный параметр для inline-режима, `isAvailable`-флаг для disabled-команд и поле-источник (client-native/agent) для визуального разделения секций (см. Decisions), сама логика фильтрации не переписывается.
- Не реализуется полноценный `editProfile()` или WebSocket reconnect — это отдельный change `complete-transport-setup-actions`.

## Decisions

- **Видимость палитры — поле `isCommandPaletteOpen` в `CodeLabShellState`**, переключаемое через `openCommandPalette()`/`closeCommandPalette()` в кубите. Альтернатива (локальный `StatefulWidget`-флаг в `workbench_shell.dart`) отклонена: presentation не должен быть source of truth для session/UI state (`docs/architecture/state-management.md`), а `Esc`-обработчик в `AcpWorkbenchShortcuts` уже привязан к кубиту, а не к локальному widget state.
- **Рендер палитры — `Overlay`/условный виджет поверх `AcpWorkbenchLayout` в `workbench_shell.dart`**, а не отдельный route: в приложении нет роутинга (единственный экран), поэтому палитра — модальный слой, а не push route.
- **Команды с реальной опорой маппятся на существующий публичный метод кубита**: `/new` → `createSession()`, `/reconnect` → `reconnect()`, `/logs` → делает видимым `AcpDebugLogPanel` (снимает `Offstage` инспектора, если layout узкий).
- **`/plan`, `/permissions`, `/compact` помечаются как `AcpCommandAction` с `isAvailable: false`** (или аналогичным явным флагом) — палитра показывает их неактивными/с пометкой "coming soon" вместо выполнения и вместо скрытия. Скрывать их из списка нельзя: спека требует, чтобы палитра "presents core actions such as ... /plan, /permissions, ... /compact ...", то есть они обязаны быть видны как часть набора команд — просто честно как ещё не реализованные, а не имитировать выполнение.
- **Закрытие по выбору команды** — синхронно в том же методе, что выполняет действие (для `/new`, `/reconnect`, `/logs`); для недоступных команд палитра не закрывается автоматически, чтобы не создавать впечатление, что действие произошло.
- **Правило триггера `/`**: срабатывает, только если `/` — это позиция 0 текста композера, или ей непосредственно предшествует пробел/перенос строки. `/` внутри слова (например, `path/to/file`) не триггерит палитру — предотвращает ложные срабатывания на путях/URL, набираемых в обычном сообщении.
- **Inline-режим — новый опциональный параметр у `AcpCommandPaletteSurface`, не отдельный виджет.** Добавляется `queryOverride: String?`/`showSearchField: bool = true`: когда `showSearchField: false`, виджет не рендерит свой internal `TextBox`, а фильтрует список по значению, переданному родителем извне (текст композера после `/`) — переиспользуется вся существующая логика фильтрации/рендера строк (`AcpCommandAction.filter`, `_AcpCommandActionRow`), не дублируется отдельным списком.
- **Позиционирование inline-палитры** — плавающий слой над композером (не по центру workbench, как для `Ctrl/Cmd+K`), т.к. это должно визуально читаться как продолжение того, что печатает пользователь, а не отдельный модальный слой. Реализовано через `OverlayPortal` + `CompositedTransformFollower`/`CompositedTransformTarget` (а не буквальный `Positioned` внутри локального `Stack`) — это единственный способ вырваться за пределы layout-границ композера и его родителей на произвольную высоту, не будучи обрезанным ими.
- **Клавиатурное поведение, специфичное для inline-режима**: пока inline-палитра открыта — `↑`/`↓` двигают выделение по списку, `Enter` выбирает выделенную команду (переопределяя штатное поведение `TextBox` "вставить перенос строки" только в этом состоянии), `Esc` закрывает палитру, оставляя набранный текст как есть, backspace, стирающий триггерный `/`, тоже закрывает палитру. Вне этого состояния поведение композера (включая `Ctrl/Cmd+Enter` на submit) не меняется.
- **Выбор команды из inline-режима** очищает фрагмент `/word` из текста композера и выполняет команду тем же обработчиком, что и выбор через `Ctrl/Cmd+K` — не вводится отдельный путь исполнения.
- **`AvailableCommandsUpdate` маппится в `CodeLabShellState.agentCommands: List<AcpCommandAction>`**, полностью заменяемый на каждый новый `session/update` с этим вариантом — тот же паттерн "later update replaces the list", что и у `PlanEntry`/`add-plan-progress-checklist`. Список очищается при смене активной сессии и при создании новой сессии (агент, который ещё не прислал `availableCommandsUpdate` для активной сессии, не имеет объявленных команд — палитра в этом случае показывает только шесть client-native).
  **Уточнение по факту реализации**: очистка "при потере соединения" из более ранней версии этого решения не реализована — `CodeLabShellCubit` нигде не подписан на `AcpClientApplication.connectionStateChanges`, и `connectionStatus` в целом меняется только внутри явных `connect()`/`reconnect()`, а не реактивно на спонтанный disconnect. Это не пробел, специфичный для `agentCommands` — ни один кусок state (сессии, `pendingApproval`, transcript) сегодня не реагирует на спонтанную потерю соединения. Добавление такой реакции — самостоятельная архитектурная фича, а не точечный фикс палитры; вынесена в отдельный будущий OpenSpec change.
- **`AcpCommandAction` получает поле `source` (`client`/`agent`, или булев `isFromAgent`)** — используется палитрой только для визуального разделения на секции ("From agent" ниже client-native списка), не влияет на фильтрацию (`AcpCommandAction.filter()` работает по объединённому списку без учёта источника).
- **Выбор агентской команды не выполняет её напрямую.** В отличие от `/new`/`/reconnect`/`/logs` (прямой вызов метода кубита), выбор `AcpCommandAction` с `source: agent` вставляет `/{name} ` в текст композера (плюс `input.hint`, если `AvailableCommandInput` присутствует — как серый placeholder, не как готовый текст) и закрывает палитру, оставляя фокус в композере. Пользователь дополняет аргументы и отправляет как обычный `session/prompt` — агент сам разбирает текст, никакого нового исходящего RPC-метода не вводится.
- **Коллизия имён между client-native и agent-командой не разрешается склейкой** — обе показываются как отдельные строки в своих секциях (даже если, например, агент вдруг объявит команду с именем `new`); палитра не пытается угадать, что имел в виду пользователь, это ответственность агента — не объявлять команды, дублирующие client-native набор.

## Risks / Trade-offs

- [Пользователь может продолжать считать `/plan`/`/permissions`/`/compact` "почти готовыми", раз они видны в палитре] → явная надпись "coming soon"/disabled-стиль вместо просто серого текста, плюс отдельные будущие changes на каждую из трёх фич, на которые можно сослаться из UI-подсказки при необходимости.
- [Overlay поверх `AcpWorkbenchLayout` может конфликтовать с существующими `CallbackShortcuts` из `AcpWorkbenchShortcuts`, если фокус не передаётся палитре] → добавить widget-тест, что после открытия палитры `Esc` закрывает именно её, а не триггерит `onCancel` шелла.
- [Ложные срабатывания inline-триггера на "/", напечатанном как часть обычного текста сразу после пробела (например, начало пути `/usr/local`)] → принимается как известный minor-компромисс — то же происходит в Slack/Discord-подобных чатах с похожим паттерном; не блокирует MVP.
- [Переопределение `Enter` для выбора команды в inline-режиме может конфликтовать со штатным "вставить перенос строки" в многострочном `TextBox`, если состояние "палитра открыта" определено неточно] → переопределение должно быть строго обусловлено видимостью inline-списка, с явным widget-тестом на то, что вне этого состояния `Enter` продолжает вставлять перенос строки как раньше.
- [Агент может прислать `availableCommandsUpdate` с большим или "шумным" списком команд, забивающим палитру] → не вводится никакого лимита/пагинации в этом change — если станет реальной проблемой в использовании, это отдельный будущий change; сейчас важнее не потерять ни одной команды, которую агент считает нужным показать.
