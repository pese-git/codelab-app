## Context

`_AcpTranscriptEntryRow` (`packages/flutter/acp_ui/lib/src/organisms/acp_transcript_panel.dart:113-119`) рендерит `entry.body` единообразно для всех `AcpTranscriptEntryKind`, ограничивая его `_bodyMaxLines` (1/4/8 в зависимости от `AcpViewMode`) с `TextOverflow.ellipsis`. Это нарушает уже одобренный сценарий `agent-workbench-ui` "Меняется режим отображения" ("не теряя данных") для тех кодов, где `body` несёт содержательный, произвольной длины текст — реплику пользователя, ответ агента, причину approval-запроса, текст диагностики/ошибки.

Проверено, что реально использует `body` у каждого kind (по существующим usages в `apps/codelab_app` и тестам `acp_ui`):
- `user` — текст промпта пользователя (`shell_cubit.dart`, `_transcriptEntriesForSession`).
- `agent` — текст ответа/размышления агента, после `add-streaming-message-coalescing` — полный схлопнутый ответ, а не один короткий чанк.
- `approval` — краткая причина approval-запроса (например, "The agent wants to run a shell command.") — критична для решения allow/reject, не декоративна.
- `diagnostic` — сообщение об ошибке (`"Failed to send prompt: ..."`, `"invalid params"`).
- `toolCall` — по всем найденным usages `body` для этого kind **не задаётся**; содержательные поля (`name`/`target`/`status`/`detail`) идут через отдельное поле `entry.toolCall: AcpToolCallSummary`, рендерящееся отдельным виджетом (`_toolCallForMode`) с собственной, не входящей в этот фикс логикой детализации по `viewMode`.

## Goals / Non-Goals

**Goals:**
- `entry.body` для `user`/`agent`/`approval`/`diagnostic` рендерится полностью, без обрезки по числу строк, независимо от `viewMode` — данные не теряются ни в одном режиме.
- `AcpViewMode` (`summary`/`normal`/`verbose`) продолжает осмысленно работать там, где действительно уместно варьировать детализацию без потери данных — детализация `AcpToolCallSummary` (через `_toolCallForMode`) не меняется этим fix'ом.

**Non-Goals:**
- Не меняется публичный API `AcpTranscriptPanel`/`AcpTranscriptEntry` — те же поля, тот же конструктор.
- Не меняется логика детализации `AcpToolCallSummary`/`_toolCallForMode` по `viewMode`.
- Не добавляется механизм "свернуть/развернуть" (`ExpandableSection`, "Show more" и т. п.) — при отсутствии ограничения по строкам он не нужен для соответствия требованию "не теряя данных"; сам `AcpTranscriptPanel` уже прокручиваемый (`ListView.separated`), это уже существующий, достаточный механизм для просмотра длинного текста.
- Не меняется `title`/`timestampLabel` — они остаются с `maxLines: 1`/`ellipsis`: это метки, а не содержательный текст диалога, усечение однострочного заголовка не теряет данных о самом диалоге.

## Decisions

- **Обрезка по `_bodyMaxLines` сохраняется только для `AcpTranscriptEntryKind.toolCall`** (единственный kind, где `body`, если он вообще когда-либо будет задан, — вторичная подпись, а не основной канал содержания, которым для tool call служит отдельное поле `toolCall`). Для `user`/`agent`/`approval`/`diagnostic` `body` рендерится без `maxLines`/`overflow` вовсе (эквивалент `maxLines: null`, естественный перенос строк).
  - Альтернатива (отклонена): поднять `_bodyMaxLines` до большого, но всё ещё фиксированного числа (например, 100) для всех kind. Отклонено — это не устраняет проблему принципиально (любой достаточно длинный ответ агента всё ещё может превысить лимит), а просто отодвигает её; риск "тихой" потери данных остаётся тем же по своей природе, только реже проявляется.
  - Альтернатива (отклонена): добавить collapsible "Show more" по образцу `add-approval-option-kinds`'s "View raw input". Отклонено как YAGNI для этого fix'а — `AcpTranscriptPanel` уже прокручиваемый список, дополнительный collapse-контрол добавил бы UI-сложность без необходимости соответствовать требованию "не теряя данных"; можно вернуться к этой идее отдельным change'ем, если реальная длина ответов агента на практике сделает список неудобным для навигации.
- **Ограничение по kind, не по глобальному флагу/параметру.** Различение "содержательный текст" vs "вторичная подпись" встроено в сам `_AcpTranscriptEntryRow` через `entry.kind`, а не через новый параметр конструктора `AcpTranscriptEntry`/`AcpTranscriptPanel` — не расширяем публичный API ради внутреннего решения о рендеринге.

## Risks / Trade-offs

- [Очень длинный ответ агента (например, объёмный сгенерированный код или многошаговое рассуждение) сделает одну transcript-запись визуально высокой, увеличивая прокрутку] → Осознанно принято: приоритет "целостность данных" (AGENTS.md §2, п.3) выше UX-компактности (п.7); `ListView.separated` уже справляется с записями произвольной высоты, это не новый для панели сценарий (tool call detail в verbose-режиме уже может быть многострочным).
- [Существующие widget-тесты в `acp_ui`, полагавшиеся на компактность `summary`-режима для `.agent`/`.user`/`.diagnostic`/`.approval` body, могут перестать проходить, если они непреднамеренно проверяли обрезку] → Проверено заранее: ни один существующий тест в `acp_organisms_test.dart` не проверяет усечение/`ellipsis` для этих kind (тест "renders transcript summary mode with compact details" проверяет только подавление deталей tool call, не body агента) — фикс не должен сломать существующие тесты; будет перепроверено запуском `melos test` на этапе задач.
