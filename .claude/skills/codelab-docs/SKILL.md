# Документация CodeLab

Этот стандарт задаёт, **что** документируется, **для кого**, **где лежит** и **как проверяется**. Пишет по нему субагент `docs-writer` (команда `/docs`), но правило «документация меняется вместе с кодом» касается всех исполнителей.

## 1. Аудитории

| Аудитория | Кто это | Что ему нужно |
|---|---|---|
| **Пользователь** | человек, который работает в CodeLab app или `codelab` в терминале | как установить, запустить, настроить, решить задачу; что значат сообщения и ошибки |
| **DevOps** | тот, кто собирает, разворачивает и сопровождает: CI, сервер с `codelab-agent`, корпоративная установка | сборка, артефакты, переменные окружения, файлы конфигурации и их расположение, порты, логи, коды выхода, безопасность, обновление |
| **Разработчик** | тот, кто меняет код пакета или встраивает его | назначение, место в слоях, публичное API, схема зависимостей, ключевые потоки, как запускать тесты, правила пакета |

Не каждой единице нужны все три аудитории. Раздел без реального содержания НЕ пишется (AGENTS.md §13 — никакой церемонии ради формы).

## 2. Матрица: что документировать в какой единице

| Единица | Пользователь | DevOps | Разработчик | «Экраны» |
|---|---|---|---|---|
| `apps/codelab_desktop` | да, основная | сборка и поставка, где лежат файлы | да | PNG окна приложения |
| `apps/codelab_cli` | да, основная | headless в CI, коды выхода, окружение | да | текстовые снимки терминала; PNG — только для TUI |
| `apps/codelab_agent` | подключение к клиентам (Zed и др.) | да, основная: `serve --stdio`/`--ws`, порты, логи | да | текстовые снимки |
| `codelab_ui` | — | — | да | PNG виджетов |
| `codelab_agent_io`, `codelab_setup` | — | расположение конфигурации и журналов — ссылкой на `docs/ops/` | да | — |
| остальные `packages/dart/*` | — | — | да | — |

Если сомневаешься, нужна ли аудитория, — спроси себя: «есть ли у этого человека причина открыть этот пакет?» Нет — раздела нет.

## 3. Где лежит документация

```text
apps/<app>/README.md                 вход: что это, кому какой документ, 5-минутный старт
apps/<app>/doc/user-guide.md         пользователь: оглавление руководства
apps/<app>/doc/user/NN-<тема>.md     пользователь: главы руководства (00-overview, 01-…)
apps/<app>/doc/operations.md         DevOps
apps/<app>/doc/development.md        разработчик: короткий вход — собрать, проверить, куда смотреть
apps/<app>/doc/NN-<тема>.md          разработчик: главы (00-getting-started, 01-overview, …), оглавление — doc/README.md
apps/<app>/doc/images/*.png          скриншоты
packages/<dart|flutter>/<pkg>/README.md      разработчик; для маленького пакета — единственный файл
packages/<dart|flutter>/<pkg>/doc/*.md       углублённые темы большого пакета
docs/user/                           сквозное руководство пользователя: оглавление и темы на стыке приложений
docs/ops/                            сквозное руководство DevOps: оглавление и темы на стыке приложений
```

Правила:
- `doc/` (а не `docs/`) — соглашение pub для каталога документации пакета.
- **Один факт — одно место.** Факт, специфичный для приложения или пакета, живёт в его `doc/`; `docs/user/` и `docs/ops/` дают оглавление и сквозные сценарии и ссылаются на пакеты. Не копируй текст между файлами — ставь ссылку.
- **Общие факты.** Факт, общий для нескольких приложений (переменные `CODELAB_*`, раскладка `CODELAB_HOME`, расположение конфигурации и журналов), пока его описывает одно приложение, живёт в документе этого приложения. Когда его начинает описывать второе — факт переносится на отдельную страницу `docs/ops/` (или `docs/user/` для пользовательского), а оба приложения ссылаются на неё.
- Не трогай `docs/architecture/` (зона `codelab-architect`) и `docs/protocols/` (референс, изменять запрещено). На них можно и нужно ссылаться из раздела для разработчика.
- `AGENTS.md` пакета — правила для агентов и разработчиков; README не дублирует его, а ссылается.
- **Ссылки** — только относительные пути к существующим файлам и каталогам, с точным регистром имени. Абсолютные пути (`/…`, `C:\…`, `file:`) и адреса GitHub на файлы этого репозитория запрещены: на сайте их нельзя перевести в адрес страницы. Якорь в ссылке на опубликованный документ должен существовать.
- **Сырой HTML** — только `details`, `summary`, `br`, `kbd`, `sub`, `sup`, без атрибутов (кроме `open` у `details`). Всё остальное, в том числе `<host>` вне обратных кавычек, считается тегом: GitHub его вырезает, а сайт отвергает.
- **Документы публикуются на сайте.** Документы из allowlist сайта (`site/src/lib/publish.ts`, `add-astro-site` D3: `README.md` и `doc/` приложений и пакетов, `docs/user/`, `docs/ops/`) собираются в страницы `site/`. Нарушение правил ссылок, HTML или маскировки путей (§7) — ошибка сборки, и джоб `site` в CI становится красным. Отключать проверку ради merge нельзя: правится документ.

## 4. Язык

- Русский, простой и прямой. Пиши так, как объяснил бы коллеге вслух.
- Короткие предложения: одна мысль — одно предложение. Активный залог: «Агент читает файл», а не «Файл читается агентом».
- Термин объясняется при первом упоминании в документе: «ACP (Agent Client Protocol) — протокол, по которому клиент и агент обмениваются сообщениями». Англоязычные термины без перевода — только если так говорят все (`stdio`, `WebSocket`, `CI`), тогда в коде-шрифте или с пояснением.
- Для пользователя — без внутренних имён классов и пакетов. «Встроенный агент», а не `EmbeddedAgentHost`.
- Инструкции — нумерованными шагами, один шаг — одно действие, после шага — что пользователь увидит.
- Идентификаторы, команды, флаги, ключи конфигурации, пути — в `коде`. Команды для копирования — в блоке ```` ```bash ````, без `$` в начале и без вывода внутри.
- Нельзя: канцелярит («осуществляется», «производится», «данный»), маркетинг («мощный», «удобный», «революционный»), обещания без проверки («скоро», «будет»), пересказ кода.
- Даты — абсолютные. Версии берутся из `pubspec.yaml`, а не пишутся по памяти.

## 5. Структура документов

Шаблоны — в `templates/` рядом с этим файлом:
- `templates/package-readme.md` — README пакета (разработчик);
- `templates/app-readme.md` — README приложения (вход для всех аудиторий);
- `templates/user-guide.md` — руководство пользователя: каркас одной главы `doc/user/NN-<тема>.md`; `doc/user-guide.md` — только оглавление (введение, кому, таблица глав «что внутри»). Возможности агента, общие для всех клиентов (инструменты, режимы разрешений, навыки, `AGENTS.md`, шаблоны команд, определения агентов, MCP, сессии), описываются только в `apps/codelab_agent/doc/user/`; руководства app и `codelab` описывают свой интерфейс и ссылаются туда за смыслом;
- `templates/operations.md` — руководство DevOps;
- `templates/development.md` — вход разработчика приложения (`apps/*/doc/development.md`); устройство и рецепты — в главах `doc/NN-<тема>.md`.

Шаблон — каркас, а не анкета: удаляй разделы, которым нечего сказать, и не оставляй заглушек «TBD».

## 6. Mermaid-схемы

Схема нужна, когда текстом связи читаются хуже, чем картинкой: зависимости, потоки сообщений, состояния. Схема-украшение не нужна.

| Что показать | Тип |
|---|---|
| место пакета среди соседей, зависимости, слои | `flowchart LR` или `TD` |
| обмен сообщениями клиент ↔ агент, порядок вызовов | `sequenceDiagram` |
| жизненный цикл: соединение, сессия, запрос | `stateDiagram-v2` |
| путь пользователя в интерфейсе | `flowchart LR` |
| развёртывание: процессы, порты, файлы | `flowchart LR` с `subgraph` |

Правила:
- Не больше ~15 узлов. Больше — разбей на две схемы.
- `flowchart` и `stateDiagram-v2`: подписи узлов и рёбер с кириллицей, пробелами, скобками, `/`, `:` — в кавычках: `A["Встроенный агент"]`, `A -->|"session/prompt"| B`.
- `sequenceDiagram`: кавычки НЕ ставятся — Mermaid выводит их буквально. Участник: `participant cli as Терминальный клиент`; сообщение: `cli->>agent: session/prompt`. Символы `;` и `#` в тексте сообщения не используй.
- ID узлов — латиницей без пробелов: `cli`, `core`, `agent`.
- Без цветов и `style`/`classDef` с жёсткими цветами: схема должна читаться в светлой и тёмной теме GitHub и IDE.
- Перед схемой — одно предложение, что на ней; после — пояснение неочевидного.
- Каждая стрелка и узел соответствуют коду: зависимость — в `pubspec.yaml`, сообщение ACP — в `codelab_acp_protocol`, состояние — в типе состояния. Придумывать ACP-методы и состояния ЗАПРЕЩЕНО (AGENTS.md §3.4).
- Проверка синтаксиса: если установлен `mmdc` (`@mermaid-js/mermaid-cli`) — прогоняй им; если нет — не устанавливай сам, а сообщи в отчёте, что синтаксис проверен только визуально.

## 7. Скриншоты и снимки экрана

**Главное правило:** каждый снимок получен с реально запущенной программы текущей ветки. Нарисованные, отредактированные или «примерные» снимки ЗАПРЕЩЕНЫ. Допустима только маскировка (ниже).

### Подготовка окружения (один раз перед снимками)

1. Сгенерируй код, без него бинари не собираются (в worktree `*.freezed.dart` нет): шаг генерации из `docs/user/run-from-source.md`.
2. Изолируй данные и секреты — снимок не должен видеть настоящий `HOME` пользователя:

   ```bash
   export SNAP=<scratchpad>/docs-snap
   mkdir -p "$SNAP/home" "$SNAP/project" "$SNAP/bin"
   cp .fvmrc "$SNAP/project/"   # иначе fvm вне репозитория возьмёт глобальный SDK
   ```

   Каждую команду запускай с `CODELAB_HOME="$SNAP/home"` и через `env -u` для всех переменных с ключами провайдеров (`*_API_KEY`, `CODELAB_SECRET_*`), даже если они вроде бы не нужны.
3. Для снимков, где программа должна видеть терминал (REPL, мастер первого запуска, TUI), собери бинарь: через `fvm dart run` stdout не является терминалом.

   ```bash
   fvm dart compile exe apps/codelab_cli/bin/codelab.dart -o "$SNAP/bin/codelab"
   ```

4. После снимков останови все запущенные процессы и серверы (`tmux -L <имя> kill-server`).

Сеть: допустимы только loopback-адреса (например, недоступный `127.0.0.1:9`, чтобы показать ошибку соединения). Запросы к настоящим провайдерам моделей ЗАПРЕЩЕНЫ.

### Терминал (`codelab`, `codelab-agent`)
- «Скриншот» терминала — **текстовый снимок**: блок ```` ```text ```` с реальным выводом команды. Он ищется поиском, копируется и не устаревает незаметно.
- Неинтерактивный вывод (`--help`, подкоманды, headless `-p`): `fvm dart run apps/codelab_cli/bin/codelab.dart <аргументы>`.
- Интерактивный построчный режим (REPL, мастер): собранный бинарь под PTY — `script -q <файл> <бинарь>`; перед запуском задай размер окна `stty rows 40 cols 120`, иначе Dart не распознаёт терминал.
- Полноэкранный TUI (`--ui=tui`): основной снимок — **текстовый кадр** из `tmux -L <имя> new-session -d -x 120 -y 40 …` и `tmux capture-pane -p`. PNG — дополнение, только если есть честный способ снять окно.
- Перед блоком — команда, которая его дала. Длинный вывод сокращай с явной пометкой `…` и только в середине.
- Маскировка (AGENTS.md §10, §16): пути — `~/.codelab`, `~/projects/demo`; имя пользователя и хоста — `user`, `host`; имя пользователя в путях домашнего каталога (`/Users/…`, `/home/…`, `C:\Users\…`) — только `user` или `me` (или `~`), любое другое имя — ошибка сборки сайта (`add-astro-site` D11); токены, ключи, идентификаторы сессий — `<token>`, `<session-id>`; строки, которые пришли из личной среды (личные навыки, проекты, история), — `…`. Больше ничего в снимке не меняется.

### Ход агента

**Терминал `codelab` — снимается тестовой моделью.** `bin/codelab.dart` сценарий не принимает, но точка входа e2e-тестов принимает:

1. `cd apps/codelab_cli && fvm dart compile exe test/e2e/support/embedded_cli_main.dart -o <scratchpad>/bin/codelab-e2e`.
2. Сценарий модели — JSON в scratchpad (не в репозитории): например, шаг с вызовом `edit` и шаг с ответом `done`.
3. Запуск в tmux (ширина 120) в папке-образце, окружение изолировано: `env -u OPENAI_API_KEY -u ANTHROPIC_API_KEY CODELAB_HOME=<scratchpad>/home CODELAB_CONFIG=<конфиг с провайдером на 127.0.0.1:9> CODELAB_E2E_LLM_SCRIPT=<сценарий> CODELAB_E2E_PERMISSION_MODE=standard`.
4. Ввод и ответы — `tmux send-keys`, вывод — `tmux capture-pane -p`. Маскировка — как в разделе выше; ответ тестовой модели (`done`) поясни в тексте перед снимком.

Так снят блок одобрения в `apps/codelab_cli/doc/user/02-repl.md#разрешения`.

**Настольное приложение — пока нет.** Сценарный открыватель в сборку app не попадает (`AGENTS.md` §5), поэтому ход агента в app (ответ модели, карточка одобрения, вызов инструмента) до change `docs:screenshots` — маркер `<!-- screenshot: … -->`, а не выдуманный снимок.

### Настольное приложение
1. Запусти приложение с расширением драйвера: `cd apps/codelab_desktop && fvm flutter run -d macos -t test_driver/app.dart --print-dtd`.
2. Доведи экран до нужного состояния через `flutter_driver` (Dart MCP) по стабильным `ValueKey` виджетов, а не кликами по координатам.
3. Сними окно в файл. Данные на экране — демонстрационные: проект-пример, без настоящих токенов, путей и переписки.
4. Положи в `apps/codelab_desktop/doc/images/`.

Автоматическая генерация (`melos run docs:screenshots`) пока не сделана: это отдельный OpenSpec change, потому что он добавляет скрипт и прогон приложения (AGENTS.md §17, §21). До него — ручной процесс выше; если снять скриншот не удалось, оставь в тексте явный маркер `<!-- screenshot: <что снять> -->` и перечисли его в отчёте. Подписи «тут будет скриншот» в видимом тексте ЗАПРЕЩЕНЫ.

### Файлы изображений
- Имена: `kebab-case`, по экрану и состоянию: `settings-connection-empty.png`.
- PNG, ширина окна не больше 1600 px, без лишнего рабочего стола.
- Каждое изображение со смысловым `alt`: `![Страница «Подключение» без профилей](doc/images/settings-connection-empty.png)`.
- Под изображением — что на нём главное, одной строкой.

## 8. Проверка фактов (обязательна)

Документация продуктового уровня вредна, если врёт. Перед сдачей проверь **каждый** факт по коду и запиши в отчёт, где проверил:

- команда, подкоманда, флаг — есть в парсере аргументов (`apps/codelab_cli/lib/src/cli_args.dart` и аналоги), и снимок вывода получен запуском;
- ключ конфигурации, переменная окружения, путь к файлу — есть в коде загрузки конфигурации;
- код выхода — есть в `exit_codes.dart` или аналоге;
- публичный класс или функция — экспортируется барелем `lib/<package>.dart`;
- зависимость на схеме — есть в `pubspec.yaml`;
- ACP-метод и поле — есть в `codelab_acp_protocol` и `docs/protocols/acp/`;
- ссылка — файл и якорь существуют.

Не смог подтвердить — не пиши. Нашёл расхождение кода со спецификацией `openspec/specs/` — не описывай «как в коде» молча, а сообщи в отчёте (AGENTS.md §3.1).

Если найдено поведение, которое выглядит как баг, — документация описывает, как есть, а баг попадает в отчёт отдельным пунктом.

## 9. Документация меняется вместе с кодом

- Изменение, которое меняет то, что описано в документации (команда, флаг, ключ конфигурации, экран, публичное API, зависимость на схеме), ДОЛЖНО обновить соответствующий документ в том же change.
- Устаревшая документация — дефект, как устаревший комментарий (AGENTS.md §15).
- В `/change` и `/implement` за это отвечает шаг 2а: оркестратор сверяет diff с документацией и передаёт затронутые документы `docs-writer` для точечного обновления и проверки фактов.
- Изменение только документации кодовых проверок не требует (AGENTS.md §21); для `openspec/` — `openspec validate --strict`.
- Правку опубликованного документа (§3) проверяет сборка сайта: локально — `cd site && npm ci && npm run verify`, если установлен Node; в CI — джоб `site`.

## 10. Отчёт исполнителя

В конце работы:
1. созданные и изменённые файлы;
2. таблица «факт → где проверен» (кратко, по группам);
3. команды, реально запущенные для снимков, и что не удалось запустить;
4. оставшиеся маркеры `<!-- screenshot: … -->`;
5. найденные расхождения кода со спецификацией и похожие на баги места;
6. проверен ли синтаксис mermaid инструментом или только визуально.
