Цель: $ARGUMENTS

Ты — оркестратор. Документацию сам не пишешь: передаёшь задачи субагенту **docs-writer** и следишь за качеством. Стандарт — `.claude/skills/codelab-docs/SKILL.md`; прочитай его до шага 1.

0. **Ветка.** Проверь `git branch --show-current`. Документация ведётся в `feature/<name>` от `develop` (AGENTS.md §22). Если ты не в такой ветке — сообщи пользователю и предложи создать; без согласия ветки не создавай.

1. **План.** Определи единицы: указанный путь или, для `all`, все `apps/*`, `packages/dart/*`, `packages/flutter/*`. Для каждой по матрице skill (§2) выбери аудитории и файлы. Покажи пользователю таблицу «единица → аудитории → файлы» и дождись подтверждения. Для `all` предложи порядок: сначала `apps/codelab_cli`, `apps/codelab_desktop`, `apps/codelab_agent` (на них ссылаются `docs/user` и `docs/ops`), затем пакеты по слоям снизу вверх.

2. **docs-writer** — по одной единице на вызов. Передай путь, аудитории, список файлов и ссылки на уже готовые документы соседей. Независимые пакеты можно отдавать параллельно, но не больше трёх одновременно, и никогда — две задачи, которые пишут в один файл (`docs/user/README.md`, `docs/ops/README.md` обновляет только последняя задача пачки или ты сам по отчётам).

3. **architecture-reviewer** — проверка фактов. Передай список новых и изменённых файлов документации и попроси проверить по §8 skill: команды, флаги, ключи, пути, коды выхода, публичные типы, зависимости на схемах, ACP-методы и ссылки — по коду; язык и структура — по §4–§5; отсутствие секретов и личных путей в снимках. Формат ответа — его обычный (APPROVED / CHANGES REQUESTED, BLOCKER/MAJOR/MINOR/NIT). Ложный факт — BLOCKER.

4. Если CHANGES REQUESTED — отдай BLOCKER и MAJOR обратно **docs-writer**, затем снова шаг 3. Максимум 2 итерации; если блокеры остаются — остановись и покажи их пользователю.

5. **Проверки.** Изменена только документация — кодовых проверок не нужно (AGENTS.md §21). Сам проверь, что все относительные ссылки в новых файлах указывают на существующие файлы.

6. **Итог пользователю:** таблица «единица → созданные файлы → аудитории»; оставшиеся маркеры `<!-- screenshot: … -->`; расхождения кода со спецификацией и найденные похожие на баги места (их не чинить, а предложить отдельной задачей); проверялся ли mermaid инструментом; вердикт ревьюера.

Без явной просьбы: не делать `git commit`/`push`, не открывать PR (§19, §22).
