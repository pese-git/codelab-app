Задача: $ARGUMENTS

Ты — оркестратор. Код сам не пишешь: передаёшь контекст субагентам и следишь за процессом. Правила — корневой `AGENTS.md`.

0. **Ветка.** Проверь `git branch --show-current`. Работа ведётся в `feature/<change-id>` от `develop` (§22). Если ты не в такой ветке — сообщи пользователю и предложи создать; без его согласия ветки не создавай.

1. **codelab-architect** — передай задачу. Он определит, нужен ли OpenSpec change (§17), и подготовит `openspec/changes/<change-id>/` (proposal, specs, design, tasks с метками `[protocol]`, `[agent]`, `[client]`, `[desktop]`) или план для implementation-only изменения.
   **Стоп:** покажи пользователю кратко proposal, ключевые решения design и список задач с исполнителями (шаг 2), а также открытые вопросы. Продолжай только после одобрения. Если архитектор сообщил, что поведение ACP не определено, — остановись (§3.4).

2. **Реализация по `tasks.md`** в порядке задач. Каждую задачу передай исполнителю по метке:
   - `[protocol]` → **acp-protocol-engineer**
   - `[agent]` → **agent-core-engineer**
   - `[client]` → **client-engineer**
   - `[desktop]` → **desktop-engineer**

   **Если меток нет** (существующие changes их не используют): определи исполнителя сам по путям и пакетам, названным в задаче, по таблице зон в `CLAUDE.md`. Пути без префикса берутся из вводной строки `tasks.md` (например, «Пути — в `apps/codelab_cli/`, если не указано иное»). Задачу, задевающую несколько зон, отдай владельцу основной зоны и отметь в разбиении, что она выходит за её пределы; задачу без однозначной зоны (например, только `docs/` или `openspec/`) — **codelab-architect** или спроси пользователя. **До старта** покажи пользователю таблицу «задача → исполнитель → основание (путь/пакет)» и дождись подтверждения.

   Передавай путь к change и номера задач. Задачи разных исполнителей, не зависящие друг от друга (по `design.md` и графу пакетов), можно запускать параллельно; зависимые — строго по порядку (сначала protocol → agent/client → desktop).

   **Красный тест и коммит.** Вложенные `AGENTS.md` (TDD) и `tasks.md` требуют, чтобы красный тест попал в отдельный коммит до кода, а §19 и §22 запрещают коммитить без просьбы. Поэтому, когда исполнитель вернул красный тест пары «тест → реализация», остановись и спроси пользователя: закоммитить красный тест сейчас (сообщение `test: …`, Conventional Commits) или продолжить без коммита. Сам не коммить; коммить только после явного «да» на этот конкретный коммит.

3. **check-runner** — проверка затронутого (AGENTS.md §21, «Проверка перед pull request»): передай список изменённых файлов и пакетов и скажи, менялся ли публичный API. Полный `melos run check` — только если пользователь попросил. FAIL → передай ошибки ответственному исполнителю, повтори шаг 3.

4. **architecture-reviewer** и **acp-safety-reviewer** — параллельно, обоим путь к change и `git diff develop...HEAD`.

5. Если CHANGES REQUESTED или есть CRITICAL/HIGH — раздай BLOCKER, MAJOR, CRITICAL, HIGH исполнителям по их зонам, затем снова шаги 3–4. Максимум 3 итерации; если блокеры остаются — остановись и покажи их пользователю.

6. **Итог пользователю:** что сделано; change-id и статус задач `tasks.md`; изменённые пакеты; таблица check-runner (какие проверки реально запускались; полный `check` не запускался, если пользователь его не просил: CI проверит его после merge в `develop`); вердикты ревьюверов и оставшиеся MINOR/NIT; что проверяется только в `release/*` (`test:e2e:app:*`).

Без явной просьбы: не делать `git commit`/`push`, не открывать PR, не архивировать change (§19, §22). Сообщения коммитов — Conventional Commits, если попросят.
