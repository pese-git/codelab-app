# Формат golden-фикстуры

Глава описывает файл фикстуры так, как его читает загрузчик: поля, кто из драйверов какое поле использует, как кадры сравниваются и что делает `_schema.json`. Формат принят в [`14-golden-fixtures.md`](../../../../docs/architecture/proposals/agent-core/14-golden-fixtures.md), требования — в спецификации [`acp-golden-fixtures`](../../../../openspec/specs/acp-golden-fixtures/spec.md). Если они расходятся с кодом, прав код: глава написана по `lib/src/fixtures/fixture.dart` и `lib/src/fixtures/matcher.dart`.

## Что такое фикстура

Фикстура — один JSON-файл с одним сценарием обмена между клиентом и агентом по ACP (Agent Client Protocol, протокол, по которому клиент и агент обмениваются сообщениями JSON-RPC). В файле три части: начальные условия (`setup`), скрипт ответов модели (`llm`) и упорядоченный список кадров (`frames`). Кадр — одно сообщение JSON-RPC с направлением: `c2a` (клиент → агент) или `a2c` (агент → клиент).

Один файл проверяет обе стороны. Драйвер клиента играет агента: подаёт клиенту кадры `a2c` и ждёт от него кадры `c2a`. Драйвер агента играет клиента: шлёт агенту кадры `c2a` и ждёт кадры `a2c`. Поле `roles` сужает фикстуру до одной стороны.

Корпус лежит плоско в `packages/dart/codelab_acp_testing/fixtures/acp/`: подкаталоги запрещены, имя файла — `<область>-<сценарий>[-<исход>].json` в kebab-case (`prompt-text-end-turn.json`, `tool-read-range.json`). Файлы с `_` в начале — не фикстуры (`_schema.json`). На 2026-11-25 в корпусе 85 фикстур: 45 для обеих ролей, 37 только для агента, 3 только для клиента (`acp/errors-unknown-session-update-tolerated`, `acp/prompt-update-plan`, `acp/tool-kind-unknown-tolerated`).

Пример целиком — [`fixtures/acp/prompt-text-end-turn.json`](../fixtures/acp/prompt-text-end-turn.json): промпт, модель отвечает текстом, агент присылает дельты, необязательное название сессии и ответ `end_turn`.

## Верхний уровень

| Поле | Обязательно | Смысл |
|---|---|---|
| `id` | да | `acp/<имя файла без .json>`; загрузчик сверяет с именем файла |
| `spec` | да, непустой | ссылки `<файл>.md#<якорь>` на разделы `docs/protocols/acp/protocol/`, которые обосновывают кадры |
| `description` | да | что проверяет сценарий |
| `goals` | нет | id целей паритета; загрузчик их только хранит |
| `extensions` | нет | расширения CodeLab, которые использует фикстура (`usage`, `usageLedger`, `task` …) |
| `roles` | нет | `["agent"]`, `["client"]` или оба; по умолчанию оба |
| `setup` | да | начальные условия |
| `llm` | нет | скрипт модели; читает только агентский прогон |
| `frames` | да, непустой | кадры по порядку |
| `normalize` | нет | дополнительные правила замены перед сравнением |
| `after` | нет | ожидаемое состояние после сценария |

Лишний ключ на любом уровне — ошибка загрузки. Это сделано намеренно: опечатка в имени поля иначе дала бы фикстуру, которая молча проверяет меньше, чем задумано.

Поле `extensions` нужно по двум причинам. Тест корпуса (FIX-4) запрещает `_meta.codelab`, `data.codelab` и методы `_codelab/*` в кадрах фикстуры без `extensions`. А клиентский драйвер читает метку `usageLedger`: с ней он объявляет в ответе на `initialize` возможность запроса журнала usage.

## `setup`: начальные условия

Не каждый драйвер читает каждое поле. Колонка «кто читает» показывает, на какой стороне поле работает.

| Поле | Кто читает | Смысл |
|---|---|---|
| `cwd` | клиент | рабочая папка сценария, по умолчанию `/work/fixture`; в кадрах пишется `${cwd}`. Агентский драйвер значение не использует: он создаёт временный каталог и подставляет его |
| `files` | клиент и агент | `{"a.txt": "содержимое"}`. Клиент кладёт файлы в свою файловую систему в памяти (ответы на `fs/*`). Агентский драйвер пишет их во временный `cwd`, чтобы работали локальные `ls` и `search`; содержимое файла агент получает кадрами `fs/read_text_file` фикстуры |
| `profile` | агент | профиль хоста агента, по умолчанию `agent-serve` |
| `mode` | клиент и агент | режим сессии на старте. Агент получает его от фабрики (`AgentFixtureSetup.mode`). Клиентский драйвер отвечает на `session/new` блоком `modes` из этого одного режима |
| `config` | агент | фрагмент конфигурации агента как JSON; разбирает фабрика агента, неизвестный ключ — громкий провал |
| `clientCapabilities` | клиент и агент | что клиент объявляет в `initialize`. Агентский драйвер шлёт объект как есть (по умолчанию `fs` на чтение и запись и `terminal: true`). Клиентский сверяет его как подмножество |
| `terminal` | клиент | сценарные процессы: `{"/bin/sh -c dart test": {"output": "…", "exitCode": 0}}`; ключ — команда с аргументами через пробел или только команда |
| `skipInitialize` | клиент и агент | `true` — кадры `initialize` и `session/new` фикстура пишет сама |
| `sessions` | агент | журналы сессий до сценария: `{"<sessionId>": [заголовок, записи…]}`; `${cwd}` подставляется |
| `mcp` | агент | поддельные MCP-серверы: `{"<имя>": {"era": "modern"\|"legacy", "tools": […], "results": {…}}}` |
| `transport` | транспортный драйвер | `{"kind": "stdio"}` или `{"kind": "ws", "attempts": [{"authorization": "none"\|"wrong"\|"valid", "expectStatus": 401}]}` |
| `web` | никто | загружается и хранится, но ни один драйвер его не читает; `test-scenario` пропускает фикстуры с `setup.web` |

Фикстура с `setup.transport` не играется в памяти: агентский драйвер её пропускает, её берёт транспортный драйвер ([глава 2](02-drivers.md#транспортный-драйвер-и-test-scenario)). Для `attempts` обязательны оба поля, и они допустимы только у `ws`.

### Стандартный handshake

Если `skipInitialize` не задан, драйвер сам делает рукопожатие до первого кадра фикстуры, поэтому первый кадр сценария — уже действие пользователя. Кадры рукопожатия получают отрицательные индексы (у агентского драйвера от `-5`, у клиентского от `-4`), и в отчёте о провале это видно: `handshake frame`.

- Агентский драйвер шлёт `initialize` с `id` 0 и `session/new` с `id` 1. Из ответа на `session/new` он захватывает `sessionId`. Необязательный `available_commands_update` после ответа входит в рукопожатие. Поэтому числовые `id` запросов клиента в фикстуре начинаются с 2 (`session-list-cwd-filter.json`) либо берутся матчером `$capture`.
- Клиентский драйвер ждёт от клиента `initialize` и `session/new` и отвечает на них сам: протокол версии 1, `sessionId` всегда `fixture-session-1` (константа `standardFixtureSessionId`).

## `frames`: кадры

| Поле | Смысл |
|---|---|
| `dir` | `c2a` или `a2c` |
| `frame` | JSON-RPC-объект кадра: запрос, уведомление или ответ; допустимы матчеры и переменные |
| `unordered` | вместо `frame`: непустой массив кадров одного направления, которые могут прийти в любом порядке. Ровно одно из `frame` и `unordered` |
| `note` | пояснение для человека; попадает в отчёт о провале |
| `optional` | кадр может не прийти (название сессии, рассуждения модели) |
| `repeat` | единственное допустимое значение — `"+"`: кадр повторяется один раз или больше (дельты текста) |
| `match` | только вместе с `repeat`: `{"$text": "…"}` — склейка `params.update.content.text` всех повторов должна равняться строке |

Пример кадра с `repeat` и `match` — дельты ответа агента, склейка которых дана одной строкой (`fixtures/acp/prompt-text-end-turn.json`):

```json
{
  "dir": "a2c",
  "frame": {
    "jsonrpc": "2.0",
    "method": "session/update",
    "params": {
      "sessionId": "${sessionId}",
      "update": {
        "sessionUpdate": "agent_message_chunk",
        "content": {"type": "text", "text": {"$any": true}}
      }
    }
  },
  "repeat": "+",
  "match": {"$text": "Привет! Чем помочь?"}
}
```

Правила работы с `optional` и `repeat` — в [главе 2](02-drivers.md#открытые-шаблоны-optional-и-repeat).

## `llm`: скрипт модели

Блок задаёт ответы модели по шагам: n-й запрос к модели получает n-й шаг. Читает его только агентский прогон; клиентский игнорирует. Загрузчик проверяет структуру, а выполняет блок `ScriptedStreamFunction` из `codelab_agent_core` ([глава ядра о тестировании](../../codelab_agent_core/doc/12-testing.md), формат шага — [§14.7](../../../../docs/architecture/proposals/agent-core/14-golden-fixtures.md#147-scripted-модель-в-фикстуре)).

| Поле | Смысл |
|---|---|
| `model` | `provider`, `modelId`, `contextWindow` и необязательные цены `cost` (`input` и `output` обязательны, `cacheRead` и `cacheWrite` нет; числа не меньше нуля) |
| `steps[].expect` | утверждение о запросе к модели (`lastMessage`, `toolResult`, `tools`); загрузчик его не разбирает |
| `steps[].reply` | блоки ответа; в каждом блоке ровно одно из `text`, `thinking`, `toolCall` (`id`, `name`, `arguments`) |
| `steps[].error` | вместо `reply`: `{"class": "auth", "message": "401"}`; `reply` и `error` вместе — ошибка загрузки |
| `steps[].stopReason` | `stop`, `toolUse`, `length`, `error`, `aborted` |
| `steps[].delayMs`, `waitForCancel`, `usage` | пауза, ожидание отмены, `usage` ответа |

Пример шага из `fixtures/acp/tool-read-range.json`: модель вызывает инструмент, затем отвечает текстом. Шаг с `toolCall` заканчивается `toolUse`, последний — `stop`.

## `after`: состояние после сценария

- `after.files` — `{"README.md": "# bar\n"}`: ожидаемое содержимое файлов рабочей папки. Клиентский драйвер сверяет его с файловой системой клиента. Агентский — с последним `content` кадра `fs/write_text_file` на этот путь, а если записи не было, с `setup.files`.
- `after.mcpCalls` — `{"<сервер>": [{"name": "echo", "arguments": {…}}]}`: точный список вызовов `tools/call`, которые получил поддельный MCP-сервер; пустой список значит «вызовов не было». Только агентский прогон: драйвер отдаёт поле фабрике, а проверяет `AgentUnderTest.verify()` фабрики.

## Переменные, нормализация и матчеры

Сравнение точное. Ожидаемый и фактический кадры проходят одинаковую нормализацию, затем сравниваются по правилам ниже. Порядок ключей объекта не важен, порядок элементов массива важен, лишний ключ в фактическом кадре — расхождение.

### Переменные

| Запись | Значение |
|---|---|
| `${cwd}` | рабочая папка прогона. В фактическом кадре префикс `cwd` в строках заменяется на `${cwd}`, разделители пути приводятся к `/` |
| `${sessionId}` | id сессии из ответа на `session/new` |
| `${имя}` | значение, захваченное матчером `{"$capture": "имя"}` |

Строка, которая целиком состоит из одной переменной, сохраняет тип значения: `"id": "${read1}"` даёт то значение `id`, которое захвачено (число или строку). Неизвестная переменная — `FixtureMatchException: unknown variable ${имя}`.

### Время

`"<ts>"` в ожидаемом кадре означает «время». Фактическое значение подходит, если оно строка и либо лежит в поле `updatedAt`, `timestamp` или `created`, либо похоже на дату ISO-8601 (`2026-01-01T00:00:00Z`). Клиентскому драйверу, который отправляет такой кадр, вместо `<ts>` подставляется фиксированное время `2026-01-01T00:00:00Z`.

### Матчеры

Матчер — объект ровно с одним ключом, который начинается с `$`. Он ослабляет сравнение только на своём месте. Неизвестный `$`-ключ — `FixtureMatchException: unknown matcher "$…"`.

| Матчер | Что проверяет |
|---|---|
| `{"$any": true}` | любое значение, но ключ обязан быть. `{"$any": []}` — то же, а клиентский драйвер отправляет клиенту `[]` вместо заглушки (нужно, когда клиент разбирает значение как список или объект) |
| `{"$absent": true}` | ключа быть не должно; допустим только как значение ключа объекта |
| `{"$capture": "имя"}` | любое значение; сохраняется в `${имя}`. Захваты записываются, только если в кадре нет расхождений |
| `{"$regex": "…"}` | строка, в которой есть совпадение с регулярным выражением |
| `{"$contains": "…"}` | строка, содержащая подстроку (в подстроке работают переменные) |
| `{"$partial": {…}}` | объект, в котором есть перечисленные ключи; лишние допустимы |
| `{"$oneOf": […]}` | значение совпадает с одним из вариантов (непустой список) |
| `{"$repeat": {"text": "x", "times": 2097152}}` | строка `text`, повторённая `times` раз. Для мегабайтных строк (`acp/stdio-framing-large-line`) |

`_meta` всегда сравнивается как `$partial`: спецификация ACP разрешает реализациям добавлять туда свои ключи.

`$text` в этом списке нет: это не матчер на месте значения, а ключ поля `match` кадра с `repeat`. Если написать `{"$text": …}` внутри `frame`, матчер назовёт его неизвестным. `$regex` и `$absent` в корпусе пока не встречаются, их проверяют тесты `matcher_test.dart`.

Фрагменты из корпуса:

`$capture` и подстановка — id запроса агента не фиксирован, поэтому ответ клиента ссылается на захваченное значение (`fixtures/acp/tool-read-range.json`):

```json
{"dir": "a2c", "frame": {"jsonrpc": "2.0", "id": {"$capture": "read1"}, "method": "fs/read_text_file",
  "params": {"sessionId": "${sessionId}", "path": "${cwd}/a.txt", "line": 10, "limit": {"$oneOf": [5, 6]}}}},
{"dir": "c2a", "frame": {"jsonrpc": "2.0", "id": "${read1}", "result": {"content": "line 10\nline 11\nline 12\nline 13\nline 14"}}}
```

`unordered` — параллельные вызовы, порядок статусов не задан (`fixtures/acp/prompt-parallel-tool-calls.json`, кадр с `"unordered": [ … ]`). Драйвер подбирает такое соответствие кадров шаблонам, при котором совпадают все.

### `normalize.replace`: правки перед сравнением

Когда в кадре есть переменная часть, которую не выразить матчером (числа внутри текста), `normalize` заменяет её в обеих сторонах. Правило — `path` (JSON-путь вида `$.params.update.content.text`), `regex`, `with`. Заменяются только строки по указанному пути. Пример из `fixtures/acp/compact-usage-summary.json`:

```json
"normalize": {
  "replace": [
    {
      "path": "$.params.update.content.text",
      "regex": "(?<=^Compacted: )\\d+ → \\d+(?= tokens\\.$)",
      "with": "<N> → <N>"
    }
  ]
}
```

## Загрузчик

`loadFixtureFile(путь)` читает один файл, `loadFixtureCorpus({directory})` — каталог: все `*.json`, кроме файлов с `_`, отсортированные по `id`. Подкаталог в каталоге корпуса — `FixtureFormatException`. Без аргумента каталог — `defaultFixtureCorpusDirectory()`: он находится через конфигурацию пакетов (`Isolate.resolvePackageUriSync`), а если её нет (под `flutter test`), по ближайшему `.dart_tool/package_config.json` выше текущей папки. Поэтому тесты не зависят от текущего каталога.

`AcpFixture.fromJson(json, fileName: …)` — разбор из уже прочитанного объекта; именно его используют тесты, которые правят копию фикстуры в памяти.

Загрузчик проверяет и структуру, и часть смысла. Каждое нарушение — `FixtureFormatException` с файлом, JSON-путём и причиной:

```text
FixtureFormatException: prompt-text-end-turn.json: $.frames[1].dir: expected "c2a" or "a2c", got "a2d"
FixtureFormatException: unk.json: $.id: expected "acp/unk" to match the file, got "acp/prompt-text-end-turn"
```

Что проверяется помимо типов полей и неизвестных ключей: `id` равен `acp/<имя файла>`; `spec` и `frames` не пусты; `roles` без дубликатов и только `agent`/`client`; в кадре ровно одно из `frame` и `unordered`; `repeat` равен `"+"`; `match` только с `repeat` и только вида `{"$text": "…"}`; в шаге `llm` не вместе `reply` и `error`; в блоке ответа ровно один ключ; `stopReason` из списка; цены не отрицательны; `normalize.replace[].path` начинается с `$`, а `regex` компилируется; `setup.transport.kind` равен `stdio` или `ws`, `attempts` только у `ws`; `setup.mcp.<имя>.era` равен `modern` или `legacy`.

Загрузчик не проверяет, что ссылки `spec` указывают на существующий раздел, и не сверяет кадры с протоколом. Первое делает тест корпуса (FIX-1, [глава 3](03-testing-and-coverage.md#инварианты-корпуса)), второе — драйверы при проигрывании.

## `_schema.json`

`fixtures/acp/_schema.json` — формальное описание формата (JSON Schema draft 2020-12, `additionalProperties: false` на каждом закрытом объекте). Он нужен автору фикстуры и редактору с проверкой схемы; загрузчик его не читает, а проверяет формат собственным кодом. Чтобы они не разошлись, `fixtures_schema_sync_test.dart` сравнивает схему с таблицей `fixtureFormatKeys` в `fixture.dart`: множества свойств каждого объекта, обязательные поля верхнего уровня, значения `enum` (`roles`, `dir`, `stopReason`, `mcpServer.era`), а также форму `setup.mcp`, `after.mcpCalls` и `llm.model.cost`.

Тест не сравнивает всё подряд. Типы значений, `pattern`, `minimum` и `default` схемы и загрузчика могут разойтись, не вызвав падения. Известные расхождения:

- схема требует `id` по шаблону `^acp/[a-z0-9]+(-[a-z0-9]+)*$`, а загрузчик проверяет только совпадение с именем файла: файл `Other_Name.json` с `id` `acp/Other_Name` загрузится;
- схема объявляет `mode` по умолчанию `standard`, а в коде значение по умолчанию — `null`: «режим профиля» для агента и отсутствие блока `modes` в ответе клиентского драйвера.

Правила правки формата — в [рецепте «Как изменить формат»](04-recipes-and-troubleshooting.md#как-изменить-формат-фикстуры).
