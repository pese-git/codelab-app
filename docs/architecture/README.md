# Архитектура CodeLab

Каталог содержит архитектурную документацию CodeLab — monorepo из трёх продуктов: настольного клиента CodeLab app (`apps/codelab_desktop`, Flutter), терминального клиента `codelab` (`apps/codelab_cli`) и Dart-агента `codelab-agent` (`apps/codelab_agent`), ядро которого встраивается и в процесс клиента. Клиенты и агент говорят по ACP (Agent Client Protocol).

Документы предназначены для:

* разработчиков;
* AI coding agents;
* ревью кода;
* проектирования новых фич;
* анализа архитектурных изменений.

Обязательные правила репозитория — корневой [`AGENTS.md`](../../AGENTS.md); вложенные `AGENTS.md` пакетов и приложений уточняют правила своих каталогов.

Поведение продукта — [`openspec/specs/`](../../openspec/specs/), активные изменения — [`openspec/changes/`](../../openspec/changes/).

Референсная спецификация ACP — `docs/protocols/acp/` (схема сообщений — `protocol/17-Schema.md`); её не изменяют (`AGENTS.md` §3.4).

## 1. Назначение архитектурной документации

`AGENTS.md` определяет, **что необходимо соблюдать**.

`docs/architecture/` объясняет:

* как устроена система;
* где проходят архитектурные границы;
* какой компонент владеет тем или иным поведением;
* как взаимодействуют слои;
* какие архитектурные инварианты ДОЛЖНЫ сохраняться;
* почему выбраны те или иные решения.

OpenSpec определяет **поведение продукта и контракты**.

Таким образом:

```text id="gh7bl1"
AGENTS.md
    │
    └── обязательные инженерные правила

docs/architecture/
    │
    └── устройство системы и архитектурные решения

openspec/specs/
    │
    └── ожидаемое поведение и контракты

openspec/changes/
    │
    └── проектируемые изменения
```

## 2. Архитектурные принципы

Архитектура проекта строится вокруг следующих принципов.

### Явные границы

Внешние системы ДОЛЖНЫ быть отделены от логики приложения.

Внешние границы:

* ACP;
* файловая система;
* сеть;
* хранение данных (persistence);
* защищённое хранилище секретов;
* операционная система;
* нативные API;
* внешние процессы.

Flutter UI НЕ ДОЛЖЕН напрямую управлять этими системами.

### Стороны и пакеты

Пакеты-библиотеки называются по схеме `codelab_<сторона>_<слой>` ([ADR-0002](adr/0002-name-packages-codelab-side-layer.md)): сторона — `acp` (общий протокольный слой), `client` или `agent`; слой — `core` (логика без IO), `io` (адаптеры `dart:io`), `acp` (проекция стороны в протокол) или предметное имя у общего слоя. Пакеты без стороны — мосты `codelab_setup` и `codelab_embedded`, через которые клиенты получают агентскую сторону, кит виджетов `codelab_ui` и сторож `codelab_architecture_tests`.

Рабочие зависимости между пакетами (`dependencies` в `pubspec.yaml`; показаны основные рёбра; пакеты зависят и от нижележащих пакетов напрямую, где это нужно):

```text id="k2p8sd"
клиентская сторона
  apps/codelab_desktop ─► codelab_ui
  apps/codelab_desktop, apps/codelab_cli
      ─► codelab_client_io ─► codelab_client_core ─► codelab_client_acp
      ─► codelab_acp_transports ─► codelab_acp_protocol

мосты (только через них клиенты получают агента)
  apps/codelab_desktop, apps/codelab_cli
      ─► codelab_setup ────► codelab_agent_io ─► codelab_agent_core
      ─► codelab_embedded ─► codelab_agent_acp, codelab_agent_mcp, codelab_agent_io

агентская сторона
  apps/codelab_agent ─► codelab_agent_acp, codelab_agent_mcp, codelab_agent_io
  codelab_agent_acp ─► codelab_agent_core, codelab_acp_transports ─► codelab_acp_protocol
  codelab_agent_mcp, codelab_agent_io ─► codelab_agent_core
```

Правила пакетов (направление зависимостей, чистый Dart в `packages/dart/`, запрет `package:codelab_agent_*` в клиентах, `codelab_acp_testing` только как `dev_dependency`, web-безопасные барели) задаёт корневой `AGENTS.md` §5; проверяемые сторожем запреты и allowlist-ы — требование spec [`workspace-architecture`](../../openspec/specs/workspace-architecture/spec.md) «Автоматический сторож границ пакетов», инварианты ядра — PKG-1…PKG-6 ([`proposals/agent-core/01-layers-and-packages.md`](proposals/agent-core/01-layers-and-packages.md) §1.5). Почему граф устроен так:

* пакеты не знают приложений и не образуют циклов — иначе общий слой нельзя переиспользовать во втором клиенте (`apps/codelab_cli`) и тестировать без приложения;
* клиенты получают агента только через мосты — клиентский код говорит с агентом по ACP и не ветвится по виду агента, а мосты остаются единственным местом, где меняется сборка агентской стороны (ADR-0002, §53 `layers-and-dependencies.md`);
* ядро агента не знает пакетов проекта и `dart:io` — одно ядро собирается в бинаре, в процессе клиента и в web; узкий allowlist держит поверхность сторонних зависимостей ядра под контролем;
* `codelab_acp_testing` не входит в рабочие зависимости — фикстуры и двойники не попадают в релизную сборку; исключение `apps/codelab_cli` нужно рабочей команде `test-scenario`.

Подробно — [`layers-and-dependencies.md`](layers-and-dependencies.md) §2 и §53, корневой `AGENTS.md` §5. Сайт `site/` (Astro, [ADR-0003](adr/0003-build-project-site-with-astro-in-monorepo.md)) — вне pub workspace и Melos, в граф пакетов не входит.

Где в коде. Члены pub workspace — `workspace:` корневого `pubspec.yaml`; границы проверяет сторож `packages/dart/codelab_architecture_tests` (`melos run guard`): правила импортов — `test/support/rules.dart`, allowlist-ы зависимостей — `test/pubspec_allowlist_test.dart`, имена пакетов — `package_naming_test.dart`.

### Feature-first

Код приложения организуется прежде всего вокруг пользовательских и прикладных возможностей, а не вокруг технических типов файлов.

Предпочтительна структура по фичам:

```text id="kn3tkv"
features/
├── workbench/
├── settings/
├── onboarding/
└── terminal/
```

а не глобальная структура:

```text id="uf8ls2"
controllers/
services/
repositories/
models/
widgets/
```

Внутри сложной фичи МОЖНО разделить код на:

```text id="8zn3l3"
domain/
application/
infrastructure/
presentation/
```

Фича не обязана иметь все эти слои; пустые слои ЗАПРЕЩЕНЫ (`AGENTS.md` §6).

В коде фичи `apps/codelab_desktop/lib/features/` — `workbench`, `settings`, `onboarding`, `project_files`, `terminal`, `protocol`, `usage`; в них есть только `application/` и `presentation/`, а клиентская логика без UI живёт в пакетах `codelab_client_*` ([`layers-and-dependencies.md`](layers-and-dependencies.md) §11, §12).

### Направление зависимостей

Основное направление зависимостей внутри приложения:

```text id="ubqzy4"
presentation
     │
     ▼
application
     │
     ▼
domain

infrastructure
     │
     └────► application / domain
```

Внешние технологии располагаются на краях архитектуры.

---

### ACP — внешняя граница протокола

Проводная модель ACP — не модель UI.

```text id="ofop1f"
ACP
 │
 ▼
Протокол
 │
 ▼
Транспорт
 │
 ▼
Application
 │
 ▼
Состояние приложения
 │
 ▼
Presentation
```

Изменения ACP НЕ ДОЛЖНЫ без необходимости распространяться по всему приложению.

Клиент говорит с агентом только по ACP — и с внешним, и со встроенным: встроенный агент отличается лишь транспортом (`InProcessAcpLink` вместо stdio или WebSocket), а не контрактом, поэтому клиентский код не ветвится по виду агента ([`acp-boundary.md`](acp-boundary.md), [ADR-0001](adr/0001-embed-dart-agent-core-behind-acp.md)).

---

### Явное состояние

Сложное состояние приложения ДОЛЖНО моделироваться явно.

Особенно это относится к:

* жизненному циклу соединения;
* жизненному циклу сессии;
* выполнению промпта;
* потоковым событиям;
* отмене;
* переподключению;
* запросам разрешений.

СЛЕДУЕТ избегать набора независимых флагов, допускающих невозможные состояния.

---

### Контролируемые побочные эффекты

Побочные эффекты ДОЛЖНЫ иметь явного владельца.

Например:

```text id="20m91d"
filesystem
network
ACP transport
secure storage
process execution
native APIs
```

НЕ ДОЛЖНЫ вызываться произвольно из виджетов или domain.

---

### Пропорциональность архитектуры

Архитектура ДОЛЖНА защищать границы, а не увеличивать количество файлов.

Не требуется создавать:

```text id="m3ydt2"
Repository
RepositoryImpl
Service
ServiceImpl
UseCase
Manager
```

для каждой простой операции.

Абстракция вводится тогда, когда есть реальная архитектурная граница или выигрыш в тестируемости (`AGENTS.md` §13).

## 5. Архитектурные инварианты

Следующие инварианты ДОЛЖНЫ сохраняться независимо от конкретной реализации.

### INV-001 — Domain независим от Flutter

Код domain не зависит от:

* Flutter;
* виджетов;
* `BuildContext`;
* навигации;
* диалогов.

---

### INV-002 — UI не управляет инфраструктурой напрямую

Виджеты не обращаются напрямую к:

* ACP-транспорту;
* файловой системе;
* хранению данных;
* защищённому хранилищу секретов;
* API платформы;
* внешним процессам.

---

### INV-003 — ACP DTO не является состоянием приложения

Проводное представление ACP НЕ ДОЛЖНО становиться внутренней моделью всего приложения.

Изменения, специфичные для протокола, локализуются на границе протокола и application.

---

### INV-004 — Жизненный цикл сессии явный

Жизненный цикл соединения и сессии моделируется явным состоянием.

Невозможные комбинации состояний НЕ ДОЛЖНЫ быть представимы там, где это практически возможно.

---

### INV-005 — Устаревшие события не изменяют актуальное состояние

Событие старого:

* соединения;
* сессии;
* запроса;
* вызова инструмента;

НЕ ДОЛЖНО случайно изменить новое состояние.

---

### INV-006 — У побочных эффектов есть владелец

Долгоживущая операция, подписка или внешний ресурс ДОЛЖНЫ иметь:

* владельца;
* жизненный цикл;
* стратегию очистки и закрытия.

---

### INV-007 — Политика разрешений находится вне UI

Presentation получает решение пользователя, но не определяет политику безопасности.

---

### INV-008 — Неизвестное опасное действие запрещается

Для опасной возможности действует запрет по умолчанию (deny-by-default), если спецификация явно не определяет другое поведение.

---

### INV-009 — Архитектура пропорциональна задаче

ЗАПРЕЩЕНО добавлять абстракцию только ради соблюдения шаблона проектирования.

Каждая абстракция ДОЛЖНА иметь понятную ответственность.

---

### INV-010 — Существующий шаблон предпочтительнее нового

Новый фреймворк или архитектурный шаблон не вводится, если утверждённое решение уже закрывает задачу.

---

## 6. Изменение архитектуры

Архитектурным считается изменение, которое затрагивает:

* направление зависимостей;
* границы пакетов;
* границы фич;
* стратегию управления состоянием;
* стратегию внедрения зависимостей;
* границу ACP;
* стратегию хранения данных;
* модель разрешений и безопасности;
* жизненный цикл соединения и сессии;
* модель интеграции с платформой;
* значимую сквозную абстракцию.

Такие изменения НЕ СЛЕДУЕТ выполнять попутным рефакторингом.

Перед реализацией ДОЛЖНО быть определено:

1. Какую проблему решает изменение.
2. Почему существующей архитектуры недостаточно.
3. Какие границы затрагиваются.
4. Какие альтернативы рассматривались.
5. Как изменится тестирование.
6. Есть ли влияние на миграцию и совместимость.

Если решение долгоживущее и существенно влияет на устройство системы, его СЛЕДУЕТ зафиксировать в ADR.

---

## 7. ADR

Architecture Decision Records СЛЕДУЕТ хранить в:

`docs/architecture/adr/`

Формат имени — последовательный номер и краткое название решения:

```text id="jvwy10"
docs/architecture/adr/
├── 0001-<decision>.md
├── 0002-<decision>.md
└── ...
```

Реестр решений, статусы и шаблон — [`adr/README.md`](adr/README.md) §27, [`adr/template.md`](adr/template.md).

ADR нужен для решений уровня:

* выбор фреймворка управления состоянием;
* выбор технологии хранения данных;
* изменение границ пакетов;
* изменение архитектуры сессий;
* введение нового транспорта;
* изменение модели безопасности;
* значимая стратегия интеграции с desktop.

ADR не требуется для обычных деталей реализации.

## 8. Связь ADR и OpenSpec

ADR и OpenSpec решают разные задачи.

```text id="3pnubv"
OpenSpec
    │
    └── что система должна делать

ADR
    │
    └── почему выбрано архитектурное решение

Architecture docs
    │
    └── как система устроена сейчас
```

Одно изменение может требовать одновременно:

* OpenSpec change;
* ADR;
* обновления архитектурной документации;
* изменения кода.

После принятия архитектурного решения основная документация ДОЛЖНА описывать **актуальное состояние**, чтобы для понимания текущей архитектуры не требовалось читать всю историю ADR.

---

## 9. Поддержание документации

Архитектурная документация — часть проекта и ДОЛЖНА обновляться вместе с архитектурой.

При изменении архитектурного поведения агент ДОЛЖЕН проверить, нужно ли обновить:

* `AGENTS.md`;
* соответствующий документ в `docs/architecture/`;
* ADR;
* OpenSpec;
* диаграммы;
* тесты.

Документация НЕ ДОЛЖНА описывать архитектуру, которой больше нет.

При конфликте документации с кодом ЗАПРЕЩЕНО молча исправлять документацию под код.

Сначала ДОЛЖНО быть определено, что является ожидаемым поведением и утверждённой архитектурой.

## 10. Основной принцип

Архитектура клиентов CodeLab ДОЛЖНА обеспечивать следующий поток:

```text id="lbrz8f"
┌──────────────────────────┐
│       Presentation       │
│   Flutter UI / терминал  │
└────────────┬─────────────┘
             │ намерение / состояние
             ▼
┌──────────────────────────┐
│       Application        │
│  оркестрация / политики  │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│          Domain          │
│  понятия / инварианты    │
└──────────────────────────┘

             ▲
             │ порты
             │
┌────────────┴─────────────┐
│      Infrastructure      │
├──────────────────────────┤
│ ACP │ FS │ Storage │ OS  │
└──────────────────────────┘
```

В коде application и domain клиентов — пакеты `codelab_client_acp` и `codelab_client_core` (без UI, общие для app и CLI); Cubit-ы app в `features/*/application/` только отображают их состояние; инфраструктура — `codelab_acp_transports`, `codelab_client_io` и адаптеры платформы app в `apps/codelab_desktop/lib/core/platform/` и `lib/app/`; presentation — фичи app и терминальный вывод `apps/codelab_cli`. У агента та же идея: ядро `codelab_agent_core` получает всё внешнее портами, реализации даёт хост ([`layers-and-dependencies.md`](layers-and-dependencies.md) §2, §53).

Главная цель этой структуры — не формальное соблюдение Clean Architecture.

Цель — обеспечить:

* предсказуемое состояние;
* изоляцию ACP;
* контролируемые побочные эффекты;
* безопасность действий агента;
* тестируемость логики приложения;
* устойчивость потоковых событий и переподключения;
* развитие клиентов без неконтролируемой связанности.
