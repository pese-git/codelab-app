## 16.1. Что не входит в MVP и почему

| Возможность | Почему не сейчас | Этап (proposal §9.1) |
|---|---|---|
| Skills (Markdown-инструкции с frontmatter) и шаблоны промптов как команды | нет у Python-агента; сначала цели Must. Спецификация — §17.2 | шаблоны — 8; skills — после 9 |
| Субагенты (инструмент `task`) | отдельные сессии, отмена и вывод дочерних ходов — сложная оркестрация; мультиагентность у Python-агента только в backlog. Спецификация — §17.3 | после 9 |
| Web-инструменты (`web_fetch`, `web_search`) | новый канал утечки данных и недоверенного контента; нужен отдельный уровень `network` и защита от SSRF. Спецификация — §17.1 | после 9 |
| Правки по якорям строк (адресация строки хешем её содержимого) | `edit` с точным единственным совпадением закрывает паритет; формат патчей — отдельное решение | после 9; спецификация — §17.11.3 |
| Структурное сжатие (скрытие записей с раскрытием по запросу модели) | классический компактор (§9) проще и проверяется тестами; структурный требует инструмента раскрытия и сложной проекции | после 9; спецификация — §17.13.4 |
| Правила посреди стрима (прерывание ответа модели по шаблону в тексте) | требует продолжения прерванного ответа, которого нет в MVP | после 9 |
| Песочница уровня ОС (seatbelt, namespaces, Job Objects) | `BoundedEnv`, разрешения и профили закрывают известные дефекты границы папки; песочница — этап укрепления безопасности | после 9 |
| Собственный протокол рядом с ACP | ACP уже связывает ядро и клиентов во всех режимах; второй протокол удвоит сопровождение. A2A (§17.15) — не второй протокол клиента: он связывает агента с другими агентами, а клиенты по-прежнему говорят только ACP | не планируется |
| A2A: удалённые агенты как субагенты и агент как A2A-сервер (E-22, E-23) | нужен готовый `task` с продолжением (C-06, C-17); сервер открывает агента с shell для других программ — отдельная модель угроз. Спецификация — §17.15 | после 9 |
| Супервизоры цикла (зависший инструмент, финальный гейт) | нужны в автономных прогонах; MVP интерактивен; точки подключения описаны в §5. Пустой ответ (§5.4.1, C-07) и повтор одинаковых неверных вызовов (§6.3.7, C-08) входят в MVP | после 9; спецификация — §17.12.3–§17.12.4 |
| Продолжение ответа модели после сбоя посреди стрима | сложная склейка частичного ответа; MVP завершает шаг ошибкой. Продолжение хода **между** шагами после сбоя есть (SES-9) | после 9 |
| Fork, rewind и навигация по дереву сессии | формат готов (§8.4); нет UI и ACP-методов (`_codelab/session/*` через OpenSpec). Спецификация — §17.6 | после 9 |
| Фоновые задачи shell и мягкая уступка для `exec` | нужны управление задачами, журнал вывода и восстановление после сбоя; в MVP yield-токен не отменяется (§3.3). Спецификация — §17.9 | после 9 |
| Lease сессии (один писатель на файл между процессами) | в MVP один процесс на сессию; второй писатель — ошибка конфигурации. Спецификация — §17.6.8 | 9+ (цель S-09) |
| Автоматический заголовок сессии моделью | заголовок из первого сообщения пользователя (§8.10) достаточен | после 9 |
| Сохранение «разрешить всегда» между сессиями | решение живёт в памяти сессии (§7.4); долговременное хранение требует UI отзыва решений | после 9 |
| Удаление чтения устаревшего `codelab.toml` и зависимости `package:toml` | читатель нужен, пока пользователи переходят с Python-агента; после этапа 9 он объявляется устаревшим, удаление — отдельным OpenSpec change (§15.7) | после 9 |
| Миграция сохранённых Python-сессий | форматы разные, сессии быстро теряют актуальность; журналы живут в разных каталогах (§8.9) | не планируется |
| Живая перезагрузка конфига, запись конфига из CLI и клиентов, реестр настроек, предконфигурация провайдера из окружения, хранилища секретов кроме связки ключей, переподключение MCP | MVP читает конфиг один раз при старте, а настройки правятся в YAML руками. Спецификация — §17.5 | 8 (страница MCP в app, E-13, — 9+) |

## 16.2. Решённые вопросы

| Вопрос | Решение | Где |
|---|---|---|
| Как работают `ls` и `search` поверх `AcpClientExecutionEnv` | при stdio клиент и агент на одной машине: листинг и поиск идут через локальную файловую систему под тем же `BoundedEnv`; при WebSocket инструменты выключены с причиной, модель пользуется `exec` через `terminal/*` | §10.4 |
| Маппинг `TurnEnded(failed)` в ACP | JSON-RPC ошибка `-32603` с `data.codelab.errorClass`; `end_turn` скрыл бы сбой | §13.8 |
| Повторная доставка `session/request_permission` при переподключении | новый запрос с новым JSON-RPC id и тем же `toolCallId` в окне `detachGrace` (30 с); JSON-RPC id относится к запросу, а не к вызову инструмента, поэтому новый id не нарушает спецификацию; поздний ответ на старый id игнорируется | §13.5, §13.10 |
| Как передаётся команда в `terminal/create` | `command: "/bin/sh"`, `args: ["-c", <команда>]`; shell настраивается `exec.shell` | §4.7, §13.9, §15.4 |
| Имена встроенных инструментов | наши: `read`, `write`, `edit`, `ls`, `search`, `exec`, `update_plan`. Имена видит только модель (пользователь видит `title`), поэтому совместимость с Python-именами не нужна; короткие имена дешевле в каждом запросе и не путаются с методами ACP `fs/*` | §6.4 |
| Где живёт `PersistentWebEnv` | новый пакет `packages/dart/codelab_agent_web` (зависит от ядра и `package:web`, который ядру запрещён), этап 10 | §1, §4.3 |
| Режим одобрения по умолчанию у каждого профиля | `standard` (`PermissionMode.write`) везде; `codelab -p` без TTY — отказ всему, что требует вопроса, пока не указан `--approve` (политика ответа CLI) или `--permission-mode` | §7.7, §10.5 |
| Переносить ли Python-сессии | нет | §16.1 |
| Формат golden-фикстур | JSON, кадры как на проводе | §14.3 |
| Формат конфига и судьба `codelab.toml` | YAML 1.2 в строгом профиле — единственный формат чтения и записи (`config.yaml`, `.codelab/config.yaml`, `.codelab/config.local.yaml`); разбор `package:yaml`, запись `package:yaml_edit`, оба в `codelab_agent_io`. `codelab.toml` Python-агента — только чтение, когда YAML-конфига нет; перевод — `codelab config migrate`; удаление чтения — после этапа 9 отдельным OpenSpec change | §15.1, §15.5, §15.7, §17.5.5 |
| `session/set_mode` при его отсутствии в `acp_protocol` | OpenSpec change этапа 4 добавляет модель из спецификации; до этого `-32601`, режимы — через `configOptions` | §13.6 |
| Вынос огромного результата инструмента в файл (T-28) | этап 3 вместе с журналом: полный отредактированный текст в `<файл журнала без .jsonl>/spills/<n>.txt`, модели и журналу — один фрагмент с путём; повторное чтение через `readOnlyRoots` с доверием исходного результата; расширение ACP `_meta.codelab.spill` — после 9 через OpenSpec | §17.4 |
| Где хранятся ключи и как клиенты меняют настройки агента | ключи — в хранилище ОС (`keychain-macos`, `secret-service`, `wincred`), иначе переменные `CODELAB_SECRET_<…>`; открытый файл — только явным `secrets.backend = "file"`; конфиг пишет только `ConfigWriter` (с сохранением формата, атомарно, после валидации) и только для локального агента; агент подхватывает правку живой перезагрузкой | §17.5 |
| Steering через ACP (C-03) | метод расширения `_codelab/session/steer` с capability `agentCapabilities._meta.codelab.steering`; доставка на границе шага, недоставленное возвращается клиенту (`steerReturned`); `session/prompt` во время хода по-прежнему `-32602 turnActive`; `_meta` на `session/prompt` и «только клиентская очередь» отклонены | §17.7 |
| UI доверия проекту (`trusted_projects`) | отдельного диалога нет: `codelab config set trusted_projects …` и общий редактор настроек (ключ `shared`, пишется только в пользовательский слой); после записи проектные слои переоцениваются той же перезагрузкой | §17.5.5, §17.5.6, §17.5.8 |
| Код выхода `codelab -p`, когда ход закончился заметкой о пустом ответе (H-02) | `0`: заметка — непустой ответ `end_turn` (`agent_message_chunk`), человек видит её вместо пустоты; маркер `_meta` и расширение ACP не вводятся. Код `1` — только `end_turn` без единого `agent_message_chunk` (например, внешний агент без заметок) | §5.4.1, §13.10 |
| Лицензия репозитория и место `THIRD_PARTY_NOTICES.md` | MIT; `LICENSE` и один `THIRD_PARTY_NOTICES.md` — в корне репозитория (этап 0) | dart-agent-and-clients §9.5 (задача 0.9), §7а, §11 |
| Кодек изображений для подготовки картинок (T-29) | отдельный пакет `codelab_agent_images` на `package:image` (`PureDartImagePreparer`, в `lib/io.dart` — `IsolateImagePreparer`); ядро держит только порт `ImagePreparer`, allowlist ядра не растёт; добавление `image` — OpenSpec change и запись в `technology-stack.md` | §1.2, §17.11.2.1 |
| SHA-256 в ядре (C-16, PKCE, снимок запроса) | `package:crypto` в allowlist ядра (PKG-2): официальный пакет dart-lang на чистом Dart, работает в web; своя реализация не окупается | §1.2, §17.11.2.2 |

## 16.3. Открытые вопросы

| Вопрос | Когда решить |
|---|---|
| Песочница уровня ОС (Won't «сейчас», P-13): оставить границу папки (`BoundedEnv`), одобрения и профили хостов; песочница только на macOS; полноценная песочница на трёх ОС (seatbelt, namespaces, Job Objects, сетевой фильтр) — по модели угроз после вывода Python-агента | этап 9, задача 9.11 ([dart-agent-and-clients.md](../dart-agent-and-clients.md) §9.14); итог — ADR и правка P-13 в матрице |
| Запускать ли встроенное ядро в отдельном isolate с первого дня (разбор журнала и сжатие уже можно вынести в `Isolate.run`) | этап 7, по замерам задержки UI |
| Передача usage и стоимости клиенту: `_meta.codelab.usage` в ответе `session/prompt` или отдельное уведомление (OpenSpec change `add-usage-extension`; цели L-11, U-13, D-09 — Should) | после этапа 9; до него клиенты показывают usage как неизвестный (VIEW-6, [dart-agent-and-clients.md](../dart-agent-and-clients.md) §12.1) |
| Пути Windows: ядро в MVP работает только с POSIX-путями; `LocalExecutionEnv` на Windows приводит `C:\proj` к `/c/proj` — достаточно ли этого для `cwd` из ACP и для слага каталога сессий | до поддержки Windows-хоста |
| Обобщение «разрешить всегда» до префикса команды или маски пути | после 9, OpenSpec |
| A2A: проверять ли подпись карточки (`AgentCardSignature`, каноническая запись) и чем — набор доверенных ключей в конфиге или цепочка сертификатов хоста; до решения карточка доверяется по TLS и совпадению хоста с конфигом (§17.15.3) | до включения E-22 по умолчанию для внешних хостов |
| A2A: интерактивная авторизация удалённого агента (OAuth2 Authorization Code, Device Code, OpenID Connect; ответ на `TASK_STATE_AUTH_REQUIRED`) — через `OAuthLoginService` (§17.10.6) и UI клиента или только внешняя авторизация; в v1 — только Bearer, APIKey и Client Credentials | после E-22, по запросам пользователей |
| A2A: push-уведомления (`*TaskPushNotificationConfig`) для задач длиной в часы и привязки gRPC и HTTP+JSON/REST; в v1 — только JSON-RPC, поток и опрос (§17.15.1) | после E-23, если появится оркестратор, которому мало потока и опроса |
| A2A-сервер: steering (§17.7) сообщением в идущую задачу и вопрос `ask` через `TASK_STATE_INPUT_REQUIRED`; в v1 — `-32004` и capability `userQuestions` off (§17.15.4) | после E-23 |
| Индекс полнотекстового поиска по журналам (вместо просмотра с бюджетом 200 журналов / 256 МиБ / 2 с, §17.6.17): нужен ли и где хранить (рядом с `index.json`) | после D-17, по замерам на больших каталогах сессий |

Документ дополняется по мере ответов; закрытый вопрос переносится в соответствующий раздел и в
таблицу §16.2.
