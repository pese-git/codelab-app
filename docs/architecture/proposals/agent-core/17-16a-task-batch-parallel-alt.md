# 17.16a. Альтернатива D39-alt: `task_*` в параллельном пакете

## 17.16a.1. Суть и механизм

Сейчас все четыре инструмента `task_create`, `task_update`, `task_list`, `task_get` объявляют
`executionMode => ToolExecutionMode.sequential` (общий базовый класс `_TaskTool`,
`codelab_agent_core/lib/src/tools/tasks/task_tools.dart`). По LOOP-4 ([§5](05-agent-loop.md))
один такой вызов делает последовательным весь пакет: `task_update` рядом с `agent` или `read`
лишает их параллельности.

D39 (barrier) меняет цикл: последовательный вызов становится барьером внутри пакета —
параллельные вызовы до него идут вместе, барьер ждёт их и исполняется один (как Codex).

D39-alt (parallel) не трогает цикл. Меняется только `executionMode` у `_TaskTool`: геттер
удаляется (или возвращает режим по умолчанию), и `task_*` исполняются в параллельной ветке
`_runBatch` (`lib/src/loop/agent_loop.dart`): сначала `announce` всех вызовов пакета, затем
`Future.wait` по `complete`. Сериализация остаётся только на замке списка —
`SessionTaskList._locked` (`lib/src/tools/tasks/task_list.dart`): операции применяются по одной
в порядке захвата замка, `TaskListChanged` публикуется под замком и ждётся внутри `execute`
вызова, то есть до его `ToolCallFinished`. Так устроен OpenCode: все вызовы шага стартуют сразу.

## 17.16a.2. Что происходит с инвариантами

- **TSK-1** (ровно один `TaskListChanged` и одна запись `task` на изменившую операцию, §17.16.7).
  Сохраняется: число событий не зависит от режима. Сохраняется и локальный порядок —
  `TaskListChanged` вызова идёт до его `ToolCallFinished`, потому что публикация ждётся под
  замком внутри `execute`. Пропадает глобальный порядок
  `Started(c1) → Changed(c1) → Finished(c1) → Started(c2)`: в параллельном пакете сначала идут
  все `ToolCallStarted` (announce), затем `TaskListChanged` и `ToolCallFinished` разных вызовов
  перемежаются.
- **TSK-2 / TSK-3** (ацикличность, неповторяемость id). Сохраняются: проверки и выдача id идут
  под замком, `_nextId` монотонен. Меняется детерминизм: несколько `task_create` одного пакета
  получают id в порядке захвата замка, а не в порядке вызовов в ответе модели. На практике
  порядки совпадают — `complete` стартует по порядку и до `apply` не ждёт ничего внешнего, — но
  это не гарантия: хук `beforeToolCall` или проверка разрешений с разной задержкой переставят
  захваты. Тесты в этом режиме обязаны проверять множество выданных id, а не их порядок.
- **Зависимости внутри пакета.** `task_create B blocked_by: [<id A>]` в одном пакете с созданием
  A невозможен во всех режимах: модель не знает id A заранее. Новый риск parallel —
  `task_update id: "1"` в том же пакете, что и `task_create` пункта 1: при перестановке захватов
  обновление придёт раньше создания и получит `unknown_id`. В sequential и barrier такой пакет
  исполняется в порядке ответа.
- **D35** (`plan._meta.codelab.taskChange.toolCallId`). Не меняется, но становится единственным
  способом привязать `plan` к вызову: соседство кадров в потоке больше ничего не значит. Клиенты
  CodeLab уже привязывают только по ключу (D35, «Клиент»); сторонний клиент без ключа видит
  обычный план.
- **Журнал.** Записи `task` пишутся в порядке эмита, то есть в порядке замка. Реплей и
  `buildTaskList` детерминированы относительно журнала (TSK-6 не страдает), но не относительно
  порядка вызовов в ответе модели. `ToolResultMessage` идут в транскрипт в порядке вызовов
  (`Future.wait` сохраняет порядок), так что транскрипт и журнал задач могут расходиться в
  порядке.
- **Отмена.** В параллельной ветке `_runBatch` нет `abandon` после отмены: уже объявленные
  `task_*` доезжают, как `read`. Это согласуется с правилом D35 «Отмена» (начатая операция
  применяется и получает результат), но расширяет его на весь пакет: в sequential не начатые
  вызовы отменяются, здесь начатыми считаются все.
- **Тесты.** Golden `test/tools/golden/tasks.txt` и фикстура `acp/prompt-task-plan` содержат по
  одному вызову на шаг и не меняются. Меняется `test/tools/tasks/task_batch_order_test.dart`,
  который закрепляет последовательный режим: он переписывается на проверку TSK-1 (локальный
  порядок), множества id и `unknown_id` при перестановке захватов.

## 17.16a.3. Сравнение с D39 (barrier)

| Критерий | D39 (barrier), принято | D39-alt (parallel) |
|---|---|---|
| Порядок событий | `Started → Changed → Finished` барьерного вызова не перемежается с другими | все `Started` первыми, далее `Changed`/`Finished` перемежаются; гарантирован только локальный порядок вызова |
| `agent` + `task_update` в одном пакете | параллельные вызовы до барьера идут вместе, `task_update` ждёт их | всё идёт сразу, `task_update` не ждёт `agent` |
| Детерминизм id `task_create` | по порядку ответа модели | по порядку захвата замка; совпадает на практике, не гарантирован |
| `task_update` пункта, созданного в том же пакете | работает в порядке ответа | возможен `unknown_id` |
| Отмена | не начатые барьерные вызовы отменяются | все объявленные вызовы доезжают |
| Сложность | изменение `_runBatch` и LOOP-4, тесты цикла | один геттер у `_TaskTool`, переписать `task_batch_order_test.dart`; цикл не меняется |

## 17.16a.4. Вариант 2: очередь по ключу (`lockKey`)

Простой parallel (§17.16a.1–17.16a.3) отдаёт порядок `task_*` гонке за замком `SessionTaskList`.
Вариант 2 («детерминированный parallel») возвращает порядок ответа модели только вызовам
`task_*` между собой, не делая пакет последовательным.

### Механизм

- **Контракт.** В `AgentTool` (`codelab_agent_core/lib/src/tools/agent_tool.dart`) рядом с
  `lockPath` ([§6.3.4](06-tools.md), TOOL-7) появляется член
  `String? lockKey(Map<String, Object?> args) => null` — ключ очереди, не являющийся путём. По
  умолчанию `null`, поэтому существующие инструменты (встроенные, MCP, субагенты) не меняются.
- **Точка исполнения.** `ToolCallExecutor.announce` (`lib/src/tools/executor.dart`) занимает
  место в очереди ключа так же, как для `lockPath` (§6.3.4, «Точка исполнения занимает место в
  очереди…»): `reserve(key)` в announce, то есть в порядке ответа модели. Ключи держит отдельный
  экземпляр `PathLock`, чтобы ключ не совпал с путём файла. Захват — на шаге 6 алгоритма
  §6.3.1, после `beforeToolCall` и проверки отмены; сначала путь, затем ключ. Освобождение — в
  `finally` `complete`/`abandon`, как у билета пути, на любом пути завершения.
- **Взаимоблокировок нет.** Обе очереди занимаются в announce в одном глобальном порядке вызовов
  пакета, а захват идёт в фиксированном порядке «путь, затем ключ». Поэтому каждый вызов в любой
  из очередей ждёт только вызовы, объявленные раньше него, и цикл ожидания невозможен.
- **`task_*`.** Все четыре инструмента (`_TaskTool`) возвращают общий ключ `tasks`;
  `executionMode` остаётся `null`, как в простом parallel. Итог: `task_*` пакета исполняются
  между собой строго в порядке ответа модели, а `read`, `agent` и остальные вызовы идут
  параллельно с ними — пакет остаётся параллельным по LOOP-4 ([§5.5](05-agent-loop.md), шаг 1).
- **Замок `SessionTaskList`** остаётся: через него идут вызовы потомков (субагенты пишут в
  список корня, §17.16.2) и `restore`. Очередь ключа живёт в точке исполнения одной сессии и
  вызовы потомков не упорядочивает.

Механизм обобщает `lockPath`: путь — частный случай ключа очереди, у которого есть нормализация и
многофайловый захват (`runAll`, LSP-3). Отдельный член, а не «путь `tasks`», нужен, чтобы ключ не
проходил нормализацию пути и не пересекался с реальными файлами.

### Что восстанавливается

- **Порядок id = порядок ответа.** Несколько `task_create` одного пакета получают id в порядке
  вызовов: следующий `task_*` не войдёт в `execute`, пока предыдущий не освободил ключ, а
  `TaskListChanged` предыдущего уже опубликован внутри его `execute`. Тест снова может
  проверять порядок id, а не множество.
- **`task_create` + `task_update` того же пункта в одном пакете** детерминированы: обновление
  исполняется после создания, `unknown_id` из-за перестановки не бывает.
- **Журнал и `TaskListChanged`.** Записи `task` и события `TaskListChanged` идут в порядке вызовов
  `task_*` в ответе; журнал задач и транскрипт больше не расходятся по порядку.
- **TSK-1, TSK-3, D35** сохраняются, как в простом parallel: одно событие и одна запись на
  операцию, событие до `ToolCallFinished` своего вызова; `_nextId` монотонен; `plan` привязан к
  вызову по `taskChange.toolCallId`.

### Что остаётся отличием от barrier (D39)

- Все `ToolCallStarted` и `in_progress` пакета идут первыми, как у любого параллельного пакета;
  `beforeToolCall` и `markInProgress` срабатывают пачкой после announce всего пакета.
- События `task_*` (`plan`, `completed`) перемежаются с событиями других вызовов пакета; цепочка
  `pending → in_progress → plan → completed` одного вызова на проводе не идёт подряд. Привязка
  `plan` к вызову — только по D35.
- Отмена. Объявленные вызовы не получают `abandon`. Но `task_*`, который ждёт ключ, после
  захвата проверяет отмену так же, как вызов с `lockPath` (шаг 6 §6.3.1), и завершается
  `cancelled`, ничего не изменив в списке. Уже начатая операция применяется до конца. Это
  ближе к barrier, чем простой parallel: не начатые операции списка после отмены не
  применяются. Поведение закрепляют `task_batch_deterministic_test.dart` и
  `task_list_cancel_test.dart` («cancel while the second call waits for the key»). Раньше этот
  тест ожидал два созданных пункта, теперь ожидает один.
- От barrier Codex (`RwLock`: последовательный вызов ждёт все параллельные) вариант отличается
  тем, что друг друга ждут только вызовы с одним ключом; `agent` и `read` `task_*` не ждут
  ни в каком порядке ответа.

### Новое в контракте

Член `AgentTool.lockKey` — расширение TOOL-7 с путей на произвольные ключи очереди: «вызовы с
одним ключом исполняются в порядке ответа модели». Принятый текст §6.3.4 и TOOL-7 не меняется;
если вариант будет принят, расширение оформляется в `06-tools.md` и `design.md` change
отдельным решением. По поведению это ближе всего к Claude Code: новые `TaskCreate`/`TaskUpdate`
помечены безопасными для параллельного исполнения, порядок держит хранилище списка.

## 17.16a.5. Источники

Код не копировался (AGENTS.md §5; `dart-agent-and-clients/07-decision-sources.md` §7а), сравнение
— только поведения.

- Codex — `openai/codex`, `codex-rs/core/src/tools/parallel.rs`: RwLock, параллельные вызовы
  под чтением, последовательные под записью — модель D39 (barrier).
- Claude Code — прежний `TodoWrite` исполнялся барьером; новые `TaskCreate`/`TaskUpdate`
  помечены безопасными для параллельного исполнения и сериализуются на хранилище списка.
- OpenCode — `sst/opencode`, `packages/core/src/session/runner/step.ts`: все вызовы шага
  стартуют сразу, порядок обеспечивает сам инструмент — модель D39-alt.
