## 7а. Политика стороннего кода

Правила действуют для всех пакетов монорепозитория и проверяются на ревью.

1. **Код пишется по нашим документам.** Источник для реализации — документ ядра, это
   предложение и `design.md` OpenSpec change этапа. Если документов не хватает, сначала
   дополняется документация, потом пишется код.
2. **Сторонний код не копируется**: ни файлы, ни функции, ни тесты, ни промпты, ни фикстуры —
   ни целиком, ни частями. Это относится и к open-source проектам с разрешительными лицензиями.
3. **Атрибуция.** Если реализация близко воспроизводит конкретный внешний алгоритм, список или
   таблицу (например, набор критических шаблонов команд, правила декодирования SSE из публичной
   спецификации, правила приведения типов), то:
   * в документе, который описывает фрагмент, указывается источник;
   * в коде ставится комментарий с источником и лицензией;
   * в `THIRD_PARTY_NOTICES.md` в корне репозитория добавляется запись: название, URL, лицензия,
     текст уведомления об авторском праве, какие файлы затронуты.
4. **Проверка лицензии.** До воспроизведения фрагмента проверяется, что его лицензия совместима с
   лицензией репозитория — MIT (§11): разрешительные лицензии (MIT, BSD, Apache-2.0) совместимы,
   copyleft (GPL, AGPL, LGPL для копируемого кода) — нет. Без подтверждённой лицензии фрагмент не воспроизводится.
   Публичные спецификации (SSE в HTML Living Standard, JSON-RPC 2.0, ACP, MCP, API провайдеров)
   — описание интерфейса, а не код; ссылка на них в документе обязательна, запись в NOTICE — нет.
5. **Зависимости с pub.dev** допустимы по правилам `AGENTS.md` §4: лицензия проверяется при
   добавлении, новая технология, меняющая архитектуру, — только через архитектурное решение.
   Для ядра действует allowlist зависимостей (документ ядра §1, PKG-2).
6. **Чек-лист ревью** (пункт в `.github/pull_request_template.md`, этап 0): «Воспроизводит ли
   изменение внешний алгоритм или данные? Если да — источник в документе, комментарий в коде,
   запись в `THIRD_PARTY_NOTICES.md`, лицензия проверена».

## 7б. Второй этап: наработки Python-агента

Python-агент — не эталон поведения, а источник идей. Каждую наработку берём, только когда
сработает условие из таблицы. Пути в репозитории `codelab-agent` — необязательные подсказки.

| Наработка | Суть | Брать, когда… | Где посмотреть (необязательно) |
|---|---|---|---|
| Порядок «уведомления → ответ → последующие сообщения» | Ответ на `session/prompt` отправляется только после того, как в транспорт ушли все `session/update` этого хода; сообщения, порождённые ответом (например, `available_commands_update` после смены режима), идут после него. `session/prompt` обрабатывается в фоне, чтобы соединение принимало `session/cancel` и ответы на `session/request_permission`, пока ход идёт. Пока ход ждёт разрешения, ответ на `session/prompt` откладывается и хранится в реестре ожидающих ответов | спецификация и фикстуры не определяют порядок или гонку (ожидается для `request_permission` вместе с отменой) | `codelab-agent/src/codelab/server/protocol/` (маршрутизатор ответов, реестр ожидающих запросов) |
| Реестр отмены по поколениям | Каждому ходу выдаётся номер поколения; `session/cancel` увеличивает поколение сессии; любое событие, помеченное старым поколением, отбрасывается до проекции в ACP. Так поздние события отменённого хода (стрим, который уже был в пути) не попадают в следующий ход | поздние события отменённого хода проходят мимо `CancelToken` | `server/protocol/turn_cancellation.py` |
| Сценарии scripted LLM | Формат scripted LLM у нас — блок `llm.steps` фикстуры (agent-core-architecture §14.7): шаг — проверка запроса `expect`, ответ `reply` (текст, вызовы инструментов с аргументами) со `stopReason` или `error`. Существующие сценарии Python-агента описывают тот же многошаговый диалог без реальной модели и переводятся в шаги `llm.steps` | нужно переиспользовать существующие сценарии как заготовки фикстур; только как разовый перевод в блок `llm.steps`, без второго формата в `ScriptedStreamFunction` | `server/llm/scripted_mock.py` |
| MCP-мапперы контента и вывод `kind` | Результат MCP (`text`, `image`, `resource`, `resource_link`) переводится в блоки контента ACP; вид инструмента выводится из аннотаций MCP-инструмента: `readOnlyHint: true` → `read`; `destructiveHint: true` → `edit` при `openWorldHint: false`, иначе `execute`; иначе `other`; уровень доступа всегда `exec` (agent-core-architecture §6.4) | результаты MCP или `ToolKind` для MCP-инструментов недоопределены | `server/mcp/` |
| Определения агентов в Markdown | Файл с YAML-frontmatter (имя, описание, разрешённые инструменты, модель) и телом-промптом; набор таких файлов даёт режимы агента | режимы или определения агентов попадают в матрицу | каталог определений агентов Python-агента |
| Slash-команды | Команды агента описываются файлами; агент публикует их через `available_commands_update` и разворачивает в промпт с подстановкой аргументов | `available_commands_update` попадает в матрицу | `server/protocol/handlers/slash_commands/` |
| Совместимые ключи `codelab.toml` | Набор ключей текущей конфигурации (провайдер, модель, ключи API через env, MCP-серверы, режим по умолчанию). Новый агент читает старый файл только для чтения и только пока нет YAML-конфига; запись — только в `config.yaml`; `codelab config migrate` переводит ключи в `config.yaml` и комментирует отброшенные (agent-core-architecture §15.7) | перед переключением профиля по умолчанию (текущие пользователи) | `codelab.toml.example` |
| Особенности провайдеров Zen, Go, LMStudio | Нестандартные заголовки, поля usage, отличия в формате потока вызовов инструментов у OpenAI-совместимых серверов | соответствующая строка матрицы не проходит | `server/llm/providers/` |
| Идеи Context Manager | Контекст делится на эпохи; старые эпохи заменяются сводкой; файлы в контексте заменяются «скелетом» (сигнатуры без тел), построенным через tree-sitter | классическое сжатие заметно теряет качество | модуль Context Manager |
| OpenSpec specs Python-агента | Перечень требований к поведению текущего агента | при составлении блока «не регрессировать» — как перечень требований, не как тестовый оракул | `codelab-agent/openspec/specs/` |
