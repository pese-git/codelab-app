# 3. Рассмотренные варианты

> Часть предложения [«Dart-агент и клиенты CodeLab»](../dart-agent-and-clients.md). Status: Accepted. Исходные решения, связанные документы и порядок чтения — в оглавлении.

Основа ядра выбрана: собственная архитектура из документа ядра. Здесь сравниваются варианты
**встраивания**: как совместить интерфейс внутри процесса и ACP.

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **V1. ACP-ядро + loopback** | ядро говорит только ACP-моделями; in-process — это ACP-сообщения через пару потоков в памяти | минимум кода; app не меняется | ACP становится внутренним API ядра: событий меньше, чем нужно (нет usage, heartbeat, steering); хосты без ACP (тесты ядра, сторонние Dart-приложения) платят за протокол; противоречит цели «протокол — надстройка» |
| **V2. Доменное ядро + ACP-адаптер** (рекомендуется) | ядро имеет собственный Dart API (`AgentRuntime`, `AgentSession`, закрытые `AgentEvent`); ACP-сервер — отдельный пакет-адаптер; клиенты встраивают ядро через in-process транспорт, который соединяет их с адаптером без JSON | ядро не зависит от протокола по построению; хосты выбирают уровень: прямой API или ACP; у клиента один путь кода для внешних и встроенных агентов | нужен адаптер ACP (меньше, чем протокольный слой Python-агента) |
| **V3. Доменное ядро, клиенты на прямом API** | как V2, но клиенты переходят с `AcpClientApplication` на прямой API ядра | максимум возможностей в UI (usage, steering, ветки) | в каждом клиенте два пути кода: прямой API для своего ядра и ACP для чужих агентов; удвоение UI-логики |

**Выбор: V2**, с возможностью точечно добавить клиентам возможности ядра через ACP-расширения
(`_meta`, методы с префиксом `_codelab/`), когда они понадобятся. V3 отклонён: он оправдан, только
если клиенты откажутся от поддержки сторонних агентов (§4.5).
