# Архитектура ядра агента CodeLab

Status: Accepted

Date: 2026-10-21

Решение: [ADR-0001](../adr/0001-embed-dart-agent-core-behind-acp.md)

> Это **предложение**. Документ описывает целевое устройство пакета `codelab_agent_core` и его
> адаптеров, которых в репозитории ещё нет. Общая картина миграции, клиенты и план этапов —
> в [`dart-agent-and-clients.md`](dart-agent-and-clients.md); здесь — только ядро агента.
>
> Документ (это оглавление и файлы каталога `agent-core/`) — **единственный источник** для реализации ядра. В нём описаны все решения, контракты,
> алгоритмы, форматы и способы проверки; другие материалы для реализации не нужны. Если чего-то
> не хватает, сначала дополняется этот документ (или OpenSpec design соответствующего change),
> затем пишется код. Код, промпты и тесты ядра пишутся с нуля по этому описанию.
>
> Python-агент (`codelab-agent/`, отдельный репозиторий) — не эталон поведения, а источник идей
> второго этапа (ADR-0001, п. 8 и 10; [`dart-agent-and-clients.md`](dart-agent-and-clients.md) §7б).
> Там, где документ на него ссылается, нужное поведение всё равно описано здесь словами;
> открывать Python-код для реализации не обязательно.

## Как пользоваться документом

Каждый раздел устроен одинаково: **Назначение** → **Контракт** (Dart-код, достаточный для
реализации) → **Алгоритм** (нумерованные шаги или псевдокод) → **Примеры** → **Инварианты** →
**Обоснование решения** → **Как проверить** (имена тестов и что они утверждают). Реализуйте
раздел целиком: контракт без алгоритма и тестов не считается готовым.

## Термины и соглашения

| Термин | Значение в этом документе |
|---|---|
| **обвязка агента** | всё, что окружает модель: цикл вызовов, инструменты, контекст, сохранение состояния, разрешения, защитные проверки. Ядро CodeLab — это обвязка агента |
| **ход** (turn) | обработка одного `prompt()` от получения сообщения пользователя до остановки. Совпадает с ACP prompt turn (`session/prompt` → `stopReason`) |
| **шаг** (step) | один вызов модели плюс исполнение пакета инструментов из её ответа. Ход состоит из одного или нескольких шагов |
| **попытка** (attempt) | один HTTP-запрос к провайдеру внутри шага. Шаг может состоять из нескольких попыток (повторы, fallback) |
| **фиксация попытки** (commit) | момент, когда попытка выдала первый видимый вывод; после него попытка не повторяется |
| **видимый вывод** | первый контентный фрагмент ответа модели (текст, рассуждение или начало вызова инструмента), показанный потребителю |
| **транскрипт** | список сообщений `Agent` в памяти: то, что сказано в разговоре |
| **payload** | то, что реально уходит провайдеру в одном запросе: системный промпт + сообщения после всех преобразований + схемы инструментов. Payload строится из транскрипта и не меняет его |
| **журнал** | JSONL-файл сессии (§8): единственный долговечный источник истории |
| **хост** | код, который собирает ядро и отдаёт ему порты: `apps/codelab_agent`, `codelab_embedded`, тесты |
| **порт** | интерфейс в ядре, реализацию которого передаёт хост (`ExecutionEnv`, `PermissionGate`, `SessionStore`, `Logger`, `http.Client`, `Clock`, `IdGenerator`) |
| **инструмент** | `AgentTool`: схема для модели + исполнение поверх `ExecutionEnv` |
| **пакет вызовов** (batch) | все вызовы инструментов из одного ответа модели |
| **корень сессии** | рабочая папка сессии (`cwd` из `session/new`); граница для всех файловых операций |
| **профиль** | три разных понятия: **профиль хоста** — набор capability и сервисов сборки ядра (`agent-serve`, `embedded-cli`, …; `--profile`/`CODELAB_PROFILE`, §10.4, §15.6); **профиль подключения** — как клиент запускает агента или подключается к нему (`--agent <профиль>`, `/profile`, `~/.codelab/profiles.json`, dart-agent-and-clients §9.11); **промпт-профиль** — определение агента с телом промпта, например `architect`, выбирается опцией `agent` (§17.12.2, §13.6) |

* Ключевые слова ДОЛЖЕН / НЕ ДОЛЖЕН / СЛЕДУЕТ / МОЖЕТ — как в `AGENTS.md` §1. Инварианты пронумерованы с префиксом раздела (`LLM-3`, `PERM-5`). На них ссылаются OpenSpec designs и имена тестов.
* Dart-код в документе — контракт: имена типов, полей и методов фиксированы. Реализация МОЖЕТ добавлять приватные поля и вспомогательные методы, но НЕ ДОЛЖНА менять смысл контракта без правки документа. Пути `packages/dart/...` и `apps/...` — относительно корня этого репозитория.
* Все тексты, которые видит модель (результаты инструментов, сообщения об ошибках, уведомления об усечении), — на английском языке и фиксированы в документе: на них опираются golden-тесты, а модели лучше всего следуют англоязычным служебным текстам. Тексты для человека (логи, UI) — по правилам клиента.
* Время — только через порт `Clock`, идентификаторы — через `IdGenerator`, случайность (джиттер) — через `Random`, переданный хостом. В тестах все три детерминированы.
