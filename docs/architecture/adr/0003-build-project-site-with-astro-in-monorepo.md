# ADR-0003: Build the CodeLab site with Astro in `site/` of the monorepo

Status: Accepted

Date: 2026-11-17

## Context

У CodeLab нет публичной точки входа. Продуктовая документация уже есть и живёт рядом с кодом: `docs/user/`, `docs/ops/`, `README.md` и `doc/` приложений и пакетов (стандарт — `.claude/skills/codelab-docs/SKILL.md`). Её читают на GitHub. Человеку, который впервые слышит о CodeLab, этого мало:

* нет страницы, которая за минуту объясняет три продукта — CodeLab app, терминальный клиент `codelab` и агент `codelab-agent` — и ведёт к установке;
* документация разбросана по каталогам репозитория; оглавления `docs/user/README.md` и `docs/ops/README.md` помогают, но навигации между аудиториями нет;
* выпуски не объявляются: тегов и changelog пока нет, а с выпуска 1.0 появится установщик (`docs/user/run-from-source.md`).

Ограничения:

* **Один факт — одно место** (`codelab-docs` §3). Сайт не должен стать второй копией документации, которая расходится с кодом. Документы продолжают читаться на GitHub как есть.
* **Стек репозитория — Dart и Flutter** (`technology-stack.md`). Новый язык сборки и пакетный менеджер — новая технология в monorepo, которую надо отделить от pub workspace, Melos и сторожа `codelab_architecture_tests`.
* **CI проверяет затронутое** (`AGENTS.md` §21, `testing.md` §74). Файл вне пакетов workspace сейчас запускает полный прогон всех Dart-джобов (`tool/ci/ci_scope.dart`); сайт не должен этого делать на каждую правку текста.
* **Безопасность и данные** (`AGENTS.md` §2, §10, §16). Публиковать можно только продуктовую документацию: не `openspec/`, не `docs/architecture/`, не `docs/backlog/` (отчёты смоук-прогонов), не `AGENTS.md`.
* **Хостинг не выбран.** Публикация не входит в это решение, но конфигурация не должна мешать подключить GitHub Pages или другой статический хостинг.

Затрагиваемые границы: структура monorepo (`AGENTS.md` §5), CI (`.github/workflows/ci.yml`, `tool/ci/`), процесс документации (`codelab-docs`, агент `docs-writer`) и выпуска (`AGENTS.md` §22).

## Decision

### 1. Сайт — статический Astro в `site/`

Сайт-визитка CodeLab собирается генератором статических сайтов [Astro](https://astro.build) (MIT) в каталоге `site/` этого monorepo. Сборка даёт статический HTML без серверной части.

`site/` — отдельный Node-проект:

* свой `package.json` (`"private": true`), закоммиченный `package-lock.json`, точные версии зависимостей (без `^` и `~`, `save-exact` в `site/.npmrc`);
* версия Node закреплена в `site/.nvmrc`; пакетный менеджер — npm;
* `site/` НЕ входит в pub workspace (`workspace:` корневого `pubspec.yaml`) и в Melos; сторож `codelab_architecture_tests` его не видит, потому что обходит только члены workspace и каталоги своих правил.

Сайт только на русском.

### 2. Документация читается на месте

Astro content collections читают Markdown из репозитория без копирования. Публикуется закрытый список источников (allowlist):

* `docs/user/**`, `docs/ops/**`;
* `apps/*/README.md`, `apps/*/doc/**`;
* `packages/*/*/README.md`, `packages/*/*/doc/**`.

Всё остальное не публикуется, в том числе `openspec/`, `docs/architecture/`, `docs/protocols/`, `docs/backlog/`, `docs/design/`, `AGENTS.md`.

В `site/` хранится только то, что существует ради сайта: главная, страницы возможностей, новости, оформление.

Ссылки и картинки в документах остаются относительными путями репозитория — на GitHub они работают как есть. При сборке плагин сайта переводит относительную ссылку на опубликованный файл в адрес страницы сайта, а ссылку на неопубликованный файл — в адрес этого файла на GitHub. Ссылка на несуществующий файл ломает сборку.

### 3. Mermaid рисуется в браузере

Блоки ```` ```mermaid ```` рисует `mermaid.js` на стороне браузера, с учётом светлой и тёмной темы сайта. Отрисовки при сборке нет.

### 4. Новости — коллекция сайта

Новость — одна запись на выпуск в `site/src/content/news/`. Её пишет `docs-writer` в ветке `release/<version>` вместе с changelog; пункт входит в чек-лист выпуска (`AGENTS.md` §22).

### 5. Оформление как у приложения

Цвета, шрифты и стиль Fluent берутся из `packages/flutter/codelab_ui` и `docs/design/claude-design/` (`fluent.css`). Есть светлая и тёмная темы. Токены описывает новый skill `.claude/skills/codelab-site/`.

### 6. CI без публикации

Отдельный джоб `site` в `.github/workflows/ci.yml`: `npm ci`, `astro check`, тесты плагинов, `astro build`, проверка внутренних ссылок. Джоб обязательный: его ждёт итоговый джоб `ci`, и красный `site` блокирует merge в `develop`. Решение «запускать ли» принимает тот же джоб `scope` (`tool/ci/ci_scope.dart`): правка `site/**`, опубликованных источников и `openspec/**` запускает `site`, но правка только `site/` не запускает Dart-джобы. Публикации нет; `site` и `base` Astro задаются при сборке, а ссылки на GitHub по умолчанию ведут на коммит сборки, чтобы хостинг подключался без переделок.

### 7. Команда

Новый агент `.claude/agents/site-engineer.md` (зона — `site/` и CI сайта) и новый skill `.claude/skills/codelab-site/`. Ревью — `architecture-reviewer` по чек-листу skill. Метка задач — `[site]`.

Детали — design.md change `add-astro-site`.

## Alternatives

### Alternative 1 — Отдельный репозиторий для сайта

Сайт в своём репозитории, документация подтягивается при сборке (git submodule или checkout второго репозитория в CI).

Почему не выбран:

* правка документации и ссылок на неё проверяется в разных репозиториях и в разное время: сломанная ссылка обнаружится после merge;
* вторая история изменений и второй набор правил для одной документации;
* выигрыш (изоляция Node от Dart) достигается и каталогом `site/` вне pub workspace.

### Alternative 2 — Генератор на Dart (`jaspr`, `static_shock`)

Остаться в одном языке и в Melos.

Почему не выбран:

* экосистема контент-сайтов на Dart заметно беднее: content collections со схемой, обработка Markdown через remark/rehype, оптимизация картинок, проверка типов шаблонов — пришлось бы писать самим;
* сайт попал бы в pub workspace и в граф пакетов, хотя к коду продукта отношения не имеет;
* зрелость и поддержка сторонних Dart-генераторов ниже, долгосрочный lock-in выше.

### Alternative 3 — Генератор документации (MkDocs Material, Docusaurus, VitePress)

Сайт-документация «из коробки» с поиском и навигацией.

Почему не выбран:

* главная, страницы возможностей и новости в них — второстепенные возможности, оформление Fluent пришлось бы накладывать поверх чужой темы;
* MkDocs добавляет Python, который monorepo уже вывел (change `retire-python-agent`);
* Docusaurus тянет React-приложение в клиент, а сайту-визитке достаточно статического HTML; VitePress — тема документации на Vue, главную и новости пришлось бы строить поверх неё.

### Alternative 4 — Копировать документацию в `site/` при сборке или скриптом

Скрипт копирует Markdown в `site/src/content/` и переписывает ссылки.

Почему не выбран:

* либо копия попадает в git и расходится с оригиналом, либо это шаг сборки, который делает то же, что content collections, но хуже: ошибки указывают на копию, а не на исходный файл;
* нарушает «один факт — одно место».

### Alternative 5 — Mermaid при сборке (`rehype-mermaid`, `mermaid-cli`)

SVG готов в HTML, JavaScript не нужен.

Почему не выбран:

* сборке нужен браузер (Playwright или Puppeteer): тяжёлая зависимость в CI и локально;
* одна картинка на две темы: для тёмной темы пришлось бы рисовать каждую схему дважды.

## Consequences

### Positive

* у CodeLab есть точка входа для новых пользователей, а документация остаётся там же и читается на GitHub как раньше;
* сайт проверяет ссылки документации при каждой её правке: битая относительная ссылка находится в pull request, а не читателем;
* Node изолирован в `site/`: Dart-пакеты, Melos, сторож и Dart-джобы CI его не видят;
* хостинг подключается позже без изменения структуры.

### Negative

* в monorepo появляется второй тулчейн (Node, npm) и второй lock-файл; обновление зависимостей сайта — отдельная работа;
* `docs-writer` и все, кто правит документацию, получают новое ограничение: ссылки только относительные и только на существующие файлы, иначе красный джоб `site`;
* в `tool/ci/ci_scope.dart` появляется второе измерение охвата (сайт), а у джоба `scope` — второй выход;
* mermaid загружается в браузере: тяжёлый скрипт на страницах со схемами (загружается только на них).

### Risks

* **Сборка ломается правкой документации**, которую делает не site-engineer, и блокирует merge: джоб `site` обязательный. Снижение: правило ссылок в `codelab-docs`, понятное сообщение об ошибке с путём исходного файла и строкой, локальная команда проверки сайта.
* **Публикация лишнего** (секреты, личные пути, `docs/backlog`). Снижение: закрытый allowlist источников, а не denylist; маскировка в документах по `codelab-docs` §7; тест плагина на то, что неопубликованный файл не становится страницей.
* **Рост времени CI.** Снижение: джоб `site` идёт только по path-фильтру и параллельно с Dart-джобами; правка только сайта не запускает Dart-джобы.
* **Цепочка поставок npm.** Снижение: точные версии, закоммиченный lock, `npm ci`, проверка лицензий при добавлении (`AGENTS.md` §4), без копирования стороннего кода (`AGENTS.md` §5).

---

## Migration

Не требуется: сайт добавляется рядом, существующий код, пакеты и документы не перемещаются. Документы, которые нарушают правило ссылок, исправляются в том же change.

Откат: удаление `site/`, джоба `site` и ветки `site` в `ci_scope.dart`; документация не зависит от сайта.

---

## Validation

* джоб `site` в CI: `npm ci`, `astro check`, тесты плагинов, `astro build` с непустым `base`, проверка внутренних ссылок;
* тесты `tool/ci/ci_scope.dart` в `codelab_architecture_tests` (`ci_scope_test.dart`): правка `site/**` не запускает Dart-джобы и запускает `site`;
* `melos run guard` и `melos run check-format` проходят при установленных `site/node_modules`;
* ручная проверка собранного сайта в светлой и тёмной темах.
