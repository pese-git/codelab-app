# Backlog: задержка UI-isolate под потоком ответа модели 2026-11-02

Находки замера 7.8 change `add-embedded-agent-mode` (итерация 5, задача 5.1; ветка
`feature/add-embedded-agent-mode-isolate`). Замер —
`packages/dart/codelab_embedded/benchmark/stream_latency_benchmark.dart`, числа и методика — design.md change,
«Решение 7.8».

Условия:
- Apple M1 Max, 64 ГБ, macOS 27.0.1 (26A434), Dart 3.13.0 `macos_arm64`, AOT `fvm dart compile exe`;
- 10 000 чанков по 16 символов, таймер 1 мс в том же isolate, по три прогона, медианы;
- режим `sse`: настоящий провайдер над поддельным `http.Client`, `--burst=N` — N SSE-событий на одно чтение сокета.

Итог: критерии D11 (p99 ≤ 8 мс, максимум ≤ 50 мс) выполняются при N ≤ 7, задержка растёт ≈1 мс на событие в
пачке. Решение пользователя 2026-11-02 — остаётся `InProcessAcpLink`, `IsolateAcpLink` (задача 5.4) не делается.

Разбивка по слоям при N=1: весь конвейер ≈307 мкс на чанк. Агент, провайдер, SSE и транспорт — ≈132 мкс (≈43%).
Клиентская проекция kit (`AcpClientApplication`, `ClientWorkspace`) — ≈175 мкс (≈57%). Isolate унёс бы только
агентскую часть: граница по p99 сдвинулась бы примерно с N ≈ 8 до N ≈ 13.

Не проверялись:
- реальный размер пачки SSE у живых провайдеров (PERF-2);
- Linux-раннер CI — справочный по D13, п. 3;
- кадры Flutter: замер меряет задержку цикла событий в чистом Dart, без отрисовки.

Приоритеты и колонки — как в [smoke-2026-10-30.md](smoke-2026-10-30.md). Серия PERF — находки замеров
производительности, нумерация своя (smoke-находки — SMK-*).

## Карточки

### PERF-1. Удешевить клиентскую проекцию потока чанков в kit (P3)

**Где:** `codelab_client_acp` (`AcpClientApplication`, применение `session/update`) и `codelab_client_core`
(`ClientWorkspace`, транскрипт, публикация состояния).

**Факт:** проекция одного `agent_message_chunk` стоит ≈175 мкс — 57% стоимости чанка во всём конвейере
встроенного агента. При N SSE-событиях на чтение сокета она выполняется N раз подряд без отдачи циклу событий,
поэтому именно она задаёт наклон ≈1 мс на событие. Проекция работает в UI-isolate при любом транспорте: перенос
ядра в `IsolateAcpLink` её не убирает. Затронуты и внешние агенты по stdio и WebSocket.

**Ожидание:** стоимость проекции на чанк заметно ниже без изменения ACP и наблюдаемого порядка событий. Идеи для
разведки:
- склейка подряд идущих `agent_message_chunk` одного сообщения в пределах оборота цикла событий или кадра;
- батч-публикация состояния: одна эмиссия на пачку обновлений, а не на каждое;
- профилирование: где именно уходят 175 мкс (копии транскрипта, пересборка неизменяемого состояния, логирование).

Нужен OpenSpec change клиентского слоя: меняется частота и гранулярность публикации состояния, на которую
опираются Cubit-ы app и REPL CLI. Поздние и повторные события, отмена хода и `session/load` ДОЛЖНЫ сохранить
нынешнюю семантику (`AGENTS.md` §9).

**Критерий готовности:** замер `--mode=sse` с полным клиентом даёт границу по p99 > 8 мс заметно выше N = 8
(ориентир — N ≥ 16) на той же машине и сборке; `--no-client` не ухудшается.

**Риск:** без правки пачки из ≥ 8 событий (занятый цикл событий, буферизующий прокси, провайдер без flush)
дают задержку UI больше 8 мс. Приоритет P3, пока PERF-2 не покажет такие пачки на практике; тогда — P2.

### PERF-2. Замерить реальный размер пачки SSE на LM Studio и облачном провайдере (P3)

**Где:** слой провайдера `openai-compatible` в `codelab_agent_io` (чтение потока байтов ответа и разбор SSE).

**Факт:** реальный N не измерен. Оценка по исходникам `package:http` и `dart:io`: элемент потока — то, что вернул
сокет (до 64 КБ, TLS ≈16 КБ); SSE-событие ≈250 байт. Сервер с flush на каждый токен обычно даёт N ≈ 1; при
50–100 токенах/с токен приходит раз в 10–20 мс. Пачки копятся, если цикл событий занят. Решение 7.8 опирается
на N ≈ 1.

**Ожидание:** разовая разведка без изменения поведения. Записать распределение размеров элементов потока (байты
и число SSE-событий на элемент) за несколько ходов:
- LM Studio локально, модель из smoke-тестов (`qwen/qwen3.5-9b`);
- облачный провайдер по TLS;
- длинный ответ и ход с параллельной нагрузкой на цикл событий (например, загрузка сессии).

Запись — временной инструментацией или отладочным логом без содержимого ответа: тексты модели и ключи в журнал
не попадают (`AGENTS.md` §10, §16).

**Критерий готовности:** p50, p99 и максимум N по каждому провайдеру записаны в design.md change-а, где
проводится замер, или в этот файл. Если N ≥ 8 встречается на практике — решение 7.8 пересматривается, PERF-1
поднимается до P2.

**Риск:** нет для данных. Без замера решение 7.8 держится на оценке по исходникам.
