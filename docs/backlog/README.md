# Backlog

Здесь лежат отчёты ручных смоук-прогонов, ревью и замеров. Каждый отчёт — список найденных пунктов: дефекты, неудобства, вопросы. Из пунктов заводят OpenSpec changes и GitHub issues.

Backlog не заменяет `openspec/`. Утверждённое поведение описано в [`openspec/specs/`](../../openspec/specs/), решения по исправлению — в changes. Отчёт фиксирует, что нашли, и ссылается на change, который это закрыл.

Каталог не публикуется на сайте: его нет в allowlist `site/src/lib/publish.ts`.

## Формат отчёта

1. Заголовок `# Backlog: …` с датой, затем условия: сборка, агент, модели, что прогоняли.
2. `## Сводка` — таблица `ID | P | Тип | Область | Кратко | OpenSpec | Issue`:
   - **P** — приоритет: P1 — безопасность, данные или проектные настройки работают неверно; P2 — заметный дефект основного сценария или диагностики; P3 — UX и мелочи (определение — в [`smoke-2026-10-30.md`](smoke-2026-10-30.md));
   - **OpenSpec** — нужен ли change по `AGENTS.md` §17;
   - **Issue** — ссылка на GitHub issue или `—`.
3. `## Карточки` — по разделу `### <ID>. <заголовок> (<P>)` на пункт: где, шаги, факт, ожидание, риск. В новых отчётах вместо ожидания и риска — почему важно и что сделать.

Закрытый пункт в сводке зачёркнут и помечен `**Закрыто** change <id>`, в карточке — абзац `**Закрыто** change […]` со ссылкой на change. Частично решённый помечен `**Частично**` и остаётся открытым; в карточке — блок `**Частично (сверка с кодом …):**`: что сделано и что осталось.

Номера сквозные по префиксу: `SMK` — смоук-прогоны, `REV` — ревью, `PERF` — замеры. Новый пункт берёт следующий свободный номер: сейчас это `SMK-50`, `REV-19`, `PERF-3`.

Отчёт по сайту ([`site-2026-11-18-hosting-and-followups.md`](site-2026-11-18-hosting-and-followups.md)) устроен иначе: одна таблица `№ | Что | Откуда | Приоритет` без карточек и отметок закрытия.
