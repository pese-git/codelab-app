# AGENTS.md — ACP Client (Dart/Flutter + FVM + Melos)

Этот файл — инструкция для AI-агентов, разработчиков и CI, работающих в этом monorepo.

Проект: **клиент AI agent с протоколом взаимодействия ACP — Agent Client Protocol**.

Стек: **Dart/Flutter + FVM + Melos + MonoRepo**.

---

## 1. Приоритеты

При конфликте требований использовать следующий порядок:

1. **Безопасность**
2. **Корректность протокола ACP**
3. **Наблюдаемость и отладка**
4. **Стабильность клиентского состояния**
5. **UX и производительность Flutter-приложения**
6. **Скорость разработки**

---

## 2. Назначение проекта

Проект — это **клиентская сторона ACP**.

Клиент должен:

- подключаться к AI agent;
- вести сессии;
- отправлять prompts;
- получать streaming-обновления от agent;
- отображать сообщения, tool calls, статусы и ошибки;
- запрашивать у пользователя разрешения на опасные действия;
- отменять текущую работу agent;
- корректно обрабатывать разрыв соединения и переподключение.

Клиент **не должен** сам реализовывать LLM-инференс, если это не отдельный модуль.

---

## 3. Стек и инструменты

Используется:

- **Dart**
- **Flutter**
- **FVM** — управление версиями Flutter SDK
- **Melos** — управление monorepo
- **MonoRepo** — несколько пакетов и приложений в одном репозитории

### 3.1. FVM

FVM используется для фиксации версии Flutter SDK в корне monorepo.

Файл:

```text
.fvm/fvm_config.json
```

Правила:

- Все команды Flutter/Dart выполнять через FVM: `fvm flutter ...`, `fvm dart ...`.
- Не использовать глобальный Flutter SDK напрямую.
- При смене версии SDK обновлять `.fvm/fvm_config.json` и запускать `fvm use <version>`.
- CI также обязан использовать FVM.

### 3.2. Melos

Melos управляет monorepo: линкование пакетов, запуск команд во всех пакетах.

Правила:

- После добавления/удаления пакетов или изменения зависимостей выполнять `melos bootstrap`.
- Запускать команды во всех пакетах через Melos: `melos run <script>`, `melos exec ...`.
- Не редактировать сгенерированные файлы (`.fvm/`, `pubspec_overrides.yaml`) вручную.

## 4. Структура monorepo

```text
.
├── AGENTS.md
├── melos.yaml
├── .fvm/
│   └── fvm_config.json
├── openspec/            # спецификации и изменения (OpenSpec)
│   ├── config.yaml
│   └── changes/         # активные и архивные изменения
├── apps/                # Flutter-приложения
│   └── codelab_app/     # основное клиентское приложение
└── packages/            # общие Dart-пакеты
    ├── acp_protocol/    # реализация протокола ACP (клиентская часть)
    ├── core/            # базовые утилиты, модели, ошибки
    └── ui_kit/          # переиспользуемые Flutter-виджеты
```

Правила зависимостей:

- `apps/*` могут зависеть от `packages/*`.
- Пакеты не зависят друг от друга циклически.
- `acp_protocol` — чистый Dart, без Flutter (чтобы его можно было использовать в CLI/сервере).
- UI-логика не проникает ниже уровня `ui_kit` и `core`.

## 5. Команды

Все команды выполняются из корня monorepo через FVM/Melos:

```bash
# Установка зависимостей всех пакетов
melos bootstrap

# Статический анализ во всех пакетах
melos analyze        # fvm dart analyze

# Форматирование
melos format         # fvm dart format .

# Тесты во всех пакетах
melos test           # fvm flutter test / fvm dart test

# Запуск приложения
fvm flutter run --directory apps/codelab_app
```

Перед завершением работы агент обязан:

1. Прогнать `melos analyze` — без ошибок.
2. Прогнать `melos format`.
3. Прогнать затронутые тесты (`melos test` или точечно `fvm flutter test <path>`).

## 6. Конвенции кода (Dart/Flutter)

- Стиль: `dart format` + `dart analyze`, строгие предупреждения.
- `analysis_options.yaml` — общий в корне, наследуется пакетами.
- Имена: `lower_case_with_underscores` для файлов и переменных, `UpperCamelCase` для классов.
- Публичный API пакетов — только через `lib/<package>.dart` (barrel file).
- Асинхронность: `async/await`, без raw `Future.then` цепочек.
- Ошибки: типизированные исключения из `core`, не бросать `Exception`/`String`.
- Состояние Flutter: использовать единый выбранный подход (state management) во всём приложении; не смешивать подходы.
- Протокол ACP: все сообщения — типизированные модели с версией схемы; неизвестные поля сохранять, а не отбрасывать (forward compatibility).
- Логирование: единый логгер из `core`, уровни, без `print` в production-коде.
- Секреты: не хардкодить ключи/токены; конфигурация — через environment/secure storage.

## 7. OpenSpec workflow

Проект использует **OpenSpec** (`openspec/`) для управления изменениями. Команды: `/opsx-*`.

Правила:

- Любое изменение поведения (feature, fix с изменением контракта) оформляется как change: `openspec/changes/<name>/` (proposal → specs → design → tasks).
- Мелкие правки без изменения поведения (типографика, рефакторинг без смены API) можно делать напрямую.
- Перед реализацией — прочитать `proposal.md`, `specs/`, `design.md` change.
- По завершении — отметить задачи в `tasks.md` и заархивировать change (`/opsx-archive`).
- Спецификации в `openspec/specs/` — источник истины о поведении; код не должен им противоречить.

---

## 8. Правила для AI-агентов

1. **Не выдумывать API ACP.** Если сообщение/метод протокола не описан в `openspec/specs/` или `packages/acp_protocol`, сначала уточнить у пользователя.
2. **Не менять протокол молча.** Изменение контракта ACP — только через OpenSpec change.
3. **Сохранять обратную совместимость** клиентского состояния (сессии, история) при миграциях.
4. **Streaming-обновления** обрабатывать идемпотентно: дубликаты и повторные доставки не должны ломать UI.
5. **Разрыв соединения** — всегда предсказуемое состояние: показывать статус, сохранять буфер, предлагать переподключение.
6. **Разрешения (permissions):** опасные действия agent (файлы, сеть, shell) — только после явного подтверждения пользователя.
7. **Не коммитить** секреты, `.fvm/`-бинарники, сгенерированные `pubspec_overrides.yaml`.
8. **Не коммитить** изменения без явной просьбы пользователя.
9. Перед завершением задачи — прогнать команды из раздела 5.

---

## 9. Наблюдаемость и отладка

- Все сетевые события ACP логируются (входящие/исходящие сообщения, с маскировкой чувствительных полей).
- В debug-сборках доступен лог протокола (полный дамп сообщений) — выключен в release.
- Ошибки протокола (неизвестный метод, невалидная схема) — логируются с контекстом: session id, message id, версия схемы.
- Crash/ошибки — с идентификатором сессии для корреляции.
